# 第5章 软件工程基础知识 —— 笔记

> 定位：这一章的大部分"术语"你日常都在实践（敏捷/Scrum、单元测试、OO设计、需求变更处理……），核心价值不是学新知识，而是把"你已经会做的事"对齐到教材的**正式框架和标准表述**上——这是转型架构师后用来做技术选型论证、评审发言、团队流程设计的"共同语言"。

## 一、核心概念

### 1. 软件过程模型体系（项目/产品级别）

| 模型 | 核心思想 | 现实映射 |
|---|---|---|
| 瀑布模型 | 严格串行，前一阶段输出=后一阶段输入 | 致命缺陷：需求一次说清不现实、串行导致偏差损失大、"一次性完全正确"不现实——这三点是后续所有模型要解决的问题 |
| 原型模型 | 抛弃型原型（确认需求后即弃用）/ 演化型原型（不断打磨成产品） | 抛弃型≈技术选型前的POC demo；演化型≈MVP逐步加功能 |
| 螺旋模型 | 原型思想+生命周期模型结合，**风险驱动**的4象限循环（目标设定→风险分析→开发验证→评审） | "先攻克风险最大的部分"这个直觉，你在做架构选型时一直在用 |
| RUP（统一过程） | **9大核心工作流**（业务建模/需求/分析设计/实现/测试/部署/配置变更管理/项目管理/环境）+ **4阶段**（初始→细化→构造→移交）+ **4+1视图模型**（逻辑/进程/实现/部署视图+用例视图串联） | "迭代增量"思想是敏捷/Scrum的直接理论前身；4+1视图贯穿全书架构设计相关章节 |
| 敏捷 | 一种价值观总称（不是具体模型），两大本质特征：**适应性≠预设性**（拒绝长周期详细预先计划）、**面向人≠面向过程** | XP/Scrum/Crystal/FDD 是"伞"下的具体方法 |
| CMM/CMMI | **组织级别**的流程能力成熟度评估框架（评估"团队做软件这件事规不规范"，不是"项目具体怎么做"） | 与上述模型不在同一维度，不可类比对立 |

**敏捷与其他模型的关系图谱**（重点）：
- 敏捷 vs 瀑布：不是"敏捷不做计划"，而是把"一次性做完整个大计划"拆成"小计划→验证→调整"的多轮循环
- 敏捷 vs 原型：都有迭代影子，但原型产出是"样子货"（确认需求用），敏捷每个迭代产出的是**真实可交付的功能**
- 敏捷 vs 螺旋：螺旋每圈都有正式的风险分析驱动，敏捷驱动力是**客户价值优先级**（backlog排序）——可理解为敏捷简化掉了螺旋模型里"沉重的风险分析动作"
- 敏捷 vs RUP：**RUP是敏捷的"重装版祖先"**——Scrum的一个Sprint骨子里就是RUP一次精简版迭代；RUP要求详尽文档产出物，敏捷"可工作的软件胜过详尽文档"

### 2. 需求工程全流程

- **需求获取**六种技术，按场景选用：访谈（常规）、专题讨论会/JRP（解决多方需求冲突，对应你的需求评审会）、问卷调查（验证假设，问题设计不当会带偏答案）、现场观察（业务复杂时）、原型化方法（UI/报表类高度不确定需求）、头脑风暴（全新业务无先例）
- **需求变更控制流程（4步）**：①问题分析和变更描述 → ②变更分析和成本计算 → ③决策 → ④变更实现。对应你熟悉的 PR/MR评审流程 + Jira变更工单流程
  - **需求基线（Baseline）**：需求文档评审通过后客户与开发方的"约定"，任何变更都要走上述流程，不能直接从配置库删除/修改原始变更请求（对应git不能强推覆盖历史）
  - 敏捷"拥抱变化" ≠ 变更能随意插队当前迭代，通常进入**下一次迭代的backlog**——这是常见的误解点
- **需求追踪**：正向追踪（需求→有没有落地实现）、逆向追踪（代码/测试用例→反查对应哪条需求）、合称**双向追踪**，靠"需求追踪矩阵"维护。现实中对应 Jira Story-Epic关联、测试用例对应验收标准、commit关联工单号

### 3. 系统分析与设计方法论

**结构化方法（SASD，1978）**：先问"系统要做哪些事"，按**数据流**切分系统
- 结构化分析SA（画DFD，描述做什么）→ 结构化设计SD（转成模块结构图）→ 结构化编程SP（单入口单出口）
- 提出的设计准则：分解与抽象、模块独立性、信息隐蔽——后来被OO方法继承发扬

**面向对象方法（OOA/OOD/OOP）**：先问"系统里有哪些对象，各自该负责什么"，数据和操作绑定成对象

**本质区别**：结构化方法="过程/数据流"视角切分系统；OO方法="对象自治"视角切分系统。**两者不是二选一，而是不同层次的工具**——做数据密集型系统/ETL管道时结构化直觉更自然；做架构设计时常是"结构化方法定顶层数据流和模块边界，OO方法定模块内部实现"

**OOA八大原则**：抽象（过程抽象+数据抽象，数据抽象是OOA核心）、封装、继承、分类、聚合（整体-部分关系）、关联、消息通信（对象间只能通过消息通信，是封装能生效的底层保障）、粒度控制（分层次理解复杂系统）

### 4. 软件测试体系

**三个独立分类维度**（非互斥，可交叉）：
- 静态（不运行，代码审查/静态分析，如ESLint/SonarQube）vs 动态（真运行，如单测）
- 黑盒（只看输入输出）vs 白盒（关心内部路径，覆盖率是其量化标准）vs 灰盒（看日志/监控等"现象"判断内部状态，不追踪每行代码——对应你用可观测性工具判断系统状态）
- 人工 vs 自动化

**测试阶段与方法组合规律**（测试金字塔的理论依据）：
1. 单元测试：先静态检查，黑盒出基本用例→白盒补覆盖率，高可靠性模块要求路径覆盖
2. 集成测试：白盒+黑盒结合，重点测**模块间接口**（对应微服务的接口契约测试）
3. 系统测试：以黑盒为主，**必须由独立测试小组做**，需求持续变更导致必须做**多轮回归测试**
4. 验收测试：与系统测试的关键区别不是内容而是**谁测、依据什么**（用户按合同/验收标准测，而非开发按需求规格测）；之后是 Alpha测试（开发环境下用户测）、Beta测试（真实环境多用户测，对应灰度发布/内测）

### 5. 净室软件工程（Cleanroom Software Engineering）

核心哲学：**用数学正确性证明预防错误，而非靠测试事后挑错**（芯片洁净室理念的软件类比）

- 理论基础：函数理论（程序=数学函数，可用推理验证正确性）、抽样理论（穷举不可能，用统计抽样推断可靠性）
- 四大技术手段：统计过程控制下的增量式开发、基于函数的规范与设计（盒子结构：黑盒→状态盒→明盒逐层细化）、**正确性验证**（CSE核心）、统计测试与软件认证
- 为什么现在少见：太理论化，需要额外数学训练成本高；不做传统模块测试但现实中编译器/OS本身可能有bug；诞生于大型长周期高可靠性系统年代（NASA/IBM），与互联网快速迭代范式格格不入
- **留下的遗产**：类型系统（TS/Rust强类型=编译时验证代替运行时测试）、契约式设计、形式化验证（TLA+）都是这套"预防优于发现"思想的现代延伸

### 6. 基于构件的软件工程（CBSE）

核心哲学：**"购买而非重新构造"**（Fred Brooks）——重心从写代码实现功能转移到组装现成构件，工程师角色从"实现者"变"集成者"。现实映射：用npm/maven依赖、云厂商SDK而非重复造轮子

**构件接口不兼容的3种情况**（高实操价值）：
1. 参数不兼容——名字一样但参数类型/个数不同
2. 操作不兼容——提供接口和请求接口操作名不同
3. 操作不完备——一个构件接口是另一个的子集（或反之）

解决办法：编写**适配器构件**——这正是"适配器设计模式"的工程学源头，你封装第三方SDK、写防腐层（Anti-Corruption Layer）对接遗留系统，本质都是在写适配器构件

### 7. 软件项目管理四要素

进度管理（活动定义→排序→资源估计→历时估计→制定计划→控制）、配置管理（版本控制）、质量管理、风险管理——这四者分别解决"何时完成、如何管版本、质量达标、风险可控"四个问题

## 二、易混淆 / 易错点

1. **敏捷 ≠ 一个具体模型**：它是XP/Scrum/Crystal/FDD等具体方法共同的价值观"伞"，不要把"敏捷"和"瀑布/原型/螺旋/RUP"直接放在同一层级类比
2. **RUP与敏捷不是对立两派**：RUP是敏捷的重装版理论前身，Scrum一个Sprint本质上是RUP一次精简版迭代——常见误解是把二者当成互斥选项
3. **过程模型 vs CMM/CMMI 不是同一维度**：前者回答"项目具体怎么做"，后者回答"组织做软件这件事规不规范"。可以是CMMI 5级公司却在项目上用敏捷，两者互不排斥
4. **抛弃型原型 vs 演化型原型**：确认需求后扔掉重新走瀑布 vs 确认需求后继续打磨成产品——不要混为一谈
5. **原型模型 vs 敏捷**：都有迭代影子，但原型产出是"样子货"用于确认需求，敏捷每次迭代产出真实可交付功能——目的完全不同
6. **敏捷"拥抱变化" ≠ 变更可以随意插队当前迭代**：合理的做法是变更进入下一次迭代的backlog，仍然要走变更评估，不是来什么改什么
7. **结构化方法 vs 面向对象方法**：不是"新旧替代"关系，是"过程/数据流视角"与"对象自治视角"两种不同的切分工具，实际架构设计中常常配合使用而非二选一
8. **黑盒/白盒/灰盒 与 静态/动态 与 人工/自动化**：这是三个独立的分类维度，不是三选一的互斥关系，同一测试可以同时归入多个类别
9. **系统测试 vs 验收测试**：区别不在"测试内容"而在"谁测、依据什么"——系统测试是开发团队按需求规格测，验收测试是用户按合同/验收标准测
10. **净室工程"不做模块测试"不代表不测试**：它用正确性验证替代传统模块测试，但仍有统计测试环节；容易误解成"净室=完全不测"
11. **需求追踪的"正向"与"逆向"方向别记反**：正向=从需求出发查有没有实现；逆向=从代码/测试出发反查对应哪条需求
