# 第7章 系统架构设计基础知识 —— 学习笔记

> 定位：本章是全书"架构方法论 + 架构风格"的总纲。第12~18章（信息系统架构、层次式、SOA、云原生、嵌入式、通信、安全架构）本质上都是把本章的风格和ABSD方法论应用到具体领域的展开。

---

## 一、核心概念

### 1. 软件架构的本质定义（7.1.1）

Bass/Clements/Kazman 定义：**架构 = 构件 + 构件外部可见属性 + 构件之间的相互关系**。

关键点：架构关心的是构件"对外承诺什么"（接口、SLA、依赖关系），而不是构件内部怎么实现——内部实现是详细设计/编码阶段的事。

架构不是可运行软件，而是一种"表达"，作用是：
1. 分析设计是否满足需求
2. 在改动成本还低的阶段考虑替代方案
3. 提前降低构造风险

**实践映射**：技术方案评审评的就是这三件事——先画架构图/写设计文档，而不是直接甩代码。

---

### 2. ABSD 方法（基于架构的软件开发方法，7.2）

**与传统瀑布模型的本质区别**：传统模型里架构在需求分析完成之后才出场；ABSD 中架构从项目一开始（功能框架刚明确、需求还没抽取完）就与需求分析**并行**推进，不等需求100%明确。适用场景：产品线系统、长期演进系统（这类系统需求本来就不可能提前想全）。

**ABSD 三大基础**：
1. 功能分解（基于模块的内聚耦合技术）
2. 架构风格选择（实现质量属性和商业需求）
3. 软件模板（复用已有成熟结构）

**六个子过程**（核心骨架，可迭代）：

```
体系结构需求 → 体系结构设计 → 体系结构文档化 → 体系结构复审 → 体系结构实现 → 体系结构演化
```

| 子过程 | 目的 | 关键点 |
|---|---|---|
| 需求 | 获取需求，标识构件 | 需求来源三方面：系统质量目标、系统商业目标、开发人员商业目标 |
| 设计 | 从抽象风格细化到实际构件 | 5步：选风格→映射构件→分析交互→产生体系结构→设计评审 |
| 文档化 | 让抽象架构可被实现 | 两个核心产出：体系结构规格说明 + 质量设计说明书 |
| 复审 | 尽早发现缺陷 | 需外部人员（用户代表+领域专家）参与 |
| 实现 | 落地为可运行系统 | —— |
| 演化 | 应对需求变化 | 6步：需求变动归类→制定演化计划→改构件→更新交互→组装测试→技术评审 |

**用例 vs 质量场景**（容易被问到的对比点）：
- 用例：捕获**功能需求**
- 质量场景：捕获**非功能需求**，分变更/性能/可靠性/交互性场景；须同时包含**预期场景**（如用户量年增10%）和**非预期场景**（如年增100%），非预期场景用于测试设计的边界条件

**实践映射**：容量规划、压测方案设计本质就是在写"质量场景"，只是平时没对应到这个术语。

### 3. 软件架构风格（7.3）—— 实践价值最大的一节

架构风格的意义：**团队沟通的压缩协议**——说出风格名字，同事立刻理解结构，不用画细节图。

#### (1) 数据流风格 —— 管道-过滤器
数据单向流经一串独立过滤器，过滤器互不知晓彼此存在，可并发执行。
**例子**：Unix shell 管道、编译器（词法→语法→语义→代码生成）、Kafka Streams/Flink 算子链、ETL流水线。

#### (2) 调用/返回风格
- **主程序/子程序**：单线程，过程调用，子程序正确性依赖被调用者。例：无框架单体脚本
- **面向对象**：数据+操作封装进对象，方法调用交互，内部实现可自由替换而不影响外部。例：任何OOP系统
- **层次型**：每层只服务上层、依赖下层，非相邻层不可见；只要相邻层接口一致，内部可自由替换（复用/可维护性的根本原因）。例：三层架构（表现层/业务层/数据层）、OSI七层模型
- **C/S**：两层结构，"胖客户机瘦服务器"。例：早期银行柜台系统（后续会演化为三层C/S、C/S与B/S混合，见第10章）

#### (3) 以数据为中心（仓库）风格 —— 黑板体系结构
三要素：**知识源**（独立处理单元）+ **黑板**（共享数据区）+ **控制模块**（调度谁该执行）。
适用于"没有确定算法、需要多种启发式方法协同逼近答案"的问题。
**例子**：语音识别、模式识别、专家系统；现代变体：多智能体系统中共享上下文/状态池、由Orchestrator调度的协作模式。

#### (4) 虚拟机风格
- **解释器**：包含解释引擎、代码存储区、引擎状态、执行进度记录。牺牲执行效率换灵活性。例：脚本语言解释器、专家系统、SQL引擎
- **规则系统**：规则 + 规则引擎，按数据状态匹配触发规则。例：Drools、风控规则层、Feature Flag/工作流引擎

#### (5) 独立构件风格 —— 事件驱动
构件间不直接调用，靠事件/消息异步交互，彼此解耦，互不知晓监听者。
**例子**：消息队列驱动的微服务、GUI事件回调模型、事件溯源（Event Sourcing）。

**风格对照速查表**：

| 风格 | 核心机制 | 典型技术 |
|---|---|---|
| 管道-过滤器 | 单向数据流 | Unix管道、ETL、流处理 |
| 主程序/子程序 | 过程调用 | 无框架单体脚本 |
| 面向对象 | 方法调用 | 任何OOP系统 |
| 层次型 | 相邻层调用 | 三层架构、OSI模型 |
| C/S | 请求-响应 | 传统胖客户端系统 |
| 黑板 | 共享数据+多知识源+中心调度 | 语音识别、多Agent协作 |
| 解释器 | 虚拟机解释执行 | 脚本语言、SQL引擎 |
| 规则系统 | 规则匹配触发 | 规则引擎、风控系统 |
| 独立构件/事件驱动 | 异步消息 | 消息队列微服务、事件溯源 |

**现代大型系统很少用单一风格，而是混合多种风格**——架构师的核心能力是判断"子问题该用哪种风格"，而非只是认识这些风格。

### 4. 软件架构复用（7.4）

架构复用比代码复用**更抽象**——复用的是结构性设计决策（构件划分方式、交互方式、风格选择），而不是某段实现。架构模式本身就是架构复用的成果。

**复用三阶段**：
1. 获取可复用资产（可靠、易理解、易修改）
2. 管理可复用资产 —— 核心是**构件库**，需解决**构件分类**和**构件检索**两个关键问题
3. 使用可复用资产 —— 获取需求→检索→定制（修改/扩展/配置）→组装集成

**实践映射**：公司内部脚手架/中台组件库/共享SDK的运作逻辑。

### 5. 特定领域软件体系结构 DSSA（7.5）

**定义**：在特定应用领域中为一组应用提供的**通用参考架构**——复用的是"整个领域的架构骨架"，而非单个构件。

**必备特征**：
1. 严格定义的问题域和问题解域
2. 具有普遍性
3. 对领域构件组织模型的恰当抽象
4. 具备领域固定、典型的可重用元素

**领域两种划分**：
- **垂直域**：覆盖一整个系统族，产出通用架构（要求领域成熟稳定，现实难满足）
- **水平域**：只覆盖多个系统族的共有部分功能（粒度更小，更易实现一致方案）

**三个基本活动**：
1. 领域分析 → 产出**领域模型**（描述领域共同需求）
2. 领域设计 → 产出**DSSA本身**（通过多选一/可选方案体现变化性）
3. 领域实现 → 产出可重用构件

**四种参与角色**：领域专家 → 领域分析人员 → 领域设计人员 → 领域实现人员

**实践映射**：业务中台 ≈ 垂直域DSSA的尝试；支付中心/消息中心等通用能力组件 ≈ 水平域DSSA。

## 二、易混淆 / 易错点

1. **架构 vs 设计**：架构关心构件划分+外部可见属性+交互关系；内部实现细节不属于架构范畴，属于详细设计
2. **黑板风格 vs 事件驱动（独立构件）风格** —— 最容易混的一对：
   - 黑板有**共享数据区**（大家读写同一份数据），事件驱动**没有共享数据**，只传递离散消息
   - 黑板有**中心控制模块**做调度，事件驱动**没有中心调度者**，组件各自订阅、自主触发
   - 黑板的目标是**多方协作收敛出单一答案**，事件驱动是**各组件各自完成独立副作用**，无需收敛
   - 黑板耦合的是"共享数据结构"，事件驱动耦合的是"消息schema"
3. **用例 vs 质量场景**：用例=功能需求，质量场景=非功能需求；质量场景必须同时包含预期和非预期场景，不要只写预期场景
4. **ABSD 与传统瀑布模型的架构介入时机不同**：不要以为"先需求分析完、再做架构"是唯一正确顺序，ABSD明确主张两者并行
5. **架构复用 vs 代码复用**：层次不同，架构复用是设计决策层面的复用，比代码复用更抽象，不要混为一谈
6. **垂直域 vs 水平域 DSSA**：不是"哪个更好"的关系，是范围大小和实现难度的权衡——垂直域范围大但要求领域成熟稳定（难做到），水平域范围小但更容易落地
