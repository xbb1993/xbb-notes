# 第8章 系统质量属性与架构评估 —— 学习笔记

> 定位：本章直接承接第7章7.2.2的"质量场景"概念，把它从"设计时的思考工具"升级为"可执行的架构评估方法论"。学完本章，手上就有一套可以直接搬到"架构评审/技术方案评审"场景中使用的标准动作。

---

## 一、核心概念

### 1. 软件属性的两个组成部分（8.1.1）

**软件属性 = 功能属性 + 质量属性**。架构设计的基本需求是"在满足功能属性的前提下，重点关注质量属性"——这划清了架构师与普通开发的分工边界：普通开发主要对功能负责，架构师主要对"系统扛不扛得住、改不改得动、维护得起"负责。

**质量属性（Quality Attribute）**：系统"可测量或可测试的属性"，用来描述系统满足利益相关者需求的程度。**关键在"可测量"**——质量属性必须能被量化验证，否则无法做架构评估。

GB/T 16260.1 质量6维度：功能性、可靠性、易用性、效率、维护性、可移植性（宏观分类，了解即可）。

**开发期质量属性 vs 运行期质量属性**：
- 开发期（6个）：易理解性、可扩展性、可重用性、可测试性、可维护性、可移植性 —— 给开发团队自己用，关心"好不好改、好不好测"
- 运行期：可用性、性能、安全性、易用性等 —— 给最终用户/生产环境用，关心"跑起来好不好用、扛不扛得住"

**实践映射**：技术评审如果只关注运行期指标（性能好不好），完全没讨论开发期指标（三个月后好不好改），是很多系统"能跑但没法维护"的根源。

---

### 2. 质量属性场景（Quality Attribute Scenario）—— 本章最核心的工具（8.1.3）

**作用**：把一句模糊的非功能需求（"系统要高可用"）拆解成结构化的、可验证的陈述。

**六要素**（因果链条：谁在什么条件下做了什么 → 打到哪 → 系统怎么反应 → 怎么验收）：

| 要素 | 含义 |
|---|---|
| 刺激源（Source） | 谁触发的——人、系统、内部/外部 |
| 刺激（Stimulus） | 具体发生了什么条件 |
| 环境（Environment） | 刺激发生时系统处于什么状态（正常/过载/降级） |
| 制品（Artifact） | 被影响的对象——整个系统还是某部分 |
| 响应（Response） | 系统应该做出的反应 |
| 响应度量（Measurement） | 怎么量化验证响应是否达标 |

**六类质量属性场景关注点速览**：

| 类别 | 关注什么 | 典型响应度量 |
|---|---|---|
| 可用性 | 故障频率、多久恢复、能否降级运行 | 可用时间、故障修复时间 |
| 可修改性 | 改一个功能/属性的成本 | 改动影响元素数量对应的成本 |
| 性能 | 响应速度 | 等待时间、吞吐量、抖动、丢失率 |
| 可测试性 | 发现缺陷的难易程度 | 测试执行时间、已执行语句百分比 |
| 易用性 | 学习/使用系统的难易程度 | 任务时间、错误数量、用户满意度 |
| 安全性 | 能否正确识别授权/非授权访问 | 绕过防范所需时间/资源、检测到攻击的概率 |

**实践映射**：写架构设计文档的"非功能需求"部分，可以直接按六要素模板逐条列，比空泛的"要求性能好"更有评审价值。

### 3. 系统架构评估（8.2）

**定义**：在架构分析、评估基础上，对架构策略的选取进行决策——即"方案对比会"的系统化方法。

**三类评估方法**（8.2.1）：
1. **基于调查问卷/检查表**：靠经验打分，缺点是主观性强
2. **基于场景**：分析架构对场景的支持程度来判断质量需求满足度——**SAAM 和 ATAM 都属于此类**
3. **基于度量**：先建立"质量属性↔度量指标"映射，再从架构文档采集度量数据反推质量属性水平

**风险承担者（Stakeholders）**：不同角色关心的质量属性完全不同（任务专家关心功能性/可用性/灵活性；系统管理员关心易于定位问题；网络管理员关心网络性能；系统设计师关心可移植性/灵活性/性能）。**一次严谨的架构评估必须让不同角色都参与**，否则评估结果只反映片面视角。

**场景在评估中的角色**：得出精确质量目标的机制，常用"刺激-环境-响应"三要素描述（是六要素的简化版）。

---

### 4. 三大架构评估方法（8.2.2）—— 核心中的核心

#### SAAM（Scenario-based Architecture Analysis Method）
- 最早成文、被广泛使用的架构分析方法（1983，SEI Kazman等提出）
- **核心目标**：验证架构假设和原则，评估架构固有风险；最初专注**可修改性**，后扩展到可移植性、可扩充性
- **5个评估步骤**：场景开发 → 架构描述 → 单个场景评估 → 场景交互评估 → 总体评估
- **直接场景 vs 间接场景**：直接场景是架构无需修改即可支持的场景；间接场景是需要修改才能支持的场景——**间接场景越多、改动越大，说明架构可修改性越差**，这是SAAM判断架构优劣的隐含核心逻辑
- **局限**：不考虑已有知识库的可重用性（后来ATAM用ABAS弥补）

#### ATAM（Architecture Tradeoff Analysis Method）—— 架构权衡分析法
- 在SAAM基础上发展，核心目标是在**多个相互竞争的质量属性**间系统性找出"此消彼长"关系，帮助做有意识的取舍
- 重点关注四类质量属性：**性能、安全性、可修改性、可用性**
- **核心工具：效用树（Utility Tree）**：树根（系统整体良好程度）→ 质量属性 → 属性分类 → 质量属性场景（叶子）
  - 建树流程：头脑风暴收集场景（用例场景/增长场景/探索性场景三种类型）→ 挂到对应分支 → 修剪（保留≤50个）→ 每个场景打**重要度**和**实现难易度**两个维度的优先级（H/M/L）
  - (H,L)：重要且易实现，优先落地；(H,H)：重要但难实现，是真正的架构风险点，需重点投入资源
- **关键产出概念**：
  - 风险点（Risk）：未来可能造成问题的决策
  - 非风险点（Non-risk）：经分析认为安全的决策
  - 敏感点（Sensitivity Point）：一个参数变化会显著影响**某一个**质量属性的点
  - 权衡点（Tradeoff Point）：影响**不止一个**（且相互冲突的）质量属性的敏感点
- **四个活动阶段**：场景和需求收集 → 架构视图和场景实现 → 属性模型构造和分析 → 折中（权衡）

#### CBAM（Cost Benefit Analysis Method）—— 成本效益分析法
- **建立在ATAM之上，在ATAM结束后开始**，直接复用ATAM的场景和结果
- **核心思想**：架构策略影响质量属性 → 质量属性给干系人带来收益（"效用"）→ 协助干系人根据 **ROI（投资回报率）** 选择架构策略
- **8个步骤**：整理场景（筛优先级最高的1/3）→ 场景求精（定义最坏/当前/期望/最好四档响应级别）→ 确定场景优先级（干系人投票生成场景权值）→ 分配效用（给四档响应级别打效用分）→ 关联架构策略（"策略-场景-响应级别"对应关系）→ 内插法确定效用 → 计算总收益（场景权值×效用值汇总）→ 按ROI选策略（收益÷成本）

**三者关系（递进而非并列）**：
```
SAAM（单一质量属性，主要可修改性）
   ↓ 扩展为多属性权衡
ATAM（多属性权衡，产出风险点/敏感点/权衡点）
   ↓ 在其结果上做经济性分析
CBAM（算ROI，指导投入优先级）
```

### 5. ATAM 实践四阶段（8.3，案例：胡佛架构 vs 银行架构）

1. **演示（Presentation）**：介绍ATAM流程 → 介绍业务驱动因素 → 介绍待评估架构
2. **调查和分析**：
   - 生成质量属性效用树：三类利益相关者（用户/架构师/开发人员）头脑风暴场景，挂到效用树
   - 场景优先级投票规则：**票数 = 场景总数 × 30%**，按总票数排序取截止线以上场景
3. **测试ATAM（分析架构）**：拿场景实测架构，找出风险/非风险/敏感点/权衡点
   - 案例结论：两种架构都因组件数量多而无法做到最快速度处理任务；数据保密级别对"应用嵌入地点数量"敏感，任务处理速度对"涉及组件数量"敏感——这两个参数因同时影响安全性和性能，被判定为**权衡点**
4. **报告ATAM**：汇总产出——效用树、场景集合、分析问题集合、风险与非风险清单、确定的架构方法

**案例核心启示**：ATAM 不替你做"哪个架构更好"的决定，只输出结构化证据（风险、权衡点），最终选择权交给决策者——这正是"权衡分析法"命名的由来。

## 二、易混淆 / 易错点

1. **质量属性 vs 普通非功能需求描述**：质量属性必须"可测量"，"性能好"这种表述不是合格的质量属性场景，必须拆成六要素
2. **开发期质量属性 vs 运行期质量属性**：不要把"可维护性""可扩展性"和"可用性""性能"混为一谈——前者服务开发团队，后者服务生产环境，两者不可偏废
3. **敏感点 vs 权衡点** —— 最容易混的一对：敏感点只影响**一个**质量属性；权衡点影响**多个相互冲突**的质量属性。所有权衡点都是敏感点，但敏感点不一定是权衡点
4. **SAAM vs ATAM 的适用边界**：SAAM 只适合单一质量属性（主要可修改性）比较；如果需求涉及多个质量属性互相牵制，必须上ATAM，不能用SAAM硬套
5. **CBAM 不是独立方法**：它不能脱离ATAM单独使用，是在ATAM结果基础上做的经济性延伸分析，顺序不能颠倒
6. **直接场景 vs 间接场景**：直接场景考察架构"现在能不能做到"，间接场景考察架构"要花多大代价才能做到"——评估可修改性时不要只看直接场景
