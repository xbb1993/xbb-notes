# 第9章 软件可靠性基础知识 —— 学习笔记

> 定位：本章和第8章是姊妹篇——第8章讲"怎么描述和评估质量属性"（偏方法论、偏架构决策层面），本章聚焦"可靠性"这一个具体质量属性，讲透它的定量计算、建模假设、设计技术和测试方法，是第8章"可靠性质量属性场景"背后的技术支撑。

---

## 一、核心概念

### 1. 软件可靠性的定义（9.1.1）

IEEE定义：**在规定的条件下、规定的时间内，软件不引起系统失效的概率**，该概率是系统输入和系统使用的函数，也是软件中存在缺陷的函数。

**核心逻辑**：缺陷是内在的、静态的（写完代码那一刻就确定了）；失效是外在的、随机的（取决于有没有触发到对应输入条件）。这正是可靠性只能用"概率"描述的根本原因——不存在"绝对可靠"的软件，只能说"在某类使用场景下不出问题的概率是多少"。可靠性与**运行剖面**（实际输入分布）强相关。

定义的四个关键要素：规定的时间（用运行时间衡量最合理）、规定的条件（运行环境）、所要求的功能（不同任务调用路径不同，可靠性不同）、概率化描述。

软件与硬件在可靠性视角下的关键差异：软件复杂性远高于硬件（设计错误是主因）；软件不存在物理退化（正确的软件任何时刻均可靠，硬件会随时间失效）；软件具有唯一性（复制不改变软件本身）。

---

### 2. 可靠性的定量描述体系（9.1.2）—— 核心计算公式

| 指标 | 含义 | 公式/特征 |
|---|---|---|
| 失效概率 F(t) | 到t时刻为止出现失效的概率 | F(0)=0，单调递增，F(+∞)=1 |
| 可靠度 R(t) | 到t时刻为止不失效的概率 | **R(t) = 1 - F(t)**，R(0)=1，R(+∞)=0 |
| 失效强度 f(t) | 单位时间内出现失效的概率（瞬时速率） | f(t) = F'(t) |
| **MTTF** | 平均失效前时间——平均能无故障运行多久 | R(t) 在(0,∞)上的积分 |
| **MTTR** | 平均恢复前时间——故障到修复成功的期望时间 | 越短，易恢复性越好 |
| **MTBF** | 平均故障间隔时间 | **MTBF = MTTF + MTTR** |

**MTBF公式的实践意义**：提升MTBF有两条路——延长MTTF（提高代码质量、加强测试，让系统更不容易坏）或缩短MTTR（监控告警、自动化恢复、双机热备，让坏了以后修得更快）。现代架构越来越强调"故障是常态，快速恢复比完全避免故障更现实"，本质是在优先压缩MTTR。

**可靠性度量的前提说明**：脱离具体场景空谈"可靠性99.99%"没有意义，必须先明确软件对象边界、失效定义、运行环境、时间基准（自然/运行/执行时间）等前提条件。

### 3. 软件可靠性模型（9.2）

**作用**：用统计理论把测试中收集的失效数据，拟合出F(t)、R(t)、MTTF等指标的具体数值。

**两种确定参数的方式**：估计（用已收集数据做统计分析，事后）、预测（用软件产品属性和开发过程特征确定参数，可在执行前完成）。

**三大共同假设**（模型局限性的根源）：

1. **代表性假设**：测试用例的选取代表软件实际运行剖面。**容易被打破**——测试覆盖"正常业务流程"，生产环境输入五花八门，导致"测试通过率高、上线故障率却高"
2. **独立性假设**：软件失效独立发生于不同时刻，一次失效不影响另一次。**容易被打破**——现实中常见"连锁故障"（如慢查询耗尽连接池导致所有依赖服务超时）
3. **相同性假设**：所有软件失效后果（严重等级）相同，建模只关心失效发生时刻。**局限**——同一套模型衡量"UI小bug"和"核心交易失败"显然不合理，需结合失效严重程度分级做补充

**工程提醒**：如果预测过程中发现引入新错误或修复导致新故障不断出现，应停止预测，等数据稳定后重新估计参数——刚发布大版本时不宜立即用故障率曲线判断版本质量好坏。

### 4. 软件可靠性管理（9.3）—— 贯穿全生命周期

核心理念：可靠性不是测试阶段才关注的事，要贯穿全生命周期，越早介入、后期返工成本越低（与第7章ABSD"架构从一开始就介入"是同一种思维）。

| 阶段 | 核心动作 |
|---|---|
| 需求分析 | 确定可靠性目标、分析影响因素、定验收标准、制定管理框架和数据收集规范 |
| 概要设计 | 确定可靠性度量、可靠性设计、收集数据 |
| 详细设计 | 可靠性设计、**可靠性预测**（估计可靠性度量值） |
| 编码 | 可靠性测试（含于单元测试）、排错 |
| 测试 | 可靠性测试（含于集成/系统测试）、**可靠性建模**、**可靠性评价** |
| 实施 | 可靠性测试（含于验收测试）、调整模型、可靠性评价 |

规律：需求阶段定目标和规范 → 设计阶段做可靠性设计+预测 → 编码/测试阶段做测试+建模+评价（验证预测准不准）→ 实施阶段持续验收+调整模型。"收集数据"和"调整计划"贯穿每个阶段，说明这是持续反馈迭代的过程。

**可靠性数据收集的现实困难**：规范不统一、连续性难保证、缺乏收集工具、完整性难保证、质量准确性难保证。**关键结论：用不准确数据做可靠性评价，误差可能比模型本身预测误差还大一个数量级**——数据治理比模型选择更重要。

教材坦诚：可靠性管理目前仍停留在定性描述水平，难以量化管理，是一个长期研究课题。

### 5. 软件可靠性设计（9.4）—— 实践价值最高

核心逻辑：测试阶段的查错排错只能有限改善可靠性，不能从根本上提高；**保障可靠性最有效、最经济的手段是在设计阶段就把可靠性"设计"进去**。

#### (1) 容错设计技术（用于失效后果特别严重的场合，如飞控/空管/核反应堆）

- **恢复块设计**：选一组操作作为容错单元，一个恢复块内含若干**功能相同、设计不同**的程序块文本，运行中一旦出错立即切换备用文本，构成"动态冗余"
- **N版本程序设计**：多个不同版本对相同输入做**多数表决**，防止某版本故障提供错误服务。前提：需求说明完全精确 + 设计过程完全不相关（不同团队、不同算法、不同语言、不交流）
- **冗余设计**：软件冗余不同于硬件冗余——不能用完全相同的代码互为备份（同样输入会在同样地方都出错），必须用**不同路径/算法/实现方式**做备份。代价：接近双倍开发成本（但文档测试人力可复用，实际增量成本远低于重新开发一个版本），且会增加存储/内存/运行时间开销

#### (2) 检错技术（成本更低，但不能自动解决问题）

核心是"发现故障+报警"，不能自愈。四个设计要素：**检测对象**（检测点选在易错且影响大的位置）、**检测延时**（发现故障的滞后时间）、**实现方式**（判断返回结果范围/运行时间/状态标志位）、**处理方式**（大多是"查出→停止→报警"，也有不停止的情况）

#### (3) 降低复杂度设计

软件复杂度和缺陷数正相关，复杂度超过阈值后缺陷数急剧上升、可靠性急剧下降。思路：在满足功能前提下简化结构、缩短代码、优化数据流向——本质是"高内聚低耦合"等设计原则与可靠性的直接挂钩。

#### (4) 系统配置技术——从代码层面上升到部署架构层面

**双机热备技术**：两台服务器+外接共享磁盘阵列+热备份软件，靠"心跳"机制检测主机故障并自动切换到备机。**本质是通过自动检测+自动切换压缩MTTR，从而提升整体可用性**。

三种工作模式对比：

| 模式 | 结构 | 特点 | 类比 |
|---|---|---|---|
| 双机热备（Active/Standby） | 一台工作，一台监控准备 | 应用最广，但备机闲置浪费资源 | 主从数据库 |
| 双机互备 | 两个独立应用互为备机 | 出故障对方接管，对性能要求高 | 微服务实例互为灾备 |
| 双机双工 | 两台都活动，同时运行相同应用 | 集群的一种形式，资源利用率最高 | 多活架构（Active-Active） |

**服务器集群**：双机热备的进一步延伸，从两台扩展到多台节点冗余（了解即可，不深究实现细节）。

### 6. 软件可靠性测试（9.5）

**关键操作要求**：必须是受控测试——同一测试过程中每个用例须用**相同软件版本**（版本一变，等于开始新测试，之前数据不能沿用），这呼应了独立性假设。可靠性测试与非统计测试（如覆盖测试）的顺序很关键：覆盖测试若在可靠性测试**之前**完成，统计数据仍有效；若在**之后**做，可能污染可靠性评估准确性。

**"强化输入"技巧**：用比正常输入更恶劣（但合理）的输入加速暴露缺陷——本质是**混沌工程的理论雏形**，重点方向包括屏蔽误操作能力、错误提示准确性、异常退出检测、数据有效性校验、硬件/网络/模块故障时的受损与补救情况。

**软件可靠性数据的4种分类**（可互相转化）：
- 失效时间数据：单次失效累积经历的时间
- 失效间隔时间数据：本次失效与上次失效的间隔
- 分组时间内失效数：某区间内发生的失效次数
- 分组时间累积失效数：到某区间为止的累积失效总数

## 二、易混淆 / 易错点

1. **MTTF vs MTTR vs MTBF**：MTTF是"能扛多久"，MTTR是"坏了修多久"，MTBF是两者之和——不要把MTBF和MTTF混为一谈，MTBF包含了故障+修复的全部时间
2. **可靠性设计 vs 可靠性测试**：测试只能"发现"问题、有限改善，设计阶段的措施才是"从根本上提高"可靠性的手段——不要高估测试阶段能挽回的设计缺陷
3. **N版本程序设计 vs 冗余设计**：两者都是"多版本"思路，但N版本设计强调**多数表决**（同时运行多个版本比对结果），冗余设计强调**主备切换**（备用版本平时不运行，出故障才启用）；恢复块设计则是冗余设计思路在"块级别"的具体实现
4. **容错设计 vs 检错技术**：容错能自动继续运行（恢复块自动切换文本），检错只能报警不能自愈，出故障后仍需人工/其他机制介入——不要把两者的能力边界混淆
5. **软件冗余 ≠ 硬件冗余**：硬件冗余可以用完全相同的备份元件，软件冗余若用完全相同的代码做备份**没有意义**（相同输入会在相同地方让两份代码都出错），必须采用不同实现路径
6. **可靠性模型的三大假设是局限，不是保证**：不要误以为用了可靠性模型算出来的MTTF/可靠度就一定准确——代表性假设、独立性假设、相同性假设任何一个被打破，模型结果都会失真
