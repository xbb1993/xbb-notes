# 第10章 软件架构的演化和维护 —— 学习笔记

> 定位：本章是第7章7.2.9"体系结构演化"的完整展开，也呼应第9章可靠性设计里"容错/降级"如何在真实系统中持续迭代。核心命题贯穿全章：**"软件架构是演化来的，而不是设计来的。"**

---

## 一、核心概念

### 1. 架构演化的重要性（10.1）

软件架构的演化 = 软件整体结构的演化，涵盖架构需求获取、建模、文档、实现、维护的全生命周期。架构演化的目的是**维持架构自身的有用性**，应对用户新需求、业务环境、运行环境的持续变化。

**为什么从架构层面演化更合理（三层逻辑）**：
1. 架构是系统骨架，直接决定性能、可靠性、安全性、易维护性等质量属性的上限——架构演化是保障这些属性朝预期方向发展的关键措施
2. 直接在代码层面管控复杂性成本极高，基于架构进行检测和修改成本相对更低
3. 良好架构设计天然为演化铺路：①形式化可视化表示提高可构造性；②整体结构/配置/约束信息帮助提前考虑未来演化场景；③对组件耦合的描述有助于动态调整（呼应第7章"层次型风格低耦合利于内部替换"的思路）

---

### 2. 软件架构演化方式的分类（10.2/10.3）—— 核心框架

**按是否处于系统运行期，这是本章最核心的分类**：

- **静态演化**：发生在架构的设计、实现和维护过程中，系统未运行或处于停止状态——对应"停机发布、停机升级"
- **动态演化**：发生在软件系统**运行过程中**——对应"热更新、不停机扩缩容、灰度发布、动态配置下发"

**演化时期的四级细分**（提前规划程度递减、实施难度递增）：

| 时期 | 特点 |
|---|---|
| 设计时演化 | 发生在架构模型和代码编译之前，自由度最高 |
| 运行前演化 | 编译后、执行前，不用考虑应用程序状态，但要考虑体系结构本身 |
| 有限制运行时演化 | 系统设计时预先规定演化条件，置于"安全模式"，满足约束才允许演化——**对应Feature Flag、配置中心热更新、K8s滚动更新/HPA自动扩缩容** |
| 运行时演化 | 架构已无法满足要求时被迫发生，需同时保证系统完整性、演化正确性、服务不中断，**四种里最难实现** |

### 3. 静态演化的一般过程（5步骤）

```
软件理解 → 需求变更分析 → 演化计划 → 系统重构 → 系统测试
```

软件理解（提取架构抽象表示）→ 需求变更分析（找出新旧需求差异）→ 演化计划（定范围和方案）→ 系统重构（按计划实施）→ 系统测试（验证效果）。静态演化需求来源两方面：设计时演化需求（保证实现与架构一致）、运行前演化需求（环境变化需要升级修改）。组件变更影响分析可用可达矩阵量化变更波及范围。

---

### 4. 软件维护的4种类型

| 类型 | 触发原因 |
|---|---|
| 更正性维护（排错性维护） | 系统运行中暴露的缺陷/bug |
| 适应性维护 | 外部环境变化（系统升级、硬件更换、政策法规变动） |
| 完善性维护 | 用户新需求、功能扩展 |
| 预防性维护 | 主动为将来可维护性/可靠性做准备（重构、清理技术债务） |

**规律**：系统运行初期更正性、适应性维护较多；运行后期完善性、预防性维护较多。若一个"老系统"长期停留在"天天救火修bug"阶段，说明系统本身质量或架构存在深层问题。这4类维护本质上都属于**静态演化**范畴。

---

### 5. 软件架构演化原则（10.4）—— 18种原则，按逻辑归为四类

1. **成本与风险可控类**：演化成本远小于重新开发成本、进度可控、风险可控
2. **结构质量类**：主体维持（增量增长平稳）、系统总体结构优化、平滑演化（速率稳定）、模块独立演化、影响可控、复杂性可控、有利于重构/重用——本质是把"低耦合高内聚""降低复杂度"的设计原则套用到"演化过程本身"，防止架构在多次小改动中逐渐腐化
3. **一致性与规范性类**：设计原则遵从性、适应新技术（技术独立性）、环境适应性、标准依从性、目标一致
4. **价值导向类**：质量向好（演化后质量优于演化前）、适应新需求（不能为解决眼前问题牺牲未来适应新需求的能力）

**统一认知**：架构演化本身也需要被当作一个需要被设计、被评估的过程，而不是随意的改动行为。

---

### 6. 架构演化评估方法（10.5）

**演化过程已知**：对每个中间版本（A₀→A₁→...→Aₙ）做质量属性度量，计算相邻版本间的**架构质量属性距离** D(i-1,i)，综合得出整体质量变化趋势。价值：评估单次演化影响、监控演化过程（架构健康度曲线）、定位关键演化节点（质量剧变处往往对应重大架构改动）。

**演化过程未知**：只有演化前后两个版本，无中间记录。做法：分别度量前后版本，比较差异和质量属性距离，**逆向推测**发生了哪些演化操作、作用对象、以及高层驱动原因，再验证这次演化是否达到预期效果。

---

### 7. 大型网站系统架构演化实例（10.6）

案例展示了网站架构从**单体架构**出发，依次经历垂直架构（应用/数据/文件分离）、引入缓存、应用集群+负载均衡、数据库读写分离、CDN+反向代理、分布式文件/数据库系统、NoSQL与搜索引擎、业务拆分、分布式服务化等十个阶段的演化过程。核心启示：**没有一步是提前设计好的，全部是当前方案撑到极限后被迫演化到下一步**，是"架构是演化来的"这一命题最贴近实践的例证（细节案例性质强，不作为记忆重点，需要时可查阅原文）。

### 8. 软件架构维护（10.7）

分三个管理内容：

- **架构知识管理**：架构知识 = 架构设计 + 架构设计决策，核心是记录"为什么这么设计"。若不管理，关键决策会随人员流动"沉没腐蚀"——对应业界的ADR（架构决策记录）实践
- **架构修改管理**：建立"隔离区域"（Region of Quiescence），保障区域内修改对其他部分影响很小甚至没有——对应灰度发布、影子流量、微服务边界隔离等"变更爆炸半径控制"实践
- **架构版本管理**：为演化的版本控制、使用、评价提供依据，为量化度量（如架构质量属性距离）奠定基础

## 二、易混淆 / 易错点

1. **静态演化 vs 动态演化的判断标准只有一个**：是否处于系统运行期，不要用"改动大小"来判断——小改动如果发生在运行时也算动态演化，大改动如果是停机做的也算静态演化
2. **"有限制运行时演化" vs "运行时演化"**：前者是系统设计时就规划好的、有约束条件的"合法动态调整接口"（如Feature Flag）；后者是架构已无法满足要求、被迫发生的调整，没有提前规划，难度远高于前者——不要把两者混为"都是运行时改动"就等同看待
3. **4种维护类型都属于静态演化**：不要把"软件维护"和"动态演化"混为一谈，传统维护理论本质上都是停机状态下进行的调整
4. **演化成本控制原则 ≠ 越省钱越好**：原则要求的是"演化成本远小于重新开发成本"，是一个相对比较，不是追求绝对最低成本而牺牲质量
5. **架构知识 ≠ 架构设计方案本身**：只有设计图纸/文档，没有"设计决策与依据"，不算完整的架构知识管理——这是很多团队文档"有结构没决策"的通病
6. **业务拆分 vs 分布式服务（10.6案例中容易混的两个阶段）**：业务拆分是按产品线做**纵向**的应用拆分；分布式服务是把各应用间**共用的业务能力**抽取出来独立部署——前者解决业务复杂度问题，后者解决数据库连接数量爆炸问题，两者驱动因素不同
