# 第12章 信息系统架构设计理论与实践 —— 学习笔记

> 定位：本章核心是 TOGAF/ADM 企业架构方法论——这是业界真实在用的架构师工作框架，与工作深度交叉，重点消化。信息系统架构分类、4种架构模型部分与第7章（架构风格）、第13章（层次式架构）高度重叠，作复用处理而非重学。信息化工程方法论（CSF/SST/BSP）和案例分析偏管理咨询/行业背景性质，从简记录。

## 一、核心概念

### 1. 信息系统架构（ISA）的本质

- **两个层次**：概念层次（艺术、科学、方法、建设风格——"想怎么设计"）vs 物理层次（一系列架构工作后产生的实际物理结构——"最终落地成什么样"）
- **架构的本质 = 组成成分 + 组成成分之间的关系**
- **柔性/适应性的来源**：系统内部存在两类部分——无论环境怎么变都**不变**的稳定核心，和**随环境变化而变**的部分。不同系统里两者比例不同。这是判断"哪些逻辑该抽象隔离、哪些该沉淀为稳定层"的第一性原理
- **架构对开发组织的反作用**：架构决定了可以按其边界对项目组分工（呼应康威定律）；成功的架构会反过来带来新商机（可复用性提升+团队经验积累），形成"架构↔组织"的正反馈——教材称之为**架构的商业周期**

### 2. 信息系统架构分类

- **物理结构**：集中式（早期单机系统，资源集中易管理但"一挂全挂"，现代信息系统建设基本不用）vs 分布式（现代主流，又分"一般分布式"和"C/S模式"两种）
- **逻辑结构**：按管理职能划分的功能子系统综合体，强调子系统间关系不能被忽视

### 3. 信息系统常用4种架构模型（与第7、13章复用，本章补充细节）

- **单机应用模式**：跑在一台机器上的独立程序（可多进程/多线程），单机系统≠简单系统（如CATIA、AutoCAD、Photoshop内部复杂度极高）
- **C/S 模式四种细分**：
  - 两层C/S："胖客户端"，前台界面+业务逻辑打包在客户端，后台只是数据库（PowerBuilder、Delphi、VB时代产物）
  - 三层C/S/B/S：前台与后台服务分离，靠协议通信，7种通信方式（裸Socket → 自定义消息机制 → RPC → CORBA/IIOP → Java RMI → J2EE JMS → **HTTP**）
  - **关键结论**：B/S 本质是"采用通用客户端界面（浏览器）的三层C/S结构"，不是独立发明的新架构
  - 多层C/S：三层以上，实践中常见三层/四层
- **SOA与多服务集合**
- **企业数据交换总线**：本质是"连接器（Connector）"中间件，基于消息中间件/CORBA构建，按预定义配置做数据接收分发；国内主要银行、电信等高信息化行业采用

### 4. 企业信息系统总体框架

四个层面对应管理金字塔三层：

| 管理层级 | 系统层级 |
|---|---|
| 战略管理 | 第一层：战略系统 |
| 战术管理 | 第二层：业务系统 → 应用系统 |
| 运行管理 | 第三层：信息基础设施 |

启示：企业级架构不能只盯技术（应用系统+基础设施），业务战略层面也要纳入架构视野——这也是TOGAF专设"业务架构"独立阶段的原因

### 5. TOGAF 与 ADM 架构开发方法（本章核心重点）

**TOGAF**：The Open Group制定的企业架构标准（1995年发布），基础是美国国防部TAFIM。六大组件中 **ADM 是核心**，其余五个（ADM指南和技术、架构内容框架、企业连续体和工具、参考模型、架构能力框架）都是围绕ADM的支撑体系。

**ADM 与企业连续体的闭环关系**：业务需求→纳入ADM→加深对需求的理解并产出新方案→内容沉淀进架构内容框架/企业连续体→运营变化又反哺更新企业连续体，驱动下一轮需求。

**ADM 十阶段环形模型**：

```
预备阶段 → 需求管理（贯穿中心，非普通环节）
     ↓
A.架构愿景 → B.业务架构 → C.信息系统架构(应用&数据) → D.技术架构
     ↓
E.机会和解决方案 → F.迁移规划 → G.实施治理 → H.架构变更管理 → (回到A，开始新一轮)
```

**三级迭代概念**（理解ADM"非瀑布式"的关键）：
1. 整体环形迭代：跑完一圈回到起点，持续演进
2. 多阶段间迭代：允许"跳回"之前阶段（如D阶段发现问题跳回B业务架构）
3. 单阶段内部迭代：单个阶段内部也可多轮细化

**各阶段要点**（目标-步骤-输入-输出四要素结构，是ADM的通用表达范式）：

- **准备阶段**：搭台子——定义组织架构、裁剪架构框架、定义架构原则、落实工具
- **需求管理**（贯穿所有阶段）：识别/存储需求，送进/取出各阶段；建需求基线→监控→处理变更（增删改+重排优先级）→评估变更对已完成阶段的影响→必要时触发H阶段。核心思想：需求管理不是前置一次性动作，而是贯穿始终、可随时把变化插回任意阶段的动态过程
- **A.架构愿景**：拿到管理层承诺、定义范围、识别干系人、确认业务原则/目标/驱动力/KPI，产出"得到批准的架构工作说明书"（相当于项目立项文档）
- **B/C/D（业务/信息系统/技术架构）**：套路完全一致——**开发基线架构描述 → 开发目标架构描述 → 执行差距分析**（"现状-未来-gap"三部曲），只是作用对象不同（业务流程/应用&数据/技术平台）
- **E.机会和解决方案**：决定技术路线（制造/购买/重用、外包、商用、开源），评估优先级、识别依赖，项目分组纳入过渡架构
- **F.迁移规划**：对E阶段项目做绩效分析和风险评估，产出详细实施迁移计划
- **G.实施治理**：定义实施项目的架构约束，提供架构监督，发布"架构契约"，监测项目合规性——**ADM中唯一直接面向"真正开始搭建系统"的阶段**
- **H.架构变更管理**：评估架构性能，管理变更请求（技术变化：新技术/成本削减/技术退役；业务变化：业务发展/异常/战略变化），触发新一轮ADM循环

**类比参照（帮助理解，非教材原文）**：

| ADM阶段 | 类比你熟悉的开发流程 |
|---|---|
| 预备阶段 | 项目启动前的技术选型/团队组建 |
| 需求管理 | 贯穿全程的需求变更管理（类似持续流转的需求单） |
| A愿景 | 项目立项/需求评审 |
| B/C/D | 业务流程梳理 / 系统设计(含数据模型) / 技术选型&基础设施设计 |
| E/F | 技术方案决策(自研/买/开源) + 实施排期 |
| G | 开发落地阶段的架构守护(架构评审/code review) |
| H | 上线后的架构演进管理 |

### 6. 信息化总体架构方法（了解，非重点）

信息化建设生命周期五阶段：系统规划 → 系统分析 → 系统设计（总体+详细）→ 系统实施 → 运行维护（本质是传统SDLC的管理咨询版表述）。

总体规划方法论三种（知道名字定位即可）：CSF（关键成功因素法）、SST（战略目标集转化法）、BSP（企业系统规划法，用得最多）。

## 二、易混淆 / 易错点

1. **B/S 不是独立于 C/S 的新架构**：B/S 本质是"采用通用客户端界面（浏览器）的三层C/S结构"，浏览器和Web服务器之间的通信仍是TCP/IP，只是在应用层把协议格式标准化为HTTP——不要把B/S和C/S当成平行对立的两种架构来记
2. **需求管理不是ADM的"第一步"，而是贯穿全程的中心环节**：容易被误解成"需求管理只发生在项目开始阶段"，实际上它可以在任何阶段被触发、把变更插回任意阶段
3. **ADM是环形迭代，不是瀑布式的单向流程**：允许"多阶段间迭代"——比如做完D技术架构发现问题可以跳回B业务架构重做，不是走完就走完
4. **B/C/D三个阶段方法论相同，对象不同**：都是"基线-目标-差距分析"三部曲，容易误以为业务架构、信息系统架构、技术架构是完全不同的方法论，实际上是同一套方法应用在三个不同对象上
5. **信息系统架构风格 = 第7章通用架构风格**：本章没有引入新的架构风格分类，不要误以为ISA有独立于第7章的一套风格体系
6. **集中式结构在现代信息系统建设中已很少使用**：容易在"集中式vs分布式"对比时忽略这个现状判断，误以为两者是并列常用的选项
