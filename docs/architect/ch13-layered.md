# 第13章 层次式架构设计理论与实践 —— 学习笔记

> 定位：本章和日常开发工作深度重叠——MVC/MVP/MVVM、ORM/Hibernate/MyBatis、工厂模式做数据访问、连接池设计，这些大多已在实践中使用，本章价值在于把"为什么这么设计、各方案取舍在哪"系统化。数据访问层设计（13.4）和PetShop案例（13.7.1）是含金量最高的两块。物联网层次架构（13.6）等偏行业特定内容，从简记录。

## 一、核心概念

### 1. 层次式架构的本质与代价

- **软件体系结构的三个作用**：利益相关人员的交流工具（不限于程序员）、系统设计的前期决策（早期决策影响深远）、可传递的系统级抽象（促进系统级复用）
- **层次式架构（N层架构）**：每层为上层服务、作为下层客户，常见分层为表现层→中间层（业务层）→数据访问层（持久层）→数据层，不强制规定分几层
- **核心特性：关注分离**——每层只负责本层逻辑，职责清晰，易开发/测试/管理/维护
- **污水池反模式（architecture sinkhole anti-pattern）**：请求简单穿过多层但某层几乎不做业务逻辑，判断标准是二八原则——空转请求超过20%时应考虑让该层"开放"（允许跳过）
- 分层的代价：可能导致分布式复杂度上升、健壮性下降、代码规模膨胀——分层不是免费的

### 2. 表现层三大设计模式及其演进关系

- **MVC**：Controller接收请求→调用Model处理业务→调用View格式化展示。**View可以直接从Model读数据**。优点：允许多种UI扩展、易维护、模型可被多视图复用
- **MVP**（从MVC演变）：**View与Model之间的通信必须经过Presenter**，View不能直接读Model。Presenter依赖抽象的IView接口，带来更好的可测试性（可脱离UI做单元测试）；一个Presenter可服务多个View
- **MVVM**（为解决MVP接口爆炸问题而提出）：ViewModel通过**DataBinding实现View与Model的双向绑定**，减少样板代码；代价是双向绑定导致问题定位困难（无法直接判断是数据问题还是业务逻辑问题）。建议用官方组件（ViewModel、LiveData）实现而非自建绑定机制
- **演进主线**：MVC→MVP是"进一步隔离View和Model，提升可测试性"；MVP→MVVM是"用自动绑定取代手动接口调用，减少样板代码，牺牲调试透明度"

### 3. UIP设计思想

把表现层拆成 **UI Components**（用户交互，原表现层）+ **UI Process Components**（用户不可见，负责导航/工作流控制/状态管理）。解决"导航流程代码和UI代码混在一起难维护、难跨平台复用"的问题。现代变体：前端路由守卫+状态管理（Redux/Vuex）分离页面展示与流程编排。

### 4. XML设计表现层

用XML描述GUI控件结构（本质是**策略模式**）：装载XML配置→用对应表现技术的解析器解析→得到GUI实例对象。好处是开发者只需维护一套XML文件，针对不同表现形式（Web Form/Windows Form）用不同解析器渲染。

### 5. 中间层（业务逻辑层）架构设计

- 业务逻辑组件以DAO组件为基础，**面向接口编程**，通过**IoC/DI（依赖注入）**由容器（如Spring）完成组件装配和实例化
- 事务代理设计：继承事务代理模板 或 单独指定事务代理属性
- 最终对外提供统一**Facade接口**，前台Web层只依赖该接口——Web层与后台业务层松耦合，可独立替换任一层
- **业务逻辑层实体的表示方式**：XML（标准支持/灵活性/互操作性）、通用DataSet（灵活但弱类型）、强类型DataSet（编译时类型检查但编码量大）——本质是"灵活性 vs 类型安全"的取舍
- **Domain Model—Service—Control互动关系**：Service运行依赖Domain Model状态，也会改变其状态；Control根据Domain Model状态决定Service执行顺序——这是MVC"控制与显示分离"思想在中间层内部的复用
- **工作流（WFMC定义）**：业务流程全部或部分自动化，文档/信息/任务按预定规则流转，实现组织成员间协调以达成业务目标

### 6. 数据访问层设计（本章重头戏）

**5种数据访问模式**：
1. 在线访问：占用一个连接，每个操作直接交互，最基本最常用
2. DAO模式：标准J2EE设计模式，分离底层数据访问与高层业务逻辑
3. DTO模式：两种实现路径——用平台内置通用集合（DataSet/SDO）承载数据+类型信息，或自定义类实现（编译时类型检查但编码量大），也可用代码生成技术折中
4. 离线数据模式：以数据为中心，特点是离线（独立于连接/事务）、与XML集成、独立于数据源
5. O/R Mapping：解决"关系模型数据 vs 对象模型程序"的根本错配，是目前最主流的持久层设计思路

**工厂模式在数据访问层的应用**：定义统一数据库访问接口，工厂方法根据实际数据库类型决定实例化哪个具体实现类，实现"数据库无关"——把"选哪个实现"的决策从调用方剥离

**ORM/Hibernate/CMP2.0**：
- ORM本质是把"生成DAL"这件事自动化，好处是降低学习/开发成本、减少代码量和出错率、通过Cache隔离存储与业务层便于性能调优
- Hibernate：对JDBC做轻量级对象封装，提供Java类到数据表映射；两种运行方式——轻型体系（应用自管连接和事务，只用最小子集）、全面解决体系（JDBC/JTA API全部抽象，Hibernate照管细节）
- **Hibernate vs MyBatis 核心取舍**：Hibernate全自动，强大但复杂笨重、SQL对开发者黑盒；MyBatis半自动，需手写SQL但灵活小巧上手快——**没有绝对更优，只有更适合团队/场景的判断**（业务查询复杂需要SQL精细调优 → MyBatis更合适；CRUD为主追求开发效率、能接受黑盒调优成本 → Hibernate更合适）
- CMP2.0是J2EE早期EJB容器管理持久化方案，现已基本被Hibernate/JPA取代，了解出处即可

**事务处理设计**：核心原则——业务逻辑层实体本身不启动事务，事务由使用它的上层应用/业务过程发起；数据访问层负责提供事务执行能力。呼应Spring里`@Transactional`该标在Service层而非DAO层。

**连接对象管理设计（连接池）**：应用**资源池设计模式**解决JDBC连接频繁创建/销毁的性能问题。建立步骤：①建立静态连接池（初始化时按配置创建好连接，不能随意关闭）②分配策略（有空闲连接则分配，无空闲则在已分配连接中找一个复用）③释放策略（无其他使用者则放回池中而非关闭）。核心哲学：**用"借用-归还"取代"创建-关闭"**，是HikariCP、Druid等连接池组件的底层设计依据。

### 7. 数据架构规划与设计

- **数据库设计与类的设计融合**：建模本质是艺术，不存在唯一正确的数据模型，只存在相对更好的模型；好模型的目标是把工程项目整个生命周期的花费降到最小，同时为未来变化留出适应空间
- **数据库设计与XML设计融合**：用XML描述数据库元数据/结构映射，呼应ORM映射配置思路

### 8. PetShop案例的架构演化（活案例，价值高）

- **PetShop 2.0**：无独立数据访问层，业务逻辑层与数据访问逻辑职责混乱，性能占优但换数据库/改数据访问逻辑代价巨大
- **PetShop 3.0**：数据访问逻辑独立成单独一层，引入**DAL Interface**（抽象数据访问逻辑）+ **DAL Factory**（数据访问层对象工厂），具体实现`SQLServerDAL`/`OracleDAL`都实现`IDAL`接口
- **PetShop 4.0**：核心结构沿用3.0，性能上引入缓存（CacheDependency）和异步处理机制，用ASP.Net 2.0 Membership功能；`IDAL`模块使业务逻辑层与具体数据库实现解耦，换数据库实现不影响业务逻辑层

## 二、易混淆 / 易错点

1. **MVC/MVP/MVVM三者的核心区别不是"更先进"，而是View能否直接访问Model**：MVC允许View直接读Model，MVP不允许（必须经Presenter），MVVM靠ViewModel做自动双向绑定——不要笼统地认为MVVM就是"更好的MVC"，三者是针对不同问题（可测试性 vs 数据驱动场景）的不同取舍
2. **MVP的可测试性来自"Presenter依赖抽象接口IView"，不是来自"分了三层"**：容易只记住"MVP把View和Model隔离了"，忽略了这个隔离能落地成单元测试的关键是接口抽象
3. **Hibernate和MyBatis没有优劣之分，只有场景适配问题**：容易简单地认为"全自动=更先进"或"半自动=更专业"，实际上要看业务查询复杂度和团队对SQL可控性的需求
4. **工厂模式在数据访问层的价值是"数据库无关"，不是"减少代码行数"**：容易把工厂模式仅仅理解成一种代码组织技巧，忽略了它真正解决的是"运行时决定用哪个数据库实现"这个架构层面的解耦问题
5. **连接池的"借用-归还"不等于"创建-关闭"**：容易把连接池简单理解为"缓存连接"，实际上核心是分配/释放策略（空闲复用优先，无空闲时多客户共享同一连接）
6. **事务应该在Service层（业务逻辑层）发起，不应在DAO层（数据访问层）发起**：数据访问层实体本身不启动事务，只提供执行事务的能力——容易把`@Transactional`误标在DAO方法上
7. **PetShop 2.0的"性能更优"是有代价的**：不要只看到"少一层调用性能好"的表面结论，2.0恰恰是反面教材，代价是牵一发动全身的维护成本
8. **建模没有唯一正确答案，这是一个态度问题不是知识盲区**：容易在做领域建模/数据库设计评审时纠结"哪个方案是标准答案"，教材明确态度是"评估相对优劣，而非寻找唯一解"
