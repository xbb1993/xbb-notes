# 第19章 大数据架构设计理论与实践 —— 学习笔记

> 定位：本章和工作关联度较高——Lambda/Kappa架构模式是做数据平台、实时计算、离线+实时融合系统时的经典设计范式。核心收获：Lambda和Kappa不是"新旧替代关系"，而是针对不同业务形态（历史数据深度探索 vs 持续增量流）的不同设计取舍，选型应按业务需求、复杂度承受能力、历史数据处理规模理性判断。具体案例细节和技术组件选型从简记录。

---

## 一、核心概念

### 1. 传统数据处理系统的演进困境

演进链条：应用直接访问数据库（负载过大超时）→ 加异步队列缓冲（未从根本解决数据库过载）→ 数据库分区/Horizontal Partitioning（应用需感知分区规则）→ resharding困境（数据迁移+地址更新+代码更新，耗时痛苦易出错）。

**核心教训**：每一步"缓解"手段都在给系统增加新的运维复杂度（队列/分区/复制/resharding脚本），应用程序被迫承担本该由基础设施负责的职责（感知数据存储位置、分区规则、schema）——大数据架构要解决的核心问题就是把这些复杂性从应用层"下沉"到平台层。

### 2. 大数据处理系统的8大关键属性（Nathan Marz提出，评价任何大数据架构的通用标尺）

1. **鲁棒性和容错性**：机器会宕机，人会犯错（写bug产生错误数据），系统必须对两者都有适应能力——**人为操作容错性比机器容错性更重要**，大部分生产事故根源是人写的代码/配置出错而非硬件故障
2. **低延迟读取和更新能力**：从几毫秒到几百毫秒，取决于具体需求
3. **横向扩容（Scalable）**：通过增加机器数量维持性能（scale out），而非增强单机性能（scale up）
4. **通用性**：能支持金融/社交网络/电商等各类应用场景
5. **延展性（Extensible）**：新功能需求出现时能加入系统，包括大规模迁移能力
6. **即席查询能力**：用户能按自己需求灵活查询，而不只是跑预定义报表
7. **最少维护能力**：**核心洞察**——大数据系统设计要通过"减少系统本身的复杂性"来减少出错概率，而不是指望靠更多监控运维手段弥补一个天生复杂的系统
8. **可调试性**：系统运行中每个值都要能被追踪，明确其产生过程

第1条和第7条是Marz的核心洞察，也是Lambda架构"不可变性+批流分离"设计的直接理论来源。

### 3. Lambda架构

**三层结构**：
- **批处理层（Batch Layer）**：存储全量数据集，预计算生成Batch View——结果精准全量，但时延很高。关键工作是根据业务需求，为实际会用到的查询模式定义对应的View，而非漫无目的地预计算所有可能
- **加速层/速度层（Speed Layer）**：只处理最近增量数据流，不断更新Real-time View——时延很低，但数据可能不准确/不全量
- **服务层（Serving Layer）**：合并Batch View和Real-time View，响应查询请求；合并逻辑依赖**Monoid性质**（满足结合律）——满足则可简单合并两个View结果，否则需转换成多个满足该性质的子查询分别合并

**三大设计优点**：
- **容错性**：Speed Layer的数据也会不断写入Batch Layer，Batch Layer重新计算覆盖后当前Real-time View可丢弃——Speed Layer中的错误会在Batch Layer重新计算时被自动修正，本质是CAP理论"最终一致性"的体现
- **复杂性隔离**：Batch Layer处理离线数据逻辑简单可控，Speed Layer用增量算法复杂度天然更高——把复杂性隔离在Speed Layer，让Batch Layer保持简单，提升整个系统的鲁棒性，是"用架构划分把复杂度限制在最小可控范围"的设计智慧
- **横向扩容**：数据量/负载增大靠增加机器资源维持性能

**不可变性与重新计算**：应对人为和机器错误的常用方法——采用不可变数据模型（数据只增不改），出错时遍历数据集丢弃错误数据、利用数据时间序列顺序重新计算即可得到正确结果（Datomic、Kafka都是这一思路的例子）。

### 4. Kappa架构

**核心思路**：既然Speed Layer已能做实时处理，为何还要单独维护Batch Layer？删除Lambda架构中的Batch Layer，只通过一条流计算链路计算并产生视图，用消息队列替代原来的批处理数据通道。历史数据分析需求靠**重放（replay）**：数据长期存储为有序日志流，需要重新计算时让历史数据重新流入流计算引擎。

**三层结构**：实时层（实时数据处理引擎处理输入数据）→ 历史数据存储+结果数据存储 → 服务层（服务后端处理，提供业务查询）

**Kappa与Lambda的本质区别**（关键澄清）：**Kappa不是Lambda的替代架构，而是简化版本**。Kappa放弃批处理支持，更擅长业务本身是增量数据写入的场景（如时序数据，天然有时间窗口概念）；Lambda直接支持批处理，更适合需要对历史数据做任意条件组合探索性分析的场景（如数据分析师深挖历史数据）。**区分标准不是"哪个更先进"，而是两者服务的分析需求形态本身不同**。

**Kappa实现机制**（以Kafka为例）：部署Kafka设置数据日志保留期（决定能重新处理多久历史数据）→ 需要改进算法时重启新作业实例，Log Offset设为0从头计算，输出到新视图 → 新视图进度赶上旧视图后切换读取 → 停止旧实例删除旧视图。

**Kappa的优缺点**：
- 优点：实时离线代码统一，方便维护，统一数据口径，避免Lambda的离线数据合并复杂性，查询历史数据只需重放
- 缺点：①消息中间件缓存数据量和回溯数据有性能瓶颈（长期存储压力大，大规模回溯订正消耗实时计算资源大）②大量不同实时流关联时非常依赖实时计算系统能力，可能因数据流顺序问题丢失数据③抛弃离线数据处理模块的同时也抛弃了离线计算更稳定可靠的特点——这是trade-off而非纯优化

**常见变形**：Kappa+架构（Uber提出，流计算直接读HDFS数据仓库数据，用Hudi等支持增量更新/删除的存储格式解决消息队列存储成本高的问题）、混合分析系统（Kappa基础上接入ElasticSearch弥补展示分析能力不足，是Kappa和Lambda间的折中方案）

### 5. Lambda与Kappa的对比及选型逻辑

| 对比维度 | Lambda架构 | Kappa架构 |
|---|---|---|
| 复杂度与维护成本 | 需维护两套系统，复杂度高、成本高 | 只需维护一套系统，复杂度低、成本低 |
| 计算开销 | 相对较小 | 计算开销大（全量重算消耗大） |
| 实时性 | 满足实时性 | 满足实时性 |
| 历史数据处理能力 | 批式全量处理，吞吐量大，能力强 | 流式全量处理，吞吐量相对低，能力较弱 |

**设计选择的4个考虑因素**（计算开销差异不大，不作为主要决策依据）：
1. **业务需求与技术要求**：强依赖Hadoop/Spark/Storm等批处理技术→Lambda；偏好流式计算依赖Flink→Kappa
2. **复杂度**：需频繁修改算法参数→Kappa更简单；但若实时处理和离线处理结果**不能统一**（如机器学习：离线训练模型+实时验证测试），批处理层和流处理层无法合并→必须选Lambda
3. **开发维护成本**：Lambda需两套系统全流程维护，适合资源充足团队；Kappa只维护一套，适合不想过多投入维护成本的团队
4. **历史数据处理能力**：需频繁分析海量历史数据（如过去十年数据）→选Lambda；始终使用小规模数据集→选Kappa

## 二、了解即可

- **大数据处理系统面临的三大挑战**：非结构化/半结构化数据处理（结构化数据仅占约15%）、复杂性和不确定性建模刻画、数据异构性与决策异构性的关系——偏学术研究视角
- **具体案例**：某网奥运大数据应用（Lambda架构，"当日概览"用实时计算+"赛事回顾历史统计"用离线计算，印证Lambda"实时性和精确性各司其职"的设计思想）、某网广告平台演进、某证券公司大数据系统、某电商智能决策大数据系统——案例性质，用于验证理论在真实业务中的落地，不需记具体技术选型细节和数字
- **具体技术选型示例**：Hadoop(HDFS)存储主数据集+Spark/Storm构成速度层+HBase作为服务层+Hive创建可查询视图——了解"三层结构可用不同大数据组件实现"这个思路即可

## 三、易混淆 / 易错点

1. **Kappa不是Lambda的"升级版"或"替代品"，而是针对不同业务形态的简化版本**：容易认为技术更新的Kappa全面优于Lambda，实际上两者服务的分析需求形态不同（持续增量流 vs 历史数据深度探索），选型要看业务而非技术新旧
2. **"复杂度"这个决策维度不只是"要不要维护两套系统"，还包括"实时和离线结果能否统一"**：容易忽略当实时处理和离线处理结果无法统一时（如机器学习训练+验证场景），批流层根本无法合并，此时Kappa的"合并优势"不适用，必须选Lambda
3. **Lambda架构的容错性不是靠"减少错误发生"，而是靠"错误会被后续重新计算自动修正"**：这是一种被动式、最终一致性式的容错设计，不要理解成主动的错误预防机制
4. **Kappa的"计算开销大"和Lambda的"计算开销小"是相对的，且教材明确指出两者计算开销差异不大，不应作为选型的主要依据**：容易过度强调这一维度的差异
5. **Marz提出的"最少维护能力"讲的是通过降低系统复杂性来减少错误，不是靠增加运维人力/工具来维持系统稳定**：这是一个设计原则层面的观点，容易被简单理解成"要做好监控"这类运维层面的建议

- **第10章《软件架构的演化和维护》**：本章19.1传统数据处理系统的演进困境（单体数据库→读写分离→分库分表→resharding），与第10章大型网站架构演化的第一/二/三阶段（单体架构→垂直架构→缓存优化）是同一类"系统在数据量/用户量增长下被迫演进"的现象在不同层面（应用架构 vs 数据架构）的体现
- **第14章《云原生架构设计理论与实践》**：Lambda架构的"复杂性隔离"设计原则（把复杂的Speed Layer和简单的Batch Layer分开）与云原生的"服务化原则"（不同生命周期模块分开迭代）在设计哲学上相通；Kappa架构基于消息队列的事件驱动流处理，与第14章事件驱动架构（EDA）模式相关
- **第7章《系统架构设计基础知识》**：Lambda/Kappa架构本质上是"管道-过滤器"和"仓库"两种通用架构风格在大数据领域的具体应用（批处理层类似仓库风格存储全量数据，流处理层类似管道过滤器处理增量事件流）
