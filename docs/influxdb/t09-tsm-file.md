# TSM 文件结构与读取

> 专题 9 · 模块三 · ★ 核心必会 · 主线：S Q
> 地图位置：写入路径第 ⑧ 步的产物；查询路径第 ④ 步"从 TSM 读数据"。
> 依据：云端 1.6.7 实测；自写的解析脚本（按 1.13.2 源码 `writer.go`、`reader.go`、`encoding.go` 的格式，因为 apt 包里没有 `influx_inspect`）。

## 一、核心概念

### 1.1 从需求推出结构

文件写完后就不再修改。它需要满足四个要求：能快速找到某一列；能只读某一段时间；文件要小；能发现损坏。

| 步骤 | 问题 | 设计 |
|---|---|---|
| 1 | 怎么快速找到某一列、怎么压得小 | 同一个 key（`series key#!~#field`）的值连续存放，key 按字节顺序排序 |
| 2 | 一列太长，不能为了查一小段而全部解压 | 切成**块**，每块最多 1000 个点（`DefaultMaxPointsPerBlock = 1000`），每块单独压缩 |
| 3 | 怎么知道某段时间在哪一块 | 文件末尾放**索引**：每个 key 一条记录，记录它每块的最早时间、最晚时间、偏移、大小 |
| 4 | 写文件时，块的位置要写完才知道 | 索引只能放在末尾；最后 8 字节是 **footer**，记录索引从哪里开始 |
| 5 | 识别文件格式、发现损坏 | **header** 是魔数 `0x16D116D1` 加版本号 1；每块前面带 **CRC32** 校验和 |

块内布局（源码 `packBlock`）：类型(1B) + 时间戳段长度(变长整数) + 时间戳段 + 值段。时间戳和值分开压缩（具体编码见专题 10）。

索引里每个 key 的记录格式：key 长度(2B) + key + 类型(1B) + 块数(2B) + 每块 [最早时间 8B, 最晚时间 8B, 偏移 8B, 大小 4B]。

### 1.3 实测：拆开一个文件（专题 6 的宽表数据：100 块表 × 4 个 field × 1 天 × 每 15 秒）

```
文件大小 14,410,264 B
key 数（列数）=400，块数=2400，平均每列 6.0 块，平均块大小 5,970 B
m1#!~#kwh：6 块，前 5 块各 1000 点、最后一块 760 点，CRC 全部校验通过
第 0 块：类型=float，时间戳段 12 B，值段 5857 B
```

- 400 列 = 100 × 4，正好对应存储层的 series。每列 5760 个点 ÷ 1000 = 6 块。
- 索引只占文件的 0.57%。
- 1000 个时间戳只占 12 B：上报间隔固定，可以压缩成"起点 + 间隔 + 次数"。
- 每个值约 5.9 B（这份数据含随机数，比真实电表数据更难压缩）。整个文件平均每个值 6.25 B，不压缩需要 16 B。
- 同一块表的四个 field 在文件里相邻（key 按字节排序）。
- 这也回答了专题 6 的问题：磁盘大小取决于列数和每列的数据量，宽表和窄表都是 400 列，所以磁盘几乎相同。

### 1.4 读取过程与代价

```
① 由 measurement、tag 条件、field 确定要读哪些 key，再加上时间范围
② 在索引里二分查找 key
③ 只保留与查询时间范围有重叠的块
④ 通过 mmap 读出这些块并整块解压
⑤ 在解压出的点里，按精确的时间范围过滤
```

`EXPLAIN ANALYZE` 实测（1.6.7 支持，会真正执行查询并统计解压了多少块）：

| 查询 | 解压块数 | 字节 |
|---|---|---|
| m1 的 kwh，01:00～02:00（落在一块之内） | 1 | 5,932 |
| m1 的 kwh，04:00～05:00（跨过块边界） | 2 | 12,014 |
| m1 的 kwh 和 voltage，01:00～02:00 | 2 | 5,932 + 5,830 |
| 所有表的 kwh，01:00～02:00 | 100 | 580,598 |
| m1 的 kwh，全天 | 6 | 34,102 |

**查询代价 ≈ 命中的列数 × 每列覆盖的块数**。读取的最小单位是块：哪怕只要一个点，也要解压整块。

### 1.5 索引在内存中的形式

1.13.2 源码里的 `indirectIndex`：索引的原始字节留在 mmap 映射的文件里，内存中只多保存一个数组，记录每个 key 在索引里的起始位置；查找时在这个数组上二分。所以每个 TSM 文件在内存里的常驻开销大约是"key 数 × 一个位置值"。

### 1.6 mmap 与内存

**mmap**（内存映射）：把文件映射到进程的内存地址空间，读到哪一页，操作系统才把那一页加载进页缓存；内存紧张时，这些页可以被回收。

```
映射了 30 个 TSM 文件，映射总量 71,604 KB，其中实际驻留内存 10,744 KB
VmRSS 168,244 kB = RssAnon 128,488 kB + RssFile 39,756 kB
对 4 个库做全量扫描后：TSM 驻留 56,876 KB；RssFile 85,980 kB
```

- `RssAnon`：进程自己申请的内存（索引、Cache 等），需要重点关注。
- `RssFile`：已经读入的映射文件页，可以被回收。
- 容器的内存统计可能把页缓存也算进去，看监控时要分开看这两部分。

### 1.7 TSM 文件的来龙去脉

| | 说明 |
|---|---|
| 归属 | 某个 shard 目录：`data/库/RP/shard号/代号-序号.tsm` |
| 由谁创建 | 快照（Cache → 文件）或压实（多个文件 → 新文件） |
| 能否修改 | 写完就不再修改；覆盖写和删除都不改动已有文件（专题 12） |
| 何时删除 | 被压实合并后删除；shard 过期时随整个目录一起删除 |
| 每块点数 | 默认最多 1000；1.13.2 中冷 shard 深度压实时可以到 `aggressive-points-per-block`（默认 10000）；1.6.7 没有这个参数 |

### 1.8 TSM 为什么叫"树"（答疑）

- 单个 TSM 文件内部**没有树**，只有有序的块和一份有序的目录（二分查找）。
- TSM 的全称是 Time-Structured Merge Tree，借鉴了 **LSM 树**（O'Neil 等，1996 年，*Acta Informatica*，《The Log-Structured Merge-Tree (LSM-Tree)》）。原论文的结构是：内存部分 C0 加上磁盘部分 C1…Ck，每一部分都是类似 B 树的结构，数据像归并排序一样逐层向下合并。
- 后来的实现（LevelDB、RocksDB、TSM）把磁盘上的每一层换成了一批写完不改的有序文件，但保留了"Merge Tree"这个名字。所以这里的"树"指的是"**内存一层 + 磁盘多层，逐层合并**"的整体结构。
- InfluxDB 中每个 shard 都是这样一个结构。1.13.2 源码 `compact.go` 规定：文件名是"代号-序号"，序号小于 4 时序号就是层级，4 及以上都算第 4 层；快照产生的文件序号为 1。

```
一个 shard
  C0（内存层）  Cache（+ WAL）              ← 新写入（专题 8）
       │ 快照
  第 1 层       ...-000000001.tsm × 若干     ← 小文件，数量多
       │ 压实
  第 2 层       ...-000000002.tsm            ← 如 s6wide 的 000000002-000000002.tsm
       │
  第 3/4 层     更大、更少的文件
```

| | MySQL B+ 树 | LSM / TSM 的合并树 |
|---|---|---|
| "树"指什么 | 一个结构内部的根、中间、叶子节点 | 多层之间的合并关系；每一层是有序文件 |
| 写入 | 原地修改所在的页（随机写） | 追加到内存和 WAL（顺序写），再批量写成新文件 |
| 读一个 key | 只有一个位置 | 可能分散在 Cache 和多个文件里，需要合并，以新数据为准 |
| 修改 / 删除 | 原地修改 | 写入新数据或墓碑标记，压实时才真正处理 |

推论：shard 里的文件越多，读一列时要合并的地方就越多。压实既省空间，也降低读取成本（专题 11）。

### 1.9 串联图

```
快照 / 压实 → TSM 文件（写完不改）
 ┌ Header：魔数 + 版本
 ├ Blocks：按 key 排序 → 同一列连续 → 每块 ≤1000 点 = 时间戳段 + 值段（各自压缩）+ CRC
 ├ Index：每个 key 一条 → 每块的 [最早时间, 最晚时间, 偏移, 大小]
 └ Footer：索引起始位置
查询：确定 key → 索引二分查找 → 按时间范围挑选块 → mmap 读取 → 整块解压 → 精确过滤
代价 ≈ 列数 × 块数；内存中只多存位置数组；文件页属于页缓存（RssFile）
多个文件 + Cache 组成一个 shard 内的"合并树"
```

## 二、易混淆 / 易错点

| 错误理解 | 正确理解 |
|---|---|
| TSM 文件内部是树形结构 | 单个文件是有序块 + 有序目录；"树"指内存与多层文件的合并结构 |
| 查询代价取决于返回多少个点 | 取决于要解压多少个块；只要一个点也要解压整块 |
| 时间范围越窄，一定只读一块 | 跨过块边界就要读两块 |
| 多选几个 field 对代价没有影响 | 每个 field 是一列，会多解压对应的块 |
| 索引会全部加载进内存 | 原始字节留在映射文件里，内存只多存一个位置数组 |
| RSS 一直在涨就是内存泄漏 | 先区分 RssFile（页缓存，可回收）和 RssAnon |
| 宽表行少，所以磁盘更小 | 磁盘取决于列数和每列的数据量 |
| 覆盖写会修改已有的 TSM 文件 | 文件写完不改，覆盖写会产生新文件（专题 12） |

## 四、诊断实践

| 现象 | 看哪里 | 判断与处置 |
|---|---|---|
| 某条查询比预期慢 | `EXPLAIN ANALYZE` 中的 `*_blocks_decoded`、`*_blocks_size_bytes` | 解压的块太多：缩小时间范围、减少命中的 series、只选需要的 field |
| 时间范围很窄却解压了 2 块 | 块的时间边界 | 跨过了边界，属于正常现象 |
| 进程 RSS 持续增长 | `/proc/PID/status` 中的 `RssAnon` 和 `RssFile` | RssFile 增长是页缓存；RssAnon 增长才需要排查 |
| 怀疑 TSM 文件损坏 | 1.13.2 的 `influx_inspect verify`（讲到工具时再核实） | CRC 对不上说明块已损坏 |
| 想了解某个文件的组成 | `influx_inspect dumptsm -index -blocks`，或本讲的解析脚本 | 看 key 数、块数、时间范围 |
