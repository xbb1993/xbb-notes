# IoT 通信的约束与 MQTT 的诞生

> 专题 1 · 模块一 · ☆ 高频重点 · 侧重设备接入
> 版本基线：MQTT 5.0，3.1.1 差异单独标注
> 贯穿场景：一台计量电表每 10 秒上报一次功率，云端偶尔下发"改采样周期"指令，现场 4G 网络时断时续

本专题回答"为什么需要 MQTT"。后面学的每个机制（心跳、QoS、会话、遗嘱……）都是在回答这里提出的某个问题。读完这一篇只需要有一张**全景地图**，每个概念在哪一篇讲透，见第 3 节的对照表。

## 1. 核心概念

### 1.1 场景与四个约束

```
  [电表 meter3] ──4G──> (运营商 NAT) ──Internet──> [云端]
   每 10 秒上报功率                                  偶尔下发"改采样周期"
   内存小、可能靠电池                                  要管 10 万台表
```

| 约束 | 电表上的表现 |
|---|---|
| 带宽小、按流量计费 | 物联网卡每月可能只有几十 MB |
| 功耗敏感 | 每多收发一个字节，射频模块都在耗电 |
| 网络不稳定 | 信号差时频繁断线，断了自己往往不知道 |
| 连接数巨大 | 一个服务端要面对数万到数百万台设备 |

**NAT**（Network Address Translation，网络地址转换）：运营商让很多设备共用少量公网 IP。效果是**设备能主动连出去，外面连不进来**；而且 NAT 会回收长时间没有流量的连接映射。

### 1.2 朴素方案 HTTP 的问题

HTTP（超文本传输协议）是"一问一答"：客户端问，服务端答，**服务端不能主动开口**。

- 上报：每 10 秒 POST 一次，可以接受。
- 下发指令：服务端连不进设备，只能让设备**轮询**（隔一段时间问一次"有我的指令吗"）。

> 类比：HTTP 轮询 = 每 10 秒给快递站打电话问包裹到了没，99% 的回答是"没有"；MQTT = 一直开着对讲机频道，有事对方直接喊你。

```
轮询间隔 ↓  →  指令延迟小，但空请求暴增（流量、电量、服务器压力）
轮询间隔 ↑  →  省流量，但指令要等很久
```

### 1.3 流量估算（估算，不是实测）

假设：载荷约 30 字节，主题 `m/meter3/power`（14 字节），HTTP 请求头 + 响应头合计 500–700 字节，TCP/IP 包头每包约 40 字节。

| 每小时 | HTTP（上报 + 每 10 秒轮询） | MQTT（QoS 1 上报 + 推送指令） |
|---|---|---|
| 应用层字节 | 约 470 KB | 约 20 KB |
| 含 TCP/IP 包头与 ACK | 约 580 KB | 约 80 KB |
| 指令延迟 | 平均约 5 秒 | 约一个网络往返 |

一条 MQTT 上报 ≈ 固定头 2 + 主题长度 2 + 主题 14 + 包 ID 2 + 载荷 30 ≈ 50 字节（5.0 还多 1 字节属性长度）；确认 PUBACK 4 字节；最小报文（心跳 PINGREQ）**2 字节**。

结论：应用层差约 20 倍，算上 TCP/IP 后**约 7 倍**。更大的收益是**指令实时推送 + 不再空轮询**。

### 1.4 从问题推出 MQTT 的设计

```
                    ┌────────────────────── broker ──────────────────────┐
  电表 ──TCP长连接──>│ 认证 → 会话 → 按主题路由 → 投递（QoS） → 离线排队 │──> 后端/大屏
   (设备主动连出)    │        保留消息    遗嘱消息    心跳检测            │<── 下发指令
                    └────────────────────────────────────────────────────┘
```

| 问题 | MQTT 的回答 |
|---|---|
| 服务端连不进设备 | 设备**主动**建一条 TCP 长连接到 broker，之后双向都走这条连接 |
| 头部太胖 | 二进制报文，固定头最少 2 字节 |
| 发送方不该关心谁接收 | 发布订阅：电表只往主题发，broker 负责转给订阅者 |
| 断线了不知道 / NAT 回收空闲连接 | Keep Alive 心跳 |
| 数据重要程度不同 | QoS 0 / 1 / 2 分级 |
| 设备掉线要让人知道 | 遗嘱消息（LWT） |
| 断线期间的消息 | 会话与离线排队 |
| 新订阅者想立刻拿到当前值 | 保留消息 |

**Broker**：消息代理服务器，所有客户端都连它，由它按主题转发。类比邮局：寄信人只写"栏目"，不需要知道谁订了这个栏目。

### 1.5 诞生与版本（已联网核实，来源见文末）

- **1999 年**，IBM 的 Andy Stanford-Clark 与 Arcom 的 Arlen Nipper 设计，用于**石油管道 SCADA 监控**（SCADA：数据采集与监视控制系统），设备走**卫星链路**，流量极贵，目标是省带宽、轻量、省电。
- "MQ" 来自 IBM MQSeries 产品线；2013 年起 MQTT 不再作为缩写解释。
- 版本线：3.1（IBM 公开）→ 2013 年提交 OASIS → **3.1.1：2014-10-29** OASIS 标准，后为 ISO/IEC 20922:2016 → **5.0：2019-03-07**。
- 默认端口：明文 **1883**，TLS **8883**。

### 1.6 局限与适用边界

| 场景 | 为什么 MQTT 不一定合适 | 替代 |
|---|---|---|
| 长期休眠的电池设备 | 长连接要定期心跳，射频不能深睡 | MQTT-SN、CoAP |
| 一天只报一次 | 维持长连接不划算 | HTTP |
| 大文件（如固件包） | MQTT 不擅长大载荷 | HTTP 下载，MQTT 只发通知 |
| 极弱网 | TCP 重连 + TLS 握手开销大 | MQTT over QUIC |
| 载荷格式 | 协议不管载荷是什么 | Sparkplug 等上层规范 |

## 2. 易混淆 / 易错点

| 错误理解 | 正确理解 |
|---|---|
| MQ = Message Queue，所以 MQTT 是消息队列 | 名字是历史遗留，本质是**发布订阅**；"排队"只在离线会话里出现 |
| MQTT 省是因为用 UDP | MQTT 跑在 **TCP** 上，省在报文格式和长连接 |
| MQTT 比 HTTP 省几十倍流量 | 应用层约 20 倍，算上 TCP/IP 约 7 倍（本例估算）；核心收益是推送 |
| 有了 MQTT，IoT 里就不用 HTTP | 低频上报、OTA 大文件下载仍常用 HTTP |
| 长连接是免费的 | 每条连接都占 broker 内存和文件描述符，百万连接是工程难题 |
| 设备和后端直接通信 | 都只和 broker 通信，彼此不知道对方 |
