# 消息中间件通识

> 专题 2 · 模块一 · ★ 核心必会 · 侧重通用学习
> 版本基线：MQTT 5.0，3.1.1 差异单独标注
> 贯穿场景：电表 meter3 每 10 秒上报"本周期用电 0.1 kWh"；后端有入库服务（3 个实例）、告警服务、大屏三方要用

**对应全景图的哪一块**：专题 1 全景图里"电表 → broker → 后端"中间的 broker 为什么存在、承诺什么、不承诺什么。后面的 QoS、会话、共享订阅，用的都是本篇的词汇。

## 1. 核心概念

### 1.1 问题：直接调用导致紧耦合

```
            ┌──> 入库服务 10.0.1.5
 电表 ──────┼──> 告警服务 10.0.1.8
            └──> 大屏     10.0.1.9
```

| 问题 | 后果 |
|---|---|
| 电表要知道每个后端地址 | 后端扩容、换 IP，所有电表都要改 |
| 后端重启 | 这段时间数据丢失 |
| 要等所有后端回复 | 一个慢服务拖住电表 |
| 新增消费方 | 要升级所有电表 |

### 1.2 Broker 与三个角色

> 类比：邮局。投稿人不需要知道谁订了杂志；读者出差回来杂志还在；投完就走，不等读者读完。

```
 电表 ──发布──> [ broker ] ──投递──> 入库服务 / 告警服务 / 大屏
```

| 角色 | 通用叫法 | MQTT 叫法 | 本场景 |
|---|---|---|---|
| 发送方 | Producer 生产者 | Publisher 发布者 | 电表 |
| 接收方 | Consumer 消费者 | Subscriber 订阅者 | 三个后端服务 |
| 中间人 | Broker | Broker | 接收、暂存、转发 |

### 1.3 解耦的三个维度

| 维度 | 含义 | 电表场景 | 前提 |
|---|---|---|---|
| 空间解耦 | 互不知道对方地址 | 电表只知道 broker 和主题名 | 无 |
| 时间解耦 | 不必同时在线 | 入库服务重启期间消息由 broker 暂存 | **broker 必须存消息**（MQTT 需持久会话 + QoS ≥ 1，见专题 12） |
| 同步解耦 | 发完不用等处理完 | 电表发完继续采样 | 无 |

### 1.4 队列模型 vs 发布订阅模型

| | 队列（点对点） | 发布订阅 |
|---|---|---|
| 一条消息给几个消费者 | 一个（竞争消费） | 每个订阅者各一份 |
| 类比 | 银行叫号 | 广播电台 |
| 用途 | 分摊负载 | 一份数据多方使用 |

真实系统常组合使用：**组间发布订阅，组内队列**。

```
                       ┌──> 告警服务
 电表 ──> broker ──────┼──> 大屏
                       └──> 入库组 ──> 实例A / 实例B / 实例C（组内三选一）
```

- MQTT 本质是发布订阅；"组内三选一"由 5.0 **共享订阅**提供（专题 19）。
- Redis 对照：Pub/Sub = 纯发布订阅、离线即丢；Streams + Consumer Group = 组间发布订阅 + 组内队列。

### 1.5 丢失与重复的推演（本篇最核心）

只看一跳：电表 → broker，网络会丢包。

**第一版：发完不管 → 至多一次**

```
电表 ──msg#7──X        broker 没收到，电表也不知道  → 可能丢，不会重复
```

**第二版：ACK + 超时重发 → 至少一次**

ACK（Acknowledgement）：接收方回"收到了"。

```
情形①：消息丢了                     情形②：ACK 丢了
电表 ──msg#7──X                     电表 ──msg#7──> broker 处理✔(第1次)
电表 ──msg#7──> broker 处理✔         电表 <──X── ACK#7
电表 <── ACK#7                      电表 ──msg#7──> broker 处理✔(第2次!)
                                    电表 <── ACK#7
```

**发送方分不清①和②**（都是"没等到 ACK"），只能重发。

> 只要有重试，就一定会有重复。这是"不丢"的代价，不是 bug。

**第三版：接收方按 ID 去重 → 恰好一次（效果上）**

```
电表 ──msg#7──> broker  ID=7 没见过 → 处理✔，记下 7
电表 <──X── ACK#7
电表 ──msg#7──> broker  ID=7 见过 → 丢弃，但仍回 ACK
电表 <── ACK#7
```

> **恰好一次 = 至少一次 + 去重（或幂等）**，由接收方多存一份"记忆"换来。

| 语义 | 做法 | 丢 | 重复 | 成本 | MQTT |
|---|---|---|---|---|---|
| 至多一次 At most once | 发完不管 | 可能 | 不会 | 最低 | QoS 0 |
| 至少一次 At least once | ACK + 重试 | 不会\* | 可能 | 多一次往返；发送方暂存未确认消息 | QoS 1 |
| 恰好一次 Exactly once | ACK + 重试 + 去重 | 不会\* | 不会 | 接收方存已处理 ID，且要决定何时删 | QoS 2 |

\* 前提：重试次数够、发送方重试期间没崩溃、暂存的消息没丢。

### 1.6 幂等

**幂等**（Idempotent）：执行一次和执行多次结果相同。把操作设计成幂等，比维护去重表更省心。

| 非幂等 | 幂等 |
|---|---|
| `总电量 += 0.1` | 按（设备号, 时间戳）唯一键插入 |
| Redis `INCR` | Redis `SET` |
| 采样周期"加 10 秒" | 采样周期"设为 30 秒" |

计量场景的设计启发：

- 上报**累计表底值**而不是增量：重复无害，丢一条下一条能补回。
- 指令用"设为"，不用"加减"。

### 1.7 确认时机与"单跳 vs 端到端"

```
方案 X：先 ACK 后处理              方案 Y：先处理后 ACK
 收到 → ACK → 写库                 收到 → 写库 → ACK
          ↑ 崩溃                            ↑ 崩溃
 broker 不再重发 → 【丢失】          broker 会重发 → 【重复】（需幂等）
```

```
 电表 ──(跳1)──> broker ──(跳2)──> 入库服务 ──(应用)──> 数据库
      QoS 管这里       QoS 管这里         QoS 管不到
```

MQTT 的 QoS 只保证**每一跳**；端到端的恰好一次只能靠应用层幂等。

### 1.8 背压

**背压**（Backpressure）：下游处理不过来时，把压力反向传给上游。

| 策略 | 做法 | 代价 |
|---|---|---|
| 缓冲 | broker 先存着 | 内存/磁盘上涨，满了仍要选下面一种 |
| 丢弃 | 丢最旧或最新 | 数据丢失 |
| 限流 | 让生产者变慢 | 上游被拖慢，设备缓存也可能满 |

实时大屏可丢旧数据；计费数据不能丢，只能缓冲 + 限流。MQTT 对应 Receive Maximum（专题 13）、broker 队列上限与丢弃策略（专题 28）。

### 1.9 推 vs 拉（了解）

| | 推 Push | 拉 Pull |
|---|---|---|
| 谁主动 | broker | 消费者 |
| 优点 | 延迟低 | 天然背压 |
| 缺点 | 慢消费者需额外流控 | 轮询开销或延迟 |
| 例子 | MQTT、Redis Pub/Sub | Redis Streams `XREADGROUP` |

### 1.10 局限与适用边界

- broker 带来**多一跳延迟和一个故障点**；一对一、双方稳定在线时直接调用可能更简单。
- "恰好一次"有成本，且只在一跳或一个系统内成立；跨系统一律按"至少一次 + 幂等"设计。
- 消息中间件一般不保证全局顺序（MQTT 的顺序保证见专题 13）。

## 2. 易混淆 / 易错点

| 错误理解 | 正确理解 |
|---|---|
| 用了 broker 就天然有时间解耦 | 要 broker 存消息才行；MQTT 默认（QoS 0、非持久会话）下订阅者离线消息直接丢 |
| 解耦了就没有依赖了 | 依赖转移到 broker 和主题名上：broker 挂全挂，主题名改两边都得改 |
| 发布订阅和队列是一回事 | 一条消息给"每个"订阅者 vs 给"其中一个"消费者 |
| 至少一次出现重复是 bug | 发送方分不清"消息丢"和"ACK 丢"，重复是不丢的必然代价 |
| 恰好一次是一种更好的传输方式 | 它是至少一次 + 接收方去重，代价是状态存储 |
| 用了 QoS 2 就端到端不丢不重 | QoS 只管一跳；应用写库前崩溃照样丢，先写后确认照样重 |
| ACK 只是协议层的事 | 应用"先确认还是先处理"决定了丢还是重 |
| 去重就是幂等 | 去重靠记住 ID；幂等靠操作本身重复无害，后者通常更省心 |

## 4. 诊断实践

### 4.1 实验：10% 丢包信道上发 1000 条

模型：每次传输（消息或 ACK）独立以 10% 概率丢失，最多重发 10 次；每条 0.1 kWh，接收方用 `+=` 累加。

**云端真实输出**（Python 3.13，随机种子 42）：

```
N=1000  单次传输丢失率=10%  每条=0.1kWh  正确总量=100.0kWh

策略                    发送次数   丢失   重复处理   累加电量kWh
A 无确认                  1000      90        0        91.0
B 确认+重试               1223       0      107       110.7
C 确认+重试+按ID去重       1223       0        0       100.0
```

- A 丢 9%，电量少算；B 不丢但多算 10.7 kWh（计费场景比丢更糟）；C 网络代价与 B 相同，结果正确。

本地复现（纯标准库）：

```python
import random

N, LOSS, MAX_RETRY, DELTA = 1000, 0.10, 10, 0.1

def run(strategy, seed=42):
    rng = random.Random(seed)
    lost = processed = sends = 0
    seen, total_kwh = set(), 0.0
    for msg_id in range(N):
        delivered_once = False
        for _ in range(1 if strategy == "no_ack" else MAX_RETRY):
            sends += 1
            msg_arrived = rng.random() >= LOSS
            if msg_arrived:
                delivered_once = True
                if not (strategy == "ack_retry_dedup" and msg_id in seen):
                    seen.add(msg_id); processed += 1; total_kwh += DELTA
            if strategy == "no_ack":
                break
            if msg_arrived and rng.random() >= LOSS:   # ACK 也可能丢
                break
        if not delivered_once:
            lost += 1
    return sends, lost, processed - (N - lost), round(total_kwh, 1)

for name in ["no_ack", "ack_retry", "ack_retry_dedup"]:
    print(name, run(name))
```

可尝试：`LOSS = 0.3` 观察重复率上升；`MAX_RETRY = 2` 观察"至少一次"在重试不足时也会丢。

### 4.2 现象 → 怀疑 → 观察点

| 现象 | 优先怀疑 | 观察点 |
|---|---|---|
| 数据库有重复行 | 至少一次 + 写库不幂等 | 同一（设备号, 时间戳）多次出现；broker 重传计数 |
| 数据有缺口 | 至多一次，或先确认后处理时崩溃 | 设备侧序号不连续；消费者重启时间点 |
| 电量对不上 | 增量上报 + 重复或丢失 | 对比表底值差与增量之和 |
| broker 内存上涨 | 消费者跟不上 | 队列深度；生产速率与消费速率之差 |
