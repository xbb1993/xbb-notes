# 报文结构：MQTT 为什么省流量

> 专题 5 · 模块二 · ★ 核心必会 · 侧重通用学习
> 版本基线：MQTT 5.0，3.1.1 差异单独标注
> 贯穿场景：电表 meter3 以 QoS 1 向 `m/meter3/power` 上报功率 `12.3`

**对应全景图的哪一块**：电表与 broker 之间那根线上流过的东西。本篇的主线是：**从报文格式的角度，说清楚 MQTT 为什么节约流量和传输成本**。阅读标准是能看懂"表格视图"，不要求手工拆十六进制。

## 1. 核心概念

### 1.1 协议 = 填表规则，报文 = 填好的表

> 类比：快递单。每一栏的位置是固定的，快递员看位置就知道那一栏写的是什么，不用读栏目名。

MQTT 更进一步：**连栏目名都不写，只按约定顺序写内容**。

```
JSON 写法：栏目名 + 内容（约 60 字节）
{"type":"PUBLISH","qos":1,"topic":"m/meter3/power","id":1,"payload":"12.3"}

MQTT 写法：只写内容，顺序事先约定（25 字节）
[PUBLISH,QoS1] [长度] [m/meter3/power] [1] [12.3]
```

代价是收的一方必须严格按约定顺序读。

### 1.2 省流量的四个设计

| 设计 | 怎么省 |
|---|---|
| 二进制、不写栏目名 | 去掉反复出现的字段名 |
| 报文类型 + 标志挤在 1 个字节 | 类型、QoS、是否重发、是否保留，一共只占 1 字节 |
| 剩余长度可变（1～4 字节） | 127 字节以内的小消息只用 1 字节表示长度；最大约 256 MB |
| 字段按需出现 | QoS 0 没有包 ID；没有确认的报文不带多余内容；最小报文（心跳）只有 2 字节 |

剩余长度可变的账：每条比固定 4 字节省 3 字节，一台 10 秒一报的电表一天约 8640 条，省约 26 KB；乘以 10 万台、按流量计费时就值得了。

**但要知道边界**：TCP/IP 每个包约 40 字节的头部省不掉（专题 1），带宽极度敏感时，**减少报文条数（批量上报）比抠头部更有效**。

### 1.3 为什么需要"长度"

**TCP 只是一根字节水管**：保证字节按顺序送达，但不知道一条消息从哪开始、到哪结束。

```
电表发：  [消息A][消息B]
broker 收到可能是：  [A的前半] [A后半+B] ...
```

所以必须有办法"定边界"：

| 方案 | 问题 |
|---|---|
| 分隔符（HTTP 头用空行） | 要逐字节扫描；内容里出现分隔符要转义 |
| 固定 4 字节长度 | 小消息白花字节 |
| **可变长度（MQTT）** | 小消息最省 |

同理，主题名这种**长短不一的文字，前面先写长度**，读的人数够了就知道这一栏结束，下一栏开始。数字则固定占 1、2 或 4 字节，位置固定直接读。

### 1.4 三段结构

```
┌──────────────┬──────────────────────┬────────────────┐
│  固定头       │  可变头               │  载荷           │
│  所有报文都有  │  控制信息（部分报文有）  │  内容（部分报文有）│
└──────────────┴──────────────────────┴────────────────┘
  类型+标志、剩余长度   主题名、包ID、属性      业务数据、Client ID、订阅列表
```

### 1.5 表格视图：一条 PUBLISH

```
┌─────────────────── PUBLISH（电表上报功率）───────────────────┐
│ 【固定头】                                                    │
│   类型：PUBLISH   标志：QoS=1，非重发，不保留                    │
│   剩余长度：23（后面还有 23 字节）                               │
│ 【可变头】                                                    │
│   主题名：m/meter3/power                                       │
│   包 ID：1            ← 取件号，用来和确认配对；QoS 0 没有这一栏 │
│   属性：无            ← 5.0 才有这一栏，空的也要写"0 条"         │
│ 【载荷】                                                      │
│   12.3                                                        │
└───────────────────────────────────────────────────────────────┘
```

- **包 ID**：电表寄出编号 1，broker 回"1 号收到"，电表就知道哪条成功了（专题 2 的 ACK 配对）。
- **属性**：5.0 新加的"附加条款"栏，若干条"条款名 + 值"，如消息过期时间（专题 17）。

### 1.6 15 种报文（按用途分组）

| 组 | 报文 | 后续专题 |
|---|---|---|
| 连接 | CONNECT、CONNACK | 6 |
| 发布 | PUBLISH、PUBACK、PUBREC、PUBREL、PUBCOMP | 10、11 |
| 订阅 | SUBSCRIBE、SUBACK、UNSUBSCRIBE、UNSUBACK | 8、9 |
| 心跳 | PINGREQ、PINGRESP | 7 |
| 断开 | DISCONNECT（3.1.1 仅客户端发，5.0 双向） | 6、16 |
| 认证 | AUTH（**5.0 新增**，3.1.1 只有 14 种） | 21 |

只有 PUBLISH 的标志位有含义（DUP、QoS、RETAIN），其他报文的标志位是写死的。

## 2. 易混淆 / 易错点

| 错误理解 | 正确理解 |
|---|---|
| MQTT 省流量是因为用了 UDP 或压缩 | 跑在 TCP 上，也不压缩；省在二进制、不写字段名、字段按需出现 |
| 剩余长度只有 1 字节，所以消息最大 127 字节 | 1～4 字节可变，最大约 256 MB；实际上限由 broker 配置决定 |
| 每个 PUBLISH 都有包 ID | 只有 QoS 1、2 有 |
| 3.1.1 和 5.0 的报文一样 | 5.0 多了属性栏（空的也占 1 字节）、AUTH 报文、确认里的原因码 |
| 抠报文头部是省流量的主要手段 | TCP/IP 头部省不掉，减少报文条数往往更有效 |
| 一次接收正好拿到一整条报文 | TCP 是字节流，必须按剩余长度凑齐再处理 |

## 4. 诊断实践

### 4.1 实验：同一条上报的四种发法（云端真实输出，Mosquitto 2.0.18 + tshark 4.2.2）

| 发法 | PUBLISH 总长 | 与标准那条的差别 |
|---|---|---|
| 5.0 + QoS 1（标准） | 25 字节 | — |
| 3.1.1 + QoS 1 | 24 字节 | 没有属性栏 |
| 5.0 + QoS 0 | 23 字节 | 没有包 ID |
| 5.0 + QoS 0 + 200 字节数据 | 220 字节 | 剩余长度从 1 字节变成 2 字节 |

broker 的确认：

| | PUBACK 总长 | 内容 |
|---|---|---|
| 3.1.1 | 4 字节 | 只说"1 号收到" |
| 5.0 | 5 字节 | 多一个原因码 0x10 = No matching subscribers（当时没人订阅；消息已被接受，不是错误） |

本地复现：

```bash
sudo tcpdump -i lo -w t05.pcap 'tcp port 1883' &
mosquitto_pub -V 5   -i meter3 -t m/meter3/power -m 12.3 -q 1
mosquitto_pub -V 311 -i meter3 -t m/meter3/power -m 12.3 -q 1
mosquitto_pub -V 5   -i meter3 -t m/meter3/power -m 12.3 -q 0
python3 -c "print('x'*200, end='')" > p200 && mosquitto_pub -V 5 -i meter3 -t m/meter3/power -f p200
kill %1
tshark -r t05.pcap -Y "mqtt.msgtype==3 || mqtt.msgtype==4" -T fields -e frame.number -e _ws.col.Info -e tcp.payload
```

### 4.2 现象 → 怀疑 → 观察点

| 现象 | 可能原因 | 观察点 |
|---|---|---|
| 连接被 broker 直接断开 | 报文格式错误（标志写错、长度非法、文字编码非法） | broker 日志；5.0 原因码 0x81 Malformed Packet；Wireshark 标出 Malformed |
| 大消息发不出去 | 超过 broker 或接收方的报文上限 | 5.0 原因码 0x95 Packet too large；broker 报文大小配置 |
| 自研设备客户端偶发解析失败 | 假设"一次接收 = 一整条报文" | 抓包看报文是否跨 TCP 包；检查是否按剩余长度凑齐再解析 |
| 流量费超预期 | 报文条数太多（心跳过密、逐条小包上报） | 统计每小时报文条数；考虑批量上报、调整 Keep Alive |
