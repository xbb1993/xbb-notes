# QoS 0 / 1：流程、包 ID、重发与 DUP

> 专题 10 · 模块三 · ★ 核心必会 · 侧重两者兼顾
> 版本基线：MQTT 5.0，3.1 / 3.1.1 差异单独标注
> 贯穿场景：电表 meter3 每 0.1～10 秒上报电能表底值，入库服务订阅后写库

**对应全景图的哪一块**：电表 → broker → 入库服务两段路上，"至少一次"如何实现，重复在哪里产生。

## 1. 核心概念

### 1.1 两跳框架

```
          第 1 跳                       第 2 跳
 电表 ──── PUBLISH ────> broker ──── PUBLISH ────> 入库服务
      电表选的 QoS             订阅时声明的 QoS（上限）
```

> 类比：快递转运。寄件人选的服务等级只管第一段，转运中心按收件人订的等级走第二段。

- QoS 只管**一跳**，不是端到端。
- 实际投递 QoS = **min（发布 QoS，订阅 QoS）**。端到端可靠性取决于最弱的一跳。

### 1.2 QoS 0：发完不管

无包 ID、无确认，发完即删。

| 情况 | 丢否 | 原因 |
|---|---|---|
| 连接正常，网络偶发丢包 | 不丢 | TCP 重传保证送达 |
| 连接断开（半开、被踢、broker 重启） | **丢** | 缓冲区与在途数据随连接消失 |
| 订阅者离线 | **丢** | QoS 0 不为离线订阅者保存 |
| broker 内存/队列满 | 可能丢 | 优先丢 QoS 0 |

### 1.3 QoS 1：确认 + 补发

```
电表                                        broker
 │ ① PUBLISH(QoS1, 包ID=7)  ───────────────> │ ② 接收、转发
 │   保留副本，等确认                          │
 │ <─────────────── ③ PUBACK(包ID=7)          │
 │ ④ 删除副本，包ID=7 释放可复用                 │
```

| 角色 | 职责 |
|---|---|
| 发送方 | 分配包 ID；保留副本直到收到同 ID 的 PUBACK |
| 接收方 | 回 PUBACK；回完后再收到相同包 ID 的 PUBLISH，**当作新消息**（不负责去重） |

**包 ID 是取件号，不是消息身份证**：只在一个客户端与 broker 之间、一次交互内有效，确认后即复用，不能用于应用层去重。

### 1.4 补发时机（最易误解）

| 版本 | 规则 |
|---|---|
| 3.1 | 等确认超时就在同一连接上重发 |
| 3.1.1 | 重连且会话仍在时**必须**补发；这是唯一必须补发的情况 |
| **5.0** | 重连且会话仍在时**必须**补发；**其他任何时候不得补发** |

为什么：连接活着时 TCP 已保证送达，MQTT 层再补发只会制造重复；真正会丢只有"连接断了"。

```
半开连接 ──(Keep Alive 发现)──> 重连 ──(Session Present=是)──> 补发未确认的 QoS 1（DUP=1）
  专题 7                         专题 6                          本篇
```

注意：HiveMQ《MQTT Essentials》仍写"合理时间内没收到 PUBACK 就重发"，属 3.1 时代说法。

| 条件 | 结果 |
|---|---|
| 重连 Clean Start=否 且会话在 | 两端按原包 ID 补发 |
| Clean Start=是 或会话过期 | 规范层面无"补发"；broker 侧未确认消息随会话丢弃；客户端是否当新消息重发取决于库 |
| 设备重启 | 内存中的副本丢失；需 flash 持久化（专题 43） |

**QoS 1 = 不丢 的前提**：持久会话 + 客户端进程未重启 + 两跳都是 QoS 1。

### 1.5 重复与 DUP

重复来源：某一跳的 PUBLISH 已送达，PUBACK 丢失（或连接断开）→ 重连补发 → 接收方又处理一次。两跳都会发生。

| 误以为 | 实际 |
|---|---|
| DUP=1 可以丢弃 | 只表示"可能发过"，接收方也许没收到第一份 |
| DUP=0 就不是重复 | broker 转发是新的一次投递，DUP 重新判断 |
| 订阅者能靠 DUP 发现重复 | **DUP 只在一跳内有意义**（实验已验证） |

去重只能靠应用层：载荷带"设备号 + 序号/时间戳"，入库幂等。

### 1.6 消息分级建议

| 消息 | 建议 | 理由 |
|---|---|---|
| 实时功率（大屏） | QoS 0 | 丢一条下一条就来 |
| 电能表底值（计费） | QoS 1 + 幂等入库 | 不能丢；表底值天然幂等 |
| 告警事件 | QoS 1 + 事件 ID | 不能丢，按 ID 去重 |
| 下发指令 | QoS 1 + 指令 ID + 设备回执 | QoS 只保证送到，执行结果靠回执 |
| 在线状态（遗嘱） | QoS 1 | 专题 15 |

QoS 1 代价：每条多一个 PUBACK；两端保存未确认副本；broker 为离线订阅者排队。

### 1.7 局限

- "不丢"依赖内存副本，重启即丢；可靠补传需设备持久化（41、43）。
- 重复无法在协议层消除，只能应用层幂等。
- 飞行窗口满后新消息在客户端排队，长时间断线会积压（13、43）。

## 2. 易混淆 / 易错点

| 错误理解 | 正确理解 |
|---|---|
| QoS 0 网络一抖就丢 | 连接活着时 TCP 保证送达；主要在断线、接收方离线时丢 |
| QoS 1 超时没确认就重发 | 5.0 只在重连且会话在时补发，其他时候禁止 |
| QoS 1 = 不丢 | 需持久会话 + 进程未重启 + 两跳都是 QoS 1 |
| 包 ID 可用来去重 | 用完复用，仅用于配对确认 |
| DUP=1 就可以丢弃 | 只表示"可能发过"，且只在一跳内有效 |
| 发布 QoS 1，订阅者就收 QoS 1 | 取两者较低 |
| QoS 越高越好 | 成本越大，按重要程度选 |
| QoS 1 保证指令被执行 | 只保证送到客户端，执行结果靠应用层回执 |

## 4. 诊断实践

### 4.1 实验：QoS 降级（云端真实输出，Mosquitto 2.0.18）

```
订阅 QoS 0，发布 QoS 0 → 订阅者实际收到的 QoS = 0
订阅 QoS 0，发布 QoS 1 → 订阅者实际收到的 QoS = 0
订阅 QoS 1，发布 QoS 0 → 订阅者实际收到的 QoS = 0
订阅 QoS 1，发布 QoS 1 → 订阅者实际收到的 QoS = 1
```

### 4.2 实验：断线时的丢失与重复（云端真实输出，Mosquitto 2.0.18 + paho-mqtt 2.1.0）

电表每 0.1 秒发一条（载荷为序号 1～150），持久会话，Keep Alive 3 秒；入库服务 QoS 1 订阅。第 3.5 秒起静默丢弃电表旧连接的包，电表靠 Keep Alive 发现后重连。

| 场景 | 发出 | 收到 | 丢失 | 重复 | 电表补发（DUP=1） | 订阅者看到 DUP=1 |
|---|---|---|---|---|---|---|
| QoS 0，双向丢包 | 150 | 85 | 65（序号 31～95） | 0 | 0 | 0 |
| QoS 1，双向丢包 | 150 | 150 | 0 | 0 | 20 | 0 |
| QoS 1，只丢 broker→电表 | 150 | 153 | 0 | 3 | 20 | 0 |

- QoS 0：断网到重连约 6.5 秒窗口内的消息全丢，会话在也不补发。
- QoS 1 补发 20 条 = paho 默认飞行窗口 20，其余消息在客户端排队。
- 只丢确认时补发 20 条却只重复 3 条：broker→电表方向连 TCP 确认也被丢，电表 TCP 降速，多数消息卡在发送缓冲区没到 broker；只有 3 条"到了但确认丢了"（基于 TCP 原理的解释，未逐包验证）。
- 订阅者看到的 DUP 始终为 0：DUP 不跨跳。

本地复现（需 root、本机 1883 有 broker、paho-mqtt 2.x）：

<details>
<summary>qos_lab.py</summary>

```python
"""专题 10 实验：断线时 QoS 0 / QoS 1 的丢失与重复。
用法: python3 qos_lab.py <qos> <drop: both|ack>
需要 root（用 iptables 模拟静默断网），broker 在 127.0.0.1:1883。
"""
import sys, time, subprocess, threading
import paho.mqtt.client as mqtt
from paho.mqtt.properties import Properties
from paho.mqtt.packettypes import PacketTypes

QOS, MODE = int(sys.argv[1]), sys.argv[2]
N, INTERVAL, CUT_AT, KA = 150, 0.1, 3.0, 3
TOPIC = "em/meter3/up/telemetry/energy"
V2 = mqtt.CallbackAPIVersion.VERSION2

recv, dup_flags = [], 0
def on_msg(c, u, m):
    global dup_flags
    recv.append(int(m.payload)); dup_flags += m.dup

# 后端订阅者（稳定连接）
sub = mqtt.Client(V2, client_id="svc-ingest-1", protocol=mqtt.MQTTv5)
sub.on_message = on_msg
sub.connect("127.0.0.1", 1883, 60); sub.subscribe(TOPIC, qos=1); sub.loop_start()
time.sleep(0.5)

# 电表（持久会话：Clean Start=0，会话保留 300 秒）
events, resent_dup = [], 0
pub = mqtt.Client(V2, client_id="meter3", protocol=mqtt.MQTTv5)
pub.reconnect_delay_set(1, 2)
def on_log(c, u, level, s):
    global resent_dup
    if s.startswith("Sending PUBLISH") and "d1" in s: resent_dup += 1
pub.on_log = on_log
pub.on_connect = lambda c,u,f,rc,p: events.append(f"{time.time()-T0:5.1f}s 电表连接成功 session_present={f.session_present}")
pub.on_disconnect = lambda c,u,f,rc,p: events.append(f"{time.time()-T0:5.1f}s 电表断开: {rc}")
props = Properties(PacketTypes.CONNECT); props.SessionExpiryInterval = 300
T0 = time.time()
pub.connect("127.0.0.1", 1883, KA, clean_start=False, properties=props); pub.loop_start()
time.sleep(0.5)
port = pub.socket().getsockname()[1]

rules = []
def cut():
    time.sleep(CUT_AT)
    if MODE in ("both",):
        rules.append(["INPUT","-p","tcp","--sport",str(port),"-j","DROP"])   # 电表→broker
    rules.append(["INPUT","-p","tcp","--dport",str(port),"-j","DROP"])        # broker→电表（含 PUBACK）
    for r in rules: subprocess.run(["iptables","-A"]+r)
    events.append(f"{time.time()-T0:5.1f}s ✂ 开始静默丢弃旧连接的包（{'双向' if MODE=='both' else '只丢 broker→电表，即只丢确认'}）")
threading.Thread(target=cut, daemon=True).start()

for i in range(1, N+1):
    pub.publish(TOPIC, str(i), qos=QOS); time.sleep(INTERVAL)
time.sleep(8)
for r in rules: subprocess.run(["iptables","-D"]+r)
pub.loop_stop(); sub.loop_stop()

got = set(recv)
lost = [i for i in range(1, N+1) if i not in got]
dups = len(recv) - len(got)
print(f"\n### QoS {QOS}，断网方式：{'双向丢包' if MODE=='both' else '只丢确认（PUBACK）'}")
for e in events: print("  " + e)
print(f"  电表发出 {N} 条；后端收到 {len(recv)} 条")
print(f"  丢失 {len(lost)} 条" + (f"（序号 {lost[0]}~{lost[-1]}）" if lost else ""))
print(f"  重复 {dups} 条；电表补发时带 DUP=1 的 PUBLISH {resent_dup} 个；后端收到的消息里 DUP=1 的 {dup_flags} 条")
```

</details>

运行：

```bash
sudo python3 qos_lab.py 0 both
sudo python3 qos_lab.py 1 both
sudo python3 qos_lab.py 1 ack
```

### 4.3 现象 → 怀疑 → 观察点

| 现象 | 优先怀疑 | 观察点 |
|---|---|---|
| 断网恢复后数据有缺口 | QoS 0，或会话没保住，或设备重启 | 上报 QoS；Session Present；设备重启记录 |
| 数据库重复行 | QoS 1 补发 + 入库不幂等 | 重复是否集中在重连时刻；是否有唯一键 |
| 设备 QoS 1 上报仍丢数据 | 订阅端 QoS 0 降级 | 后端 SUBSCRIBE 的 QoS、SUBACK 授予值 |
| 断线后内存涨、重连后突发 | 未确认 + 排队积压 | 飞行窗口与队列长度 |
| 靠 DUP 去重仍有重复 | DUP 不跨跳 | 改用载荷业务 ID |
