# 消息顺序、飞行窗口与流控

> 专题 13 · 模块三 · ☆ 高频重点 · 第二遍 · 简述（与 9、16、42、49 合讲）
> 云端实测：Receive Maximum 限住在途消息数（Mosquitto 2.0.18，原始 5.0 报文）；顺序保证范围按规范"消息顺序"一节通常理解整理，未逐字核对原文

**这一章解决什么**：MQTT 保证什么顺序、不保证什么；接收方处理不过来时怎么限速。

## 1. 核心概念

### 1.1 顺序：保证的范围很窄

只保证"同一发送方、同一主题、同一 QoS、一条连接内，先发先到"。

| 情况 | 有保证吗 | 见过 |
|---|---|---|
| 同一块表、同一主题、同一 QoS 连续发送 | 有 | |
| 不同主题之间 | 没有 | |
| 不同电表之间 | 没有 | |
| 重连后补发未确认消息 | 可能与新消息交错 | 10、43 |
| 断网补传新旧交替 | 到达顺序 ≠ 发生顺序 | 41 |
| 共享订阅多实例并行 | 同一表数据分到不同实例 | 19、41 |

结论：业务上永远按编号或采样时间排序（41）。

### 1.2 流控

发得快、处理得慢，未确认消息越堆越多会撑爆接收方。**飞行窗口**（inflight）= 已发出、未确认的消息。5.0 接收方在连接时用 **Receive Maximum** 声明"同时最多给我几条未确认的 QoS 1/2"（17、44）。

实测：订阅方声明 Receive Maximum = 2 且不回 PUBACK，发布方连发 10 条 QoS 1，broker 只推来 2 条；其余在队列排着，满了按 28 的规则丢弃。

对电表：资源小的电表用小窗口保护自己；平台大流量订阅者窗口要够大，否则吞吐上不去（Mosquitto 默认在途上限 20，28）。

## 2. 易混淆 / 易错点

| 错误理解 | 正确理解 |
|---|---|
| MQTT 保证全局顺序 | 只在同一发送方、主题、QoS、连接内 |
| 到达顺序就是发生顺序 | 重连补发、补传、共享订阅都会打乱 |
| 订阅方慢 broker 会无限推 | 受 Receive Maximum 与在途上限约束 |
| 窗口越小越安全 | 平台侧窗口太小限制吞吐 |

## 3. 与其他章节的关联

QoS 与重发（10）、Receive Maximum（17、44）、共享订阅（19）、背压与队列（28）、按编号排序（41）、重连（43）。

## 4. 诊断实践

实验脚本见专题 16 的 `errs.py` 末段。实测输出：

```
== Receive Maximum：订阅方声明最多 2 条未确认，且一直不回 PUBACK
  发布方发了 10 条 QoS 1；订阅方不确认时，broker 只推来 2 条
```

| 现象 | 优先怀疑 |
|---|---|
| 后端处理顺序错乱 | 依赖到达顺序；共享订阅并行 |
| 平台订阅者吞吐上不去 | 在途窗口太小 |
| 电表收到消息过多处理不过来 | 未设或过大的 Receive Maximum |
