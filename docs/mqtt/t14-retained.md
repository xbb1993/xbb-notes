# 保留消息（Retained Message）

> 专题 14 · 模块三 · ★ 核心必会 · 侧重两者兼顾
> 版本基线：MQTT 5.0，3.1.1 差异单独标注
> 贯穿场景：运维打开大屏，要立刻看到 10 万台电表当前谁在线、谁离线

**对应全景图的哪一块**：broker 上除"每个客户端一份的会话"外，另一种按**主题**存放、与客户端无关的数据。解决"新来的人怎么立刻知道现在的状态"。

## 1. 核心概念

### 1.1 broker 里的两种容器，以及主题、订阅的位置

| 容器 | 按什么组织 | 放什么 | 生命周期 |
|---|---|---|---|
| **会话**（专题 12） | Client ID，每客户端一份 | 订阅清单 + 要投递给它的消息 | 随会话过期 |
| **保留消息表** | 主题名，每主题一格 | 该主题最后一条保留消息 | 被覆盖、清除或过期 |

- **主题不是容器**，只是消息上的地址；broker 上没有"某主题下的消息列表"（与 Kafka 的 topic 不同）。
- **订阅存在会话里**，是贴在会话上的"要收哪些地址"的清单。

```
                                  broker
 ┌────────────────────────────────────────────────────────────────────────┐
 │  容器一：会话（按 Client ID）                                            │
 │  ┌──────────────────────────────┐   ┌──────────────────────────────┐   │
 │  │ 会话[svc-ingest]              │   │ 会话[meter3]                  │   │
 │  │  订阅清单：em/+/up/telemetry/# │   │  订阅清单：em/meter3/down/#    │   │
 │  │  待投递：[e1, e3, ...]         │   │  待投递：[cmd-7, ...]          │   │
 │  └──────────────────────────────┘   └──────────────────────────────┘   │
 │  容器二：保留消息表（按主题名，每格一条）                                  │
 │  ┌────────────────────────────┬──────────────┐                          │
 │  │ em/meter3/status            │ "online"     │                          │
 │  │ em/meter4/status            │ "offline"    │                          │
 │  │ em/meter3/cfg/period        │ "60"         │                          │
 │  └────────────────────────────┴──────────────┘                          │
 └────────────────────────────────────────────────────────────────────────┘
```

> 类比：邮局。会话 = 私人信箱；订阅 = 信箱门上的栏目清单；主题 = 信封上的栏目地址；保留消息表 = 大厅公告栏，每栏一格，只贴最新一张。

### 1.2 消息到达时 broker 做两件独立的事

```
                    ┌─ 按地址分发：检查每个会话的订阅清单，匹配的放一份副本 ─┐
 消息到达 broker ───┤    在线 → 立即投递；离线且持久 → 进待投递；无匹配 → 不做  │
                    ├─ 若 RETAIN=1：再复印一份贴到公告栏对应格（覆盖旧的）    │
                    │   空载荷 = 撕掉这一格                                    │
                    └──────────────────────────────────────────────────────┘
 两件事做完，原件丢弃。
```

- 原件不属于任何人；进会话的副本属于订阅者的会话；贴公告栏的副本属于主题格子，与会话无关。

| 有匹配会话 | RETAIN | 存在哪 |
|---|---|---|
| 有 | 0 | 只在匹配会话里 |
| 有 | 1 | 匹配会话里 + 公告栏 |
| 无 | 0 | **哪儿都不存，丢弃** |
| 无 | 1 | 只在公告栏 |

新订阅者拿到保留消息的过程：订阅写入其会话 → broker 查公告栏中能被过滤器匹配的格子 → 各复印一份放进其会话、立即投递（RETAIN=1）。

### 1.3 设计哲学：MQTT 是投递中心，只为投递而缓存

| 缓存什么 | 为什么 | 边界 |
|---|---|---|
| 已发出未确认的消息 | 重连补发 | 确认即删 |
| 离线订阅者待投递消息 | 已知接收者暂时不在 | 只为已存在的持久会话，随会话过期，有上限 |
| 每主题最后一条保留消息 | 新来者知道当前状态 | 每主题一条 |

不缓存：历史；给尚不存在的接收者的消息。

| | MQTT | RabbitMQ | Kafka |
|---|---|---|---|
| 核心模型 | 投递 | 队列 | 日志 |
| 存储为了 | 送达已知接收者 | 等消费者来取 | 存储本身 |
| 消费后 | 不在 | 确认后删 | 保留期内仍在 |
| 无消费者时 | 丢弃（保留消息除外） | 持久队列一直等 | 照样写入 |
| 新消费者看历史 | 不能，最多最新一条 | 不能 | 能，可回放 |

> MQTT 像快递分拣中心，RabbitMQ 像邮局信箱，Kafka 像档案馆。

原因：broker 要扛海量长连接，内存宝贵；设备数据最有价值的是"当前值"；历史归数据库/时序库。

| 需求 | 靠 MQTT broker？ | 做法 |
|---|---|---|
| 入库服务重启几分钟不丢 | 能 | 持久会话 + QoS 1 |
| 新页面立刻显示当前状态 | 能 | 保留消息 |
| 新服务处理上个月的数据 | 不能 | 桥接进 Kafka / 数据库（42） |
| 设备离线三天的数据补齐 | 不能 | 设备本地缓存补传（41） |
| 当长期存储 | 不该 | — |

### 1.4 保留消息的规则

发布时 PUBLISH 固定头 **RETAIN=1**。

| 规则 | 说明 |
|---|---|
| 每主题最多一条 | 新的覆盖旧的 |
| 订阅成功即推送 | 过滤器匹配到的所有主题，包括通配符 |
| 订阅时推送 RETAIN=1；实时转发给已有订阅者 RETAIN=0 | 订阅者据此区分"旧值"与"新消息"（5.0 Retain As Published 可改变，专题 20） |
| 推送 QoS | min（保留消息 QoS，订阅 QoS） |
| 清除 | 发一条**空载荷**的保留消息；该空消息**照常转发**给在线订阅者 |
| 与会话无关 | 会话过期不影响保留消息 |
| 可设过期 | 5.0 Message Expiry（专题 18） |

### 1.5 保留消息 vs 离线队列

| | 保留消息 | 离线队列 |
|---|---|---|
| 属于 | 主题，每主题一条 | 订阅者会话，每会话一串 |
| 给谁 | 任何新订阅者 | 原 Client ID |
| 内容 | 最新一条 | 离线期间全部（上限内） |
| 投递时 RETAIN | 1 | 0 |
| 生命周期 | 被覆盖/清除/过期 | 随会话过期 |
| 回答 | "现在是什么状态？" | "我不在时发生了什么？" |

### 1.6 什么该保留

**判断：这条消息描述的是"状态"（随时有当前值）还是"事件"（发生了一次）？状态可保留，事件和指令不要保留。**

| 适合 | 不适合 |
|---|---|
| 在线状态 `status`（配合遗嘱，15） | 高频遥测（下一条马上来，徒增数量） |
| 当前配置、固件版本 | 事件/告警（新订阅者误以为正在发生） |
| 低频"最后读数"作初始值 | **指令**（新设备一订阅就执行旧指令，危险） |
| 设备影子的期望状态（39） | 时间敏感又未设过期的消息 |

### 1.7 局限

- 只有最后一条，无历史。
- 不自带发布时间，载荷应带时间戳。
- 一个主题一个值，主题须带设备 ID。
- 集群同步是实现问题（31）；broker 可声明不支持保留（5.0 Retain Available），云平台可能有限制（45）。

## 2. 易混淆 / 易错点

| 错误理解 | 正确理解 |
|---|---|
| 主题是存消息的地方 | 主题只是地址；容器只有会话和保留消息表 |
| 消息属于订阅者的会话 | 原件不属于任何人；副本分别属于会话或主题格子 |
| 没有会话就存不了消息 | 设了保留就存在保留消息表，与会话无关 |
| MQTT 尽量不缓存 | 只为投递而缓存：未确认、已知离线接收者、最新值 |
| 保留消息存所有历史 | 每主题只一条 |
| 保留消息只发给新订阅者 | 照常转发在线订阅者，另存一份 |
| 保留消息 = 持久会话 | 一个属于主题存最新，一个属于订阅者存离线全部 |
| RETAIN=1 说明是刚发生的 | 是订阅时补的旧值 |
| 清除要调管理接口 | 发空载荷保留消息 |
| 清除用的空消息不会发给任何人 | 照常转发，订阅者须处理空载荷 |
| 所有数据都设保留 | 数量暴涨，通配订阅时推送风暴 |
| 告警、指令设保留更可靠 | 新订阅者收到过时内容；可靠送达靠 QoS + 会话 |
| 保留消息永久安全 | 默认只在内存，重启即丢 |

## 4. 诊断实践

### 4.1 实验（云端真实输出，Mosquitto 2.0.18）

**R1 先发布后订阅**（status 保留、power 不保留，订阅 `em/meter3/#`）：

```
em/meter3/status  payload=online  retain=1
```

**R2 每主题只留最后一条**（先后保留 10、30）：

```
em/meter3/cfg/period  payload=30  retain=1
```

**R3 RETAIN 标志区分旧值与新消息**：

```
payload=online retain=1          ← 订阅时推送的旧值
payload=online-again retain=0    ← 订阅期间实时到达
```

**R4 通配符一次拿到所有电表状态**（订阅 `em/+/status`）：

```
em/meter3/status  payload=online-again  retain=1
em/meter1/status  payload=online  retain=1
em/meter2/status  payload=online  retain=1
em/meter4/status  payload=offline  retain=1
em/meter5/status  payload=online  retain=1
```

**R5 清除**：

```
-- 当时在线的订阅者看到：
payload=[offline] retain=1
payload=[] retain=0          ← 空载荷照常转发
-- 清除之后的新订阅者：
(什么都没收到)
```

**R6 保留消息 vs 离线队列**（当前保留值 30，老订阅者离线期间改为 40、50、60）：

```
-- 持久会话的老订阅者重连（不重订）：40(r0) 50(r0) 60(r0)
-- 全新订阅者：                    60(r1)
```

**R7 滥用**（1000 台 × 3 项遥测全部保留）：

```
-- broker 上保留消息总数：发布前 58 → 发布后 3058     （58 为 Mosquitto 自身 $SYS 保留主题）
-- 一个新客户端订阅 em/#，一订阅就被推送：3005 条
```

**R8 broker 重启（未开持久化）**：订阅 `em/+/status` 收到 0 条。

本地复现：

```bash
mosquitto_pub -V 5 -t em/meter3/status -m online -r
mosquitto_sub -V 5 -t 'em/+/status' -F '%t payload=%p retain=%r' -W 2
mosquitto_pub -V 5 -t em/meter3/status -n -r          # -n 空载荷 + -r 保留 = 清除
mosquitto_sub -V 5 -t '$SYS/broker/retained messages/count' -C 1
```

### 4.2 现象 → 怀疑 → 观察点

| 现象 | 优先怀疑 | 观察点 |
|---|---|---|
| 大屏刚打开状态一片空白 | 状态消息没设保留 | 订阅后是否收到 RETAIN=1 消息 |
| 显示在线其实早已离线 | 遗嘱未配；旧值未过期 | 保留消息时间戳；遗嘱配置 |
| 新设备一上线就执行奇怪指令 | 指令设成了保留 | 指令主题上的保留消息 |
| 告警服务重启报出一批旧告警 | 告警设成了保留 | 告警主题的保留消息 |
| 订阅 `em/#` 后客户端卡死 | 保留消息过多 | `$SYS/broker/retained messages/count` |
| 订阅者偶发 JSON 解析错误 | 收到清除用的空载荷 | 出错消息载荷长度 |
| broker 内存持续上涨 | 主题带变化值 + 保留 | 保留消息总数趋势 |
