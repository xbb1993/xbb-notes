# Sparkplug：命名空间、出生与死亡消息、状态管理

> 专题 37 · 模块九 · ☆ 高频重点 · 第二遍 · 简述（无云端实验）
> 已核实（HiveMQ 对 3.0 规范的解读）：对 MQTT 的要求、兼容 3.1.1、3.0 补充 5.0 会话设置、`$sparkplug/certificates/` 与 NDEATH 时间戳规则
> 未在规范原文逐字核实：消息类型全表、bdSeq、0–255 序号、STATE、Protobuf 载荷——采用前以 Eclipse 规范原文为准

**这一章解决什么**：专题 40 里自己设计的"两层上下线、网关掉线后子设备状态、字段定义"，工业界有现成规范 Sparkplug（Eclipse 维护，3.0 版）。回答：它怎么做、方案要不要用。

## 1. 核心概念

### 1.1 角色

| Sparkplug 叫法 | 对应 | 做什么 |
|---|---|---|
| Edge Node（边缘节点） | 网关 | 一条 MQTT 连接代表下面的设备 |
| Device（设备） | 网关下的电表 | 不直连 broker |
| Host Application（主机应用） | 平台 | 消费数据、下命令；可指定一个"主要主机" |
| MQTT Server | broker | 照常传话 |

```
 电表(Device) ─┐
 电表(Device) ─┼─ 网关(Edge Node) ══MQTT══ broker ══MQTT══ 平台(Host Application)
 电表(Device) ─┘
```

### 1.2 规定了什么

**固定主题**：`spBv1.0/{分组}/{消息类型}/{网关ID}/{设备ID}`，如 `spBv1.0/site01/DDATA/GW0001/AE10000001`。

**消息类型**：

| 类型 | 大白话 | 谁发 |
|---|---|---|
| NBIRTH | 网关上线报到：我有哪些数据点 | 网关 |
| NDEATH | 网关下线（注册为遗嘱） | broker 代发 |
| DBIRTH | 电表上线报到：数据点名字、类型 | 网关代发 |
| DDEATH | 电表下线 | 网关代发 |
| NDATA / DDATA | 网关 / 电表的数据 | 网关 |
| NCMD / DCMD | 发给网关 / 电表的命令 | 平台 |
| STATE | 平台自己在不在线 | 平台 |

**出生 / 死亡规则**（核心，对应专题 40 的两层上下线）：
- **先报到再发数据**：出生消息报全部数据点；之后数据里可用短编号代替名字，省流量。
- **网关死亡，名下电表一律视为不可信**：平台收到 NDEATH 即把其下所有电表标为"状态未知"（专题 40 实验"网关离线电表仍显示 online"的问题被规范解决）。
- **bdSeq（出生/死亡配对编号）**：网关快速重连时，旧连接遗嘱可能晚于新连接报到；配对编号让平台识别旧的死亡消息，防止误杀新连接。
- **0–255 循环序号**：平台发现跳号就让网关重新报到（rebirth），全量同步。
- **STATE**：网关据此知道主要主机是否在线，不在线时先缓存。

**载荷**：Google **Protobuf** 二进制，体积小，人眼读不了，调试需工具。

**对 MQTT 的要求**（已核实）：数据 QoS 0、状态 QoS 1、保留消息、遗嘱、通配符；完全符合 3.1.1 的 broker 即可；3.0 补充了 5.0 会话设置（Clean Start）。支持 Sparkplug 的 broker 要把出生消息以保留消息存于 `$sparkplug/certificates/` 下，并在投递 NDEATH 时替换为真实时间戳（遗嘱在连接时就设好，那时不知何时会断）。

### 1.3 对照方案：要不要用

它解决得好的：

| 问题 | 专题 40 的做法 | Sparkplug |
|---|---|---|
| 两层上下线 | 自己约定、平台自己算 | 规范写死：网关死亡即名下全部不可信 |
| 旧遗嘱误杀新连接 | 未处理 | bdSeq |
| 数据点含义 | 点表只在网关 | 出生消息报给平台 |
| 发现丢消息 | 业务编号断档检测（41） | 序号 + 重新报到 |
| 第三方工业软件对接 | 逐家定制 | 支持 Sparkplug 的软件直接对接 |

它带来的约束：

| 约束 | 影响 |
|---|---|
| 主题结构固定 | 与 `em/v1/租户/设备/方向/类别` 不兼容，权限模板要重设计 |
| 数据默认 QoS 0，靠序号和重新报到 | 与"QoS 1 + 唯一键幂等入库"不同；计费更看重一条不少，需评估 |
| Protobuf 二进制 | 调试抓包需工具；固件要编解码 |
| 状态机复杂 | 网关与平台实现更复杂 |
| 主要面向工业控制监控（SCADA） | 冻结数据、结算、补传完整性不直接覆盖 |

建议：
- **借鉴思想，不一定全盘采用**。直接可用的四点：出生消息带数据点定义；网关死亡则名下全部不可信；出生/死亡配对编号；序号跳变要求重新同步。
- **全面采用的时机**：客户现场大量使用支持 Sparkplug 的工业软件或需直接互通——可只在网关或平台出口提供一路 Sparkplug 数据，内部仍用自己的方案。

## 2. 易混淆 / 易错点

| 错误理解 | 正确理解 |
|---|---|
| Sparkplug 是另一种协议 | 是 MQTT 之上的规范：主题、消息类型、载荷、上下线规则 |
| 用了 Sparkplug 就要换 broker | 符合 3.1.1 的 broker 即满足基本要求；Sparkplug Aware 是额外能力 |
| 电表状态可以不管网关 | 网关 NDEATH 即名下全部不可信 |
| 遗嘱一到就代表网关下线 | 可能是旧连接的遗嘱，要用 bdSeq 对号 |
| Sparkplug 数据一定可靠不丢 | 数据默认 QoS 0，靠序号发现丢失再重新同步 |
| 采用就要全盘替换现有主题 | 可在出口兼容，内部保持自有方案 |

## 4. 诊断实践

本篇为简述，未做实验。采用前的验证建议（列入本地仿真"待验证事项"）：
- 网关快速断开重连时，旧 NDEATH 与新 NBIRTH 的先后，平台是否按 bdSeq 正确判断；
- 人为丢弃若干 DDATA，平台能否发现跳号并触发重新报到；
- 所选 broker 是否支持 `$sparkplug/certificates/` 与 NDEATH 时间戳替换。

| 现象 | 优先怀疑 |
|---|---|
| 网关刚重连就被平台判为离线 | 旧遗嘱晚到，没有按 bdSeq 对号 |
| 平台频繁要求网关重新报到 | 数据 QoS 0 丢包或序号处理错误 |
| 网关下线后电表仍显示在线 | 平台未按 NDEATH 将名下设备置为不可信 |
