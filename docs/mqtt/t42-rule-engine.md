# 规则引擎与数据集成

> 专题 42 · 模块十 · ☆ 高频重点 · 第二遍（与 9、13、16、49 合讲）
> EMQX 规则 SQL 示例与动作类型引自官方文档（已核实）；各连接器的缓冲、重试、目标宕机行为未逐一核实；本篇无实验

**这一章解决什么**：要不要让 broker 自己把消息转存到数据库、Kafka、HTTP——一次性的架构决策。

## 1. 核心概念

### 1.1 是什么

部分 broker 自带规则引擎：在 broker 里写类 SQL 规则，收到消息后筛选、转换，直接写入外部系统，不必另写订阅程序。EMQX 官方示例：

```sql
SELECT payload.data as d
FROM "t/#"
WHERE clientid = 'foo'
```

主题匹配 `t/#` 且 Client ID 为 foo 的消息，取载荷中 data 字段交给后续动作。文档列出的动作：转发到 MQTT 主题、输出到日志、写入外部系统（如 Kafka、PostgreSQL 等）。Mosquitto 没有规则引擎，靠插件或自写订阅程序。

### 1.2 与自写入库服务对比

| 维度 | broker 规则引擎 | 自写入库服务（41、50） |
|---|---|---|
| 开发量 | 小，配规则 | 写程序、部署、维护 |
| 去重、排序、按采样时间入库 | 难以表达复杂逻辑 | 完全可控 |
| 写入失败 | 取决于 broker 缓冲重试，需逐项确认 | 自己设计重试、落盘、告警 |
| 对 broker 影响 | 转换写库占资源；目标慢可能拖累 broker | broker 只传话 |
| 换 broker | 规则要重写 | 不受影响 |
| 排查 | 看 broker 内部规则日志 | 同其他业务服务 |

### 1.3 建议

- **计费核心数据入库用自写入库服务**：去重、采样时间、断档检测、水位线（41）放规则里难做好；且业务逻辑不进 broker（39）。
- **规则引擎适合简单、非关键分流**：告警事件同时转一份到 HTTP 接口、某类数据转发到别的主题。
- 若使用，专门确认目标系统宕机时 broker 是否缓存、缓存多少、会不会丢。

## 2. 易混淆 / 易错点

| 错误理解 | 正确理解 |
|---|---|
| 有规则引擎就不用写入库服务 | 核心数据的去重、排序、完整性检查仍需自己控制 |
| 规则引擎不影响 broker | 转换写库占 broker 资源，目标慢会拖累 |
| 目标宕机消息会自动保留 | 取决于连接器缓冲配置，需确认 |

## 4. 诊断实践

无实验。上线前验证项（列入仿真"待验证事项"）：目标数据库停机 10 分钟，规则引擎是否缓存、恢复后是否补写、是否丢失；规则处理是否增加 broker CPU 与延迟。

| 现象 | 优先怀疑 |
|---|---|
| 数据库短暂故障后丢一段数据 | 连接器缓冲不足或未开 |
| broker 延迟随数据库变慢而升高 | 规则写库同步阻塞或资源争用 |
| 换 broker 后数据不入库 | 规则绑定原产品 |
