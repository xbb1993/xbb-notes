# 常见故障诊断

> 专题 47 · 模块十一 · ★ 核心必会 · 中等深度
> 云端真实复现：现场 A（Client ID 冲突）、现场 B（心跳超时触发遗嘱），Mosquitto 2.0.18 + paho-mqtt 2.1.0；其余现场为综合前面专题的推理
> 贯穿场景：电表接入平台的五个典型故障现场

**这一章解决什么**：真实故障不会告诉你它属于哪一章，手里只有业务方的一句抱怨、几张监控图、一堆日志。这一章先给破案方法，再用五个现场练习把前面的知识串起来。

## 1. 核心概念

### 1.1 破案四步

**第 1 步：看范围**——一台、一批、还是全部？
- 一台：设备自身（固件、配置、证书、Client ID）。
- 一批：找共同点（地区、运营商、同一 LB/节点、同一固件版本）。
- 全部：公共部分（broker、LB、认证服务、入库服务）。

**第 2 步：看时间**——什么时候开始，和什么"变化"对得上？发版、重启、扩容、改配置、证书到期、定时任务。先问"最近改了什么"。

**第 3 步：顺着消息路径一段段排查**：

```
 电表 ──→ 网络 / 负载均衡 ──→ broker ──→ 订阅者 / 入库服务 ──→ 数据库 / 大屏
  │            │                 │              │                    │
 设备日志      LB 日志、连接数     broker 日志     服务日志、处理延迟      数据新鲜度、
 固件版本      证书、源 IP         $SYS 指标        消费速度              唯一键冲突
 重连次数                         丢弃 / 积压
```

拨测正常 = 进出 broker 的主路通，问题多半在两端；拨测失败 = 从网络、LB、broker 查起。

**第 4 步：提猜测、找证据**："如果真是这个原因，我应该能在哪里看到什么？"看到了就近一步，没看到就换猜测。不要因为"感觉像"就动手修。

### 1.2 五个现场

#### 现场 A：一块电表"时有时无"——Client ID 冲突

现象：meter3 数据断断续续、命令时成时败；全局指标正常；broker 日志反复 "already connected, closing old connection"，8 秒连了 9 次。

推理：只有一块表 → 设备自身。broker 规定同一 ID 只能一个连接，新来的踢旧的（专题 6）；真只有一台的话，被踢后应安静；不停有新连接 → **另一头还有一个"meter3"在重连**：

```
甲连上 → 乙连上踢甲 → 甲重连踢乙 → 乙重连踢甲 → ……
```

每次被踢连接中断；c1（Clean Start）使旧会话里排队的命令被清掉（专题 12）。

确认：列出所有 meter3 连接的源 IP/端口，是否交替两组；查原因（出厂同 ID、复制配置没改、换表时旧表没下线、固件里两个程序共用 ID）。

处理：
- 止血：找到另一台改 ID 或断电。
- 根治：ID 由设备身份（序列号、证书名）唯一决定（6、25）；broker 端把 ID 与证书身份绑定（25）；固件收到 5.0 原因码 0x8E（会话被接管，17）时不立刻重连并上报告警；监控"同一 ID 短时间被接管次数"。

#### 现场 B：电表被报"离线"，其实一直在工作——心跳超时触发遗嘱

现象：某工业园区每天几十次假离线，几秒后又在线；电表通过园区自建路由器上网。日志 "exceeded timeout, disconnecting"，随后重新连上。

推理：集中在一个园区 → 园区共同条件。broker 等 1.5 倍心跳没收到消息就判断开（专题 7），非正常断开即发遗嘱（专题 15）；电表在中断期间不知道连接已断，下次心跳失败才发现并重连、报 online。

最可疑的是**路由器 NAT 空闲超时**：路由器维护"谁在和谁通信"的表（NAT），连接空闲一段时间就被删，两头都收不到通知。**路由器空闲超时短于电表心跳间隔**时就会反复出现。另一可能是电表主循环被计量、写存储卡住没按时发心跳——现象相同。

确认：断开前连接存活时间是否接近某固定值；路由器 NAT TCP 空闲超时设置；电表日志里断开前心跳有没有发出（没发出 = 程序卡住；发出没收到 = 路上断）。

处理：
- 止血：告警延时确认，离线持续几分钟才通知。
- 根治：心跳间隔短于路上最短空闲超时（如 60 秒清理就设 30–45 秒）（7、43）；用 5.0 **遗嘱延迟**（15），短暂抖动内重连则不发遗嘱，会话过期时间不短于遗嘱延迟；固件心跳放独立任务；业务上离线持续一段时间才算真离线。

#### 现场 C：凌晨重启 broker 后平台反复雪崩——重连风暴

现象：重启后连接速率从每秒几十冲到几万；外部 HTTP 认证服务 5 ms → 3 s → 超时；broker CPU 满、内存耗尽被杀；反复重演；尖峰**间隔越来越大、每根都很尖**；固件用 paho-mqtt 默认重连。

推理：重启是那个"变化"。所有电表同时重连 → 每个连接调一次认证 → 认证服务先垮 → 大量连接卡在"等认证"、每个占内存（TLS 约 17 KB，32）→ broker 被杀 → 全体又断开重来。"间隔翻倍、每根都尖"正是专题 43 实验 expo 的样子；paho 默认"1 秒起翻倍、上限 120、不加随机"（43 读源码核实），完全吻合。

确认：尖峰间隔是否约 1、2、4、8…… 秒翻倍；认证请求量与连接尖峰是否对齐；被杀前是否大量"TCP 已建立、CONNECT 未完成"。

处理：
- 止血：LB 或 broker 入口限制每秒新连接数（32；EMQX 过载保护，46）；认证服务临时扩容或开缓存；分批放行入口。
- 根治：固件改"退避 + 随机"（43，治本）；认证用证书/JWT 本地验证或加缓存（23）；集群滚动重启（31）；忙时回 0x89/0x9F（17、43）；上线前做全量重连压测（48）。

#### 现场 D：新服务一上线就把一批电表"合闸"——保留消息污染

现象：上周 50 块欠费表被拉闸（运维平台走 `em/+/down/cmd` 命令通道）；新"继电器状态同步服务"订阅 `em/+/relay/desired`，立即收到 50 条 retain=True 的 `{"state":"on"}`，下发合闸。监控一切正常。

推理：

```
半年前：设计了 relay/desired，写过"合闸"保留消息，后来没人用，消息一直留在 broker
上周：  拉闸走命令通道，电表确实拉闸了，但 relay/desired 仍是"合闸"
今天：  新服务订阅 → 收到 50 条"合闸" → 以为期望≠实际 → 下发合闸
```

三个问题叠加：
1. **同一件事两个真相来源**，互不同步（39：状态只能有一份正本）。
2. **保留消息不过期、不带时间戳**（14），订阅方无法判断新旧。
3. **新服务启动即执行**，没有任何确认。

监控完全看不出——业务逻辑错误只能靠设计防。

确认：读出这些主题当前保留消息；查审计日志最后写入记录；对比运维平台拉闸记录。

处理：
- 止血：停新服务；业务确认后重新拉闸；往每个 relay/desired 发空载荷保留消息清除（14）。
- 根治：继电器状态只留一个正本，按影子管理，运维"拉闸"也写影子（39）；保留消息带版本号和时间戳，过时忽略（39）；服务启动"只同步不执行"，不一致告警等人确认；高风险操作"先选择后执行"或人工审批（39）；废弃主题清掉保留消息并收回 ACL（24）。

#### 现场 E：入库服务扩容后数据变三倍——普通订阅而非共享订阅

现象：入库服务 1 → 3 实例，月报用电量三倍；broker 收到数不变、发出数 3 倍；无报错；三个实例配置 `client_id: ingest-${HOSTNAME}`、`subscribe: em/+/up/telemetry`；表无唯一键。

推理：发出 = 3 倍收到 → broker 把每条发了 3 份。三个不同 ID 的普通订阅，规则就是"每个订阅者一份"（19），所以不报错。要分摊必须 `$share/组名/`。表若有唯一键（41），即使收到 3 份也只留 1 份——两道防线都没有。另外按此配置每个实例负担并未减轻，"处理快了"需重新核实。

确认：单个实例是否收到全部电表数据；同一电表同一时刻是否正好 3 条。

处理：
- 止血：缩回 1 实例或停写；按"电表号 + 编号/采样时间"去重；重算月报。
- 根治：改共享订阅 `$share/ingest/em/+/up/telemetry`（19）；加唯一键幂等入库（41）；共享订阅下同一电表数据分到不同实例、顺序更乱，按采样时间或编号排序（41），部分 broker 支持按客户端哈希分配（EMQX 有此类策略，未逐字核实）；扩容后核对"发出 ÷ 收到"比例（46）。

### 1.3 总表

| 现场 | 根因 | 对应专题 | 最早能从哪里发现 |
|---|---|---|---|
| A 时有时无 | 两个客户端共用 Client ID 互踢 | 6、12、17、25 | 同一 ID 短时被接管次数；日志 "already connected" |
| B 假离线 | 路由器清空闲连接，心跳超时触发遗嘱 | 7、15、43 | 日志 "exceeded timeout"；offline 后很快 online 的次数 |
| C 反复雪崩 | 重连风暴（退避无随机）+ 认证服务被压垮 | 23、31、32、43、46 | 连接速率尖峰；认证服务延迟 |
| D 误合闸 | 过时保留消息 + 两个真相来源 + 启动即执行 | 14、24、39 | 监控看不到，靠设计与业务核对 |
| E 数据三倍 | 普通订阅而非共享订阅 + 无唯一键 | 19、41、46 | "发出 ÷ 收到"比例突变 |

共同的道理：**MQTT 协议本身工作完全正常，出问题的都是协议之上的设计**——ID 分配、心跳、重连、状态正本、订阅方式、入库去重，都要在接入方案里事先想清楚。

## 2. 易混淆 / 易错点

| 错误理解 | 正确理解 |
|---|---|
| 一看到报错就动手修 | 先看范围、看时间，再按路径分段，猜测要有证据 |
| "already connected" 是正常日志 | 频繁出现说明有 ID 冲突 |
| 收到 offline 遗嘱就是设备坏了 | 可能是心跳超时或 NAT 清连接造成的假离线 |
| 心跳越长越省电越好 | 必须短于路上最短空闲超时 |
| broker 扛不住就加机器 | 重连风暴的根在客户端重连策略和认证依赖 |
| 退避了就不会风暴 | 不加随机会整齐地一波波冲 |
| 保留消息就是当前状态 | 可能是过时的遗留数据，要有版本和时间戳 |
| 多实例订阅同一主题就是分摊 | 普通订阅每个都收一份；分摊要 `$share` |
| 监控正常就没问题 | 业务逻辑错误（现场 D）监控完全看不到 |

## 4. 诊断实践

### 4.1 云端复现（Mosquitto 2.0.18）

broker 配置：

```
listener 1883
allow_anonymous true
log_dest file /tmp/t47/b.log
log_type all
log_timestamp_format %H:%M:%S
```

**现场 A**：两个 mosquitto_sub 用同一 ID（它们都会自动重连）：

```bash
mosquitto_sub -V 5 -i meter3 -t em/meter3/down/cmd > /dev/null 2>&1 &
sleep 0.3
mosquitto_sub -V 5 -i meter3 -t em/meter3/down/cmd > /dev/null 2>&1 &
sleep 8; pkill -x mosquitto_sub
grep -E "meter3|already" /tmp/t47/b.log
```

真实输出（节选）：

```
10:24:08: New client connected from 127.0.0.1:54376 as meter3 (p5, c1, k60).
10:24:09: Client meter3 already connected, closing old connection.
10:24:09: New client connected from 127.0.0.1:54388 as meter3 (p5, c1, k60).
10:24:10: Client meter3 already connected, closing old connection.
10:24:10: New client connected from 127.0.0.1:54398 as meter3 (p5, c1, k60).
10:24:11: Client meter3 already connected, closing old connection.
10:24:11: New client connected from 127.0.0.1:54410 as meter3 (p5, c1, k60).
8 秒内 meter3 的新连接次数: 9
```

**现场 B**：电表程序带遗嘱、心跳 5 秒，用 `kill -STOP` 冻结 12 秒模拟卡死/中断，再 `kill -CONT` 恢复。

`dev.py`：

```python
import paho.mqtt.client as mqtt, time
c=mqtt.Client(mqtt.CallbackAPIVersion.VERSION2, client_id="meter7", protocol=mqtt.MQTTv5)
c.will_set("em/meter7/status","offline",qos=1,retain=True)
def on_conn(cl,u,f,rc,p): cl.publish("em/meter7/status","online",qos=1,retain=True)
c.on_connect=on_conn; c.reconnect_delay_set(1,4)
c.connect("127.0.0.1",1883,keepalive=5); c.loop_forever()
```

```bash
mosquitto_sub -t em/meter7/status -F '%U %p' > status.txt &
python3 dev.py & P=$!; sleep 3
kill -STOP $P; sleep 12; kill -CONT $P; sleep 6; kill $P
```

真实输出：

```
电表程序被冻结（模拟卡死/网络中断）：第 3.0s ~ 第 15.0s
第   0.1s  监控收到 em/meter7/status = online
第  10.8s  监控收到 em/meter7/status = offline
第  16.0s  监控收到 em/meter7/status = online
10:24:27: New client connected from 127.0.0.1:46451 as meter7 (p5, c1, k5).
10:24:37: Client meter7 has exceeded timeout, disconnecting.
10:24:42: New client connected from 127.0.0.1:37411 as meter7 (p5, c0, k5).
```

（实验最后用 kill 结束程序时又会收到一次 offline，那是实验收尾造成的，与现场无关。）

现场 C 的风暴曲线见专题 43 实验 A；现场 E 的"每个订阅者一份"与共享订阅行为见专题 19。

### 4.2 速查：现象 → 第一怀疑

| 现象 | 第一怀疑 |
|---|---|
| 单台设备频繁重连，日志 "already connected" | Client ID 冲突 |
| 假离线、很快又在线，集中在某个网络环境 | NAT 空闲超时 < 心跳；设备主循环卡住 |
| 重启后连接尖峰、认证超时、反复崩 | 重连风暴 + 外部认证依赖 |
| 新服务启动就执行了不该执行的动作 | 过时保留消息 / 双真相来源 |
| 扩容后数据成倍 | 普通订阅代替共享订阅 + 无唯一键 |
