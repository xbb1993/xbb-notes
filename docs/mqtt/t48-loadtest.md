# 压测与容量规划

> 专题 48 · 模块十一 · ☆ 高频重点 · 第二遍 · 中等深度
> 云端实测：Mosquitto 2.0.18，自写阶梯压测脚本；**压测机、broker、接收端同在 2 核机器、本机回环、无 TLS**——数字只演示方法，不代表真实上限
> 压测工具名（emqtt-bench、MQTTX CLI bench、JMeter MQTT 插件）的具体用法未逐一核实

**这一章解决什么**：专题 50 的容量估算是纸面计算。怎么用压测把估算变成实测结论，再变成方案里的机器数和参数？

## 1. 核心概念

### 1.1 角色

- **被测系统**：要验证的部分，可能只是一台 broker，也可能是"LB + broker 集群 + 认证 + 入库"整条链路。先想清楚测的是谁。
- **压测机**：模拟成千上万块电表的程序和机器，它的压力就是"假设的现实"。
- **观测点**：吞吐（实际发出、实际收到）、延迟（发出到收到）、资源（CPU、内存、连接数）。
- **压测场景**：多少连接、多大消息、什么 QoS、多少订阅者。

### 1.2 架构

```
 ┌──────── 压测机（一台或多台，和被测系统分开）────────┐
 │  模拟电表 × N：连接、按速率发布、带发送时间戳        │
 └──────────────────────┬──────────────────────────┘
                        │ 真实网络（能用 TLS 就用 TLS）
                        ▼
 ┌──────────────── 被测系统 ────────────────┐
 │  负载均衡 → broker（集群）→ 认证服务        │ ← CPU、内存、连接数、丢弃、$SYS
 │                    ↓                    │
 │                 入库服务 → 数据库          │
 └────────────────────┬────────────────────┘
                      ▼
 ┌──────── 接收端（模拟后端订阅者）────────┐
 │  统计实际收到条数、计算端到端延迟         │ ← 吞吐、延迟分位数
 └───────────────────────────────────────┘
```

压测机要和被测系统分开：同机抢 CPU 和网络，上限偏低，分不清谁先到顶。

### 1.3 压测要回答的四个问题

| # | 问题 | 怎么压 | 对应方案决定 |
|---|---|---|---|
| 1 | 最多能挂多少连接 | 连接数逐级增加，保持空闲 | 每台 broker 承载多少表（26、32） |
| 2 | 稳态每秒处理多少消息 | 连接固定，速率逐级增加 | 上报周期能多短（50） |
| 3 | 全体重连扛得住吗 | 所有连接同时断开再重连 | 入口限流、认证容量、重连策略（43、47） |
| 4 | 长时间稳不稳 | 正常负载连续跑几小时到几天 | 内存慢涨、积压（28、46） |

电表场景（10 万表、每分钟一报 ≈ 每秒一千多条）问题 2 一般不是瓶颈，**重点是 1 和 3**，4 用来发现慢性病。

### 1.4 阶梯加压与拐点

一下加到最大只知道"扛不住"；要**一级级加**，每级保持一段时间。

```
延迟
 │                                    ╱ ← 崩溃区：延迟飙升、积压或丢消息
 │                                 ╱
 │                         __╱   ← 拐点：延迟突然开始变大
 │ ___________________ ___╱
 │  轻松区：加压力，延迟几乎不变
 └──────────────────────────────────────── 压力
```

**拐点**（膝点，knee）的信号，出现任一即到：延迟高分位数突然上跳；实际收到追不上实际发出；开始出现丢弃、连接失败或报错。

**分位数**：延迟从小到大排，p50 是正中间那条，p99 是第 99% 位置那条。平均值会掩盖少数慢消息，要看 p99。

**一次只改一个变量**，否则结果变差不知道怪谁。

### 1.5 常见陷阱

| 陷阱 | 后果 | 怎么避免 |
|---|---|---|
| 压测工具成为瓶颈 | 误以为系统上限低，误读延迟 | 看"实际发出"是否达标；压测机分开、多台多进程 |
| 压测机与被测系统同机 | 抢资源，上限偏低 | 物理分开 |
| 只看平均延迟 | 慢消息被掩盖 | 看 p99/p99.9 |
| 一次改多个变量 | 无法归因 | 每轮只改一个 |
| 只测一次 | 噪声当结论 | 多次重复，报告波动范围 |
| 场景不像真实 | 数字无参考价值 | 连接数、消息大小、QoS、TLS、扇出、主题数贴近真实 |
| 只测吞吐 | 漏掉连接和重连瓶颈 | 四个问题都测 |
| 没预热就记录 | 前几秒数据异常 | 每级先稳定再记录 |
| 只压 broker | 认证、入库先倒下 | 最终压整条链路 |

### 1.6 从结果到方案

1. **留余量**：按拐点的 50%–70% 规划（扛突发与单节点故障转移的负载）。
2. **按最紧的一项算台数**：连接数、消息速率、全体重连速率各算一遍，取最大；电表场景大概率是连接（TLS 内存）或重连速率决定。
3. **加冗余**：N+1，坏一台剩下仍扛得住。

方案"容量估算"一节把专题 50 纸面估算与压测实测并列，差距大处重点解释。

常用工具：emqtt-bench（EMQX 开源）、MQTTX 命令行 bench、JMeter + MQTT 插件（用法以官方文档为准）。正式压测建议用成熟工具、压测机分开部署。

## 2. 易混淆 / 易错点

| 错误理解 | 正确理解 |
|---|---|
| 压测就是测每秒多少条 | 电表场景更要测连接容量、全体重连、长时间稳定 |
| 压到崩溃的数就是上限 | 找拐点，规划再留 30%–50% 余量 |
| 延迟看平均值 | 看 p99 |
| 测出来低就是系统不行 | 先确认压测工具没到顶 |
| 压测机和系统放一起省事 | 结论不可信 |
| 一次结果就是结论 | 有噪声，多次重复 |
| 本机数字可直接写进方案 | 无网络、TLS、扇出，只能演示方法 |

## 4. 诊断实践

### 4.1 实验（云端真实输出）

设置：若干发布进程按目标速率发 QoS 1（载荷约 110 字节，含发送时刻），一个接收端订阅统计实际收到与端到端延迟；每级 6 秒；broker `max_inflight_messages 1000`、`max_queued_messages 100000`。

第一组，1 个发布进程：

```
    目标 条/秒      实际发出      实际收到   延迟p50 ms   延迟p99 ms broker CPU
      5000      5000      5000        0.2        2.9         6%
     10000     10000     10000        0.3        2.6        13%
     20000     19994     19994        0.5        2.7        24%
     40000     39991     39991        1.2       18.4        72%
     80000     69249     64506      466.1      696.2        87%
```

第二组，3 个发布进程：

```
    目标 条/秒      实际发出      实际收到   延迟p50 ms   延迟p99 ms broker CPU
      5000      4999      4999        0.2        2.3         9%
     10000      9998      9998        0.2        2.3        13%
     20000     19995     19995        0.2        2.2        22%
     40000     39996     39996        0.4        3.2        63%
     80000     79984     68170      426.9      885.9        95%
```

第三组，3 个发布进程，在 4 万–8 万之间细分：

```
    目标 条/秒      实际发出      实际收到   延迟p50 ms   延迟p99 ms broker CPU
     40000     39989     39989        0.4        3.8        47%
     50000     49990     49990        0.5        4.6        78%
     60000     59984     59984        3.8       36.6        87%
     70000     69991     69747       19.2       58.5        91%
```

解读：
1. **压测工具先到顶**：1 个进程目标 8 万只发出 69249；4 万那级 p99 18.4 ms，换 3 个进程只有 3.2 ms——那 18 ms 是压测程序自己卡顿造成的。
2. **拐点在每秒 5 万–6 万**：5 万时 p99 4.6 ms，6 万跳到 36.6 ms、p50 从 0.5 到 3.8 ms；7 万开始收不过来；8 万进入崩溃区。
3. **噪声**：同为 4 万，第二组 CPU 63%、第三组 47%。
4. **不能直接用**：2 核同机抢资源、本机回环、无 TLS、单订阅者无扇出。演示的是方法。

按 1.6 第一步：此环境拐点约 5 万/秒 → 可规划约 2.5 万–3.5 万/秒（仅示意）。

### 4.2 脚本（本地：Mosquitto；压测机最好单独一台）

broker 配置：

```
listener 1883
allow_anonymous true
max_inflight_messages 1000
max_queued_messages 100000
```

`loadgen.py`（参数：发布进程数、broker PID、逗号分隔的各级目标速率；broker 须在本机以读取 CPU）：

```python
# 阶梯压测：多个发布进程按目标速率发 QoS 1 遥测（载荷里带发送时刻），一个接收端统计实际速率与端到端延迟
import socket, struct, time, sys, multiprocessing as mp, threading
def s(x): x=x.encode(); return struct.pack(">H",len(x))+x
def rl(n):
    o=b""
    while True:
        b=n%128; n//=128; o+=bytes([b|0x80 if n else b])
        if not n: return o
def conn(cid):
    k=socket.create_connection(("127.0.0.1",1883)); b=s("MQTT")+bytes([5,2])+struct.pack(">H",600)+b"\x00"+s(cid)
    k.sendall(b"\x10"+rl(len(b))+b); k.recv(64); return k
def publisher(idx, rate, secs, out):
    k=conn(f"lg{idx}"); threading.Thread(target=lambda: [k.recv(1<<16) for _ in iter(int,1)], daemon=True).start()   # 吃掉 PUBACK
    topic=s(f"em/v1/t01/LG{idx:04d}/up/telemetry"); n=0; pid=1; t0=time.time(); end=t0+secs
    batch=max(1,int(rate/200))                                   # 每 5ms 发一小批
    while time.time()<end:
        due=int((time.time()-t0)*rate)
        while n<due:
            buf=b""
            for _ in range(min(batch,due-n)):
                vh=topic+struct.pack(">H",pid)+b"\x00"; pl=struct.pack(">d",time.time())+b"x"*100   # 约 110 字节载荷
                body=vh+pl; buf+=b"\x32"+rl(len(body))+body; pid=pid%65535+1; n+=1
            k.sendall(buf)
        time.sleep(0.002)
    out.put(n)
def sink(secs, out):
    k=conn("sink"); sb=struct.pack(">H",1)+b"\x00"+s("em/v1/+/+/up/telemetry")+b"\x00"   # 订阅 QoS 0，接收端尽量轻
    k.sendall(b"\x82"+rl(len(sb))+sb); k.recv(16); k.settimeout(1)
    buf=b""; lat=[]; end=time.time()+secs
    while time.time()<end:
        try: buf+=k.recv(1<<20)
        except socket.timeout: continue
        i=0; now=time.time()
        while True:
            if len(buf)-i<2: break
            mul,ln,j=1,0,i+1
            while j<len(buf):
                b=buf[j]; ln+=(b&127)*mul; mul*=128; j+=1
                if b<128: break
            else: break
            if len(buf)<j+ln: break
            pk=buf[j:j+ln]; tl=struct.unpack(">H",pk[:2])[0]; off=2+tl+1         # QoS0 投递：无报文标识，1 字节属性长度
            lat.append(now-struct.unpack(">d",pk[off:off+8])[0]); i=j+ln
        buf=buf[i:]
    out.put(lat)
def cpu(pid):
    f=open(f"/proc/{pid}/stat").read().split(); return (int(f[13])+int(f[14]))/100
if __name__=="__main__":
    procs=int(sys.argv[1]); bpid=int(sys.argv[2]); SECS=6
    print(f"发布进程数 {procs}；每级 {SECS} 秒")
    print(f"{'目标 条/秒':>10} {'实际发出':>9} {'实际收到':>9} {'延迟p50 ms':>10} {'延迟p99 ms':>10} {'broker CPU':>10}")
    for target in [int(x) for x in sys.argv[3].split(",")]:
        q=mp.Queue(); sq=mp.Queue()
        sp=mp.Process(target=sink,args=(SECS+2,sq)); sp.start(); time.sleep(0.5)
        c0=cpu(bpid); t0=time.time()
        ps=[mp.Process(target=publisher,args=(i,target/procs,SECS,q)) for i in range(procs)]
        [p.start() for p in ps]; [p.join() for p in ps]
        sent=sum(q.get() for _ in ps); c1=cpu(bpid); dt=time.time()-t0
        lat=sorted(sq.get()); sp.join()
        p50=lat[len(lat)//2]*1000 if lat else 0; p99=lat[int(len(lat)*0.99)]*1000 if lat else 0
        print(f"{target:>10} {sent/SECS:>9.0f} {len(lat)/SECS:>9.0f} {p50:>10.1f} {p99:>10.1f} {100*(c1-c0)/dt:>9.0f}%", flush=True)
        time.sleep(1)
```

运行：`python3 loadgen.py 3 $(pgrep -nx mosquitto) 5000,10000,20000,40000,80000`

### 4.3 现象 → 怀疑 → 观察点

| 现象 | 优先怀疑 | 观察点 |
|---|---|---|
| 实际发出达不到目标 | 压测工具到顶 | 压测机 CPU；增加进程或机器后是否改善 |
| 低负载下 p99 就偏高 | 压测机卡顿或同机抢资源 | 换多进程/分机后对比 |
| 实际收到 < 实际发出 | 被测系统或接收端到顶 | broker CPU、丢弃数；接收端 CPU |
| 同条件两次结果差很多 | 测量噪声 | 多次重复取稳定值 |
| 压测通过、上线后不行 | 场景不真实（无 TLS、无扇出、无认证） | 对照真实流量模型 |
