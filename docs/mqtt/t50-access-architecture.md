# 设备接入架构设计

> 专题 50 · 模块十二 · ★ 核心必会 · 详细
> 定位：团队电表接入 MQTT 方案的**骨架**。每个决策注明"决定什么、推荐什么、为什么、依据哪个专题"
> 规模估算基于专题 26/32 在 Mosquitto 上的实测，属估算值，需压测确认

## 1. 核心概念

### 1.1 角色

**现场侧**
- **电表**：采样、上报、执行命令、升级固件。直连型（自带 MQTT，如 4G/以太网表）或经网关型（只会 Modbus 等，由网关代报）。

**接入侧**
- **负载均衡**：分配连接、入口限流、可选 TLS 终结（32）。
- **broker 集群**：唯一传话通道（26–31）。
- **认证授权服务**：你是谁、能读写哪些主题（23–25）。

**平台服务侧**（都是 broker 的客户端）
- 入库服务（41）、影子服务（39）、命令服务（39）、OTA 服务（39）、上下线服务（15）。

**业务侧**
- 时序库（读数）、业务库（影子正本、命令记录、设备档案、在线表）。
- 业务系统（计费、运维、App 后台）**只和平台服务打交道，不直连 broker**。

**贯穿**：监控告警 = broker 指标 + 拨测 + 业务指标（46）。

### 1.2 全景架构

```
 ┌──────────────── 现场 ────────────────┐
 │ 直连电表（4G/以太网）   经网关的电表        │
 │   meter A  meter B     Modbus ─→ 网关    │
 └──────┬────────┬──────────────────┬────┘
        │  MQTT over TLS（每台一条长连接；网关代表其下所有电表）
        ▼        ▼                  ▼
 ┌─────────────────────────────────────────────────────────────┐
 │ 接入层：负载均衡（入口限流、可选 TLS 终结、PROXY protocol）        │
 └──────────────────────────────┬──────────────────────────────┘
                                ▼
 ┌─────────────────────────────────────────────┐    ┌──────────────┐
 │           broker 集群（节点 1 / 2 / 3）         │←──→│ 认证授权服务    │
 │  只管传话：路由、会话、保留消息、遗嘱             │    │（身份、ACL）    │
 └──┬──────────┬──────────┬──────────┬────────┬─┘    └──────────────┘
    │ 共享订阅   │          │          │        │
    ▼          ▼          ▼          ▼        ▼
 入库服务    影子服务    命令服务    OTA 服务   上下线服务        ← 平台服务
    │          │          │          │        │
    ▼          ▼          ▼          ▼        ▼
  时序库      业务库（影子正本、命令记录、设备档案、在线表）       ← 数据库
    │          ▲          ▲          ▲
    │          └─────HTTP 接口──────────┘
    ▼                     │
 计费 / 报表 / 大屏      运维平台、App 后台                       ← 业务系统
 ════════════════════════════════════════════════════════
 监控：broker 指标 + 拨测 + 业务指标（数据新鲜度、命令成功率）→ 告警
```

### 1.3 五条数据流

| 数据流 | 方向 | 例子 | 路径 | 关键要求 |
|---|---|---|---|---|
| ① 遥测 | 上行 | 电量、功率、电压 | 电表 → broker → 入库 → 时序库 | 不丢、可去重、按采样时间 |
| ② 状态 | 双向 | 费率、上报周期、继电器 | 业务 → 影子服务 ⇄ broker ⇄ 电表 | 最终一致，离线也收敛 |
| ③ 命令 | 下行 + 回执 | 立即抄表、复位 | 运维 → 命令服务 ⇄ broker ⇄ 电表 | 有回执、不重复执行、会过期 |
| ④ 上下线 | 上行 | 在线/离线 | 电表（含遗嘱）→ broker → 上下线服务 | 不误报 |
| ⑤ 升级 | 下行为主 | 固件 | 清单走 MQTT，文件主要走 HTTPS | 可续传、可校验、可回滚、分批 |

### 1.4 设计决策清单

**① 设备身份（6、22、23、25）**
- Client ID = 出厂序列号（或型号 + 序列号），由身份唯一决定，绝不手配（现场 A）。
- 能力够用 mTLS，证书名 = 序列号，broker 绑定 ID 与证书名；能力不够至少每台独立用户名密码，不共用。
- 证书烧录、轮换、吊销写进方案。

**② 主题规划（24、27）**：`em/v1/{租户}/{设备ID}/{方向}/{类别}`

| 用途 | 主题（示例，ID 为虚构） | 发布者 | 保留 |
|---|---|---|---|
| 遥测 | `em/v1/t01/AE12345678/up/telemetry` | 电表 | 否 |
| 事件 | `em/v1/t01/AE12345678/up/event` | 电表 | 否 |
| 在线状态 | `em/v1/t01/AE12345678/up/status` | 电表（含遗嘱） | 是 |
| 影子实际值 | `em/v1/t01/AE12345678/shadow/reported` | 电表 | 是 |
| 影子期望值 | `em/v1/t01/AE12345678/shadow/desired` | 影子服务 | 是（带版本号） |
| 命令 | `em/v1/t01/AE12345678/down/cmd` | 命令服务 | 否 |
| 命令回执 | `em/v1/t01/AE12345678/up/cmd_ack` | 电表 | 否 |
| 升级清单 | `em/v1/t01/AE12345678/ota/manifest` | OTA 服务 | 是 |

理由：设备 ID 固定在第 4 层便于 ACL 模板；up/down 分层权限一目了然；v1 便于新旧格式并存；遵守 27 的命名规则；后端用 `$share/ingest/em/v1/+/+/up/telemetry` 一条订阅覆盖全部（19）。

**③ 权限（24、25、46）**
- 电表只能发布自己的 `up/#`、`shadow/reported`；只能订阅自己的 `down/#`、`shadow/desired`、`ota/#`；禁止通配订阅他人。
- 每个平台服务独立账号、最小权限。
- `$SYS` 只给监控账号。
- 废弃主题收回权限、清保留消息（现场 D）。

**④ QoS、保留、会话（10–15、39、41）**

| 数据流 | QoS | 保留 | 其他 |
|---|---|---|---|
| 遥测 | 1 | 否 | 载荷带编号、采样时间；入库唯一键去重 |
| 状态 | 1 | 是 | 带版本号；正本在数据库 |
| 命令 | 1 | 否 | 编号 + 回执 + 超时重发 + 电表端幂等 + 消息过期 |
| 上下线 | 1 | 是 | 连上发 online，遗嘱 offline，遗嘱延迟防假离线 |
| 升级清单 | 1 | 是 | 文件走 HTTPS |

- 为什么不用 QoS 2：只保证一段路不重复，解决不了重发、补传的业务重复；QoS 1 + 业务去重更省、更完整。
- 会话：电表 Clean Start = 0，会话过期适中（几小时到一天）；离线太久让会话过期，状态靠影子收敛；不设永不过期（28、46）。
- 协议版本优先 5.0（原因码、消息过期、遗嘱延迟、Response Topic）；固件库只支持 3.1.1 时把这些放进载荷自行实现并写明差异（17）。

**⑤ 载荷（1、5、17）**
- 遥测必带：编号（seq）、采样时间（ts）、格式版本号；设备 ID 已在主题里可不重复。
- 宽裕用 JSON；4G 按量计费或设备弱用二进制（CBOR、Protobuf），通常小一半以上。
- 用户属性只放少量元数据。

**⑥ 电表侧行为规范（给固件团队的验收清单）**

| # | 要求 | 依据 |
|---|---|---|
| 1 | Client ID = 序列号，永不随机 | 6、现场 A |
| 2 | 心跳短于现场最短空闲超时（通常 30–60 秒） | 7、现场 B |
| 3 | 心跳在独立任务发送，不被计量、写存储卡住 | 现场 B |
| 4 | 重连指数退避 + 随机抖动，设上限；收到 0x89 / 0x9F / 0x8E 等更久 | 43、现场 A/C |
| 5 | 订阅写在连接成功回调里 | 43 |
| 6 | 遥测先进本地持久缓存，收 PUBACK 再删；编号断电不归零 | 41、43 |
| 7 | 恢复后边发新数据边补旧数据，补发限速 | 41 |
| 8 | 定期校时；采样时间用设备时钟 | 41 |
| 9 | 命令按编号去重，已执行编号断电不丢 | 39 |
| 10 | OTA：分块续传、单块与整包校验、验签、A/B 回滚 | 39 |
| 11 | 上线发 online，设置 offline 遗嘱 | 15 |
| 12 | 不使用 MQTT 库默认重连参数 | 43 |

**⑦ 平台侧**

| 组件 | 推荐 | 依据 |
|---|---|---|
| broker | 边缘/几千到几万台：Mosquitto；大规模要集群高可用：EMQX 类；EMQX 5.9 起 BSL 许可，商用前核对 | 3、26、31 |
| 集群 | 至少 3 节点，滚动重启 | 31、现场 C |
| 接入层 | 入口限新连接速率；TLS 位置按三种方式权衡；要真实 IP 用 PROXY protocol | 32 |
| 持久化 | 需要会话跨重启就开，并了解丢失窗口；影子正本在数据库 | 28、39 |
| 入库 | 共享订阅、唯一键幂等、按采样时间、两个时间都存 | 19、41、现场 E |
| 认证 | 优先 broker 本地可验证（证书、JWT）；外部调用加缓存 | 23、现场 C |
| 结算 | 水位线等数据到齐；断档召测 | 41 |

**⑧ 运维（46、47）**
- 最小告警集：拨测、数据新鲜度、丢弃、在线数断崖、连接速率异常、积压持续涨。
- 业务指标：数据完整率、命令成功率、OTA 成功率与回滚率。
- 变更规范：broker 滚动重启；固件分批灰度；扩容后核对"发出 ÷ 收到"。

### 1.5 经网关接入的电表

- MQTT 客户端是网关，一条连接代表几十块表；Client ID 用网关序列号。
- 主题里的设备 ID 仍是电表的；ACL 要允许"网关 X 写它名下电表的主题"，模板更复杂。
- 上下线分两层：网关在线用遗嘱；网关下某表通信失败要由网关主动上报。Sparkplug（37）专门规定了出生/死亡消息，可参考。
- 断网补传的责任在网关，要有足够本地存储。

### 1.6 规模估算（10 万块、60 秒一报）

```
电表 100,000 块，每 60s 上报一次，单条 PUBLISH ≈ 160 字节
  上行消息速率 ≈ 1,667 条/秒（平均）；若入库服务 1 份订阅，broker 出口同为 1,667 条/秒
  上行带宽 ≈ 2.13 Mbit/s（不含 TLS 与 TCP 开销）
  心跳：上报周期 60s > 心跳 45s，每周期额外 1 次 PINGREQ（全网 ≈ 1,667 次/秒）
  单块表每天遥测流量 ≈ 236 KB（≈ 6.9 MB/月，未含 TLS 握手与重连）
  broker 连接内存：明文 ≈ 78 MB，TLS ≈ 1.6 GB（仅进程内，内核缓冲另计）
  若全部电表在 30s 内重连：平均 3,333 个新连接/秒（每个都要 TLS 握手 + 认证）
  若全部电表在 300s 内重连：平均 333 个新连接/秒（每个都要 TLS 握手 + 认证）
```

- 平时压力很小，单台 broker 能扛（26：单核约 27 万条/秒 QoS 0）。
- 真正压力：**TLS 连接内存**（10 万约 1.6 GB，仅进程内）和**全体重连那一刻**（30 秒恢复需每秒 3000 多次 TLS 握手 + 认证）——这决定了认证服务与 broker 配置，也说明退避加随机和入口限流必不可少。
- 心跳细节：心跳计时在客户端每发一个报文时重置；上报周期 ≥ 心跳间隔时每周期多一次心跳；心跳设得 ≥ 上报周期则平时不额外发，但心跳又必须短于现场空闲超时，两者一起权衡。
- 每表每月约 7 MB 遥测流量，可据此谈 4G 套餐。
- 局限：内存数字来自 Mosquitto 本机实测；带宽未计 TLS/TCP 开销；以压测（48）为准。

## 2. 易混淆 / 易错点

| 错误理解 | 正确理解 |
|---|---|
| 业务系统直接连 broker 最简单 | 业务系统只对接平台服务；broker 只给设备和平台服务 |
| 所有数据一个主题、一种 QoS | 五条数据流要求不同，分别设计 |
| QoS 2 最可靠所以全用 | 解决不了业务重复，QoS 1 + 去重更完整 |
| 会话永不过期最保险 | 离线积压拖垮内存；离线久了靠影子收敛 |
| Client ID 现场配置即可 | 由身份唯一决定，并与证书绑定 |
| 平时消息量小就不用担心容量 | 压力在 TLS 内存和全体重连那一刻 |
| 网关场景和直连一样 | 一条连接多设备，ACL、上下线、补传都要另设计 |
| 估算数字可以直接写进方案 | 标注估算值，以压测和仿真为准 |

## 4. 诊断实践

### 4.1 规模估算脚本（云端实际运行，参数可改）

```python
# 电表接入规模粗估（假设值都可改；单连接内存取自专题 26/32 在 Mosquitto 上的实测）
N=100_000                 # 电表数
PERIOD=60                 # 遥测上报周期（秒）
PAYLOAD=120               # 单条遥测载荷字节（JSON，含编号、时间、5~8 个量）
TOPIC=len("em/v1/t01/AE12345678/up/telemetry")
KEEPALIVE=45              # 心跳间隔（秒）
MEM_PLAIN_KB, MEM_TLS_KB = 0.8, 17.2      # 每条空闲连接 broker 进程内存（Mosquitto 实测）
pkt = 2 + 2 + TOPIC + 2 + 1 + PAYLOAD     # 固定头 + 主题 + 报文标识 + 属性长度 + 载荷（QoS1，5.0，无属性）
puback = 4
msg_s = N/PERIOD
print(f"电表 {N:,} 块，每 {PERIOD}s 上报一次，单条 PUBLISH ≈ {pkt} 字节")
print(f"  上行消息速率 ≈ {msg_s:,.0f} 条/秒（平均）；若入库服务 1 份订阅，broker 出口同为 {msg_s:,.0f} 条/秒")
print(f"  上行带宽 ≈ {msg_s*pkt*8/1e6:.2f} Mbit/s（不含 TLS 与 TCP 开销）")
# 心跳计时在客户端每发一个报文时重置：上报周期 > 心跳间隔时，每个周期中间会多一次 PINGREQ/PINGRESP（各 2 字节）
pings_per_period = 1 if PERIOD > KEEPALIVE else 0
print(f"  心跳：上报周期 {PERIOD}s {'>' if pings_per_period else '≤'} 心跳 {KEEPALIVE}s，每周期额外 {pings_per_period} 次 PINGREQ（全网 ≈ {N/PERIOD*pings_per_period:,.0f} 次/秒）")
day = (86400/PERIOD)*(pkt + puback + pings_per_period*4)
print(f"  单块表每天遥测流量 ≈ {day/1024:.0f} KB（≈ {day*30/1024/1024:.1f} MB/月，未含 TLS 握手与重连）")
print(f"  broker 连接内存：明文 ≈ {N*MEM_PLAIN_KB/1024:,.0f} MB，TLS ≈ {N*MEM_TLS_KB/1024/1024:,.1f} GB（仅进程内，内核缓冲另计）")
for storm in (30, 300):
    print(f"  若全部电表在 {storm}s 内重连：平均 {N/storm:,.0f} 个新连接/秒（每个都要 TLS 握手 + 认证）")
```

### 4.2 方案评审时的自查问题
