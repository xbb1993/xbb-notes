# 专题 24 · MVCC：完整可见性算法

> 级别 ★ · 主线 B（衔接 A）· 实测版本：沙箱 MySQL 8.0.46

本专题回答：普通 SELECT 为什么能不等写操作就读到“该看到的”旧数据？版本存在哪里、怎么串起来？Read View 是什么、属于谁、从哪来？可见性怎么判断？RC 与 RR 在实现上差在哪？

**交互图解**：<a href="/xbb-notes/mysql-t24-mvcc.html" target="_blank">MVCC 版本链与 Read View（复现第五节实验，RR / RC 切换逐步播放，可输入任意事务 ID 判断可见性）</a>

## 一、问题：怎样让读不等写

专题 23：A 改了一行未提交，B 的普通 SELECT 立即读到旧值 1000。可选思路：

| 方案 | 做法 | 问题 |
| --- | --- | --- |
| ① 加锁 | 读之前也加锁，等 A 结束 | 读写互相阻塞（专题 3 实测加锁读等待超时） |
| ② 复制数据 | B 开始时复制整个库 | 不可行 |
| ③ 保留历史版本 + 判断规则 | 每次修改留下旧版本，读时按规则挑出该看的版本 | 即 **MVCC**（Multi-Version Concurrency Control，多版本并发控制） |

**类比：在线文档的修订历史。** 想看“昨天 3 点的样子”，不必让别人停止编辑，沿修订历史往回翻即可。MVCC 要回答两件事：历史版本存在哪、怎么串起来（**版本链**）；该看哪个版本（**Read View + 可见性规则**）。

## 二、版本链

### 2.1 每个版本带“作者”和“上一版本地址”

聚簇索引每行有两个隐藏列（8.4 手册，字节解析见专题 8）：

| 隐藏列 | 长度 | 含义 |
| --- | --- | --- |
| `DB_TRX_ID` | 6 字节 | 最后一次插入或修改该行的事务 ID —— 这个版本的**作者** |
| `DB_ROLL_PTR` | 7 字节 | 回滚指针，指向 undo log 中的记录，用它可重建修改前的内容 —— **上一个版本在哪** |

删除在内部是一次更新，只把行上的“已删除”标志置位（手册）。

### 2.2 一次 UPDATE 怎样形成版本链

Z（事务 20685）把 id=1 从 1000 改为 1111：

```
① 把修改前的内容（balance=1000 及其 DB_TRX_ID）写入 undo log
② 在聚簇索引中直接改成新值，DB_TRX_ID 写为 20685
③ DB_ROLL_PTR 指向 ① 的 undo 记录

聚簇索引（最新版本）                      undo log（旧版本）
[id=1 | 1111 | trx=20685 | roll_ptr] ──→ [1000 | trx=更早的事务 | roll_ptr] ──→ …
```

- 隐藏列在**修改时立即写入**，不等提交。所以别人读到这一行时，最新版本的作者可能是一个未提交的事务，必须判断后再决定是否往前翻。
- 表中每行只有**一个最新版本**，旧版本以“修改前的值”存于 undo，需要时还原。

| undo 类型 | 用途 | 何时可丢弃（手册） |
| --- | --- | --- |
| insert undo | 只用于回滚 | 提交后立即丢弃（插入前该行不存在，无旧版本可看） |
| update undo（修改、删除） | 回滚 + **快照读** | 没有任何快照还可能需要它时（第六节） |

::: danger 错误理解 vs 正确理解
- ❌ MVCC 给每个事务复制一份数据。
- ✅ 表里每行只有最新版本，旧版本在 undo 中，沿回滚指针按需还原。
:::

## 三、Read View：逐层推出来

### 3.1 第 1 层：要回答的问题

读一行时面对多个版本，每个版本只带一条身份信息：作者（`DB_TRX_ID`）。按专题 23 的规则“拍照那一刻已提交的修改才能看到”，对每个版本只需回答：

> **这个版本的作者，在我拍照那一刻提交了没有？**

### 3.2 第 2 层：拍照时要记什么

事务 ID 像叫号机一样递增发放。拍照那一刻，所有事务按号码分三类：

```
号码：   … 20600 … 20681 │ 20682 │ 20683  20684 │ 20685  20686  20687 …
状态：   早就提交了       │ 未提交 │ 已提交        │ 号码还没发出（还没开始）
                                                 ↑ 下一个要发的号
```

| 方案 | 记什么 | 问题 |
| --- | --- | --- |
| ① | 所有已提交的号 | 可能几百万个 |
| ② | **当时未提交的号**（通常很少）+ **下一个要发的号** | 只需几个数 |

方案 ② 足以给任意号码分类：≥ 下一个号 → 拍照时还没开始；在未提交名单中 → 正在进行；其余 → 已提交。**这份记录就是 Read View（读视图）**——“拍快照”拍的是名单，不是数据。

### 3.3 第 3 层：定义与格式

| 字段（源码 `read0types.h`） | 叫法 | 内容 | 能否由其他信息推出 |
| --- | --- | --- | --- |
| `m_ids` | 活跃名单 | 拍照时未提交的读写事务号，不含自己 | — |
| `m_low_limit_id` | **高水位** | 拍照时下一个要发的号（源码注释：high water mark，≥ 它的不可见） | **不能**：来自全局计数器，名单中没有此信息 |
| `m_up_limit_id` | **低水位** | 名单中最小的号；名单为空时等于高水位（源码注释：low water mark，< 它的全部可见） | 能：单独存放是为了先比一次就判定可见，并处理名单为空的情况 |
| `m_creator_trx_id` | 创建者 | 自己的事务号；未写过数据时为 0 | 第 3.6 节 |

**高水位为什么不能用“名单最大号 + 1”代替**：实验中名单为 [20682]，若高水位取 20683，则已在拍照前提交的 W（20683）会被判为“拍照后才开始”而不可见。最大未提交号之后可能还有已开始并已提交的事务，只看名单不知道号码发到了哪里。

::: warning 源码命名的坑
`m_low_limit_id` 是**高**水位，`m_up_limit_id` 是**低**水位，名字与含义相反，以源码注释为准。本文统一称“高水位 / 低水位”。
:::

### 3.4 第 4 层：归属、来源与生命周期

**每个事务（RC 下是每条语句）私有一份**，内容复制自全局名单：

```
              全局（实例中只有一份，实时变化）
      ┌──────────────────────────────────────────────┐
      │ trx_sys->rw_trx_ids：当前所有未提交的读写事务号 │
      │ trx_sys->next_trx_id_or_no：下一个要发的号      │
      └──────────────────────────────────────────────┘
                 │ 拍照：复制                │ 拍照：复制
                 ▼                           ▼
       ┌───────────────────┐        ┌───────────────────┐
       │ B 的 Read View     │        │ C 的 Read View     │   私有，拍完不再变
       └───────────────────┘        └───────────────────┘
```

| 环节 | 内容（源码） |
| --- | --- |
| 全局名单加入 | 事务第一次写、拿到事务号时 `rw_trx_ids.push_back(trx->id)`（`trx_set_rw_mode()`） |
| 全局名单移除 | 提交时 `trx_erase_lists()`；回滚结束后同样移除。只含读写事务——只读事务不产生版本，判断用不到 |
| 拍照 | `ReadView::prepare()`：高水位 = 全局下一个号；名单 = 复制全局名单去掉自己；低水位 = 名单最小号 |
| 何时拍 | RR：事务中第一次快照读（`WITH CONSISTENT SNAPSHOT` 则在开启事务时）；RC：每条快照读语句开始时 |
| 何时丢弃 | RR：事务结束；RC：语句结束 |
| 存放 | 事务的内存对象，大小只取决于当时未提交事务的数量，与表行数无关；不写磁盘、不存于行中 |
| 用途 | 只供**快照读**使用；当前读直接读最新版本 |

**拷贝冻结是故意的**：拍照后 Y 提交，全局名单删除 Y，但 B 的拷贝仍保留 Y，B 继续视 Y 为“拍照时未提交”。若拷贝随之删除，B 下一次读就会看到 Y 的修改——即不可重复读。

**事务 ID 不连续**：`next_trx_id_or_no` 的源码注释为“尚未被分配为事务 ID 或事务序号的最小数字”——提交时还要从同一计数器取一个提交序号（purge 据此排序），所以每次提交多消耗一个号。

### 3.5 第 5 层：判断对象与配合方式

- **被判断的**：版本上的 `DB_TRX_ID`（作者）。
- **拿什么判断**：读取方（当前事务）手中的 Read View。
- **判断结果**：描述的是**作者**在**读取方拍照那一刻**的状态。

| 角色 | 位置 | 回答的问题 |
| --- | --- | --- |
| `DB_TRX_ID` | 每个版本上 | 这个版本是谁写的 |
| Read View | 读取方事务中 | 这个作者在我拍照时提交了吗 |
| `DB_ROLL_PTR` | 每个版本上 | 不能看的话，上一个版本在哪 |

```
取这一行的最新版本
      │
      ▼
读 DB_TRX_ID（作者）──→ 用 Read View 判断：作者在拍照时已提交（或就是我）？
                              │是                       │否
                              ▼                         ▼
                   返回这个版本的数据         沿 DB_ROLL_PTR 去 undo 还原上一个版本
                                                        │
                                                        └──→ 回到“读 DB_TRX_ID”
翻到头也没有可见版本 → 该行是拍照后才插入的，对当前事务不存在
```

源码 `row_vers_build_for_consistent_read()`：当前版本不可见时，`trx_undo_prev_version_build()` 按回滚指针在内存中还原上一个版本，再用 `changes_visible()` 判断，可见即复制返回。每往前一步都要读一条 undo 并构造一次行。

### 3.6 第 6 层：判断规则（源码 `changes_visible()`）

```
① 作者 = 我自己（创建者）    → 可见
② 作者 < 低水位              → 可见   （拍照前就提交了）
③ 作者 ≥ 高水位              → 不可见 （拍照后才开始）
④ 作者在活跃名单中            → 不可见 （拍照时未提交）
⑤ 其余                       → 可见   （拍照前已提交）
```

**为什么需要规则 ①**：B 第一次写时才拿到号（实验中 20687），它可能大于自己的高水位（20685），按 ③ 连自己写的数据都看不到。源码 `trx_set_rw_mode()` 在事务第一次写时把新号码填入其 Read View 的创建者，注释原文：“So that we can see our own changes.”

::: danger 错误理解 vs 正确理解
- ❌ “RR 下能看到所有 ID 比自己小的事务的修改。” Y（20682）比 B 小，但拍照时在名单中，B 始终看不到，即使 Y 后来提交。
- ❌ “按提交时间判断。” 算法中没有时间戳，只有事务号与名单。W（20683）号码比 Y 大却可见，因为拍照时已不在名单中。
- ❌ “往前翻到作者已提交的版本就返回。” 标准是“作者在**拍照那一刻**已提交”：拍照后才提交的作者，其版本仍不可见。
- ✅ 一句话：拍照那一刻已提交的修改可见；拍照时未提交的、拍照后才开始的都不可见；自己的修改总是可见。
:::

### 3.7 第 7 层：隔离级别怎样控制可见性

**判断规则对所有级别相同，不同的只是用哪一张照片：**

```
时间 ──────────────────────────────────────────────────────────────────────▶
         B: SELECT①        Z 提交(20685)     B: SELECT②       Y 提交      B: SELECT③
RR：     [拍照] 名单[20682] 高 20685 ─────── 整个事务一直用这一张 ─────────────────▶
RC：     [拍照]                             [重新拍照]                    [重新拍照]
         名单[20682] 高 20685               名单[20682] 高 20687          名单[] 高 20689
```

| 级别 | 普通 SELECT 如何使用 Read View | 效果 |
| --- | --- | --- |
| READ UNCOMMITTED | 不使用，直接读最新版本 | 脏读 |
| READ COMMITTED | 每条语句开始时新建，语句结束丢弃 | 看到语句开始时已提交的数据 |
| REPEATABLE READ | 事务中第一次读时建立，用到事务结束 | 整个事务看到同一时间点 |
| SERIALIZABLE | 关闭自动提交时普通 SELECT 变为加锁读，不走快照 | 靠锁保证 |

## 四、实验：四种情况一次看全

### 4.1 设计与真实输出

`t_acct` 4 行，余额均为 1000，按顺序执行（B 为 RR）：

```
Y: BEGIN; UPDATE id=2 -> 2000（不提交）            trx_id=20682
W: BEGIN; UPDATE id=3 -> 3000; COMMIT              trx_id=20683（提交又消耗 20684）
B: BEGIN; 第一次 SELECT（创建 Read View）           -> (1,1000) (2,1000) (3,3000) (4,1000)
Z: BEGIN; UPDATE id=1 -> 1111; COMMIT              trx_id=20685（提交又消耗 20686）
B: 第二次 SELECT                                   -> (1,1000) (2,1000) (3,3000) (4,1000)
B: UPDATE id=4 -> 4444                             B 的 trx_id=20687
   SHOW ENGINE INNODB STATUS：Trx id counter 20688
                              Trx read view will not see trx with id >= 20685, sees < 20682
B: 第三次 SELECT                                   -> (1,1000) (2,1000) (3,3000) (4,4444)
Y: COMMIT
B: 第四次 SELECT                                   -> (1,1000) (2,1000) (3,3000) (4,4444)
```

`Trx read view will not see trx with id >= 20685, sees < 20682` 即高水位 20685、低水位 20682。这一行要在事务第一次写之后才显示（只读阶段不显示），数值在创建时已确定。

### 4.2 逐行推演 B 的第二次 SELECT

Read View：名单 [20682]，低水位 20682，高水位 20685，创建者 0。

| 行 | 版本链（新 → 旧） | 判断 | 结果 |
| --- | --- | --- | --- |
| id=3 | 3000 (20683) → 1000 | 20683 不 ≥ 20685，不在名单 → 拍照前已提交（规则 ⑤） | **3000** |
| id=2 | 2000 (20682，未提交) → 1000 | 在名单 → 不可见（④）→ 前一版本 < 低水位（②） | **1000** |
| id=1 | 1111 (20685) → 1000 | ≥ 高水位 → 拍照后才开始（③）→ 前一版本可见（②） | **1000** |
| id=4 | 1000 | < 低水位（②） | **1000** |

第三次 SELECT 中 id=4 的 4444：作者 20687 ≥ 高水位，但规则 ① 先判定为自己 → 可见。

### 4.3 同样步骤，B 为 RC

```
B 第一次 SELECT   -> (1,1000) (2,1000) (3,3000) (4,1000)
Z 提交
B 第二次 SELECT   -> (1,1111) (2,1000) (3,3000) (4,1000)    ← 新 Read View 高水位 20687，Z 可见
B UPDATE id=4
B 第三次 SELECT   -> (1,1111) (2,1000) (3,3000) (4,4444)
Y 提交
B 第四次 SELECT   -> (1,1111) (2,2000) (3,3000) (4,4444)    ← 新 Read View 名单为空，Y 可见
```

RC 各次 Read View 的数值按源码规则推算，结果与实测一致。

## 五、版本链的代价

B 以 `START TRANSACTION WITH CONSISTENT SNAPSHOT` 开启并保持，A 对 id=1 连续自动提交 UPDATE；每阶段 B（旧快照）与新连接各读 5 次取最快值：

| A 已提交更新次数 | B 旧快照读到 | B 耗时 | 新连接读到 | 新连接耗时 | history_len |
| --- | --- | --- | --- | --- | --- |
| 0 | 1000 | 0.091 ms | — | — | 48 |
| 1,000 | 1000 | 0.480 ms | 2000 | 0.097 ms | 1,000 |
| 10,000 | 1000 | 4.052 ms | 11000 | 0.087 ms | 10,000 |
| 100,000 | 1000 | **48.864 ms** | 101000 | 0.084 ms | 100,000 |

B 提交 5 秒后 history_len 降为 0。

```
[101000|最新] → [100999] → … 10 万个版本 … → [1000|B 可见]
 ↑ 新连接：第一个就可见                      ↑ B：逐个判断约 10 万次
```

旧快照读的耗时与链长成正比（约每 1000 个版本 0.5 ms）。实验时临时把 `innodb_flush_log_at_trx_commit` 设为 2 以加快更新，结束后恢复为 1，不影响链长。

## 六、purge：旧版本何时能删

**purge**：后台清理不再被需要的 update undo，并物理删除带删除标志的行（手册：删除时只打标记）。

Read View 还有字段 `m_low_limit_no`，源码注释含义：提交序号严格小于它的事务，该 Read View 不需要其 undo，若其他 Read View 也不需要，即可被 purge 删除。因此 **purge 进度取决于最老的 Read View**。专题 23 实验中 history_len 停在 5000，即因 B 的 Read View 最老。手册建议**定期提交事务，包括只做快照读的事务**，否则 undo 无法清理，回滚段可能撑满 undo 表空间。

::: danger 错误理解 vs 正确理解
- ❌ 只读事务不改数据，开多久都没关系。
- ✅ 只读事务同样持有 Read View、挡住 purge。上例中只读的 B 让 10 万个旧版本无法清理，自己的查询也慢了约 500 倍。
:::

## 七、二级索引上的 MVCC（手册说明）

二级索引记录**没有** `DB_TRX_ID` 与回滚指针，无法直接判断可见性：

- 更新二级索引列时，旧记录打删除标记，再插入新记录。
- 二级索引记录带删除标记，或其所在页**被比读取事务更新的事务修改过**，InnoDB 回到聚簇索引用 `DB_TRX_ID` 与版本链判断。
- 此时**覆盖索引失效**（即使所需列都在二级索引中也要回表）；开启 ICP（专题 11）时，可用索引列判断的条件仍先在索引上过滤，无匹配则不回表。

工程含义：高并发修改的表上，覆盖索引收益可能打折扣。沙箱难以稳定复现，此处只引用手册。

## 八、在三条主线中的位置

```
B 一致性：事务 → [MVCC：版本链 + Read View] → undo → 锁 → redo → …
A 性能：版本链越长，旧快照读越慢；覆盖索引在并发修改下可能失效
C 诊断：history list length、长事务（含只读事务）、SHOW ENGINE INNODB STATUS 中的 read view 行
```

## 九、诊断实践

### 9.1 观察入口

| 看什么 | 查询 | 说明 |
| --- | --- | --- |
| 旧版本堆积 | `SELECT COUNT FROM information_schema.INNODB_METRICS WHERE NAME = 'trx_rseg_history_len'`，或 INNODB STATUS 的 `History list length` | 持续增长不回落 → 有老 Read View 挡住 purge |
| 谁挡住了 purge | `innodb_trx` 按 `trx_started` 排序 | 最老的事务（包括只读事务） |
| 某事务的 Read View | `SHOW ENGINE INNODB STATUS` 的 TRANSACTIONS 段 `Trx read view will not see trx with id >= …, sees < …` | 只对已写过数据的事务显示 |
| purge 进度 | INNODB STATUS 的 `Purge done for trx's n:o < …` | 与最老 Read View 对照 |

### 9.2 病例

| 病例 | 现象 | 定位 | 处置 |
| --- | --- | --- | --- |
| 某些查询越来越慢，表数据量没变 | history_len 持续增长；同一查询新连接快、某些连接慢 | 存在长时间未结束的事务，旧快照沿长版本链回溯 | 结束长事务；应用及时提交；只读报表避免长时间持有事务 |
| undo 表空间持续增长 | 磁盘占用上升 | 同上，purge 被挡住 | 同上（undo 管理见专题 31） |
| 报表与线上数据对不上 | 报表读的是旧快照 | RR 下报表事务开得太早或持续太久 | 明确快照时点，用完即提交 |

## 十、本地复现（Docker mysql:8.4，四个客户端窗口 Y、W、Z、B）

```sql
USE lab;
DROP TABLE IF EXISTS t_acct;
CREATE TABLE t_acct (id INT PRIMARY KEY, name VARCHAR(10) NOT NULL, balance INT NOT NULL);
INSERT INTO t_acct VALUES (1,'A',1000),(2,'B',1000),(3,'C',1000),(4,'D',1000);

-- 查看本事务的事务号（写过数据后）
SELECT trx_id FROM information_schema.innodb_trx WHERE trx_mysql_thread_id = CONNECTION_ID();

-- Y：BEGIN; UPDATE t_acct SET balance = 2000 WHERE id = 2;           -- 不提交
-- W：BEGIN; UPDATE t_acct SET balance = 3000 WHERE id = 3; COMMIT;
-- B：BEGIN; SELECT * FROM t_acct;                                    -- 创建 Read View
-- Z：BEGIN; UPDATE t_acct SET balance = 1111 WHERE id = 1; COMMIT;
-- B：SELECT * FROM t_acct;
-- B：UPDATE t_acct SET balance = 4444 WHERE id = 4;
-- 任一窗口：SHOW ENGINE INNODB STATUS\G   -- TRANSACTIONS 段找 B 的 "Trx read view will not see ..."
-- B：SELECT * FROM t_acct;
-- Y：COMMIT;
-- B：SELECT * FROM t_acct; ROLLBACK;
-- 把 B 改为 SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED 再做一遍

-- 版本链代价：B 执行 START TRANSACTION WITH CONSISTENT SNAPSHOT; SELECT balance FROM t_acct WHERE id = 1;
-- 另一窗口循环几万次 UPDATE t_acct SET balance = balance + 1 WHERE id = 1;（每次自动提交，可用脚本）
-- B 再查并对比耗时；查看 trx_rseg_history_len；B 提交后再看
```

**预期现象**：RR 下 B 四次结果依次为 `(1,1000)(2,1000)(3,3000)(4,1000)` 两次，然后 `(4,4444)` 两次；RC 下第二次看到 1111、第四次看到 2000。事务号数值会不同，但高水位、低水位与各事务号的大小关系应与上文一致。版本链越长 B 越慢，B 提交后 history_len 回落。

::: tip PG 对照
PG 的快照（`pg_current_snapshot()` 的 xmin、xmax、xip）与 Read View 几乎一一对应：xmin ≈ 低水位，xmax ≈ 高水位，xip ≈ 活跃名单。区别在旧版本的存放位置：PG 新旧版本都在表（heap）中，每个版本带 xmin / xmax，由 VACUUM 清理，表会膨胀但读旧版本无需回溯；InnoDB 表中只有最新版本，旧版本在 undo，由 purge 清理，表不膨胀但长事务读旧版本要沿链回溯。两边的长事务都会阻止清理。
:::

## 十一、串联图

```
① 修改时：DB_TRX_ID = 自己的号，旧值写 undo，DB_ROLL_PTR 指向它 → 版本链
② 全局名单（实时：第一次写加入，提交 / 回滚结束移除）
        │ 拍照（RR：第一次快照读；RC：每条快照读）
        ▼
③ 私有 Read View（冻结）：名单、低水位、高水位、创建者
        │
④ 快照读一行：取最新版本的 DB_TRX_ID → 按 5 条规则判断
        ├─ 可见 → 返回该版本
        └─ 不可见 → 沿 DB_ROLL_PTR 还原上一版本 → 再判断
⑤ purge：最老的 Read View 不再需要的旧版本才能删除 → 长事务让链变长、查询变慢
```
