# 专题 51–53 · 可扩展性、数据分片、应用层优化与缓存（合并）

> 级别：51 ☆ / 52 ☆ / 53 ☆ · 主线 A / B · 实测环境：沙箱两个空 MySQL 8.0.46 实例 sh0（3320）、sh1（3321）充当分片

## 一、可扩展性（专题 51）

| | 垂直扩展（scale up） | 水平扩展（scale out） |
| --- | --- | --- |
| 做法 | 换更大的机器 | 加机器分摊负载 |
| 优点 | 应用零改动，无分布式问题 | 理论无上限 |
| 缺点 | 物理上限，价格非线性；**解决不了单行热点**（49） | 路由、一致性、跨节点查询、运维复杂度 |

**原则**：能垂直就先垂直；分布式复杂度是长期成本，有数据证明到了天花板（模块九）再引入。

```
读扩展（较易）：SQL / 索引优化 → 从库读写分离（40，处理写后读）→ 缓存（53）
写扩展（困难，只能在主库写）：减少写入量（批量 / 合并 / 异步）→ 垂直拆分（按业务分库）→ 水平分片（按行拆表）
```

```
垂直拆分：[订单库] [用户库] [商品库]                          ← 不同的表放不同实例
水平分片：[订单库-0: user_id 偶数] [订单库-1: user_id 奇数]   ← 同一张表的不同行放不同实例
```

垂直拆分常是微服务拆分的自然结果（架构师笔记第 15 章"每个服务自己的数据库"），代价是跨业务 JOIN 与事务消失；单个业务表仍太大、写仍太多时才水平分片。

## 二、数据分片（专题 52）

### 2.1 五个问题

```
① 一行放哪个库？           → 分片键 + 路由规则
② 主键怎么不重复？         → 全局 ID
③ 查询不带分片键？         → 广播 / 映射表 / 分片信息编进 ID
④ 排序、分页、聚合？       → 各片分别算，应用层合并
⑤ 不够了怎么扩？           → 迁移；逻辑槽
```

### 2.2 全局 ID（真实输出）

```
各分片自增：shard0 ids: 1,2,3   shard1 ids: 1,2,3        ← 撞号
步长：auto_increment_increment=2，offset 1 / 2：shard0 1,3,5   shard1 2,4,6
雪花式（64 位 = 41 位毫秒时间戳 | 10 位机器号 | 12 位序列号，应用生成）：
  118526355909382144  -> ms_since_epoch=28258885362, worker=1, seq=0
  118526355909382145  -> ms_since_epoch=28258885362, worker=1, seq=1
  118526355909386243  -> ms_since_epoch=28258885362, worker=2, seq=3
  （演示脚本两个 worker 共用序列计数器；真实实现每个 worker 各自计数）
```

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 自增步长 | 简单，仍是数据库自增 | 步长定死，加分片要重规划 offset |
| 雪花算法 | 不依赖数据库；大致按时间递增，对 B+ 树插入友好（10） | 依赖时钟，回拨会重复 / 乱序；机器号统一分配 |
| 号段模式 | 每次从发号表领一段在内存用 | 需发号服务；重启浪费号段 |
| UUID | 无需协调 | 无序、≥16 字节，页分裂严重（10），不宜做 InnoDB 主键 |

### 2.3 路由与分片键（真实输出，按 `user_id % 2` 写 2 万订单）

```
shard0 rows: 10064    shard1 rows: 9936
带分片键 user_id=1234 → 只查 shard0：3  1832.14  (7 ms, 1 次往返)
不带分片键 order_id=118526356102320636 → 只能广播：shard0 ''   shard1 '387  900.21'
```

| 分片键原则 | 说明 |
| --- | --- |
| 覆盖最高频查询 | "查我的订单"最频繁 → 按 `user_id` |
| 分布均匀 | 避免大商家等热点 |
| 尽量不跨片 | 同一用户数据在一起，事务也不跨库 |

不带分片键：① **基因法**——把 `user_id % 分片数` 编进 `order_id`；② **映射表** `order_id → user_id`；③ **异构索引**——按另一维度另存一份（常订阅 binlog，32）。

### 2.4 跨分片排序分页与聚合（真实输出）

```
全局按 created_at 倒序第 1000 页（每页 10，偏移 9990）：
  shard0 返回 10000 行   shard1 返回 9936 行（每片必须取前 offset+limit = 10000 行）
  合并 19936 行取第 9991–10000 行，只用 10 行；34 ms
  结果 == 全量排序后的第 9991–10000 行：True
  错误做法（每片各取第 500 页再合并）：False

聚合（amount > 900）：
  shard0 AVG=949.1160 SUM=981385.96 COUNT=1034
  shard1 AVG=949.4222 SUM=903849.89 COUNT=952
  错误 (AVG0+AVG1)/2 = 949.2691
  正确 (SUM0+SUM1)/(COUNT0+COUNT1) = 949.2628
```

- 事先不知全局第 9991 名在哪片，最坏全局前 10000 条都在同一片 → 代价 **分片数 × (offset + limit)** → 改游标分页 `WHERE created_at < 上一页最后值`（19），每片只返回 limit 行。
- COUNT / SUM / MAX / MIN 可直接合并；AVG 拆 SUM + COUNT；COUNT(DISTINCT)、中位数需更多数据。

### 2.5 扩容迁移（真实输出，10 万个 user_id）

```
取模 2 → 3 台：66.7%
取模 2 → 4 台：50.0%（翻倍是取模方案的最好情况）
1024 个逻辑槽 2 → 3 台（新机器从两台各接走 1/3 槽）：33.3%
```

**逻辑槽（预分片）**：`hash % 1024` 分到逻辑槽，映射表把槽分配给物理库；扩容只搬整槽、改映射表，接手多少槽搬多少数据，不必翻倍。≈ Redis Cluster 16384 哈希槽：<a href="/xbb-notes/redis/ch17-cluster.html" target="_blank">Redis 第 17 章 集群</a>。

### 2.6 路由由谁做

| 形态 | 做法 | 代表 | 取舍 |
| --- | --- | --- | --- |
| 客户端内嵌 | 应用内的库改写 SQL、路由、合并 | ShardingSphere-JDBC | 无额外网络跳；与语言绑定，各应用都要升级 |
| 代理 | 应用连一个"像 MySQL"的代理 | ShardingSphere-Proxy、Vitess | 对应用透明、跨语言；多一跳，代理需高可用 |

> **错误 vs 正确**
> - ❌ 用了分片中间件就像在用无限大的单机 MySQL。
> - ✅ 写法一样，代价不变：无分片键 → 广播；深分页代价随分片数倍增；跨片 JOIN 很贵或不支持；跨片事务需分布式事务（54）。成败取决于分片键能否让 90% 以上查询落在单片。

## 三、应用层优化与缓存（专题 53）

### 3.1 批量写入（真实输出，同一连接 5000 行，双 1）

```
① 逐行 INSERT + autocommit（5000 次提交）：            3.37s
② 逐行 INSERT，1 个事务（1 次提交）：                  0.51s
③ 每条 INSERT 500 行，1 个事务（10 条语句、1 次提交）： 0.02s
```

- ① → ② 省**提交次数**（每次提交刷 redo + binlog，29、32、44）。
- ② → ③ 省**语句次数**（每条一次往返 + 解析 / 优化 / 执行固定开销，2、3）。
- 边界：事务过大 → 复制延迟（40）、长持锁、undo 膨胀（31、50）；实践每批几百到几千行。

### 3.2 异步化

不需立即落库的写入（日志、计数、通知）进消息队列，消费者批量写库：削峰、合并写入；代价是延迟变大，需处理丢失与重复（消费者**幂等**）。

### 3.3 旁路缓存写侧的一致性

读侧（查缓存 → 未命中查库回填；穿透 / 击穿 / 雪崩）见 <a href="/xbb-notes/redis/m5-03-cache-problems.html" target="_blank">Redis 模块五 · 缓存问题</a>。写侧竞态（dict 模拟 Redis，数据库为真实 MySQL，人为交错，真实输出）：

```
场景 A：先更新数据库，再删缓存 —— 读写交错
  R: 缓存未命中，读数据库得到 'old'（未及写缓存，被调度走）
  W: 更新数据库为 'new'
  W: 删除缓存 → cache={}
  R: 把读到的值写进缓存 → cache={'user:1': 'old'}
  结果：数据库='new'，缓存='old' → 不一致，直到 TTL
  延迟双删：W 0.5s 后再删一次 → cache={}，下次回源得到 'new'

场景 B：更新数据库后"更新缓存" —— 两个写者交错
  W1: 数据库=v1   W2: 数据库=v2
  W2: 写缓存 → v2   W1: 写缓存（晚到）→ v1
  结果：数据库='v2'，缓存='v1' → 不一致
```

| 方案 | 问题 | 评价 |
| --- | --- | --- |
| 先删缓存再更新库 | 删后库未更新时读请求回填旧值，**很易发生** | 不推荐 |
| 先更新库再更新缓存 | 场景 B：写者顺序在库与缓存中可能相反；写入大量无人读的缓存 | 不推荐 |
| **先更新库再删缓存** | 场景 A：需特定交错才触发，概率低但存在 | **常用默认** |
| + 延迟双删 | 隔一段时间再删，清掉回填的旧值 | 延迟只能估算（> 一次读库 + 回填） |
| + 订阅 binlog 删缓存 | Canal 类工具订阅 ROW binlog（32），独立进程删缓存，失败可重试 | 不依赖业务代码，最可靠；链路更长 |
| 一律 TTL | 不一致最多持续一个 TTL | 兜底，所有方案都加 |

> **错误 vs 正确**
> - ❌ 顺序选对了就强一致。
> - ✅ 缓存与数据库无共同事务，只能**最终一致**，TTL 兜底；余额、库存最终扣减等直接读库或缓存仅作展示。

**叠加读写分离的坑**：删缓存后回源若读**从库**，可能读到复制延迟期间的旧值再写回缓存（40）→ 回源读主库，或 binlog 驱动删除并在延迟窗口后再删一次。

## 四、串联图

```
可扩展性（51）：先垂直；读靠从库与缓存，写靠减少写入 → 垂直拆分 → 水平分片
数据分片（52）：
  分片键：覆盖高频查询、均匀、少跨片
  全局 ID：步长 / 雪花 / 号段（UUID 不宜做 InnoDB 主键）
  无分片键：广播 / 基因法 / 映射表 / 异构索引（binlog）
  跨片分页：每片取 offset+limit → 游标分页；AVG 拆 SUM 与 COUNT
  扩容：取模迁移量大 → 逻辑槽（≈ Redis 16384 槽）
应用层（53）：
  批量写：省提交次数（fsync）与语句次数（往返）；事务别过大
  异步化：削峰、合并，消费者幂等
  缓存一致性：先更新库再删缓存 + 延迟双删 / binlog 删除 + TTL；只能最终一致
```

## 五、诊断与设计检查单

```
□ 单机是否真的到顶？（模块九：CPU / I/O / 锁 / 连接 / 热点行，哪一项？）
□ 读瓶颈 → 从库 + 缓存；写瓶颈 → 先批量 / 异步，再拆分
□ 分片键是否覆盖 90% 以上查询？剩余查询用基因法 / 映射表 / 异构索引？
□ 全局 ID 方案是否有序、不依赖单点、能应对时钟回拨？
□ 有无深分页、跨片 JOIN、跨片事务？各自替代方案？
□ 扩容方案：逻辑槽数量与映射表在哪里维护？迁移期间双写或停写？
□ 缓存：写侧顺序、延迟双删或 binlog 删除、TTL、回源读主库还是从库？
```

## 六、本地复现（Docker mysql:8.4）

```bash
export MYSQL_PWD='<自己设置>'
for i in 0 1; do docker run -d --name sh$i -p 330$((6+i)):3306 -e MYSQL_ROOT_PASSWORD="$MYSQL_PWD" mysql:8.4; done
sleep 30
q(){ mysql -h127.0.0.1 -P$1 -uroot -N -e "$2"; }   # 3306 = sh0，3307 = sh1

# 52-1 全局 ID：自增撞号 vs 步长
for p in 3306 3307; do q $p "CREATE DATABASE idtest; CREATE TABLE idtest.t(id BIGINT AUTO_INCREMENT PRIMARY KEY, v INT); INSERT INTO idtest.t(v) VALUES (1),(2),(3); SELECT GROUP_CONCAT(id) FROM idtest.t"; done
q 3306 "TRUNCATE idtest.t; SET SESSION auto_increment_increment=2; SET SESSION auto_increment_offset=1; INSERT INTO idtest.t(v) VALUES (1),(2),(3); SELECT GROUP_CONCAT(id) FROM idtest.t"
q 3307 "TRUNCATE idtest.t; SET SESSION auto_increment_increment=2; SET SESSION auto_increment_offset=2; INSERT INTO idtest.t(v) VALUES (1),(2),(3); SELECT GROUP_CONCAT(id) FROM idtest.t"

# 52-2 路由、广播、跨分片分页与聚合：任意语言写小路由器（按 user_id % 2 选端口），
#      复现"带分片键查 1 片 / 无分片键广播 / 每片取 offset+limit 再合并 / AVG 用 SUM÷COUNT"

# 52-3 扩容迁移量（纯计算）
python3 -c "
U=range(1,100001); mv=lambda f,g: sum(f(u)!=g(u) for u in U)/len(U)*100
print('mod 2->3', mv(lambda u:u%2, lambda u:u%3)); print('mod 2->4', mv(lambda u:u%2, lambda u:u%4))
S=1024; old=lambda u: 0 if u%S<512 else 1; new=lambda u: 2 if (341<=u%S<512 or 853<=u%S) else old(u)
print('slots 2->3', mv(old,new))"

# 53-1 批量写入：同一连接 5000 次 autocommit INSERT / 1 个事务 5000 条 / 1 个事务 10 条 500 行 INSERT，对比耗时
```

**预期现象**：撞号与步长结果同沙箱；迁移比例 66.7% / 50.0% / 33.3%（纯计算）；三种写入耗时依次下降约一个量级，倍数取决于本地磁盘 fsync 速度。

::: tip 与 Redis、PG、架构师笔记对照
- **Redis Cluster**：16384 槽 = 逻辑槽预分片；`MOVED` ≈ 客户端路由；Redis 集群内置槽迁移，MySQL 分片靠中间件或自研工具。
