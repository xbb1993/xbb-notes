复制链路与半同步

MySQL 专题 39、40、42 配套。一个事务 UPDATE t_acct SET balance = balance - 100 WHERE id = 1（1000 → 900，GTID 记为 …:101）从主库提交到从库生效的全过程。切换三种复制方式，逐步前进，看每一步：客户端是否已收到成功、主库其他会话看到什么、从库收到 / 执行到哪，以及如果主库此刻宕机并切换到从库，这笔事务会不会丢。

复制方式

主库 source（server_id=1）

事务执行：改 Buffer Pool 页，写 undo、redo（log buffer）
redo prepare（刷盘）
binlog 写入并刷盘（含 GTID）
redo commit：事务在引擎内提交，其他会话可见
返回客户端“提交成功”
Binlog Dump 线程：读 binlog，推给从库
binlog event →← ACK网络

从库 replica（server_id=2）

接收线程（replica_io）：收 event
relay log：写入本地中继日志 → Retrieved_Gtid_Set
协调线程（replica_sql）：读 relay log，按 last_committed 分发
worker 线程 ×4：回放并提交 → Executed_Gtid_Set

此刻的状态

假如主库此刻宕机，切换到从库当新主库

半同步还有一个前提：主库等 ACK 最多 rpl_semi_sync_source_timeout（默认 10000 毫秒）。超时后自动退化为异步，此后的事务回到“异步”模式的风险，直到从库追上重新 ACK。沙箱实测：超时设 3000 毫秒时，第一笔提交耗时 3007 ms，随后状态变为 OFF，后续提交 7 ms。
