# 第2章 简单动态字符串（SDS）

## 核心概念

**结构定义**

```c
struct sdshdr {
    int len;    // buf 中已使用字节数，即字符串长度
    int free;   // buf 中未使用字节数
    char buf[]; // 实际保存内容的字节数组
};
```

**相比 C 字符串的五个优势，以及各自的实现机制**

- **O(1) 获取长度**：直接读 `len`，不需要像 C 字符串那样遍历到 `\0`。`STRLEN` 命令因此是常数复杂度。
- **杜绝缓冲区溢出**：SDS 的修改类 API（如 `sdscat`）在执行前会先检查 `free` 是否够用，不够就自动扩容。前提是必须通过 SDS API 操作——绕开 API 直接改 `buf` 数组，保护同样失效。
- **减少内存重分配次数**，靠两个策略实现：
  - *空间预分配*（应对变长）：修改后 `len < 1MB` 时，额外分配和 `len` 等大的 `free`（即 `free = len`）；`len >= 1MB` 时，只额外多分配固定 **1MB**，不再翻倍。
  - *惰性空间释放*（应对变短）：字符串变短时不立即 `realloc` 回收多余空间，而是记入 `free`，留给未来可能的增长操作复用。
- **二进制安全**：用 `len` 而不是 `\0` 判断字符串结束，`buf` 是纯字节数组，不对内容做任何解释和过滤，因此能安全保存任意二进制数据（图片、序列化数据等）。
- **兼容部分 C 字符串函数**：SDS 仍然遵循 `\0` 结尾的惯例（这一字节不计入 `len`），使得像 `strcasecmp`、`printf("%s", ...)` 这类 `<string.h>` 函数可以直接复用，不用重新造轮子。二进制安全和这一条并不矛盾——判断结束靠 `len`，`\0` 只是额外多留的一个字节，给愿意用的场景用。

**SDS 的应用范围**：不仅是字符串对象的底层实现之一，也被 Redis 当作通用的动态字节缓冲区使用，例如 AOF 缓冲区（第11章）、客户端输入/输出缓冲区（第13章）都是用 SDS 实现的。

## 易混淆/易错点

- **`STRLEN` ≠ 实际内存占用**：`STRLEN` 反映的是 `len`（逻辑长度），不包含 `free`、SDS 头部开销、以及底层内存分配器（如 jemalloc）的对齐开销。排查"某个 key 内存异常大"时应该用 `MEMORY USAGE key`，而不是 `STRLEN`。
- **预分配"虚胖"的高发区间**：反复小幅 `APPEND` 使字符串长度在几百 KB 到 1MB 附近震荡时，实际内存占用可能接近内容长度的两倍（因为 `free = len`）；超过 1MB 门槛后，由于每次只多分配固定 1MB，浪费比例会随字符串变大而趋近于 0。真正需要警惕的是"停在 1MB 门槛以内反复变化"的场景。
- **惰性释放不等于永久不释放**：如果确定一个字符串键不会再增长，可以用 `GET` 再 `SET` 回去，相当于重新分配一个恰好等长的新 SDS，甩掉多余的 `free` 空间。但客户端查询缓冲区、AOF 缓冲区这类系统级缓冲区的回收，靠的是各自模块的定期收缩机制（第11、13章），不是 SDS 层面自动处理的。
- **不同环节的 SDS 是彼此独立、各自分配的对象，靠复制传递数据，不共享内存**：一条写命令的生命周期里，至少经过「客户端输入缓冲区 SDS → 命令参数对象 SDS → 数据库 value（及可能的 AOF 缓冲区、输出缓冲区）」这几站，每一站都是独立分配的内存，各自管理自己的扩容/回收，不是同一个对象在流转。因此数据库里某个 key 被删除，和某个客户端连接的输入缓冲区占多少内存，是两件完全独立的事。
- **"一个 key 对应一个 SDS" 是不准确的泛化**：要看 value 的类型和编码——字符串类型里，`int` 编码根本没有 SDS（整数直接内嵌存放），只有 `embstr`/`raw` 编码才真正落地为 SDS；集合类型（list/hash/set/zset）如果是 `ziplist`/`intset` 这类紧凑编码，所有元素挤在一整块连续内存里，不存在"每个元素一个 SDS"，只有编码退化为 `hashtable`/`skiplist`/`linkedlist` 时，元素才通常各自是独立的字符串对象、各自持有 SDS。

## 与其他章节的关联

- **第7章「压缩列表」**：集合类型在 `ziplist`/`intset` 紧凑编码下并不使用 SDS，元素是打包在一块连续内存里的，这是对本章"字符串就是 SDS"默认印象的重要修正，第7章会讲这种紧凑结构的具体布局。
- **第8章「对象」**：字符串对象有 `int`/`embstr`/`raw` 三种编码，只有 `embstr`/`raw` 才对应本章的 SDS 实现，`int` 编码完全不涉及 SDS。本章是理解第8章编码选择机制的前置基础。
- **第11章「AOF持久化」**：AOF 缓冲区（`server.aof_buf`）本身就是一个 SDS，是命令执行完毕到落盘之间的中转站，其扩容/收缩本质上就是本章讲的 SDS 空间管理策略在起作用。
- **第13章「客户端」**：客户端的输入缓冲区（query buffer）和输出缓冲区底层也基于 SDS（或同类结构），涉及独立于数据库存储之外的定期收缩机制和相关配置项。
