# 第3章 链表

## 核心概念

**结构定义**

```c
typedef struct listNode {
    struct listNode *prev;
    struct listNode *next;
    void *value;
} listNode;

typedef struct list {
    listNode *head;
    listNode *tail;
    unsigned long len;
    void *(*dup)(void *ptr);
    void (*free)(void *ptr);
    int (*match)(void *ptr, void *key);
} list;
```

**五个特性**

- 双端：每个节点有 `prev`/`next`，取前置/后置节点 O(1)。
- 无环：表头的 `prev` 和表尾的 `next` 都指向 `NULL`，遍历以 `NULL` 收尾。
- 带表头/表尾指针：`list.head`/`list.tail` 让获取首尾节点是 O(1)。
- 带长度计数器：`list.len` 让获取链表长度（对应 `LLEN`）是 O(1)，不需要遍历。
- 多态：节点值用 `void *` 保存，配合 `dup`/`free`/`match` 三个类型特定函数指针，让同一套链表实现能保存任意类型的值——这是 C 语言没有泛型机制时实现通用容器的经典手法。

**应用场景**：链表是 List 类型键的底层实现之一（元素多或元素字符串长时启用，另一种小体量场景用第7章的压缩列表 ziplist）；此外发布订阅、慢查询日志、监视器、服务器维护的客户端状态列表都用到了链表。

**为什么大 List 用链表而不是数组**（设计权衡，属于本章最值得记住的实践性内容）：

- List 类型需要 `LPUSH`/`RPUSH`/`LPOP`/`RPOP` 两端操作都快。普通数组尾部追加是均摊 O(1)，但头部插入删除是 O(N)（需要整体搬移），无法满足两端对称的需求。
- 即使换成能做到两端 O(1) 的环形缓冲区（deque），依然绕不开两个问题：扩容需要一整块连续内存，大列表下这块连续内存的分配和整体拷贝成本高、还有碎片化风险；`LINSERT`/`LREM` 这类中间位置的插入删除，数组结构还是要搬移元素，而链表定位到目标节点后，插入/删除本身是 O(1)，不影响其他节点。
- 链表节点相互独立，插入或删除一个节点完全不会影响其他节点，从设计上规避了第7章会讲的"连锁更新"问题（紧凑的数组式结构里，一个节点变化可能引发相邻节点连锁调整，list 越大风险影响面越大）。
- 代价：随机访问退化为 O(N)（`LINDEX` 在大链表上要遍历）；每个节点多了 `prev`/`next`/`value` 三个指针的固定开销（64位系统下约24字节）；节点内存分散、对 CPU 缓存不友好。
- 所以 Redis 的真实策略是**按体量切换编码**：小 list 用紧凑的 ziplist（O(N) 遍历中的 N 很小，不构成问题，且没有大块连续内存分配的压力，紧凑性反而是优势）；大 list 才切到本章的链表，用"随机访问变慢 + 每节点指针开销"换"两端恒定 O(1) + 不需要整块连续内存 + 不会连锁更新"。具体切换阈值和两种编码的协作机制是第8章的内容。

## 易混淆/易错点

- **链表随机访问是 O(N)，不是 O(1)**：表头表尾快不代表按下标取任意节点快。大 list 如果是链表编码，`LINDEX`、大范围 `LRANGE` 这类按下标/范围访问的命令会明显变慢，这是排查"list 类型某些操作变慢"时要想到的点。
- **不要把"链表天生比数组好"当结论**：链表牺牲了随机访问性能和内存紧凑性，只是在"两端操作要快 + 体量大 + 不想承担大块连续内存分配和连锁更新风险"这个具体场景下更划算。Redis 对小 list 用的恰恰是数组式的紧凑结构（ziplist），说明这是一个体量相关的权衡，不是绝对优劣。
- **环形缓冲区能解决两端 O(1)，但解决不了大块连续内存分配和中间插入删除的搬移问题**：容易误以为"数组只要设计得巧妙（比如用 deque）就能完全替代链表"，实际上大块连续内存的扩容成本和碎片风险，以及中间位置增删的搬移代价，是数组类结构（不管普通数组还是环形缓冲区）绕不开的固有特征。
- **本书基于 Redis 3.0 之前版本，尚未出现 quicklist**：链表本身"随机访问慢、每节点指针开销大、内存不连续对缓存不友好"这几个代价，在 Redis 3.2+ 引入的 quicklist（链表节点本身是一段 ziplist）中被进一步优化，这部分内容规划在后续"现代 Redis 补充篇"里详细展开，本章及全书涉及 List 编码的部分仍以 ziplist/linkedlist 两种编码为准。

## 与其他章节的关联

- **第7章「压缩列表」**：小 list 使用的紧凑数组式结构，"连锁更新"问题是本章"链表节点相互独立、不受影响"这一优势的直接对照面。
- **第8章「对象」**：List 对象在 ziplist 和 linkedlist 两种编码之间的切换阈值和具体机制，是本章"何时用链表"这个问题的完整答案所在。
- **第23章「慢查询日志」**：书中给出的实际用法——新日志用 `listAddNodeHead` 插入表头，超出 `slowlog-max-len` 时用 `listDelNode(list, listLast(list))` 删除表尾最旧日志，是用链表头尾 O(1) 操作实现"有界队列/FIFO"的典型模式，日常写缓存淘汰、环形日志队列时可以借鉴这个思路。
- **第13章「客户端」**：客户端输出缓冲区在需要容纳较多/较大回复内容时，也会用到链表来串联多个回复节点，具体机制到该章展开。
- **后续「现代 Redis 补充篇」**：quicklist（链表 + ziplist 的结合体）是对本章链表实现的直接演进，解决的正是这里提到的随机访问慢、指针开销大、缓存不友好这几个代价。
