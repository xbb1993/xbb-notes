# 第4章 字典

## 核心概念

**字典是什么、为什么需要它**：字典（又称符号表/关联数组/映射）是"给定一个键就能找到关联值"的抽象数据结构。很多高级语言把它内置了，但 Redis 用 C 语言写成，没有这种内置容器，只能自己实现一套。字典不是为某个具体功能量身定做的，而是 Redis 内部的通用基础设施——先有这个通用能力，后面各个子系统才按需拿去用。

**三个核心结构，层层嵌套：**

```c
// 哈希表
typedef struct dictht {
    dictEntry **table;
    unsigned long size;
    unsigned long sizemask; // 总是等于 size-1
    unsigned long used;
} dictht;

// 哈希表节点
typedef struct dictEntry {
    void *key;
    union { void *val; uint64_t u64; int64_t s64; } v;
    struct dictEntry *next; // 解决键冲突
} dictEntry;

// 字典
typedef struct dict {
    dictType *type;
    void *privdata;
    dictht ht[2];  // 平时只用 ht[0]，ht[1] 仅在 rehash 时使用
    int rehashidx; // 不在 rehash 时为 -1
} dict;
```

**`dictType`：让一套字典实现服务于所有不同消费者的关键机制**

```c
typedef struct dictType {
    unsigned int (*hashFunction)(const void *key);
    void *(*keyDup)(void *privdata, const void *key);
    void *(*valDup)(void *privdata, const void *obj);
    int (*keyCompare)(void *privdata, const void *key1, const void *key2);
    void (*keyDestructor)(void *privdata, void *key);
    void (*valDestructor)(void *privdata, void *obj);
} dictType;
```

每个字典实例创建时可以传入不同的 `dictType`，决定这个字典的键值该怎么算哈希、怎么复制、怎么对比、怎么销毁。上层消费者不需要重新实现哈希表，只需要"配置"一套符合自己场景的函数集合插进来即可——这是 C 语言没有泛型时"一套容器、多处复用"的标准手法，和第3章链表的 `dup`/`free`/`match` 是同一个思路，字典这里做得更完整。

**哈希算法与索引计算**：`hash = type->hashFunction(key)`，`index = hash & ht[x].sizemask`。用 `&` 位运算代替 `%` 取模，前提是哈希表大小必须是 2 的幂。当字典用作数据库或哈希键的底层实现时用 MurmurHash2，但这只是"当…时"的默认配置，不同用途的字典可以配置不同哈希函数。

**解决键冲突：链地址法 + 头插法**：同一索引的多个节点用 `next` 连成单向链表，新节点固定插入表头（O(1)），因为没有维护表尾指针。

**rehash 完整机制：**

- 触发条件由负载因子 `load_factor = ht[0].used / ht[0].size` 决定：无 `BGSAVE`/`BGREWRITEAOF` 时 ≥1 触发扩展，有则要 ≥5；负载因子 <0.1 触发收缩。
- 新表大小：扩展是第一个 ≥`used*2` 的 2 的幂；收缩是第一个 ≥`used` 的 2 的幂。
- 渐进式执行：`ht[1]` 分配空间，`rehashidx` 置 0；此后每次增删查改顺带迁移 `ht[0]` 在 `rehashidx` 索引上的全部节点，`rehashidx` 加一；全部迁完后 `rehashidx` 置 -1，`ht[1]` 变成新 `ht[0]`。
- rehash 期间：查找/删除/更新两个表都要找；**新增只写入 `ht[1]`**，保证 `ht[0]` 只减不增。
- **扩缩容规则是 `dict.c` 层面统一的一套逻辑，对所有字典实例一视同仁，不能通过 `dictType` 定制**。`dictType` 的六个函数指针全部是"怎么处理键值本身"的定制点，没有一个涉及"什么时候该扩容"。是否有 `BGSAVE`/`BGREWRITEAOF` 在执行是一个全局服务器状态，不挂在具体字典实例上，因此这条规则对数据库字典、哈希键字典、命令表等所有实例统一生效，没有例外。

**字典在 Redis 里的实际应用清单**（体现"通用容器、多处复用"的真实广度）：

- 数据库的 `dict`（键空间）和 `expires`（过期时间），两个独立字典实例（第9章）。
- Hash 类型键在 `hashtable` 编码下：字段名 → 字段值（第8章）。
- Set 类型键在 `hashtable` 编码下：元素 → NULL，只用字典的键去重和 O(1) 查找能力，不使用值（第8章）。
- 有序集合键在 `skiplist` 编码下，底层是 `zset` 结构，**同时包含一个字典和一个跳跃表**：字典部分是 member → score，支持 O(1) 复杂度的 `ZSCORE`；跳跃表部分负责范围/排名类操作。两者通过指针共享同一份成员和分值，不重复存储。只用字典会让范围操作退化到 O(N log N)，只用跳跃表会让按成员查分值退化到 O(log N)，两者都用才能让两类操作都保持最优（第5、8章）。
- 命令表：服务器级别唯一一份，命令名字符串（查找不区分大小写）→ `redisCommand` 结构（实现函数指针、参数个数、执行统计）（第13、14章）。
- 发布订阅频道表 `pubsub_channels`：频道名 → 订阅该频道的客户端链表（第18章）。
- Lua 脚本缓存 `lua_scripts`：脚本 SHA1 → 脚本内容，配合主从复制场景下的 `repl_scriptcache_dict`（第20章）。

## 易混淆/易错点

- **rehash 不是一次性完成的**，是靠 `rehashidx` 递增、均摊到每次增删查改操作上的渐进式过程，避免大字典集中 rehash 时阻塞服务器。
- **扩容阈值不是固定为 1**，取决于是否有 `BGSAVE`/`BGREWRITEAOF` 子进程在运行：无则 ≥1 触发，有则要 ≥5 才触发。原因是这两个命令都会 `fork` 子进程，操作系统用写时复制（copy-on-write）让子进程共享父进程内存页，若这时候父进程做 rehash（大量内存分配和数据搬迁）会导致大量共享页被迫复制，浪费内存和时间，所以刻意提高阈值把 rehash 推迟到子进程结束后。
- **扩容后的大小不一定精确是原来的 2 倍**，是"第一个 ≥`used*2` 的 2 的幂"——如果 `used*2` 本身不是 2 的幂，会向上取整（比如 `used=5`，`used*2=10`，第一个 ≥10 的 2 的幂是 16，不是 10）。
- **渐进式 rehash 期间，新增的键值对不会按正常规则计算后随便进哪个表**，而是固定只写入 `ht[1]`，这是保证 `ht[0]` 只减不增、最终清空的关键设计。
- **负载因子不只是内存利用率问题，还直接影响查找性能**：链地址法在负载因子过高时，单个索引下挂的链表变长，查找从接近 O(1) 退化到接近 O(N)。
- **渐进式 rehash 期间会有内存的瞬时双开销**：`ht[0]` 和 `ht[1]` 同时存在，扩展场景下 `ht[1]` 要新分配更大空间，rehash 完成前这部分内存是额外占用的，规模大的字典扩容时值得留意这个瞬时峰值。
- **不要把"字典只是数据库和哈希键的实现"想窄了**：字典是贯穿全书的通用基础设施，命令表、发布订阅频道表、Lua 脚本缓存、有序集合的内部实现都在用，遇到新章节看到"用字典保存了 XX 到 YY 的映射"时，应该能立刻联想回本章的结构和机制，而不是当成全新知识点。
- **扩缩容规则和 `dictType` 是两个独立的关注点**：不要以为不同用途的字典可以自定义扩容时机或负载因子阈值——这部分是 `dict.c` 内部统一逻辑，全局生效，`dictType` 只管"数据怎么被处理"（哈希、复制、对比、销毁），不管"容器什么时候该长大缩小"。

## 与其他章节的关联

- **第3章「链表」**：`dictType` 的多态机制和链表的 `dup`/`free`/`match` 函数指针是同一种"C 语言实现通用容器"的设计思路，字典这里做得更完整（多了 `hashFunction`，且 key/val 分开处理）。
- **第5章「跳跃表」**：有序集合的 `skiplist` 编码底层是"字典 + 跳跃表"的组合结构（`zset`），字典负责 O(1) 按成员查分值，跳跃表负责范围操作，两者共享数据不重复存储，是本章字典应用中最能体现设计权衡的例子。
- **第8章「对象」**：Hash 对象的 `hashtable` 编码、Set 对象的 `hashtable` 编码（值全为 NULL）、有序集合对象的 `skiplist` 编码，都是本章字典结构的具体消费场景，编码切换的阈值和触发条件在该章详细展开。
- **第9章「数据库」**：数据库由 `dict`（键空间）和 `expires`（过期时间）两个独立字典实例构成，是本章字典结构最基础、最核心的应用。
- **第13、14章「客户端/服务器」**：命令表是一个服务器级别的字典（命令名 → `redisCommand`），命令执行器的第一步就是查这张表。
- **第18章「发布与订阅」**：`pubsub_channels` 字典管理频道订阅关系。
- **第20章「Lua脚本」**：`lua_scripts` 字典缓存脚本内容，`repl_scriptcache_dict` 配合主从复制判断该传播 `EVAL` 还是 `EVALSHA`。
