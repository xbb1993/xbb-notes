# 第5章 跳跃表

## 核心概念

**跳跃表不是树，是叠了多层的有序链表**：最底层是一条包含全部元素的普通有序链表，往上每一层都是更稀疏的"快速通道"，只有部分节点会出现在高层。所有元素从头到尾只有一条统一的顺序，高层不是把数据切分成不同分支，而是这条顺序之上的多级索引——这是它和树最本质的区别：树是分支结构，元素分散到不同子树；跳跃表没有分支，只有"同一条路上不同密度的车道"。

**两个结构：**

```c
typedef struct zskiplistNode {
    struct zskiplistLevel {
        struct zskiplistNode *forward; // 前进指针
        unsigned int span;             // 跨度
    } level[];
    struct zskiplistNode *backward;    // 后退指针
    double score;                       // 分值
    robj *obj;                          // 成员对象，指向字符串对象
} zskiplistNode;

typedef struct zskiplist {
    zskiplistNode *header, *tail;
    unsigned long length; // 节点数量（不含表头）
    int level;             // 当前最大层数（不含表头）
} zskiplist;
```

层高是创建节点时按幂次定律随机生成的一个 1~32 之间的值，一次生成后不会再变化（不像平衡树需要旋转维持平衡）。

**前进指针和跨度作用完全不同**：前进指针（`level[i].forward`）用于遍历，层数越高跳得越远；跨度（`level[i].span`）**和遍历无关**，专门用来计算目标节点的排位（rank）——查找时把沿途经过的所有层的跨度累加起来，就是目标节点的排位。

**查找的核心机制（也是复杂度优势的真正来源）**：从最高层开始，能往前走就往前走（下一个节点的分值仍不超过目标），一旦再往前走会超过目标，就**下降一层，从当前节点继续**，而不是回到表头重新开始。整个查找路径是"横向前进 + 垂直下降"交替形成的一条单向路径。举例：5 个节点分值 1~5，层高分别是 1、3、1、2、4：

```
第4层  H ------------------------------------------> N5
第3层  H ---------------> N2 --------------------- > N5
第2层  H ---------------> N2 -----------> N4 ------> N5
第1层  H --> N1 --> N2 --> N3 --> N4 --> N5 --> NULL
```

查找 N4（分值4）：从 H 第4层前进到 N5，5>4 走不动，下降到第3层；从 H 第3层前进到 N2，2≤4 前进；在 N2 的第3层前进到 N5，5>4 走不动，下降到第2层；在 N2 的第2层前进到 N4，4≤4，找到。全程 4 步操作，而最底层链表需要连续走 4 步才能到 N4——数据量越大，层数带来的收窄效果越明显，平均复杂度 O(logN)。

**后退指针**：每个节点只有一个，只能一次回退一步，用于从表尾向表头方向遍历。

**排序规则**：按分值从小到大排列；分值相同时按成员对象字典序排序。同一跳跃表里成员必须唯一，但分值可以重复。

**应用范围很窄**：跳跃表在 Redis 里只有两个用途——有序集合键 `skiplist` 编码下的底层实现，以及集群节点里的一个内部数据结构（第17章）。不像链表、字典那样被广泛使用。

**为什么有序集合选跳跃表而不是红黑树/平衡树**（多维度论证，不是单纯因为查找复杂度同量级）：

- **访问模式契合度**：`ZRANGE`/`ZRANGEBYSCORE` 这类范围查询，跳跃表定位到起点后直接沿最底层链表顺序往后走即可，天然贴合"有序遍历"的使用模式；红黑树做范围查询要靠"找中序后继"逐个跳转，虽然理论上也能做到 O(logN+K)，但实现和心智上都更绕。
- **实现复杂度**：跳跃表的插入是"找位置→随机定高度→改指针"，删除是"找节点→改指针"，都不需要旋转和重新染色；红黑树的插入删除需要处理左旋、右旋、颜色调整、修复等一整套规则。对 Redis 这种底层基础设施而言，**实现简单本身就是一种可靠性**——代码越复杂，边界情况和潜在 bug 越多，后续维护和修改的风险越大。
- **"树更省空间"这个直觉需要修正**：如果红黑树也要支持 `ZRANK` 这类排名查询，同样得在每个节点维护子树大小之类的额外信息，两者的空间差距没有想象中悬殊；而且跳跃表里大多数节点其实只有 1 层，只有少数"高个子"节点才有多层指针，平均下来的额外空间开销也没那么夸张。
- **跳跃表用"概率保证平衡"替代"严格维护平衡"**：不要求任何强制的再平衡规则，只要节点层高的随机分布符合概率要求，整体性能就能达到平均 O(logN)——这是一种用概率换掉复杂平衡维护成本的工程取舍。

## 易混淆/易错点

- **不要把跳跃表理解成树**：它没有分支，是同一条有序序列之上叠加的多层稀疏索引，所有元素只有一个统一顺序。
- **最容易踩的坑：以为"逐层下降"是每一层都要重新从表头开始搜索一遍**——如果真是这样，把每层搜索步数加起来，跳跃表可能比普通链表还慢。正确理解是：下降后从**当前节点**继续往前走，整个查找是一条连续路径，不是多次独立搜索的叠加。
- **跨度（span）不是给遍历用的，是专门给排位计算用的**：`ZRANK`/`ZREVRANK` 之所以能快速算出"某个成员排第几"，靠的就是查找过程中把沿途各层的跨度累加起来。
- **层高一次随机生成后不会再调整**，这和平衡树"通过旋转动态维持平衡"是完全不同的思路——跳跃表放弃了严格平衡，换取插入删除的实现简单。
- **O(logN) 是平均复杂度保证，不是每次查找都确定更快**：最坏情况仍然是 O(N)（比如层高分布非常不均匀的极端情况）；数据量很小的时候，跳跃表额外的层级也可能没什么实际收益，不能默认"跳跃表任何情况下都比普通链表快"。
- **"跳跃表比红黑树省空间"不能当成默认结论**：要看红黑树是否也需要支持排名类查询（需要则要维护子树大小，空间优势缩小），以及跳跃表里大多数节点其实只有 1 层这一事实。

## 与其他章节的关联

- **第2章「SDS」**：跳跃表节点的成员对象 `obj` 指向字符串对象，字符串对象底层就是 SDS。
- **第4章「字典」**：有序集合的 `skiplist` 编码底层是 `zset` 结构，**同时包含一个字典和一个跳跃表**，两者通过指针共享同一份成员和分值，不重复存储。分工非常清晰：
  - **字典**负责"给成员、查分值"的点查询——`ZSCORE` 直接查字典，O(1)，完全不碰跳跃表。
  - **跳跃表**负责"要求按顺序/按名次/按分值范围"的查询——`ZRANK`（先查字典拿分值，再用跨度累加定位排位）、`ZRANGE`（按排位定位起点后沿链表顺序取）、`ZRANGEBYSCORE`（按分值定位起点后沿链表顺序取）。
  - `ZINCRBY` 不是纯 O(1) 操作：虽然查旧分值走字典是 O(1)，但分值变了意味着排序位置也要变，必须把节点从跳跃表里摘出来按新分值重新插入。
- **第8章「对象」**：有序集合对象在元素数量 <128 且所有成员长度 <64 字节时使用 `ziplist` 编码，否则使用 `skiplist` 编码（即本章的 `zset` 结构），阈值对应 `zset-max-ziplist-entries`/`zset-max-ziplist-value` 配置项。
- **第17章「集群」**：跳跃表在集群节点内部还有另一处应用，具体细节到该章展开。
