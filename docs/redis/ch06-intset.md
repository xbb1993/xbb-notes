# 第6章 整数集合（intset）

## 核心概念

**要解决的问题**：Set 类型如果全部用字典（第4章）实现，每个元素都要包一层字符串对象（背后往往还有 SDS，第2章），再挂一个 `dictEntry`，插进哈希桶数组。对于像 `{1, 3, 5, 7, 9}` 这种只有几个小整数的集合，元素本身可能就 2~8 字节，但外壳（字符串对象头 + SDS 头 + dictEntry + 哈希桶指针）远比数据本身重——这是典型的"用集装箱寄一封信"。intset 就是为这种"元素全是整数、规模不大"的场景专门做的紧凑实现。

**结构定义：**

```c
typedef struct intset {
    uint32_t encoding; // 当前用哪种整数类型存
    uint32_t length;   // 元素个数
    int8_t contents[]; // 实际存数据的数组，真实类型由 encoding 决定
} intset;
```

`encoding` 只有三种取值：`INTSET_ENC_INT16` / `INTSET_ENC_INT32` / `INTSET_ENC_INT64`，决定 `contents` 数组的真实元素类型（`int8_t` 只是声明时的占位写法）。数组元素**从小到大有序排列，且不重复**。

**为什么不直接用 int64_t 数组兜底所有情况**：这是最简单粗暴的替代方案，但代价是即使集合里全是 1、3、5 这种一位数，每个元素也固定占 8 字节，浪费了绝大多数场景下的内存。intset 选择"按需用最小够用的类型，必要时再升级"，用一次性的升级成本换日常的紧凑存储。

**升级（upgrade）机制**：当新增元素的类型比集合当前所有元素的类型都长时，触发升级，分三步：

1. 按新类型和新的元素总数（含待插入的新元素）重新分配 `contents` 数组空间。
2. 把数组里**已有的全部元素**转换成新类型，并维持有序性不变（要从后往前搬，避免转换过程中覆盖还没转换的旧数据）。
3. 把新元素放进正确位置。

举例：`INTSET_ENC_INT16` 编码的 `{1, 2, 3}`（各占16位，共48位），添加 `int32_t` 类型的 `65535`：

```
升级前  encoding=INT16, length=3
        contents: [ 1(16b) ][ 2(16b) ][ 3(16b) ]

第1步：按 int32 重新分配 4 个元素的空间（128位），旧数据格式未变
        contents: [ 1(16b旧) ][ 2(16b旧) ][ 3(16b旧) ][   空间   ]

第2步：从后往前把旧元素转换成 int32
        contents: [  1(32b)  ][  2(32b)  ][  3(32b)  ][   空位   ]

第3步：插入新元素 65535
        contents: [  1(32b)  ][  2(32b)  ][  3(32b)  ][65535(32b)]
升级后  encoding=INT32, length=4
```

因为每次可能触发升级的插入，都要对已有全部元素做类型转换，所以**添加操作最坏情况是 O(N)**，不是 O(1)。

**升级后新元素的摆放位置**：触发升级的新元素，类型长度必然超过现有所有元素，意味着它的值要么比所有现有元素都大，要么都小（不可能落在中间，中间的值本就在原类型表示范围内，不会触发升级）。因此新元素只会被放在数组最前（索引0）或最末（索引 length-1），不需要在中间查找插入点。

**降级：不支持**。一旦升级到某个类型，即使后来把触发升级的大数删除了，编码也不会自动降级，底层数组会一直用升级后的类型存储剩下的元素。这是一个主动的设计取舍：

- 若支持降级，每次删除后都要扫描剩余全部元素判断能否收缩类型，这是额外的 O(N) 检测，叠加在本可以更轻量的删除操作上。
- 会触发升级的场景（混入一个远超其他元素的大数）本身在实际业务中偏边缘，不值得为这种小概率场景增加复杂度。
- 空间浪费是有界的（跟集合大小线性相关），不是无限增长的泄漏，工程上可以接受。

**升级带来的两个好处**：灵活性（可以随意往集合里加 int16/int32/int64 而不用担心类型错误）和省内存（只在必要时才升级，不必一步到位用最大类型兜底）。

**为什么这样设计——多维度对比**（相对"一步到位用 int64 数组"和"直接用字典实现"两种替代方案）：

- 空间：intset 每个元素只是裸的定长整数，没有字符串对象、SDS、dictEntry、哈希桶等额外开销；相比一步到位用 int64，按需升级让大多数只存小整数的集合始终保持紧凑。
- 性能：数组连续、有序存放，对 CPU 缓存友好（呼应第3章"数组 vs 链表"里数组的局部性优势）；有序数组理论上可以二分查找定位元素——这一点书里没有展开具体算法，是从"数组有序"这个结构性质推出的工程判断，不是书上原文。
- 实现复杂度：不需要处理哈希冲突和 rehash，插入逻辑统一（找位置 → 必要时先升级 → 挪动数组 → 插入），不需要为三种类型分别写三套逻辑。
- 工程可靠性：逻辑简单、边界情况少，出 bug 的面更小。

**intset 是完全隐式的内部实现，用户不可见、不可选**：Redis 的 Set 类型对外只有一套命令语义（`SADD`/`SREM`/`SMEMBERS` 等），用户既不能在建 key 时指定用 intset 还是 hashtable，命令行为在两种编码下也完全一致——编码切换对用户透明。这其实是第8章会正式讲的 `redisObject` 机制的一个具体体现：Redis 的值把 `type`（类型，如 Set）和 `encoding`（编码，如 intset/hashtable）分开管理，用户命令面向 `type`，`encoding` 是 Redis 根据数据特征动态选择、可在运行时切换的实现细节。用户唯一能感知编码存在的方式：主动执行 `OBJECT ENCODING key` 查询（纯内省，不影响行为），或者间接从内存占用/性能表现上察觉差异。

**与 Set 对象编码转换的关系**（第8章细讲，这里先建立联系）：当集合同时满足"所有元素都是整数"和"元素数量不超过 `set-max-intset-entries`（默认512）"两个条件时用 intset，否则用 hashtable。只要有一个非整数元素混入，或数量超过阈值，就会执行编码转换，原 intset 中的元素被转移到字典里，且这个转换是单向的——数量再降回阈值以内也不会转换回 intset，这和本章"不支持降级"是同一种设计哲学的延伸。

## 易混淆/易错点

- **升级不是只转换新插入的元素**：C 数组要求元素定长、类型统一，不可能在同一个数组里混用两种宽度。升级必然是把已有全部元素统一转换成新类型，这正是升级复杂度是 O(N) 而非 O(1) 的根本原因。
- **升级后新元素的位置不是查找中间插入**：只可能落在数组最前或最末，因为触发升级的值必然超出现有所有元素的类型范围。
- **不要把"intset 可以自动收缩"当成默认行为**：intset 只支持升级，不支持降级，即使把导致升级的大数删除，编码也不会回退。排查"一个看起来全是小整数的 Set 类型 key 内存异常偏大"时，要考虑到"是不是曾经存过一个特别大的值导致了类型升级、但后来被删除了"——这跟第2章讲 SDS"内存虚胖不会自动收缩"是同一种"膨胀过、缩不回去"的思路，只是发生在不同结构上。
- **intset 不是用户可选项，是 Redis 内部按数据特征自动决定的编码**：不存在任何命令参数可以指定"这个 Set 用 intset"，用户只能通过 `OBJECT ENCODING` 事后查询，不能事先干预（顶多通过 `set-max-intset-entries` 调整触发转换的数量阈值，调不了"用不用 intset"这个判断逻辑本身）。
- **intset 应用范围很窄**：只是 Set 对象在满足"全整数 + 数量不超阈值"条件下的一种底层实现，别的类型（Hash、Zset 等）不会用到 intset。
- **不要孤立地把 intset 的元素类型转换理解成"每个元素单独判断要不要转"**：转换以整个 intset 为单位一次性发生，触发条件也是"新元素类型超过当前所有元素类型"，而不是逐个元素比较。

## 与其他章节的关联

- **第2章「SDS」**：intset 存储整数不使用 SDS，而是裸的定长二进制数组，这是"集合类型在紧凑编码下不是每个元素一个 SDS"这一结论（第2章笔记里提到过）的具体例子之一。
- **第3章「链表」**：intset 底层是连续数组而不是链表，其"对 CPU 缓存友好"的性能优势和第3章讨论"数组 vs 链表如何选择"时的局部性论证是同一个道理。
- **第4章「字典」**：Set 对象另一种编码 hashtable 就是用字典实现的，intset 和 hashtable 是同一个 Set 类型互斥的两种底层实现；intset 存在的意义正是绕开字典实现下每个元素额外的字符串对象/SDS/dictEntry/哈希桶开销。
- **第8章「对象」**：本章 intset↔hashtable 的编码转换规则（全整数 + 数量阈值）、转换的单向性，以及"type 和 encoding 分离、用户只面向 type 操作"这套通用机制，都会在第8章正式、完整地展开，本章是该机制在 Set 类型上的第一次具体接触。
