# 第7章 压缩列表（ziplist）

## 核心概念

**要解决的问题**：小规模的 List/Hash/Zset（元素数量少、每个元素都短），如果用链表（第3章）或字典（第4章）实现，每个元素都要背上节点指针、对象头、哈希桶等固定开销，外壳比数据本身还重——这跟第6章 intset 要解决的问题是同一类。ziplist 就是给这种"小数据量、短元素"场景做的紧凑连续内存结构。

**整体布局：**

```
[zlbytes][zltail][zllen][entry1][entry2]...[entryN][zlend]
```

- `zlbytes`：整个压缩列表的总字节数。
- `zltail`：表尾节点相对起始地址的偏移量——有了它，定位表尾节点是 O(1)，不用从头遍历。
- `zllen`：节点数量——`LLEN`/`HLEN` 这类长度类命令因此是 O(1)。

**节点（entry）的三段式构成：**

```
[previous_entry_length][encoding][content]
```

- `previous_entry_length`：记录**前一个**节点的总长度，是变长字段——前一节点长度 <254 字节时占1字节，≥254 字节时占5字节（第1字节是标记 0xFE，后4字节存实际长度）。
- `encoding`：标记 `content` 存的是字节数组还是整数、具体类型/长度是什么（字节数组分三档长度级别，整数分六档类型级别，按需选最省的表示方式——和第6章 intset"按需升级到最小够用的类型"是同一条设计哲学）。
- `content`：实际数据。

**反向遍历的实现原理**：拿到某个节点的起始地址后，用这个地址减去该节点 `previous_entry_length` 记录的值，就得到前一个节点的起始地址，一路可以退到表头。`zltail` 让程序可以先 O(1) 定位到表尾节点，再借助这条链条反向遍历整个列表。

**ziplist 没有真实的 `prev`/`next` 指针**：反向遍历完全靠"读前一个节点写好的长度值、做指针减法"实现，不像第3章链表那样每个节点显式保存指向前后节点的指针——本质是用"计算"替代"直接存指针"，省下了指针本身的固定开销。

**正向遍历需要现场计算当前节点的总长度，而不是直接读一个现成字段**：ziplist 没有任何字段直接存"当前节点自身总长度"，正向跳转时要把三部分加起来：`previous_entry_length` 字段自身占用的字节数（1或5）+ `encoding` 字段自身占用的字节数（1/2/5，视类型而定）+ `content` 的实际长度（由 `encoding` 给出或按整数类型直接推出）。算出总长度后指针往后挪这么多字节，才跳到下一个节点。反向遍历是"直接读现成值"，正向遍历是"解析当前节点后现算"，两者严格算都是 O(1)，但操作步骤不同。

**连锁更新（cascade update）**：因为 `previous_entry_length` 是变长的（1字节/5字节以254字节为界），如果连续多个节点长度恰好卡在 250~253 字节区间（`prev_len` 都只占1字节），此时在最前面插入一个 ≥254 字节的新节点，会导致后续节点的 `prev_len` 依次被迫从1字节扩展为5字节——而扩展本身又会让被扩展节点的总长度跨过254字节这个门槛，继续推着下一个节点扩展，如此连锁传导。除了插入，**删除节点也可能触发**：删掉一个把"大节点"和"一串250~253字节节点"隔开的小节点后，大节点和这串节点直接相邻，同样会触发连锁扩展。

因为最坏情况下要对 N 个节点做空间重分配、每次重分配最坏 O(N)，所以连锁更新最坏复杂度是 **O(N²)**。但实际发生概率很低：触发条件苛刻（需要一长串节点长度恰好落在临界区间），且即便触发，只要涉及节点数不多，绝对耗时可以忽略——因此 `ziplistPush` 等操作在实践中仍按平均 O(N) 对待。

**哪些类型会用到 ziplist**：List、Hash、Zset（有序集合）都会把 ziplist 作为自己的一种可选编码，判断维度是"元素数量"和"每个元素长度"两者同时够小；任一维度超标就分别转换成 linkedlist（第3章）、字典的 hashtable（第4章）、zset 结构（第5章的字典+跳跃表组合）。**Set 类型不使用 ziplist**——Set 的两种编码是 intset（第6章）和 hashtable，与 ziplist 无关。具体的数量/长度阈值第8章正式给出。

**为什么用这套方案——多维度对比**（相对链表、字典实现的小集合）：

- 空间：没有链表的 `prev`/`next` 指针开销，也没有字典的哈希桶/dictEntry 开销；`encoding` 还按数据大小选最省表示。
- 性能：物理连续存放，对 CPU 缓存友好（呼应第3章讨论链表 vs 数组时的局部性论证），小数据量场景下收益明显。
- 实现复杂度：变长记录的读写要先解析 `encoding` 才知道跳多少字节，比定长数组麻烦；但比维护哈希冲突/rehash 的字典简单。
- 工程可靠性：连锁更新是这套方案唯一不够干净的地方，是"体量变大就该切换编码"的直接原因之一，而不是可选优化。

## 易混淆/易错点

- **ziplist 没有真实指针**：不要以为它跟链表一样每个节点有 `prev` 字段，反向遍历是靠 `previous_entry_length` 做指针减法算出来的。
- **正向遍历不是靠一个现成的"自身长度"字段**：ziplist 没有为节点存自身总长度，正向跳转要现场解析 `encoding` 并累加三部分字节数才能算出来，跟反向遍历"直接读现成值"是不同的操作路径。
- **连锁更新不是只在插入时发生**：删除节点同样可能触发（把两个原本被隔开的节点变成相邻，导致 `prev_len` 跨过254字节门槛）。
- **O(N²) 是最坏复杂度，不代表实际性能差**：触发条件苛刻（需要连续多个节点长度恰好卡在250~253字节区间），且影响面通常有限，工程上按平均 O(N) 对待是合理的。
- **"连续内存"不等于"能像数组一样 O(1) 随机访问"**：ziplist 是变长记录，定位第 k 个元素要从头（或尾）顺着 `previous_entry_length`/`encoding` 逐个跳，做不到按下标直接算地址。
- **不要以为 Set 类型也用 ziplist**：List/Hash/Zset 用 ziplist，Set 用的是 intset 和 hashtable，二者判断维度不同（Set 靠"是否全整数"，List/Hash/Zset 靠"元素数量+长度"）。

## 与其他章节的关联

- **第2章「SDS」**：ziplist 节点的 `content` 直接是编码后的字节数组或整数，不经过 SDS，是"紧凑编码下不是每个元素都有独立 SDS"这一结论的又一次印证。
- **第3章「链表」**：ziplist 没有真实的 `prev`/`next` 指针，靠计算实现反向遍历；链表节点相互独立，天然不存在连锁更新问题——这也是大 List 从 ziplist 换成链表的原因之一：不只是随机访问变快，也是甩掉连锁更新这个风险面。
- **第5章「跳跃表」**：Zset 的 ziplist 编码用两个相邻节点表示"成员+分值"一对，物理结构上正是本章字节数组/整数混排机制的具体应用。
- **第6章「整数集合」**：intset 和 ziplist 都是给小规模场景做的紧凑连续内存结构，一个靠"类型升级"按需选表示方式，一个靠"多档编码"按需选表示方式，是同一种设计哲学在不同数据形态上的两次落地；Set 类型用 intset 不用 ziplist，是两者应用边界的分界点。
- **第8章「对象」（待学）**：List/Hash/Zset 各自切换到 ziplist 的具体数量和长度阈值（配置项如 `list-max-ziplist-entries`、`hash-max-ziplist-value` 等），以及编码转换的完整规则，将在第8章正式展开，本章只建立"是哪些类型在用、判断维度是什么"的框架。
