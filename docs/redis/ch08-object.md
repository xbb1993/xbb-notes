# 第8章 对象

## 核心概念

**要解决的问题**：前面六章讲的 SDS、链表、字典、跳跃表、intset、ziplist 都是裸的数据结构，直接暴露给上层会有两个问题：命令执行前无法判断"这个 key 当前是什么类型、能不能执行这个命令"；也没有统一的地方能"按场景在多种底层结构之间切换"。Redis 在这些数据结构之上包了一层对象系统解决这两个问题。

**`redisObject` 结构：**

```c
typedef struct redisObject {
    unsigned type:4;      // 类型：string/list/hash/set/zset
    unsigned encoding:4;  // 编码：具体用哪种底层数据结构实现
    void *ptr;             // 指向真正的底层数据结构
    int refcount;          // 引用计数
    unsigned lru:22;       // 最后一次被访问的时间
} robj;
```

数据库每个键值对，键总是字符串对象，值是 String/List/Hash/Set/Zset 五种类型对象之一。`type` 和 `encoding` 分离，是贯穿全书前几章"编码可以按场景切换"这一说法的正式落地机制。

**类型检查 vs 命令多态——两个不同维度的检查**：

- **类型检查**（基于 `type`）：执行类型特定命令前，先检查 key 的值对象 `type` 对不对，比如 `LLEN` 只能用于 `type` 为 List 的键，类型不对直接返回 `WRONGTYPE` 错误。
- **命令多态**（基于 `encoding`）：类型检查通过后，同一个命令还要按当前 `encoding` 选择不同的底层实现函数（`LLEN` 在 ziplist 编码下调 `ziplistLen`，在 linkedlist 编码下调 `listLength`）。
- `DEL`/`EXPIRE`/`TYPE` 这类不区分类型都能执行的命令，是另一种"基于类型的多态"，和上面"基于编码的多态"是不同维度的概念，不要混为一谈。

**字符串对象的三种编码——呼应第2章**：

- `int`：值能用 `long` 表示的合法整数时使用，整数直接存在 `ptr` 里，**完全不经过 SDS**。
- `embstr`：字符串值且长度 ≤32 字节，`redisObject` 和 `sdshdr` 用**一次内存分配**合并存在一块连续内存里，缓存友好、分配/释放开销小，但**只读**——没有为它实现任何修改函数。
- `raw`：字符串值且长度 >32 字节，`redisObject` 和 `sdshdr` 分开两次分配，是第2章讲的标准 SDS 用法。

`int`/`embstr` 在需要修改（长度变化、内容替换等）时会转换成 `raw` 再执行修改，转换单向、不可逆。判断能否用 `int` 编码看的是"能否被严格解析成合法整数"，带前导零的编号（如 `"007"`）解析不合法，不会是 `int` 编码。

**List / Hash / Set / Zset 的编码转换阈值对照**：

| 类型 | 紧凑编码 | 常规编码 | 触发紧凑编码的条件（需同时满足） |
|---|---|---|---|
| List | ziplist | linkedlist | 所有元素长度 <64字节 且 数量 <512个 |
| Hash | ziplist | hashtable | 所有键值长度 <64字节 且 键值对数量 <512个 |
| Set | intset | hashtable | 所有元素是整数 且 数量 <512个（**没有 ziplist 选项**） |
| Zset | ziplist | skiplist | 所有成员长度 <64字节 且 数量 <128个 |

**编码转换永远只能从紧凑到常规，不会反向**：数量/长度后来降回阈值以内，编码也不会自动转换回紧凑编码。这跟"数据结构内部能否收缩"是两个层次——比如 Hash 转成 hashtable 编码后，内部字典的 `dictht` 依然会按第4章的规则正常扩容收缩，但"这个对象的编码是 hashtable"这件事本身不会变回 ziplist。想让对象重新变紧凑，只能删除重建。

**引用计数与对象生命周期**：`refcount` 是所有对象通用的内存回收机制——创建时初始化为1，每被一处新引用 +1，每少一处引用 -1，减到0时对象被释放。对象生命周期分创建、操作、释放三阶段。"引用者"不限于数据库 key，还包括 Redis 服务器自身（对共享对象池的持有）、以及容器对象内部嵌套的字符串节点。

**对象共享机制**：服务器启动时预创建 0~9999 的整数字符串对象，key 保存的整数值若同时满足"能用 `int` 编码表示"和"数值落在 0~9999 范围内"两个条件，就让 key 直接指向共享对象、`refcount` +1，不新建对象。**只共享整数值的字符串对象**，不共享内容相同的字符串值对象或 List/Hash 这类复杂对象——因为要把共享对象用作 key 的值，必须先验证两者内容完全相同，验证成本随对象复杂度上升：整数 O(1)，字符串 O(N)，嵌套多值对象 O(N²)，权衡下来只对验证成本几乎为零的整数做共享。

**共享对象实际上不会被回收**：服务器自身持有的那份引用是刻意设计成永不主动释放的——只要服务器进程活着，共享对象的 `refcount` 就不会归零，这是为了保证共享池长期存在、不会因为某一刻没有 key 在用就被回收掉、下次又得重新创建。引用计数机制真正处理的"主战场"是绝大多数**非共享**的普通对象：一个 key 被删除或覆盖，它唯一引用的 value 对象 `refcount` 归零，内存立即释放，这是日常内存回收的主流路径，跟共享对象几乎无关。

**对象的空转时长**：`lru` 属性记录对象最后一次被命令访问的时间，`OBJECT IDLETIME key` 用当前时间减去这个值计算空转时长（该命令本身不会更新它查看的 `lru`）。当 `maxmemory` 开启且淘汰策略为 `volatile-lru`/`allkeys-lru` 时，空转时长大的键会被优先淘汰。`lru` 挂在**值对象**而不是键对象上，是一个可以商榷的设计取舍：贴合"淘汰真正要省的是 value 占的大块内存"这个目标，也是命令执行路径上自然会 touch 到的点；代价是当 value 被多个 key 共享时，`lru` 是共用的同一份，无法精确区分具体是哪个 key 最近被访问。

## 易混淆/易错点

- **不要把"引用计数机制"和"共享对象是否会被回收"混为一谈**：引用计数是所有对象通用的回收机制，共享对象只是恰好可能有多个引用者的特例，而且因为服务器持有永久引用，实际上走不到 `refcount` 归零那一步——回收的主流场景是普通的非共享对象。
- **不要以为 embstr 是"更优、可修改"的编码而刻意追求它**：embstr 只读，任何修改命令都会先不可逆地转成 raw，如果字符串会被频繁修改，很快就会变成 raw，享受不到 embstr 的优势。
- **不要以为"值相同就会共享"**：只共享 `int` 编码、且数值在 0~9999 范围内的字符串对象；内容相同的字符串值对象（如两个 key 都存 `"hello"`）、或者数值相同但超出 0~9999 的整数（如两个 key 都存 `50000`），都不会共享。
- **"看起来像数字"不等于会被识别成 int 编码**：带前导零的编号（如 `"007"`）按整数解析规则不合法，会被存成 embstr/raw，不享受 int 编码和共享池的优势。
- **对象编码转换和数据结构内部的弹性伸缩是两个层次**：编码转换（如 Hash 从 ziplist 变 hashtable）单向不可逆；但转换后的底层结构（比如字典）内部依然可以正常扩容收缩，不要把两者混为一谈。
- **"引用"不限于数据库 key**：还包括服务器自身对共享对象池的持有，以及容器对象内部嵌套的字符串节点，这些都是可能的引用来源。
- **`lru` 挂在值对象上是设计取舍，不是唯一正确答案**：这个设计和对象共享机制天然兼容（不用给每个 key 单独维护状态），代价是共享场景下无法精确区分具体 key 的访问时间；如果挂在键对象上则相反。两种方案各有利弊，不存在绝对的对错。

## 与其他章节的关联

- **第2章「SDS」**：字符串对象的三种编码里，只有 `embstr`/`raw` 真正对应 SDS 实现，`int` 编码完全不涉及 SDS，是本章对第2章"一个 key 是否对应一个 SDS 要看类型和编码"这句话的精确落地。
- **第3章「链表」**：List 对象的 `linkedlist` 编码就是第3章的双端链表，转换阈值（长度<64字节且数量<512）是本章新给出的具体数字。
- **第4章「字典」**：Hash/Set 对象的 `hashtable` 编码就是第4章的字典；字典内部的扩缩容规则（第4章讲的负载因子）和"对象编码转换是否可逆"是两个独立层次，不能混淆。
- **第5章「跳跃表」**：Zset 对象的 `skiplist` 编码对应第5章的 `zset`（字典+跳跃表组合），转换阈值是长度<64字节且数量<128。
- **第6章「整数集合」**：Set 对象的 `intset` 编码，转换阈值是全部为整数且数量<512，Set 没有 ziplist 选项，是本章编码表里唯一的特例。
- **第7章「压缩列表」**：List/Hash/Zset 的紧凑编码都是第7章的 ziplist，本章正式给出了三者各自的转换阈值。
- **第9章「数据库」（待学）**：数据库的键空间本身就是一个字典，键值对的值就是本章的对象；对象引用计数为0时的释放，和过期键的删除策略会在第9章进一步展开。
- **第10/11章「RDB/AOF持久化」（待学）**：持久化文件里保存的正是各类型对象及其编码信息，重启恢复数据时如何重建共享对象池，是后续可以关注的点。
