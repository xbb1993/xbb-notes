# 第9章 数据库

## 核心概念

**数据库的物理结构**：服务器所有数据库存在 `redisServer.db` 数组里，数量由 `dbnum` 决定（默认16个），`SELECT n` 本质是让客户端切换指向 `db[n]`。每个 `redisDb` 结构核心是两个字典：

```c
typedef struct redisDb {
    dict *dict;     // 键空间：保存所有键值对
    dict *expires;  // 过期字典：只保存设置了过期时间的键
    // ...
} redisDb;
```

**为什么过期时间单独开一个字典**：如果把过期时间直接作为字段嵌进每个 value 对象，大部分没设置过期时间的 key 会白白浪费这块空间，还会破坏第8章讲的 `int` 编码这类紧凑对象的紧凑性。单独开一个字典，只存"设置了过期时间"的那部分 key，两个字典里的键**指向同一个键对象、不重复存储**，跟第8章的对象共享是同一种"指针共享"思路。

**键空间操作即字典操作**：数据库的增删改查本质上都是对键空间 `dict` 的字典操作（第4章字典的一次具体应用）。读写键空间时，服务器还会顺带做几件维护动作：更新命中/不命中统计、更新键的 `lru` 时间（第8章）、检查并处理过期键、给 `WATCH` 的键打"脏"标记（第19章）、`dirty` 计数器 +1（触发持久化/复制）、按配置发送数据库通知。

**设置过期时间**：`EXPIRE`（秒/相对）、`PEXPIRE`（毫秒/相对）、`EXPIREAT`（秒/绝对）、`PEXPIREAT`（毫秒/绝对）四个命令，最终都统一转换成 `PEXPIREAT` 执行——多个用户友好的入口收敛到一种内部标准表示（毫秒级绝对时间戳），只需要维护一套判断过期的逻辑。判断是否过期：查 `expires` 字典拿到期时间戳，跟当前时间比较。

**三种过期删除策略的权衡**：

| 策略 | 内存友好度 | CPU 友好度 | 说明 |
|---|---|---|---|
| 定时删除 | 最好 | 最差 | 每个过期时间建一个定时器，到点立即删；海量定时器不现实（第12章时间事件用无序链表实现，查找 O(N)） |
| 惰性删除 | 最差 | 最好 | 只在访问时检查删除；长期不被访问的过期键会一直占内存，书里称之为类似"内存泄漏" |
| 定期删除 | 折中 | 折中 | 定时批量抽查一部分键，删除过期的，是前两者的折中 |

**Redis 实际采用惰性删除 + 定期删除组合**（不用定时删除）：

- 惰性删除由 `expireIfNeeded` 实现，所有读写命令执行前都会调用；命令实现必须同时处理"键存在"和"键不存在（含被删除）"两种情况。
- 定期删除由 `activeExpireCycle` 实现，跟着 `serverCron` 周期性触发，**分批、随机抽样**：每次遍历最多16个数据库，每个库随机抽查最多20个"带过期时间的键"，删除其中过期的，有时间上限；用 `current_db` 记录进度，下次接着往后查。**不是全量扫描，不保证一次清理干净**，惰性删除是它的必要补充。

**定期删除为什么随机抽样，而不是按"删除收益"排序**（比如借鉴 G1 GC 的 Garbage First 思路）：G1 能按垃圾量排序回收，是因为"每个 region 有多少垃圾"这个信息是它标记阶段**本来就要算**的副产品，几乎零额外成本；而 Redis 的 `expires` 字典只存"key→过期时间"，不知道每个 key 对应的 value 有多大，`MEMORY USAGE` 这类计算内存占用的操作本身是 O(N) 遍历，为了排序去主动计算反而增加了定期删除本该避免的开销；而且维护一个持续更新的排序结构，会把成本摊到所有日常写操作的热路径上。定期删除的目标只是"最终清理、少占 CPU"的常规后台任务，不是内存紧急告警下的精打细算——真正对应"内存紧张需要精打细算"的场景是 `maxmemory` 触发的淘汰策略（`volatile-lru`/`allkeys-lru`/`volatile-ttl` 等），而即便是这套更聪明的淘汰机制，Redis 用的也是"随机抽样候选、比较后选最优"的近似算法，而非维护一个精确排序结构——这跟定期删除的随机抽样是同一种设计哲学：能不维护额外统计/排序结构就不维护，需要"聪明选择"的场景也优先用抽样近似。

**过期键对持久化和复制的影响**：

| 场景 | 处理方式 |
|---|---|
| `SAVE`/`BGSAVE` 生成 RDB | 过期键不写入新 RDB 文件 |
| 主服务器载入 RDB | 过期键被过滤，不载入 |
| 从服务器载入 RDB | 过期键照样载入（不过滤），但主从同步时从库数据库通常会被清空重建 |
| AOF 写入 | 过期键被删除时，显式追加一条 `DEL` 命令到 AOF 文件 |
| AOF 重写 | 过期键不写入重写后的文件 |
| 复制（主从） | **由主服务器统一控制**：从库自己发现过期键不会主动物理删除，只有收到主库发来的 `DEL` 才删除 |

**复制场景下"主库统一控制删除"是刻意的一致性设计**：如果从库各自根据自己的判断（可能受时钟不同步影响）擅自删除，会导致主库和多个从库之间对"某个 key 是否存在"产生**永久性分歧**，这比"从库稍晚一点删除"更危险。这个设计的代价是：主写从读架构下，一个长期不被访问、又没被主库随机抽样命中的过期 key，可能在相当长一段不确定的时间里，从库都还能读到它的旧值——这个不一致窗口的主要来源是**主库自己何时"发现"这个过期 key 存在不确定性**（取决于有没有人访问触发惰性删除、或定期删除有没有抽样命中），而不只是网络复制延迟；主库自己的读请求因为每次都走 `expireIfNeeded` 实时判断，读一致性始终是准的，只有从库的读一致性依赖这个不确定窗口。

**为什么不让从库检测到过期后"通知"主库去删除**：这是一个直觉上很自然的改进方案（把惰性删除"访问触发检查"的思路从单机扩展到主从之间），但没有被采用，原因有三层：

1. **主库不能无条件相信从库的判断**：从库和主库可能存在时钟不同步，如果从库时钟偏快，可能会把"实际还没过期"的 key 误判为过期并通知主库删除——如果主库无条件听从，会造成**提前删除**，这比"稍晚删除"是更严重的错误（可能导致数据永久丢失）。所以主库收到通知后，依然要用自己的时钟重新独立验证一遍，这条通知消息的实际作用只是"提醒主库现在就去检查这个 key"，并没有绕开"最终删除决定权必须在主库、且主库要独立验证"这一原则，效果上等价于加速了一次随机抽样命中。
2. **需要新增一条反向通信通道**：Redis 复制的数据流本来是主库到从库单向的，"从库通知主库"要在这之外单独设计一套反向协议，是额外的实现和维护成本。
3. **存在"通知风暴"风险**：如果冷门过期 key 数量较多、又被多个从库的大量读流量频繁触发，没有去重/限流机制的话，会让从库的读流量直接转化成主库的额外处理压力——尤其在读写分离、从库读流量远大于主库写流量的架构里，这个代价可能超过"缩短一个本就有兜底机制的不一致窗口"带来的收益。

**给实际架构的落地建议**：如果业务采用主写从读架构，且某些场景强依赖 TTL 的精确生效（比如用过期时间做会话失效判断），在本书讲的这个版本语义下，可以考虑：时效性要求高的判断直接读主库而不依赖从库结果；给这类 key 设置更短的 TTL 缩小影响窗口；或者应用层对关键判断做一次二次校验（比如追加一次 `EXISTS` 之类的确认）。这些都是用一点点额外的读成本，换取正确性保证。

**（补充，非本书内容）现行 Redis 版本的"读时本地屏蔽"**：查证 Redis 官方复制文档，现在的 Redis 在从库上会用自己的逻辑时钟，**只针对读操作**把一个物理上还存在、但逻辑上已过期的 key 回复成"不存在"，但不会物理删除它，真正的删除依然完全由主库的 `DEL` 命令决定。这解决了"客户端从从库读到脏数据"这个具体问题，但没有改变"谁来决定真正删除时机"这一核心原则，也没有引入从库向主库反向通知的机制（也就是说，上面第一点分析的"通知机制"始终没有被采用，现行版本用的是"本地屏蔽读结果"这个更轻量的替代方案）。本书基于 Redis 2.9/3.0 时代，书里描述的是从库把旧值原样返回给客户端的更简单的行为，与这个补充机制不同。

**数据库通知**：Redis 2.8 新增，客户端通过订阅频道感知键的变化，分键空间通知（关注某个 key 执行了什么命令）和键事件通知（关注某个命令被什么 key 执行）两类，底层复用 `PUBLISH`（第18章），按需通过 `notify-keyspace-events` 配置开启。

## 易混淆/易错点

- **不要以为定期删除是全量扫描**：它只是从每个数据库的 `expires` 字典里随机抽样一小部分检查，有时间上限，不保证一次执行就能清理干净所有过期键，惰性删除是必要的兜底。
- **不要以为有定期删除兜底，"内存泄漏"风险就不存在了**：冷门、长期不被访问的过期键，既可能不被随机抽样命中，也不会触发惰性删除，风险被大幅降低但没有被彻底消除。
- **从库故意不自己删过期键，不是设计疏漏**：是为了保证主从数据一致性的中心化设计——如果从库各自判断删除，容易因为时钟不同步等原因造成主从之间"某个 key 是否存在"的永久性分歧，比统一延迟删除更危险。
- **主从架构下过期键的不一致窗口，主要来源不是网络复制延迟，而是主库自己何时"发现"过期键的不确定性**：这个窗口可能远超正常复制延迟的毫秒级量级，尤其是冷门 key。主库自己的读请求因为走实时的 `expireIfNeeded` 判断，读一致性始终是准的，只有从库的读一致性依赖这个不确定窗口。
- **定期删除按随机抽样而不是按"删除收益"排序，不是想不到更好的算法**：是因为 Redis 不知道每个候选 key 的内存占用（要算的话本身是 O(N) 遍历），且维护一个持续更新的排序结构会把成本摊到所有日常写操作上——这跟全书反复出现的"不为不常发生的场景在热路径上加额外维护成本"是同一种设计哲学，`maxmemory` 淘汰用的近似 LRU 算法（随机抽样候选再比较）也是同一个思路。
- **不要把"过期字典"和"淘汰策略（maxmemory-policy）"混为一谈**：过期字典 `expires` 和过期删除策略（惰性+定期）解决的是"到点该删的键什么时候被清理"；`maxmemory` 淘汰策略解决的是"内存不够用了，该牺牲哪些键腾地方"，两者是不同层次的机制，只是 `volatile-lru`/`volatile-ttl` 这类淘汰策略也会用到 `expires` 字典的信息。
- **"从库通知主库删除"这个直觉方案没被采用，不是因为技术上做不到**：而是因为主库依然要独立重新验证（不能无条件信从库的判断，否则时钟不同步可能导致提前误删），这条通知的实际作用只是加速一次检查，收益有限；同时需要新增反向通信通道、还有通知风暴的风险，工程上不划算。

## 与其他章节的关联

- **第4章「字典」**：数据库的键空间 `dict` 和过期字典 `expires` 都是字典的具体应用，是第4章笔记里提到过的"数据库键空间/过期字典"这个场景在本章的正式展开。
- **第8章「对象」**：键空间和过期字典的键指向同一个键对象、不重复存储，是对象共享思路的又一体现；读键时更新 `lru` 字段、`OBJECT IDLETIME` 的数据来源都在本章的"读写键空间维护动作"里。
- **第12章「事件」（待学）**：定时删除策略之所以不现实，是因为 Redis 当前时间事件用无序链表实现，查找一个事件是 O(N)，不支持高效管理海量定时器，本章提前埋了这个伏笔。
- **第10章「RDB持久化」/第11章「AOF持久化」（待学）**：过期键不写入 RDB/AOF（重写）文件、过期键被删除时追加 `DEL` 到 AOF，是本章规则在持久化模块的具体体现，两章会有更完整的实现细节。
- **第15章「复制」（待学）**：本章"主库统一控制过期键删除、从库被动等待 DEL"只是复制机制处理过期键这一个具体场景，复制的完整实现原理会在第15章展开。
- **第19章「事务」（待学）**：`WATCH` 命令依赖的"键被修改后标记为脏"这个机制在本章读写键空间的维护动作里提到，完整实现在第19章。
- **第18章「发布与订阅」（待学）**：数据库通知功能底层复用 `PUBLISH` 命令的实现，完整机制第18章讲。
