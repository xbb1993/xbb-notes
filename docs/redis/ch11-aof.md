# 第11章 AOF持久化

## 核心概念

**要解决的问题**：RDB 通过保存"某一时刻的键值对"来记录数据库状态；AOF（Append Only File）走的是完全不同的路子——**记流水账**：不保存数据本身，而是把服务器执行过的每一条写命令，按 Redis 命令请求协议（RESP，纯文本格式）追加保存到文件里。故障恢复时，把这些命令重新执行一遍，就能还原出当时的数据库状态。这跟 RDB "定期拍照"是两种完全不同的持久化哲学。

### 11.1 AOF 持久化的实现：命令追加 → 文件写入 → 文件同步

**命令追加**：写命令执行完之后，不碰磁盘，只是以协议格式追加进服务器状态里的内存缓冲区 `aof_buf`（本质是个 SDS）。比如 `SET KEY VALUE` 执行完，追加进去的是 `*3\r\n$3\r\nSET\r\n$3\r\nKEY\r\n$5\r\nVALUE\r\n`。因为是纯文本协议，AOF 文件可以直接打开用肉眼读——这是和 RDB 二进制格式最直观的差异。

**文件写入与同步**：Redis 服务器本质是一个事件循环，每一轮处理完文件事件（接收命令、执行、发送回复）和时间事件之后，都会调用一次 `flushAppendOnlyFile` 函数，决定要不要把 `aof_buf` 里攒的内容写进 AOF 文件、以及要不要同步：

```python
while True:
    processFileEvents()    # 处理命令请求，可能往 aof_buf 追加内容
    processTimeEvents()     # 处理定时任务
    flushAppendOnlyFile()   # 这一轮结束前，决定要不要写文件、要不要同步
```

**`write` 和 `fsync`（`save`）不是一回事**——这是整章最容易被忽视但最关键的一层机制。`write` 系统调用只是把数据从用户态拷进内核的页缓存，操作系统会在未来某个时机（缓冲区满或超过时限）才真正把页缓存刷到物理磁盘；`fsync`/`fdatasync` 则是强制立即刷盘的系统调用，调用它才能真正确保数据落盘，但要等真实磁盘 I/O 完成，代价较高。如果只是 Redis 进程崩溃（操作系统还活着），已经 `write` 过的数据仍会被内核自动刷盘，不会丢；只有操作系统崩溃/断电，`write` 过但没被 `fsync` 的数据才会真的丢失。

**`appendfsync` 三档配置**——不只是"频率不同"，更本质的区别在于 `fsync` 是同步阻塞主线程执行、还是丢给子线程异步执行：

| 配置 | `write` 频率 | `fsync` 时机 | 性能 | 最坏丢失窗口 |
|---|---|---|---|---|
| `always` | 每个事件循环都写 | 每个事件循环都**同步**执行（阻塞主线程等它完成） | 三档最慢 | 一个事件循环产生的命令量（近似不丢） |
| `everysec`（默认） | 每个事件循环都写 | 每隔1秒，由**子线程**异步执行一次 | 足够快 | 1秒内的命令 |
| `no` | 每个事件循环都写 | 不主动调用，交给操作系统自行决定 | `write` 最快，但攒积数据的单次同步耗时通常最长 | 上次操作系统自己刷盘之后的所有命令，窗口不可控 |

三档的 `write` 频率完全一样，真正拉开效率差距的是 `fsync` 是否阻塞主线程——`always` 慢在"每轮事件循环都要等一次真实磁盘 I/O 完成才能继续"，`everysec` 快在"`fsync` 被丢给独立子线程，主线程不用等"。

**`no-appendfsync-on-rewrite`**：可配合 `always`/`everysec` 使用，`BGSAVE`/`BGREWRITEAOF` 执行期间暂停对 AOF 文件的同步，减少 I/O 争抢，但代价是这段时间内即使是 `always` 模式，也不再能保证"最坏只丢一个事件循环"，事务的持久性（第19章）也随之失去保证。默认关闭。

### 11.2 AOF 文件的载入与数据还原：伪客户端重放

**朴素方案的问题**：如果直接解析 AOF 文件里的命令文本，手写一套"命令 → 底层数据结构操作"的翻译逻辑，等于要为每种命令维护两条执行路径（正常请求路径 + AOF 载入路径），容易出现两条路径行为不一致的隐蔽 bug（比如某个类型检查漏做）。

**实际方案：伪客户端（fake client）**——创建一个不带网络连接的伪客户端，把 AOF 文件里的命令按顺序"喂"给它，复用 Redis 正常处理客户端命令的那条完整链路（协议解析、命令分派、参数校验、类型检查等），执行效果和真实客户端完全一样，只是回复不会经网络发出去：

```
1) 创建不带网络连接的伪客户端
2) 从 AOF 文件读出一条写命令 ──┐
3) 用伪客户端执行这条命令       │ 重复，直到文件读完
   ◄────────────────────────────┘
```

AOF 文件里会包含一条服务器自动添加的 `SELECT` 命令来确保后续命令落在正确的数据库——这跟第10章 RDB 用 `SELECTDB` 自定义常量做的是同一件事，但 AOF 这里用的是一条**真实会被执行的 Redis 命令**，而不是发明新的格式常量，和"AOF 记的就是命令"这条设计哲学一致。

**代价**：AOF 载入的耗时和文件里积累的命令总数成正比，而不是和数据库最终状态的大小成正比——如果一个 key 被反复修改过很多次，恢复时要把这些历史命令全部重放一遍才能拿到最终状态,这跟 RDB 直接反序列化二进制结构（复杂度只取决于最终数据量）是本质不同的两种代价模型。这正是下一节 AOF 重写要解决的问题的直接动机。

### 11.3 AOF 重写：定期批量重建，而不是实时合并

**问题**：AOF 持续记录写命令，文件会越来越大，体积过大不仅影响宿主机，也会拖慢载入还原的速度。

**核心原理（容易被名字误导）**："AOF 重写"这个名字听起来像是"读取并整理旧文件"，但实际上**完全不读、不分析、不改写现有 AOF 文件**——重写程序直接从**当前数据库状态**读出每个 key 的现有值，反向构造出一条能重建这个值的最小等效命令，写进一个全新的文件。比如一个 `list` 键历史上被 `RPUSH`/`LPOP` 了六次，重写时不看这六条命令是什么，直接读它现在的值 `[C,D,E,F,G]`，生成一条 `RPUSH list C D E F G` 就够了。

**为什么不做成"实时合并"（写入时就把新命令和历史命令合并）**：

- 文件层面：AOF 是顺序追加的文本流，"合并"意味着要原地改写文件中间已经写过的一段内容，新旧命令字节长度往往不同，原地变长替换需要搬移后续全部内容，开销大且崩溃时容易产生半写损坏——这是顺序日志类存储的通病，不是 Redis 特有限制。
- 语义层面：判断"新命令能否和历史某条命令合并"需要为**每一种命令**单独定义合并规则（`INCR` 算不算？带随机性的命令呢？），规则数量随命令种类增长，容易出错。
- 路径层面：实时判断+原地改写的开销会叠加在最高频的写命令路径上，与"AOF 记录本该轻量"的设计初衷相悖。

**实际方案的巧妙之处**："读当前状态生成命令"是**命令无关**的通用逻辑——不管历史上执行过什么命令、语义多复杂，重写只需要"读现状、生成对应类型的构造命令"，正确性天然有保证（源于真实当前状态，不可能对不上），不需要为每种命令写合并规则。

**为什么放进子进程，而不是普通线程**：`aof_rewrite` 函数本身耗时长，直接在主线程跑会长时间阻塞服务器。用普通线程虽然不阻塞主线程，但线程共享内存地址空间，重写线程读数据库和主线程改数据库需要加锁保护，复杂且有性能代价。用 `fork` 子进程则凭借 COW 机制天然拿到一份独立的数据快照，不需要加锁就能安全读取，父进程完全不受影响、继续正常处理请求。

**新问题：子进程手里的数据会"过期"**——子进程从 `fork` 时刻开始生成新文件，如果重写期间父进程执行了新的写命令，子进程看不到这些变化，生成的新文件只反映"重写开始那一刻"的状态。

**解法：AOF 重写缓冲区（`aof_rewrite_buf`）**——从创建子进程开始，父进程执行的每条写命令，同时追加到 `aof_buf`（照常处理现有文件）和 `aof_rewrite_buf`（专门记录 fork 之后的新变化）：

```
父进程执行完写命令
    ├──▶ aof_buf         （现有 AOF 文件照常处理）
    └──▶ aof_rewrite_buf  （记录 fork 之后的新变化）
```

子进程完成新文件后向父进程发信号，父进程的信号处理函数执行两件事：①把 `aof_rewrite_buf` 的全部内容追加到新文件末尾（使新文件和当前数据库状态一致）；②对新文件改名，**原子地**覆盖现有 AOF 文件，完成新旧替换。整个过程中，**只有信号处理函数执行的这一小段时间会阻塞父进程**，其余时间（子进程生成新文件期间）父进程正常处理请求。

**载入 vs 重写：方向正好相反**——载入是"命令 → 数据"（伪客户端真实执行历史命令，重建内存状态）；重写是"数据 → 命令"（直接读内存现状，反向构造出命令写入文件）。不要把两者当成同一套机制的正反面。

**实操细节**：重写生成命令时，List/Hash/Set/Zset 若元素数量超过 `REDIS_AOF_REWRITE_ITEMS_PER_CMD`（值为64），会拆成多条命令（每条最多64个元素），避免单条命令过大撑爆缓冲区——"用最少命令表达现状"这个目标仍然要服从"单条命令不能无限大"的现实约束。

### 讨论衍生问题（已在讨论中解决，笔记留档）

**"RDB记录慢恢复快，AOF记录快恢复慢"是否成立**：**恢复维度完全成立**——RDB 恢复是 O(最终数据量)（直接反序列化，与历史操作次数无关），AOF（未重写）恢复是 O(历史写命令总数)（逐条重放，可能远超最终数据量）。**记录维度需要澄清**：RDB 单次记录动作"重"（fork+全量遍历写盘）但触发频率低、且 `BGSAVE` 不阻塞主线程；AOF 单条记录"轻"（只追加协议文本）但发生频率是每条写命令一次。不是"RDB 记录会拖慢线上请求"，而是"两者的开销分布完全不同"：RDB 是"低频、单次贵、不阻塞"，AOF 是"高频、单次便宜"。

**为什么不做命令级实时压缩合并**：这正是 AOF 重写在做的事，只是选择"定期批量"而不是"实时"——原因见上文"为什么不做成实时合并"三点（文件层面的原地改写代价、语义层面的合并规则爆炸、路径层面不该拖慢高频写路径）。批量重写的代价：`fork`+遍历全量数据库本身有开销，如果两次重写之间数据没怎么膨胀，这次开销基本浪费——这是为什么触发重写用的是膨胀比例（`auto-aof-rewrite-percentage`/`auto-aof-rewrite-min-size`）而不是无脑高频触发，跟第10章 RDB 的多档 `save` 条件是同一种"别太频繁做重量级操作"的权衡。

### 生产实战：持久化选型与一致性/成本的取舍（本章学完后的专题讨论，超出本书范围）

**先拆开"一致性"这个词的两层含义**：一层是**文件自身的自洽性**（有没有损坏、能不能被正常解析——RDB 靠 `check_sum`，AOF 靠协议格式完整性），另一层是**文件内容与故障那一刻真实数据库状态的接近程度**，也就是**数据丢失窗口**。生产里讨论"一致性够不够"，几乎总是在说第二层，下面的讨论也聚焦这一层。

**用两个可量化指标代替空谈"一致性"**：

- **RPO（Recovery Point Objective，允许丢多少数据）**：故障发生时最多能接受丢失多长时间/多少条写操作。
- **RTO（Recovery Time Objective，允许恢复花多久）**：故障之后服务要多久能重新可用。

这两个指标直接对应到本章和上一章学过的机制：

| 配置/方案 | 对应 RPO | 对应 RTO |
|---|---|---|
| 只用 RDB（`save` 多档条件） | 上次快照到故障的全部时间窗（可能是分钟级） | 快——直接反序列化，O(数据量) |
| AOF `appendfsync=no` | 不可控，取决于操作系统刷盘时机 | 慢（未重写）——O(历史命令数) |
| AOF `appendfsync=everysec`（默认） | 最坏1秒 | 慢（未重写）——O(历史命令数) |
| AOF `appendfsync=always` | 近似0（一个事件循环） | 慢（未重写）——O(历史命令数)，且性能有代价 |
| AOF + 定期重写 | 同上（取决于 `appendfsync`） | 明显改善，接近 O(数据量)（重写清空了历史冗余命令） |
| RDB+AOF 混合持久化（现代 Redis，见下） | 跟随 AOF 的 `appendfsync` | 接近 RDB 的速度 |

**成本侧：`always` 换来的一致性，实际在换什么**：把 RPO 压到近似0，代价是主线程要在每个事件循环同步等一次真实磁盘 I/O——本质是"用磁盘性能换一致性"，机械盘上代价很明显，SSD/NVMe 能缓解但不能消除。这也是 `everysec` 作为默认值、且是大多数生产场景实际选择的原因：用"最坏丢1秒"换来主线程几乎不被拖慢，这个交易在大多数业务上是划算的。

**必须说清楚的局限性**：持久化解决的只是"进程重启/单机故障后能不能恢复数据"这一类问题。如果是磁盘物理损坏、整台机器不可用，本地 RDB/AOF 文件跟着一起没了，`always` 也救不了——真正的高可靠架构，单机持久化只是第一道防线，必须叠加多机复制（模块四要学的复制/Sentinel/集群），这是持久化配置本身解决不了的边界。

**现代 Redis 的答案：混合持久化（`aof-use-rdb-preamble`，Redis 4.0+，默认开启，本书未覆盖）**：AOF 重写时不再生成纯文本等效命令，而是把当前数据库状态直接按 **RDB 格式**写在新 AOF 文件开头（preamble），后面再追加重写之后新产生的少量增量命令：

```
[RDB格式的数据快照] + [重写之后新产生的AOF命令流(通常很少)]
```

载入时先按 RDB 方式反序列化前半部分（快，O(数据量)），再对后半部分少量增量命令做伪客户端重放（因为紧跟重写发生，数量天然很少，耗时可忽略）。这相当于同时拿到了 RDB 的恢复速度和 AOF 的低丢失窗口，正是对本章"AOF 载入慢"这一局限的正式解法。

**按场景的选型建议**：

| 场景 | 建议 | 理由 |
|---|---|---|
| 纯缓存、数据能从源头（DB/计算）重建 | 关闭持久化，或只留低频 RDB 兜底 | 丢了能接受/能重建，持久化开销纯粹是浪费 |
| 常规业务数据（多数场景） | AOF `everysec` + 混合持久化（默认）+ 定期 RDB | 秒级丢失窗口多数业务可接受，混合持久化解决了恢复速度问题 |
| 计费、订单、审计类，丢失容忍接近0 | AOF `always`，配合 SSD/NVMe，且必须叠加多机复制 | 单机 `always` 只解决进程级故障，机器级故障要靠复制 |
| 灾备快照、跨机房迁移、离线分析 | 定期 RDB（即使已开 AOF，也额外留一份） | 文件体积小、格式自描述、适合搬运归档，AOF 不适合做"某个时间点整体快照"用途 |

**恢复时的实操细节（运维经验，非书本内容）**：RDB 和 AOF 同时开启时，服务器重启默认优先用 AOF 还原（通常更接近实时）。AOF 文件因断电导致尾部命令不完整时，可以用 `redis-check-aof` 工具修复（截掉不完整的最后一条命令）；`redis-check-rdb` 用于检测 RDB 文件损坏。这两个工具留个印象，具体用法留到模块五的运维专题细讲。

## 易混淆/易错点

- **`write` 成功 ≠ 数据已经落盘**：`write` 只是把数据拷进内核页缓存，只有 `fsync` 才能确保真正写到物理磁盘。这个区分是理解 `appendfsync` 三档配置到底"防住什么"的前提，也是"Redis 进程崩溃"和"操作系统崩溃/断电"两种故障下丢失情况不同的根本原因。
- **`always` 和 `everysec` 的差别不只是"频率不同"**：更本质的区别是 `fsync` 是否阻塞主线程——`always` 同步阻塞，`everysec` 丢给子线程异步执行，这是 `everysec` 性能远好于"简单粗暴地把 always 频率降低"这种直觉推算的根本原因。
- **AOF 载入不是"反序列化数据"，是"重放命令"**：伪客户端把 AOF 文件里的命令当成真实请求重新执行一遍，效果等同于把这些命令在 `redis-cli` 里重新敲一遍，这跟 RDB 直接把二进制结构铺进内存是两种完全不同的还原哲学。
- **AOF 重写不读、不分析、不改写旧文件**：这是一个容易被名字误导的点——"重写"读的是**当前数据库状态**，不是旧 AOF 文件，不能理解成"压缩/整理现有日志"。
- **AOF 重写不是命令级实时合并**：合并的时机是"定期批量"（`BGREWRITEAOF` 触发时一次性重建），不是"每次写入都尝试就地合并历史命令"，原因是原地改写文件代价高、命令语义合并规则复杂、且不该拖慢高频写路径。
- **重写用子进程而不是线程，是为了免锁而不是单纯为了不阻塞**：免锁（COW 天然隔离数据）和不阻塞主线程，是两个独立但都成立的理由，不要只记住"不阻塞"这一半。
- **AOF 载入（命令→数据）和 AOF 重写（数据→命令）方向相反**：不要把两者当成同一套机制的两个阶段，一个是重放历史，一个是给现状生成命令快照。
- **"RDB 记录慢"不等于"RDB 会拖慢线上请求"**：`BGSAVE` 靠子进程执行不阻塞主线程，"慢"指的是单次操作重、触发频率低，不是字面意义上的实时拖慢。
- **"一致性"这个词生产讨论时通常混着两层**：文件自身有没有损坏（自洽性，靠 `check_sum`/协议完整性）和文件内容离故障那一刻真实状态差多远（丢失窗口）。讨论"持久化一致性够不够"基本都在说后者，不要跟前者混着答。
- **`appendfsync=always` 不是"绝对不丢数据"的保证**：一旦开启 `no-appendfsync-on-rewrite`，重写期间 `always` 也会退化，"最坏丢一个事件循环"这个承诺不再成立；而且 `always` 只覆盖单机进程/系统级故障，磁盘物理损坏或整机不可用时照样没用，必须靠多机复制兜底。
- **混合持久化（`aof-use-rdb-preamble`）不是"AOF 和 RDB 二选一变成都要"，而是把两者物理拼进同一个 AOF 文件**：文件前半段是 RDB 格式的快照，后半段是少量 AOF 增量命令，载入时两段分别用各自的方式处理，不要理解成"同时维护两份独立文件"。

## 与其他章节的关联

- **第2章「SDS」**：`aof_buf`、`aof_rewrite_buf` 本质都是 SDS 缓冲区，命令协议文本的追加操作复用的是 SDS 的动态扩容能力。
- **第4章/第10章「COW」**：AOF 重写用子进程+`fork`，和 RDB 的 `BGSAVE`、以及第4章讨论的"`BGSAVE`/`BGREWRITEAOF` 期间调高 rehash 阈值"，是同一个 COW 机制的第三次具体应用——都是靠"fork 时刻的内存快照天然隔离、无需加锁"来解决"子进程要安全读取数据、父进程还要继续正常工作"这个共性问题。
- **第9章「数据库」**：AOF 文件里的 `SELECT` 命令和第10章 RDB 的 `SELECTDB` 常量做的是同一件事（确保后续操作落在正确数据库），但表达方式不同——一个是真实命令，一个是格式常量，这是"AOF 记的是命令、RDB 记的是数据"这条根本差异的具体体现。
- **第10章「RDB持久化」**：`BGSAVE` 执行期间 `BGREWRITEAOF` 会被延迟（上一章讲过），`no-appendfsync-on-rewrite` 配置进一步说明了 `BGSAVE`/`BGREWRITEAOF` 执行期间 AOF 同步策略的联动关系；RDB 恢复 O(数据量) vs AOF 恢复 O(命令数) 是两章内容合起来才能得出的完整对比。
- **第19章「事务」（待学）**：事务的持久性（durability）只有在 `appendfsync=always` 且未开启 `no-appendfsync-on-rewrite` 时才成立，本章讨论的这两个配置项直接决定第19章事务 ACID 性质里 D 这一条是否成立。
- **模块五「现代 Redis 补充篇」（待学）**：本书未覆盖的 RDB+AOF 混合持久化格式（`aof-use-rdb-preamble`）已在本章的生产实战讨论里提前讲过原理，是对"AOF 恢复慢"这一局限的现代解法；模块五会结合运维工具（`redis-check-aof`/`redis-check-rdb`）和更多现代特性做进一步补充。
- **第15-17章「复制/Sentinel/集群」（待学）**：生产实战讨论里点出的"单机持久化解决不了磁盘物理损坏/整机不可用"这个局限，正是复制、Sentinel、集群这几章要解决的问题——持久化和多机复制是两道独立但互补的防线，不能用一个代替另一个。
- **持久化生产实战讨论（已完成，见上文"生产实战"小节）**：呼应上一章约定推迟到本章学完后讨论的"持久化一致性与成本取舍""不同场景选型"这两个问题，用 RPO/RTO 两个指标给出了量化的判断框架和场景化选型表。
