# 第12章 事件

## 核心概念

**要解决的问题**：Redis 单线程处理命令，但要同时应付大量客户端连接、还要按时做过期键清理、持久化触发检查这类"没有客户端请求也得主动做"的维护工作。这一章回答的正是"单线程怎么同时兼顾这两类完全不同性质的工作，还不互相拖垮"这个问题——答案是把它们都抽象成"事件"，用统一的事件循环调度。

### 12.1 文件事件：网络层怎么被高效驱动

**朴素方案的碰壁**：

- 一个连接一个线程、阻塞读写——连接数一多，线程本身的内存和调度开销就先把机器压垮，而且直接破坏了"单线程不用加锁"这个前提（第4章渐进式 rehash 等机制都依赖这个前提）。
- 单线程挨个轮询检查（忙等待）——连接多但同时就绪的少时，大部分检查是空耗 CPU；检查间隔拉大又会拖慢响应。忙等待和响应延迟这对矛盾躲不开。

**方案：I/O 多路复用（multiplexing）**——把一批"关心的套接字+事件类型"一次性告诉操作系统，调用一个函数阻塞等待，操作系统在任意一个套接字就绪时主动通知。一个线程监听一堆套接字，谁醒了处理谁。

**文件事件处理器的四个组成部分**（基于 Reactor 模式）：

1. **套接字**——事件产生的源头。
2. **I/O 多路复用程序**——包装 `select`/`epoll`/`evport`/`kqueue` 这几种系统实现，每个对应源码里一个独立文件，编译期按性能自动选一个能用的最优实现，上层代码不用关心具体用的是哪一种。
3. **文件事件分派器（dispatcher）**——多路复用程序把就绪的套接字按"有序、同步、一次一个"的方式喂给它，它根据套接字当前关联的处理器类型分发调用。
4. **事件处理器**——真正干活的函数（接受连接/读命令/写回复）。

**两类事件——从服务器视角命名，不是从客户端视角**：`AE_READABLE`（服务器现在可以从这个套接字读到数据了：客户端发来命令、客户端关闭连接产生 EOF、或监听套接字上有新连接可以 `accept`）、`AE_WRITABLE`（服务器现在可以往这个套接字写数据了：客户端那边准备好接收、缓冲区没满）。**一个套接字同时可读可写时，永远先处理读、再处理写**——先把新命令读完执行完，再把最新的回复写出去，这是更自然的因果顺序。

**三个最常用的处理器，串成一次完整连接**：连接应答处理器（关联在监听套接字，`accept` 新连接、创建客户端套接字和状态）→ 命令请求处理器（关联在客户端套接字的 `AE_READABLE`，读取并执行命令）→ 命令回复处理器（命令执行完临时关联到 `AE_WRITABLE`，写完回复后解除关联）。

**局限性**：I/O 多路复用解决的是"高效知道谁就绪了"，但事件处理器本身仍是单线程依次执行——某个处理器耗时长，其他所有客户端都要排队等，这是单线程模型的固有代价（12.3 节的调度规则会展开这一点）。

### 12.2 时间事件：没有客户端请求也要主动做的事

**要解决的问题**：过期键清理、持久化条件检查、统计信息更新这些工作不是被客户端请求触发的，是"到点该做"。如果给每种定期任务单独开线程，又会重新引入并发访问数据库状态的问题，破坏单线程模型。

**方案：把"定时任务"也抽象成一种事件类型**，跟文件事件共享同一个事件循环、同一个线程调度执行，天然不存在并发冲突。

**时间事件的三个属性**：`id`（全局唯一，创建顺序递增）、`when`（毫秒精度的到达时间戳）、`timeProc`（到达时被调用的处理函数）。**两种类型靠处理器返回值区分**：返回 `AE_NOMORE` 是定时事件（触发一次就删除）；返回其他整数值是周期性事件（服务器据此更新 `when`，让它继续循环触发）。**目前版本只用周期性事件**，正常模式下唯一常规使用的时间事件是 `serverCron`。

**实现：无序链表，不按 `when` 排序**——新事件永远插入表头。这是一个反直觉但合理的设计选择：正常情况下系统里几乎只有 `serverCron` 一个时间事件（benchmark 模式最多两个），链表几乎退化成一个指针，遍历开销可忽略，用最小堆之类的排序结构去优化一个基本不存在的问题纯属过度设计。这个设计的前提是"时间事件数量极少"，如果未来场景需要同时维护大量时间事件，无序链表的 O(N) 遍历会变成真实瓶颈——这是"按当前负载特征设计"而不是"理论最优设计"的具体案例。

**`serverCron` 的职责与频率**：更新统计信息、清理过期键（第9章）、关闭失效客户端、检查触发 AOF/RDB 持久化（第10、11章）、主从同步检查等——把前面几章学过的机制串了起来。执行频率由 `hz` 配置项决定（2.6 默认固定每秒10次≈100毫秒一次；2.8+ 可调），`hz` 越大响应越及时，但自身占用的 CPU 时间也越多，是需要权衡的调优参数。

### 12.3 事件的调度与执行：`aeProcessEvents`

**核心机制**：文件事件和时间事件共用一个调度函数：

```python
def aeProcessEvents():
    time_event = aeSearchNearestTimer()      # 找到 when 最接近当前时间的事件
    remaind_ms = time_event.when - unix_ts_now()
    if remaind_ms < 0:
        remaind_ms = 0
    aeApiPoll(remaind_ms)      # 阻塞等待文件事件，最长只等 remaind_ms 毫秒
    processFileEvents()        # 处理这段时间到达的文件事件
    processTimeEvents()        # 检查并执行所有已到达的时间事件
```

**谁负责判断"该处理了"，文件事件和时间事件不对称**：文件事件由**操作系统内核**判断（套接字真的就绪，主动通知）；时间事件由**Redis 自己**判断（拿当前时间戳和 `when` 比较），没有任何外部主体给时间事件"报时"。`serverCron` 不是"发通知的一方"，它是被 `processTimeEvents` 检查后触发执行的处理器，和文件事件里的"命令请求处理器"是同一层级的角色。

**动态超时的巧妙之处**：Redis 没有专门开线程"叫醒"主循环，而是复用了 `aeApiPoll` 本身支持的"最大阻塞时间"参数——传入"距最近时间事件的剩余时间"。这段时间内如果有文件事件到达，`aeApiPoll` 提前返回；如果什么都没发生，`aeApiPoll` 会因超时而返回。不管哪种情况，紧接着的 `processTimeEvents` 都会去检查是否到点。

**这个动态超时机制真正防住的两个边界情况**（不是"追求精确命中"）：

- **避免不必要的频繁轮询**：不用像忙等待那样固定用极短间隔反复检查。
- **避免服务器空闲时时间事件被无限期拖延**——如果 `aeApiPoll` 无限阻塞、只靠文件事件唤醒，服务器长时间没有任何客户端连接时，`serverCron` 会永远没机会被检查执行。动态超时给了一个"最多等这么久就一定会检查一次"的上界。

**时间事件本身不存在"丢失"风险**：`processTimeEvents` 每次都拿当前时间和 `when` 比较，只会越来越"满足条件"，不会因为晚检查几次就漏掉——这个机制防的是"被无限拖着不执行"，不是"丢失"。而"精确命中到达那一刻"也不是这个机制的目标，它只保证等待时间的上界，实际执行时间仍可能因为下面的调度规则而晚一些。

**四条事件调度规则**：

1. `aeApiPoll` 的最大阻塞时间由最近的时间事件决定——同时避免忙等待和无限期拖延。
2. 文件事件随机到达：处理完一轮文件事件后时间事件仍未到，服务器会再次进入 `aeApiPoll` 等待，循环推进，直到时间到达 `when`。
3. 事件处理不可抢占，处理器必须主动让出执行权：命令回复处理器写入超过预设字节数会主动 `break`、把剩余数据留到下次；耗时的持久化操作丢给子进程/子线程（呼应第10、11章的 `BGSAVE`/`BGREWRITEAOF`）。
4. 时间事件的实际执行时间通常比预定时间稍晚——因为不能抢占文件事件的处理，如果这一轮正好有文件事件在处理，时间事件要排队等。

书里给出的例子把四条规则串起来：`serverCron` 预定100毫秒后执行，等待期间服务器先处理了两次文件事件（规则2），因为不可抢占（规则3），实际执行比预定时间晚了30毫秒（规则4）——这130毫秒的延迟是"合作式调度、不可抢占"这个设计必然带来的正常现象，不是 bug。

## 易混淆/易错点

- **`AE_READABLE`/`AE_WRITABLE` 是从服务器视角命名，不是客户端视角**：`AE_READABLE` 不是"客户端在写"，是"服务器现在能读了"；`AE_WRITABLE` 不是"客户端在读"，是"服务器现在能写了"。主体容易搞反。
- **`serverCron` 不是"发通知的一方"，是被检查后触发的处理器**：真正做"判断该不该执行"这件事的是 Redis 主循环自己（拿当前时间和 `when` 比较），`serverCron` 只是时间事件到达后被调用的 `timeProc`，跟文件事件里的"命令请求处理器"是同一层级角色，不能类比成"操作系统通知文件事件"那种外部通知机制。
- **时间事件用无序链表不是实现偷懒**：是按"当前几乎只有 `serverCron` 一个时间事件"这个实际负载特征做出的设计决策，不是"理论最优应该用堆"的反例——负载特征变了（大量时间事件并存），这个选择需要重新评估，不是万能设计。
- **动态超时机制的目的不是"精确命中时间事件到达的那一刻"**：它保证的是等待时间的上界（避免服务器空闲时时间事件被无限拖延），也避免不必要的频繁轮询；实际执行时间因为"不可抢占"规则，通常还是会比预定时间晚一些，不追求精确命中。
- **时间事件不存在"丢失"风险，只有"被拖延"风险**：`processTimeEvents` 每次检查都是"when 是否 ≤ 当前时间"，这个条件只会越来越满足，循环迟早会抓到；真正的风险是如果没有合理的超时上界，事件可能在服务器空闲时被无限期拖延，不是永久丢失。
- **事件处理"不可抢占"不等于"不能主动让出"**：不可抢占是说服务器不会中途打断一个正在执行的处理器，但处理器自己可以、也应该主动分批处理（命令回复分批写、持久化丢子进程），这是两件不矛盾的事。

## 与其他章节的关联

- **第4章「字典」**：文件事件处理器否掉"一连接一线程"方案的理由，和时间事件否掉"每种定期任务单独开线程"方案的理由是同一个——都是为了保住"单线程不用加锁"这个前提，渐进式 rehash 等机制正是依赖这个前提才能简化实现。
- **第9章「数据库」**：`serverCron` 的职责之一是清理过期键，这正是第9章讲的"定期删除策略"的驱动来源——过期键什么时候被定期抽查删除，答案就是"`serverCron` 这个时间事件多久触发一次"，由 `hz` 配置项决定。
- **第10章「RDB持久化」/第11章「AOF持久化」**：`serverCron` 负责检查 `save` 多档条件是否满足（第10章）、检查 AOF 缓冲区是否需要刷新同步（第11章）——这两章讲的"定期"机制，驱动它们的正是这一章的时间事件；持久化操作本身耗时长，被丢给子进程/子线程执行，正好对应本章"事件处理器不可抢占，要主动让出执行权"这条调度规则。
- **第13章「客户端」（待学）**：客户端状态（`redisClient` 结构）里保存的输入/输出缓冲区，正是命令请求处理器、命令回复处理器读写的对象；客户端连接的创建和关闭时机，跟本章的连接应答处理器直接相关。
- **第14章「服务器」（待学）**：服务器的主函数就是"初始化 → 不断调用 `aeProcessEvents` → 关闭清理"这个循环本身；`initServer` 阶段会为监听套接字关联连接应答处理器、为 `serverCron` 创建时间事件，是本章机制的具体落地起点。
