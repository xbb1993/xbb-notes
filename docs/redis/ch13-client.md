# 第13章 客户端

## 核心概念

**要解决的问题**：第12章讲的 I/O 多路复用，让服务器能用一个线程同时"关心"成百上千个客户端套接字。但轮流处理不代表可以共享状态——每个客户端读到哪、正在执行什么命令、回复攒了多少，这些中间状态必须互相隔离，否则处理 A 的时候会污染 B 的数据。这一章要解决的正是"服务器怎么给每一个正在通话的客户端准备一份专属的、不会被其他客户端干扰的档案"。

### 13.1 客户端属性：redisClient 里装了什么

**朴素方案的碰壁**：如果图省事用几个全局缓冲区存"当前读到的字节""当前执行的命令"，会直接撞上 I/O 多路复用的前提——服务器是"轮流处理不同客户端的事件"，不是"一次只服务一个客户端到底"。客户端 A 的命令还没读完，服务器转头处理 B 的事件，A 那半条命令的数据就会被 B 覆盖。必须给每个客户端单独准备一套互不干扰的暂存空间。

**方案**：每个连接到服务器的客户端对应一个独立的 `redisClient` 结构，服务器用 `clients` 链表把所有客户端状态串起来（新客户端加到链表末尾），供 `CLIENT LIST`、`serverCron` 超时检查等场景遍历使用。

用 `SET KEY VALUE` 这条命令贯穿一遍，把 `redisClient` 的核心字段挨个建立起来：

- **输入缓冲区 `querybuf`**：命令请求处理器（第12章）从套接字读到的原始字节，原样存进这个 SDS 缓冲区（`"*3\r\n$3\r\nSET\r\n$3\r\nKEY\r\n$5\r\nVALUE\r\n"`）——这套协议格式跟第11章 AOF 文件里看到的完全一样，只是这里的用途是"输入暂存"，AOF 里是"持久化落盘"，是同一份基础设施在不同场景下的复用。`querybuf` 会动态扩缩容，但有 **1GB 硬上限**，超过直接强制关闭连接，防止一条巨大命令或恶意请求把内存耗尽、卡死解析逻辑。
- **命令与参数 `argv`/`argc`**：解析完 `querybuf` 后，`"SET"`、`"KEY"`、`"VALUE"` 分别变成字符串对象存进 `argv` 数组，`argc = 3`——**容易漏算的点**：命令名本身也占一个数组位置，`argc` 不是"参数个数"，是"命令名+参数"的总数。
- **命令实现函数 `cmd`**：服务器拿 `argv[0]`（大小写不敏感）去命令表（本质是字典）里查，找到对应的 `redisCommand` 结构，`cmd` 指向它。这个结构不只有实现函数指针，还带参数个数要求、总执行次数、总耗时等统计信息。
- **输出缓冲区（两级结构）**：命令执行结果要先暂存，再被写回网络。这里用了固定+可变两级结构，而不是单一方案——只用固定缓冲区遇到大回复（如 `LRANGE` 返回几万元素）会不够用；只用链表，大多数命令回复很短，为小回复也走一次链表节点分配纯属浪费。所以：**固定缓冲区**（`buf`/`bufpos`，默认16KB，一次分配到位，覆盖绝大多数命令）+ **可变缓冲区**（`reply` 链表，装不下16KB时启用，理论上能撑住任意长回复）。这个设计在性能和空间上都合理，但留了一个隐患：可变缓冲区理论上可以无限增长，如果客户端读取跟不上，回复会一直堆积占内存——这个隐患由 13.2 的输出缓冲区限制机制收口。
- **标志位 `flags`**：分两类。角色类（`REDIS_MASTER`/`REDIS_SLAVE`/`REDIS_LUA_CLIENT`/`REDIS_UNIX_SOCKET` 等，标记这个客户端的身份）；状态类（`REDIS_MONITOR`/`REDIS_BLOCKED`/`REDIS_UNBLOCKED`/`REDIS_MULTI`/`REDIS_DIRTY_CAS`/`REDIS_DIRTY_EXEC`/`REDIS_CLOSE_ASAP`/`REDIS_CLOSE_AFTER_REPLY` 等，标记这个客户端当下的状态）。具体怎么被事务、发布订阅、复制这几章用到，留给对应章节对号。
- **身份验证 `authenticated`**：只有开启 `requirepass` 时才有意义，未验证时除 `AUTH` 外所有命令被拒绝返回 `NOAUTH`；未开启验证功能则这个字段形同摆设。
- **时间属性**：`ctime`（创建时间，对应 `CLIENT LIST` 的 `age`）、`lastinteraction`（最后互动时间，对应 `idle`，也是超时判定的依据）、`obuf_soft_limit_reached_time`（输出缓冲区首次达到软性限制的时间点，13.2 软性限制机制的计时起点）。
- **预留坑位**：复制状态信息、`BLPOP`/`BRPOP` 阻塞相关数据结构、事务和 `WATCH` 相关数据结构、发布订阅相关数据结构——留给第15、18、19章展开，这里只建立"有这些坑位"的印象。

### 13.2 客户端的创建与关闭

**常见的错误理解**：以为"客户端"就等于"一条 TCP 连接"，一一对应没有例外。**正确理解**：绝大多数客户端确实对应一条网络连接（普通客户端），但 Redis 内部还有不需要网络连接的**伪客户端**，用来让"执行命令"这个动作本身也能走统一的 `redisClient` 流程。

**普通客户端的创建**：客户端连接触发第12章的连接应答处理器（`acceptTcpHandler`），服务器调用 `createClient` 新建 `redisClient` 结构并挂到 `clients` 链表末尾——从这一刻起客户端才"存在"。

**普通客户端的关闭**，六种情况：进程退出或网络断开；发送了不符合协议格式的命令（协议错误，直接断开防止继续错误解析）；成为 `CLIENT KILL` 目标（运维手段）；设置了 `timeout` 且超过时限未通讯（`serverCron` 靠 `lastinteraction` 周期检查）；命令请求超过 `querybuf` 的1GB硬上限；**输出缓冲区超过限制**（下面单独展开）。

**输出缓冲区限制：硬性限制 + 软性限制，两道闹钟**。这套机制收口了13.1埋的隐患——如果只设一个"超过多少字节就立刻关闭"的硬阈值，会把正常的短暂业务峰值（比如一次性读一个大集合）误判成异常；如果完全不设限制，真正读取异常慢的客户端（典型是订阅了大量消息的 pub/sub 客户端）会让缓冲区无限膨胀拖垮内存。于是设计成两道判定：

- **硬性限制（hard limit）**：缓冲区大小一旦超过，**立即**关闭，没有宽限。
- **软性限制（soft limit）**：超过阈值时先记录时间点（`obuf_soft_limit_reached_time`），只有**持续**超过软性限制的时长达到配置的 `soft limit seconds` 才关闭；期间如果掉回软性限制以下就取消计时。

**常见的错误理解**：以为软性限制只是"数值更小的硬性限制"。**正确理解**：两者不是同一维度的两个刻度——硬性限制只看"大小"这一个维度，一次达标就动手；软性限制是"大小+持续时间"的联合条件，专门用来容忍短暂峰值，只惩罚真正持续读不过来的客户端。

三类客户端（`normal`/`slave`/`pubsub`）可以分别配置独立的硬/软限制大小和软性限制时长，因为它们的合理回复规模天然不同（slave 客户端用于复制，本该容忍更大缓冲区；pub/sub 客户端读取跟不上往往意味着真正的消费能力问题）。**局限性**：这套机制保护的是服务器自身不被拖垮，代价是被判定的客户端会被强制断开并**直接丢弃**还没发出去的回复（标记 `REDIS_CLOSE_ASAP`，下次 `serverCron` 执行时关闭）——如果业务上这些消息不能丢，需要在应用层自己处理重连和补偿，Redis 这一层不负责。这也是 `REDIS_CLOSE_ASAP`（直接丢弃回复再关）和 `REDIS_CLOSE_AFTER_REPLY`（先发完已攒好的回复再关，用于 `CLIENT KILL`/协议错误等场景）语义不同的地方，不要混为一谈。

**伪客户端：不需要网络连接的两种"隐藏身份"**。Redis 内部有两处需要"执行命令"但没有真实网络客户端在另一头的场景，为了不破坏"所有命令都通过 `redisClient` 统一执行"的一致性，各造了一个伪客户端：

- **Lua 脚本伪客户端 `lua_client`**：`EVAL` 执行脚本时 `redis.call()` 调用的命令需要一个身份走标准执行流程。服务器**初始化阶段**创建这一个专用伪客户端，**贯穿整个服务器生命周期**，所有脚本调用共用它，直到服务器关闭才销毁。
- **AOF 载入伪客户端**：服务器启动载入 AOF 文件时，回放动作也需要身份执行命令。这是为这次载入**临时**创建的伪客户端，载入完成后**立即关闭**。

**容易混淆的点**：两者生命周期完全不同——`lua_client` 是"一次创建，跟服务器同生共死"（因为脚本随时可能被调用，服务的持续性决定身份要一直在）；AOF 载入伪客户端是"用完就扔"（因为载入只发生在启动那一刻，是一次性步骤）。两种伪客户端都不需要13.1里跟网络相关的字段（`querybuf` 不会有真实字节流、回复不需要真的写回网络），真正用到的是 `argv`/`argc`/`cmd` 这些跟命令执行直接相关的字段——这说明 `redisClient` 结构实际承担的是两件不完全绑定的职责：**网络连接的状态管理**和**命令执行的上下文载体**，伪客户端只用到后者。这个"结构承担双重职责"的设计取舍，理解服务器整体架构（第14章）时会再用到。

## 易混淆/易错点

- **`argc` 容易少算1**：`argc` 是"命令名+参数"的总数，不是"参数个数"，命令名本身（`argv[0]`）也占一个数组位置。
- **软性限制不是"更宽松版的硬性限制"**：硬性限制只看大小，一次达标立即关闭；软性限制是"大小+持续时间"的联合条件，给了客户端一个自我恢复窗口，专门用来区分"正常业务峰值"和"真正持续读不过来"。
- **`REDIS_CLOSE_ASAP` 与 `REDIS_CLOSE_AFTER_REPLY` 语义不同，不能混用理解**：前者（输出缓冲区超限触发）直接丢弃未发送的回复内容再关闭，因为客户端本来就读不过来，继续发没有意义；后者（`CLIENT KILL`、协议错误等场景）会先把已经攒好的回复发完再关闭。
- **"客户端"不等于"一条网络连接"**：Lua 脚本伪客户端和 AOF 载入伪客户端都没有真实网络连接，但同样是 `redisClient` 结构的实例，走同一套命令执行流程。
- **两种伪客户端的生命周期不能类比混淆**：`lua_client` 贯穿服务器整个生命周期（服务能力持续存在）；AOF 载入伪客户端只在启动载入那一刻存在，用完立即关闭（一次性步骤）。判断依据是这个身份对应的动作本身是"持续性服务能力"还是"一次性启动步骤"。
- **`redisClient` 结构其实承担两件不完全绑定的职责**：网络连接状态管理（`querybuf`、输出缓冲区、连接相关的 `flags`）和命令执行上下文载体（`argv`/`argc`/`cmd`）。普通客户端两者都用，伪客户端只用后者——不要把它当成一个"纯粹只服务网络连接"的结构。
- **`authenticated` 字段的有效性依赖 `requirepass` 是否开启**：没开启验证功能时这个字段形同摆设，不代表任何客户端都处于"未验证"的危险状态。

## 与其他章节的关联

- **第12章「事件」**：本章的输入/输出缓冲区正是第12章命令请求处理器、命令回复处理器读写的对象；客户端的创建和关闭时机与连接应答处理器直接相关；`serverCron`（时间事件）负责检查客户端超时（依赖 `lastinteraction`）和输出缓冲区是否超限，是本章"关闭客户端"这几种情况里真正执行清理动作的驱动源。
- **第11章「AOF持久化」**：`querybuf` 里暂存的 RESP 协议格式，跟 AOF 文件里落盘的命令请求协议是同一套基础设施的两种用途；AOF 载入时使用的伪客户端也是本章"伪客户端"概念的具体案例之一。
- **第9章「数据库」**：过期键的定期删除策略依赖 `serverCron`（第12章），而客户端超时检测同样依赖 `serverCron` 遍历 `clients` 链表——两者都是"周期性主动检查"这一模式在不同场景下的应用。
- **第15章「复制」（待学）**：`flags` 里的 `REDIS_MASTER`/`REDIS_SLAVE` 标志、输出缓冲区限制里专门为 `slave` 客户端配置的独立档位，都要在复制机制里具体展开。
- **第18章「发布与订阅」（待学）**：输出缓冲区限制专门为 `pubsub` 客户端配置独立档位的原因（订阅者读取跟不上是这套机制最典型的应用场景），以及本章预留的发布订阅相关数据结构坑位。
- **第19章「事务」（待学）**：`flags` 里的 `REDIS_MULTI`/`REDIS_DIRTY_CAS`/`REDIS_DIRTY_EXEC`，以及本章预留的事务和 `WATCH` 相关数据结构坑位，要在事务章节里对上号。
- **第20章「Lua脚本」（待学）**：`lua_client` 伪客户端的具体使用场景（`redis.call()` 如何借用这个身份执行命令）。
- **第14章「服务器」（待学）**：`redisClient` 结构"网络连接状态管理 + 命令执行上下文载体"的双重职责划分，是理解服务器整体命令执行流程（一条命令从读取到执行到回复的完整路径）的基础。
