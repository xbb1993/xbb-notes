# 第14章 服务器

## 核心概念

**这一章的定位**：前面第9~13章讲的都是"某一块机制"（数据库、持久化、事件、客户端），这一章把它们在时间线上串成一条完整的主干——一条命令从进来到出去经过了什么、服务器在没有命令的间隙主动做了什么、服务器从0启动到能对外服务经过了什么步骤。

### 14.1 命令请求执行的完整流程

**朴素方案的碰壁**：如果命令表查到 `cmd` 就直接调用实现函数，会在好几个场景直接出问题——未身份验证的客户端直接执行命令；参数个数不对的命令（如 `GET` 不带 key）直接按错误的参数假设去读数组会越界；内存已经超过 `maxmemory` 限制还继续接受写命令；客户端正处于 `MULTI` 事务中，命令本该入队而不是立即执行。这些场景说明"查到就调用"这一步中间必须插入一层统一检查。

**方案：命令执行器的四个阶段**：

```
① 查找命令实现（argv[0] 查命令表 → cmd，第13章已讲）
② 执行预备操作（一系列检查，任何一项不通过就短路返回/入队）
③ 调用命令实现函数（真正读写数据库，产生结果对象）
④ 执行后续工作（统计、AOF传播、复制传播、慢查询记录、MONITOR通知……）
```

**②预备操作里的具体检查项**：命令是否存在（`cmd` 为空返回 `unknown command`）；参数个数是否匹配 `redisCommand.arity`（`arity` 可正可负：正数表示精确需要多少个参数，负数表示"至少"需要多少个参数，用同一个字段的符号位承载两种语义，是空间换复杂度的小设计）；身份验证（对应 `authenticated` 字段，除非命令本身是 `AUTH`）；`maxmemory` 内存限制检查；发布订阅模式下的命令限制（第18章）；主从复制场景下从服务器的只读限制（第15章）；**事务队列拦截**——客户端 `flags` 带 `REDIS_MULTI` 且当前命令不是 `MULTI`/`EXEC`/`DISCARD`/`WATCH` 本身时，命令会被放入事务队列并返回 `QUEUED`，根本不会走到③；`DIRTY_CAS`/`DIRTY_EXEC` 标记检查（`WATCH` 的键被修改或事务队列本身出过参数错误，判定 `EXEC` 必然失败）。

**为什么统一放在预备阶段而不是让每个命令自己判断**（多维度论证）：实现复杂度上，分散判断会导致几百个命令重复写同样的检查逻辑，新增一种检查要改遍所有命令；工程可靠性上，统一入口把"漏检查"的风险收敛到一处，容易审查和保证一致性；性能上，这些检查基本是 O(1) 判断，统一放前面符合"早失败"（fail fast）原则，不合法请求最早被挡掉，不浪费执行到一半的成本。**局限性**：这也不是没有代价——随着功能扩张（订阅限制、复制只读、Lua环境限制、事务拦截、内存策略等都是不同版本陆续加入的），这一层检查链会越堆越长、分支越来越多，是"集中式设计随功能扩张必然要付出的维护复杂度代价"。

**④后续工作**：命令执行完不代表流程结束，还要更新 `redisCommand` 里的调用次数/耗时统计、判断是否记录慢查询（第23章）、是否写入AOF缓冲区（第11章）、是否传播给从服务器（第15章）、是否发给 `MONITOR` 客户端（第24章）——这一层几乎是把持久化、复制、监控机制统一挂在"命令执行完成"这一个时间点上触发。

### 14.2 serverCron 的具体职责

`serverCron` 是第12章讲过的那个唯一常规使用的时间事件，由 `hz` 参数决定执行频率（默认每秒10次）。这一节把它一次执行内部具体做的事拆开：

```
① 更新服务器时间缓存
② 更新 LRU 时钟
③ 更新每秒执行命令次数统计
④ 更新内存峰值记录
⑤ 处理 SIGTERM 信号（安全关闭准备）
⑥ 管理客户端资源（超时检测、输出缓冲区限制检查）── 第13章
⑦ 管理数据库资源（过期键清理、字典收缩）────────── 第4、9章
⑧ 执行被延迟的 BGREWRITEAOF ──────────────────── 第11章
⑨ 检查持久化操作（BGSAVE/BGREWRITEAOF）运行状态──── 第10、11章
⑩ 将 AOF 缓冲区内容写入文件（视 appendfsync 配置）── 第11章
⑪ 关闭被标记为异步关闭的客户端 ────────────────── 第13章
⑫ cronloops 计数器 +1
```

**①时间缓存**：避免每次都调用系统调用去取当前时间，很多地方（如 `lastinteraction` 更新、日志时间戳）直接读这份缓存。**易错点**：不是"处处精度都变成100毫秒"，只是高频读取场景省开销，精度敏感场景该取实时时间还是会取。

**②LRU时钟**：呼应第8章对象一节的"访问时间"字段。同样是近似时钟，不是每次访问键都实时算精确时间戳，而是被 `serverCron` 周期性更新的粗粒度时钟，内存淘汰算法本来就不需要精确到毫秒级的先后顺序，这是用精度换性能的取舍。

**③④统计类**：`INFO` 里能看到的 `instantaneous_ops_per_sec` 之类指标、内存历史峰值，都是周期性更新的，不是每次命令执行/每次内存分配释放都触发。

**⑤SIGTERM**：收到关闭信号时在这里设置关闭标志，走安全退出流程，不是粗暴直接退出。

**⑥客户端资源管理**：把第13.2章讲的"关闭判定规则"真正落地执行的地方——遍历 `clients` 链表，检查每个客户端的空转时长（`lastinteraction`）是否超过 `timeout`，检查输出缓冲区是否触发硬性/软性限制。

**⑦数据库资源管理**：过期键清理的真正驱动点（呼应第9章的定期删除策略），另外还包含字典层面的**收缩**操作（第4章渐进式rehash机制不只用于扩容方向，缩容同样会用到）。

**⑧⑨⑩持久化相关三件不同的事**：⑧是"之前因为 `BGSAVE` 正在跑而被延迟的 `BGREWRITEAOF` 请求，在合适时机真正触发"；⑨是"子进程完成后的发现和收尾清理（更新最近保存时间、处理退出状态）"；⑩是"AOF内存缓冲区→文件"这个刷盘动作，**易错点**：`serverCron` 不是这个动作唯一的触发点，事件循环每一轮结束前（`beforeSleep` 回调）也会调用同一个刷盘函数，这是为了让 `appendfsync everysec` 这种"尽量每秒落盘"的语义更贴近及时性目标。

**⑪关闭异步客户端——"标记+延迟统一处理"的两阶段模式**：⑥遍历检查阶段只给要关闭的客户端打标记（`REDIS_CLOSE_ASAP` 等），不在遍历过程中直接从链表摘除；等这一轮遍历结束，⑪再统一处理所有被标记的客户端。**原因**：遍历链表途中直接删除节点会破坏正在进行的遍历（下一个节点指针可能失效，容易产生野指针或跳过节点），"先标记、最后统一处理"是常见的工程模式，不止用在这里。

**⑫cronloops**：单纯统计 `serverCron` 调用总次数，配合"每隔N次循环才做一次"的降频逻辑用，边缘细节。

**`hz` 调优的实际考量**：`hz` 越大响应越及时、CPU占用也越高。具体到⑦过期清理，大量短TTL键的缓存场景调高 `hz` 能减少"逻辑已过期但物理还占内存"的窗口，但这是拿服务器自身巡场的CPU开销换清理及时性，调整前要想清楚这笔账。

### 14.3 服务器的初始化

**五个步骤，顺序不能乱**：

```
initServerConfig（先给一套默认配置值）
        │
载入配置文件 / 命令行参数（覆盖默认值，命令行参数优先级更高）
        │
initServer（按最终配置，真正创建数据库结构、事件循环、监听套接字等）
        │
还原数据库状态（载入 RDB 或 AOF，回填进 initServer 建好的空结构里）
        │
执行事件循环（aeMain，第12章的 aeProcessEvents 开始被循环调用，正式对外服务）
```

**为什么"载入配置"必须在"initServer"之前**：`initServer` 要用最终确定的端口号、是否开启AOF等配置去创建监听套接字、决定要不要注册AOF相关初始化逻辑，顺序反了就会拿默认值去建，跟用户实际配置不一致。

**易错点**：RDB/AOF的载入不是 `initServer` 内部同步完成的一部分。`initServer` 只把数据库、事件循环这些**空结构**搭起来，真正把持久化文件内容读进结构是**独立的下一步**，必须在结构搭好之后、事件循环真正跑起来之前完成——如果顺序反了，事件循环已经开始接客户端请求，而数据还没载入完，客户端会读到空的或半载入的数据库。

**跟第12章的衔接点**：`initServer` 里会为监听套接字关联连接应答处理器（`acceptTcpHandler`）、为 `serverCron` 创建对应的时间事件——这是第12章讲过的机制第一次被真正"接上电"的地方。

## 易混淆/易错点

- **`arity` 为负数不是无效值**：正数表示命令精确需要多少个参数，负数表示"至少"需要多少个（如 `MSET` 这类不定长命令），符号位复用同一字段承载两种语义。
- **事务是否入队，判断发生在预备操作阶段，不是命令实现函数自己判断**：`SET`、`LPUSH` 等命令实现函数完全不知道自己是不是在 `MULTI` 事务里，是否入队这个分支逻辑是预备操作根据客户端 `flags` 里的 `REDIS_MULTI` 做出的，对命令本身透明。
- **预备检查是"集中式统一检查"，不是"分散在每个命令里各自判断"**：好处是避免重复代码和漏检查风险，代价是随功能扩张这一层检查链会越来越复杂，不是没有维护成本的完美设计。
- **LRU时钟不是精确时间戳**：是 `serverCron` 周期性更新的近似时钟，键对象记录的是跟这个近似时钟的相对关系，不是纳秒级精确访问时间。
- **服务器时间缓存不代表"处处精度都是100毫秒"**：只是高频读取场景省系统调用开销的手段，精度敏感场景该取实时时间依然会取。
- **每秒命令数统计、内存峰值记录是周期性更新，不是每次命令/每次内存变化实时触发**。
- **AOF缓冲区写入文件的触发点不止 `serverCron` 一处**：事件循环每轮结束前（`beforeSleep`）也会触发同一个刷盘函数，两者共同保证 `appendfsync everysec` 之类配置的及时性。
- **关闭被标记的客户端为什么不能在遍历中直接摘除**：会破坏正在进行的链表遍历，产生野指针或跳过节点风险，所以用"先标记、遍历结束后统一处理"的两阶段模式，这是通用工程模式，不止用在这里。
- **RDB/AOF载入不是 `initServer` 内部同步做的事**：`initServer` 只建空结构，载入数据是独立的后续步骤，必须在事件循环开启之前完成，顺序颠倒会导致客户端读到空/半载入的数据库。

## 与其他章节的关联

- **第4章「字典」**：`serverCron` 管理数据库资源时做的字典收缩操作，是渐进式rehash机制在"缩容方向"的应用，跟第4章讲的扩容场景是同一套机制的两个方向。
- **第8章「对象」**：LRU时钟呼应第8章提过但未展开的对象"访问时间"字段，两者共享"用近似时钟换性能"的设计思路。
- **第9章「数据库」**：`serverCron` 是第9章"定期删除策略"真正的驱动执行点，回答了"过期键抽查删除具体发生在哪个执行点"这个问题。
- **第10章「RDB持久化」/第11章「AOF持久化」**：`serverCron` 里⑧⑨⑩三步分别对应"延迟的AOF重写请求触发""持久化子进程状态收尾""AOF缓冲区刷盘"，是这两章持久化机制的具体调度落点；服务器初始化里的"还原数据库状态"步骤，正是启动时载入RDB或AOF文件的地方。
- **第12章「事件」**：`serverCron` 本身就是第12章讲的时间事件在本章的具体展开；服务器初始化中 `initServer` 为监听套接字关联连接应答处理器、为 `serverCron` 创建时间事件，是第12章机制第一次真正被启用的地方；`aeMain` 事件循环就是初始化流程的最后一步。
- **第13章「客户端」**：命令执行预备操作里用到的 `authenticated`、`REDIS_MULTI`、`DIRTY_CAS`/`DIRTY_EXEC` 等字段，都是第13.1章讲过但当时没展开用途的字段，在这里第一次看到具体被怎么用；`serverCron` ⑥⑪两步是第13.2章"客户端关闭判定规则"的执行落点，"标记+延迟统一处理"模式也补全了 `REDIS_CLOSE_ASAP` 具体怎么被执行关闭的细节。
- **第15章「复制」（待学）**：命令执行预备操作里的"从服务器只读限制"检查项，要在复制章节具体展开。
- **第18章「发布与订阅」（待学）**：预备操作里的"订阅模式下命令限制"检查项。
- **第19章「事务」（待学）**：本章讲的"事务队列拦截发生在预备操作阶段"是理解事务机制怎么截获命令的关键前提。
- **第23章「慢查询日志」/第24章「监视器」（待学）**：命令执行流程④后续工作阶段，正是慢查询记录和MONITOR通知的触发点。
