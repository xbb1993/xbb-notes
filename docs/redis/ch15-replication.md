# 第15章 复制（Replication）

## 核心概念

**要解决的问题**：单点数据库有单点故障风险，也扛不住大量读请求。让多台服务器保存同一份数据的副本（一主多从），主库负责写，从库分担读、并在主库故障时提供数据备份，这就是复制要解决的问题。

### 朴素方案：全量同步（旧版 `SYNC`）

从库第一次接入主库，两边数据完全不一致，唯一能做的就是"完整对齐一次"：

```
从库                          主库
 |-- SYNC ------------------->|
 |                             | 1. fork 子进程生成 RDB 快照
 |                             | 2. 主进程继续处理写命令，
 |                             |    暂存到"复制缓冲区"
 |<-- 发送 RDB 文件 -----------|
 | 3. 清空旧数据，加载 RDB
 |<-- 发送缓冲区里攒的写命令 ---|  ← 补齐 fork 期间的增量
 |<== 之后进入"命令传播"：主库每执行一条写命令就实时转发 ==>
```

生成 RDB 期间主库仍在写入，这段"时间差"里产生的新命令要靠**复制缓冲区**暂存、追平后补发——跟第11章 AOF 重写时"AOF 重写缓冲区"解决的是同一类"后台快照 vs 前台继续写"问题。

**代价**：fork 开销（第10章写时复制机制）+ 完整 RDB 网络传输 + 从库完整加载，数据量大时可能耗时数分钟。**核心缺陷**：旧版实现不管断线多短，重连一律重新做一次完整全量同步，哪怕只差几十条命令。

### 部分重同步：新版复制的解法

要让断线重连只补"缺的那一段"，需要三个组件配合：

1. **复制偏移量（offset）**：主库和从库各自累加"已发送/已接收的字节数"，差值就是缺失的数据量。
2. **复制积压缓冲区（backlog）**：固定大小的环形缓冲区（FIFO，跟慢查询日志固定长度链表是同一种"有限窗口"思路），主库在命令传播的同时把命令写入 backlog。从库断线的 offset 若还落在 backlog 范围内，就能补传；若已被覆盖，只能退化为全量同步。
   - **`repl-backlog-size` 的设计取舍**：越大能覆盖的"断线时长 × 写入速率"窗口越大，但占内存；配置太小会导致本该走部分重同步的场景大概率退化为全量同步，等于白设计。应按"预期最大断线时长 × 平均每秒写入字节数"估算。
3. **服务器运行ID（run ID）**：40位十六进制随机串，标识"这是哪一条复制历史"。哪怕 offset 数字凑巧落在新主库 backlog 范围内，如果 run ID 不一致（比如从库连的是故障转移后的新主库），也不能做部分重同步——因为 backlog 里存的根本不是同一批命令。

**`PSYNC <run_id> <offset>`** 三种返回结果：

| 主库返回 | 触发条件 | 结果 |
|---|---|---|
| `+FULLRESYNC <runid> <offset>` | run ID 不匹配，或 offset 不在 backlog 范围内 | 全量同步 |
| `+CONTINUE` | run ID 匹配且 offset 在 backlog 范围内 | 只补传缺失的一段命令 |
| `-ERR` | 主库版本太老不识别 `PSYNC` | 从库降级发 `SYNC`（版本兼容） |

从库第一次连接任何主库时，没有"上一次的 run ID"，只能发 `PSYNC ? -1`，必然触发 `FULLRESYNC`——部分重同步的前提是"曾经完整同步过一次，现在只是短暂断线"，不能替代第一次同步。

### 主从连接建立的完整流程（七步）

从库对主库而言，本质是一个打了特殊标志位的普通 `redisClient`（呼应第13章）：

```
① 设置主库地址和端口（REPLICAOF host port，只是记下来）
② 建立 socket 连接
③ 发送 PING，确认连接可用、主库能正常响应
④ 身份验证（AUTH，对应主库 masterauth/requirepass）
⑤ 发送从库监听端口（REPLCONF listening-port）
⑥ 同步（PSYNC，走全量/部分重同步）
⑦ 命令传播（持续进行）
```

**实用细节**：①②之间有时间差，`REPLICAOF` 执行完立即返回，真正连接由 `serverCron` 的周期任务异步发起（呼应第14章）；这期间 `INFO replication` 会显示 `master_link_status:down`，是排查"从库连不上"的第一入口。认证失败（`masterauth` 没配对）是生产上最常见的低级故障原因之一。

### 心跳检测：`REPLCONF ACK`

进入命令传播阶段后，从库默认每秒主动发送 `REPLCONF ACK <当前offset>`，承担三个作用：**检测网络状态**（长期收不到 ACK 判定从库异常）、**检测复制延迟**（对比 offset 差值，即 `INFO replication` 里的 `lag`）、**支撑 `WAIT` 命令语义**（`WAIT numreplicas timeout` 靠从库上报的 offset 判断是否已有足够从库确认收到某条写命令）。

### 从库对过期键的处理：读时打幻觉，不动手删除

从库不会自己执行物理删除：读到一个按 TTL 判断已过期的 key 时，表现得像它已经被删了（返回 nil），但物理数据保留，真正的删除动作只能来自主库通过命令传播发来的显式 `DEL`。这保证了"过期判定和删除"的权威只有主库一处，避免从库单方面删除导致的主从不一致（尤其是故障转移后从库变新主库时数据被提前丢失）。

### 复制的一致性模型：异步复制的固有代价

主库执行完写命令、给客户端返回结果的那一刻，**并不确认从库是否已收到**——命令传播是后台异步进行的。这意味着"客户端拿到成功响应"和"从库真正应用这条命令"之间存在时间窗口，主库若在此窗口内故障，故障转移选出的新主库上可能完全没有这条数据。

多维度权衡：同步复制（等从库确认再返回）能避免这个窗口，但把写延迟绑定到从库网络往返时间，跨机房场景代价很高；异步复制用"可能丢失一个窗口内的写"换取写性能。折中方案 `WAIT numreplicas timeout` 把选择权交还业务，但它只保证"确认从库收到"，不解决网络分区下的脑裂问题（留给第16、17章）。

**局限性**：主库故障存在数据丢失窗口；从库读可能读到滞后数据；复制机制本身不解决"主库挂了谁接班"，这是第16章 Sentinel 的任务。

## 易混淆/易错点

- **"部分重同步"不是无条件的**：必须同时满足 run ID 匹配 + offset 落在 backlog 范围内，缺一不可，否则 `PSYNC` 也会退化为 `FULLRESYNC`。
- **backlog 太小会让部分重同步形同虚设**：offset 一旦被覆盖，再短的断线也得走全量同步，配置大小要按断线时长和写入速率估算，不能用默认值应付。
- **从库不会自己物理删除过期键**：只做"读时逻辑过期"的表现，真正删除必须等主库的 `DEL` 命令传播过来，不能理解成从库自己独立执行惰性删除。
- **默认复制是异步的，不是同步的**：客户端拿到写成功的响应，不代表从库已经收到并应用这条命令，两者之间存在时间窗口，这个窗口是故障转移后可能丢数据的根本原因。
- **`REPLCONF ACK` 不是单纯的存活探测**：它携带的 offset 才是核心信息，复制延迟计算、`WAIT` 命令语义都靠这个 offset，不能简单理解成"心跳包收到了就行"。
- **异步复制窗口丢数据是所有基于 Redis 主从的上层机制（如 Redisson 分布式锁）都要面对的固有风险**，不是某个具体实现的 bug，业务层要有意识地做幂等/可重试/对账等自愈设计，而不是假设中间件绝对可靠。

## 与其他章节的关联

- **第9章「数据库」**：从库对过期键"读时逻辑过期、不物理删除"的策略，直接建立在第9章讲的惰性删除/定期删除机制之上，是这套机制在主从场景下的延伸规则。
- **第10章「RDB持久化」/第11章「AOF持久化」**：全量同步生成 RDB 时用到的 fork 写时复制机制来自第10章；复制缓冲区应对"后台生成快照 vs 前台继续写入"的思路，与第11章 AOF 重写缓冲区是同一类设计模式。
- **第13章「客户端」**：从库对主库而言是一个打了特殊标志位的普通 `redisClient`，复制连接的建立流程本质上是客户端连接生命周期的一个特例。
- **第14章「服务器」**：`REPLICAOF` 执行后真正发起连接的动作由 `serverCron` 周期任务异步触发，呼应第14章讲过的服务器周期任务机制。
- **第20章「Lua脚本」（Redisson watchdog讨论）**：异步复制的数据丢失窗口，正是 Redisson 分布式锁在主从故障转移场景下可能出现"锁被重复持有"问题的根本原因。
- **第16章「Sentinel」（待学）/第17章「集群」（待学）**：复制解决的是"数据怎么同步"，不解决"主库挂了谁来接替"，这是 Sentinel 的任务；心跳检测机制（`REPLCONF ACK`）也是 Sentinel 判断从库健康状态的底层信号之一。
- **第23章「慢查询日志」**：复制积压缓冲区的"固定大小、FIFO、旧数据被覆盖"的设计思路，与慢查询日志的固定长度链表是同一类"有限窗口"工程模式。
