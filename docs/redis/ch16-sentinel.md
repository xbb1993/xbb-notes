# 第16章 Sentinel（哨兵）

## 核心概念

**要解决的问题**：第15章的复制只解决了"数据怎么同步"，没解决"主库挂了谁来接班"。纯人工介入（登录从库执行 `SLAVEOF NO ONE`、逐个修改其他从库指向、修改客户端配置）耗时可能长达几十分钟，生产环境不可接受。

**朴素方案的碰壁**：写个单点脚本定时 `PING` 主库、挂了就自动执行故障转移，会撞到三堵墙——单点观察者的判断不可靠（网络抖动会被误判为主库下线）；多个独立脚本可能同时抢着执行故障转移，造成脑裂；缺乏"多方共识"机制。

**方案**：部署多个独立的 Sentinel 进程，共同监视主从库；通过投票达成共识避免单点误判；共识达成后推举一个 Sentinel 执行实际的故障转移。类比"陪审团制度"：单个陪审员判断可能有偏差，需要法定人数（quorum）共同认定才能定案；定案后由一个具体的执行人（领头 Sentinel）落实。

### Sentinel 的本质：特殊模式下的 Redis 服务器

Sentinel 不是独立产品，而是复用了 Redis 服务器代码框架、加载 `sentinel.conf`、使用专用命令表（不处理 `SET`/`GET` 等业务命令）的一种运行模式。它维护专门的 `sentinelState` 结构，记录当前监视的所有 master 及各自的从库、对等 Sentinel 信息。

**部署形态**：Sentinel 与 master/slave 是完全独立的两拨进程，**不持有业务数据**，彼此没有复制关系。数据平面（master+slave，真正存数据）和监控平面（多个 Sentinel 进程）是两层不同的东西，只通过网络连接（命令连接+订阅连接）产生关系。常见部署是"一主N从 + 3个（或以上奇数个）Sentinel"，且 Sentinel 数量和 master/slave 数量之间**没有固定比例**：一个 Sentinel 进程可以同时监视多个 master 组（各组互不相关，故障转移严格限定在各自的 master 名字范围内），一个 master 组也可以被多个 Sentinel 共同监视。1主1从这种最小拓扑同样可以（也往往应该）配置 Sentinel，是否开启取决于业务对故障恢复时间的容忍度，与从库数量无关；但 master 下若一个从库都没有，Sentinel 只能监视告警，无法真正执行故障转移（没有可提升的候选者）。

### 自动发现机制：不需要手动列出所有节点

- **发现从库**：Sentinel 与 master 建立连接后，默认每10秒发送一次 `INFO` 命令，从回复中解析出所有从库的地址，自动创建监视实例并建立连接——这正是从第15章 `INFO replication` 里 `slave0:...` 这些字段读出来的数据。
- **发现其他 Sentinel**：Sentinel 与每个被监视实例之间会同时建立命令连接和**订阅连接**，订阅该实例的 `__sentinel__:hello` 频道。每个 Sentinel 默认每2秒往这个频道 `PUBLISH` 一条消息（内容包括自己的 ip:port 和对该 master 状态的判断）。监视同一个 master 的多个 Sentinel 借助这个"公告板"互相认识，不需要在配置文件里手动写"其他哨兵地址"。

**监控关系的对应粒度是"以 master 名字为单位"**：`sentinelState.masters` 是一个以 master 名字为 key 的字典，每一条记录下面各自挂着自己的 `slaves` 字典和 `sentinels` 字典，不同 master 名字之间完全隔离，互不影响——包括后面讲的下线判定和选举，都是分别按 master 名字独立进行的。

### 主观下线（SDOWN）：单个哨兵的独立诊断

每个 Sentinel 默认每秒向所有已连接实例发送 `PING`。判断"有效回复"的标准并不是必须收到标准 `+PONG`——**只要在 `down-after-milliseconds` 规定时间内收到任何格式正确的回复（哪怕是 `-LOADING`、`-NOAUTH` 这类错误信息）都算存活**，只有完全无响应或协议格式错误才判定不可达。超过阈值无有效响应，这个 Sentinel 就独立地将该实例标记为主观下线——这只是它一个人的判断，不代表最终结论。

### 客观下线（ODOWN）：汇总多个独立视角

发现 master 主观下线的 Sentinel，会向同样监视这个 master 的其他 Sentinel 发送 `SENTINEL IS-MASTER-DOWN-BY-ADDR`，征询意见。每个被问到的 Sentinel 基于**自己独立执行的检测结果**（不是随大流附和）给出回复。当认为下线的票数（含发起者自己）达到配置的 `quorum` 值，master 被标记为客观下线。

**客观下线判定只针对 master**：从库或其他 Sentinel 的主观下线状态只是被记录下来（后续会影响它是否有资格成为故障转移候选者），不会触发"主观→客观"这套两级确认流程——因为只有 master 下线才会触发高风险的自动化故障转移操作，需要多数视角共同确认；从库下线影响小，没必要为它走重量级共识流程。

**quorum 的约束**：配置文件不会在解析时校验 quorum 是否合理，但逻辑上必须 `quorum ≤ 实际监视该 master 的 Sentinel 数量`，否则 ODOWN 永远无法达成——这是扩缩容 Sentinel 时容易被忽略的陷阱。quorum 只管"SDOWN→ODOWN"这一级，和选举领头 Sentinel 用的"过半数"门槛是两个独立的数字。

## 选举领头 Sentinel：借用 Raft 选举思路的一次性投票

**要解决的问题**：多个 Sentinel 都认定 master ODOWN 后，如果各自都去执行故障转移，会出现多个"新主库"同时接受写入的脑裂式事故，必须选出唯一执行者。

**规则**：任何判定 ODOWN 的 Sentinel 都可发起竞选。每个 Sentinel 在一轮 epoch（配置纪元，类比"任期编号"）里只能投一票，先到先得、投完不可反悔。候选人当选需同时满足：票数 > 所有已知 Sentinel 总数的一半，且票数 ≥ quorum。

**为什么必须"过半数"，仅达到 quorum 不够**：总票数固定（等于 Sentinel 总数），若只按 quorum 判断，理论上可能出现两个候选人都达到 quorum 但都没过半的情况，导致同时出现两个"领头"。"过半数"从数学上保证同一轮最多只有一个赢家（两个人的票数不可能同时超过总数的一半）。

**候选资格 vs 投票资格**：只有判定 ODOWN 的 Sentinel 才会发起竞选（当候选人）；但**投票资格不限于此**——任何监视该 master 的 Sentinel，哪怕自己没判定下线，只要收到拉票请求就可以投票，选举阶段不重新验证下线判断的正确性（这一步在 ODOWN 阶段已经确认过）。

**候选人自投是确定性的、且天然抢先**：一个 Sentinel 决定参选后，先在本地完成自投（零延迟，不涉及网络），再向外发送拉票请求。因此自投永远不会被别的候选人的请求"抢走"。

**全体撞车与随机化重试解决僵局**：若多个 Sentinel 因检测时间点接近而几乎同时参选、都先自投，会出现票数完全打散（每人1票，谁都不过半）的僵局。此时所有候选人放弃本轮，各自等待一段**随机时长**后（epoch递增）重试——由于"是否在新一轮里发起竞选"这个决定本身经过随机延迟错开，大概率某一轮里只有少数（甚至一个）哨兵率先行动，其余尚未参选的哨兵（本轮"空白票"状态）就会把票投给这个率先行动的候选人，从而收敛出结果。这与第一轮容易撞车（因为所有哨兵用相同检测标准，几乎同时得出 ODOWN 结论，没有刻意错开的机制）形成对比。候选资格池不因轮次增加而缩小，也不存在"只有上一轮候选人才能继续参选"的淘汰机制。

**去中心化的实现方式**：epoch 和票数都没有集中维护——每个 Sentinel 只在本地记录自己的 epoch 计数器和"本epoch投给谁"，epoch 通过消息传播对齐（收到更大的 epoch 就采纳）；票数由候选人自己发请求、自己统计，没有第三方计票。"同一 epoch 最多一个赢家"这个全局性质，完全靠每个节点各自遵守"一个epoch只投一票"这条本地规则+票数总和有限的算术事实叠加得出，不依赖任何中心账本。**局限性**：这套机制假设所有 Sentinel 诚实运行、只会崩溃或网络延迟，不是拜占庭容错设计，无法防御恶意节点破坏协议。

## 故障转移：领头 Sentinel 独自执行的四步

**第一步：挑选新主库**。先做资格筛选——剔除下线/断线状态的从库、剔除5秒内未响应 `INFO` 的从库、剔除与旧主库断开超过 `down-after-milliseconds×10` 的从库。再逐级排序：`slave-priority` 越小优先级越高（可设0表示永不参选）；优先级相同比复制偏移量（offset 越大数据越新）；offset 也相同则比 run ID 字典序最小者（纯粹用于打破平局，无业务含义）。

**第二步**：领头 Sentinel 向选中的从库发送 `SLAVEOF NO ONE`，使其转正为独立主库。

**第三步**：向其余从库发送 `SLAVEOF <新主库地址>`，使其重新指向新主库、按第15章讲过的 `PSYNC` 流程重新同步（通常会触发全量同步，因为彼此没有复制历史）。

**第四步**：旧主库恢复上线后，Sentinel 会强制向它发送 `SLAVEOF <新主库地址>`，将其降级为新主库的从库，绝不允许它以旧主库身份继续存在——这是防止脑裂的最后一道保险。

## 局限性

故障转移不是瞬时的，四步依次执行，中间有网络往返和可能的全量同步耗时，期间写请求可能失败或需要客户端重试。数据丢失依然可能发生：旧主库下线前尚未同步给新主库的写命令会永久丢失（第15章讲过的异步复制窗口问题在这里再次出现，Sentinel 解决的是"自动化快速切换"，不能承诺零数据丢失）。此外，客户端必须使用支持 Sentinel 感知的连接方式（如 Jedis/Lettuce 的 Sentinel 模式，通过 `SENTINEL GET-MASTER-ADDR-BY-NAME` 动态获取当前主库地址），否则故障转移对应用是不可见的，会继续往已降级的旧地址发请求。

## 易混淆/易错点

- **Sentinel 不是从库集群里的某个角色**，是完全独立部署、不持有业务数据的监控进程，与 master/slave 只有网络连接关系，没有复制关系。
- **Sentinel 与 master/slave 之间没有固定数量比例**：一个 Sentinel 可监视多个 master 组，一个 master 组可被多个 Sentinel 共同监视；1主1从一样可以且经常应该开启 Sentinel。
- **不同 master 组之间完全隔离**，包括故障转移范围严格限定在同一个 master 名字自己的从库池内，不会跨组借用从库；选举也是按 master 名字独立进行的。
- **PING 的"有效回复"不要求收到标准 `+PONG`**：只要规定时间内收到任何格式正确的回复（包括错误信息）都算存活，只有超时或协议错误才判定不可达。
- **客观下线判定只针对 master**，从库/其他 Sentinel 的主观下线只是被记录，不会触发"主观→客观"两级确认流程。
- **quorum 只是 SDOWN→ODOWN 的门槛，不是选举当选的门槛**：选举当选必须同时满足"过半数"这个独立条件，仅达到 quorum 不足以当选，因为可能出现两个候选人都达到 quorum 但都没过半、同时冒出两个"领头"的风险；"过半数"才是从数学上保证同一轮最多一个赢家的关键。
- **候选资格（能否发起竞选）限定于判定 ODOWN 的 Sentinel，但投票资格不受此限制**——任何监视该 master 的 Sentinel 都可以对收到的拉票请求投票，不要求投票者自己也认定下线。
- **候选人自投永远抢先于任何外部拉票请求**（本地操作零延迟 vs 网络请求有延迟），不存在"自投的票被别人抢走"的情况。
- **选举失败后的重试不是"上一轮候选人继续比拼"的淘汰机制**：候选资格池不随轮次缩小，只是"是否在这一轮发起竞选"这个决定经过随机延迟错开，靠这个随机性打破僵局。
- **旧主库恢复上线不会自动变回主库**：会被 Sentinel 强制降级为新主库的从库，这是防脑裂的关键保障。
- **Sentinel 选举不是拜占庭容错设计**，假设所有节点诚实运行、只会崩溃或延迟，无法防御恶意破坏协议的节点。

## 与其他章节的关联

- **第13章「客户端」**：Sentinel 复用服务器框架、切换命令表的做法，与伪客户端（`lua_client`）"复用框架、开模式开关"是同一类工程手法。
- **第14章「服务器」**：Sentinel 启动同样走服务器初始化流程，只是加载不同配置文件、注册不同命令表。
- **第15章「复制」**：Sentinel 自动发现从库直接依赖 `INFO replication` 回复（第15章心跳检测那节的数据来源）；故障转移第二、三步直接使用 `SLAVEOF NO ONE`/`SLAVEOF` 命令；数据丢失窗口的根本原因就是第15章讲的异步复制模型；选新主库时比较 offset 复用的正是第15章讲过的复制偏移量概念。
- **第20章「Lua脚本」（Redisson watchdog讨论）**：Redisson 分布式锁在故障转移场景下可能"锁被重复持有"的问题，根源正是本章讲的"故障转移过程中可能丢失异步复制窗口内的写"，两章讨论的是同一个底层风险在不同上层机制里的具体表现。
- **第17章「集群」（待学）**：集群内部的故障检测和自动故障转移思路与 Sentinel 有相通之处（都要解决"谁来判断下线、谁来执行切换"的问题），但集群是去中心化的节点间协商机制，不依赖独立的 Sentinel 进程，学到集群章节时可以回头对比两种设计的异同。
