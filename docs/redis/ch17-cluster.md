# 第17章 集群（Cluster）

## 核心概念

**要解决的问题**：复制和 Sentinel 解决了高可用问题，但都解决不了单机 Redis 的容量和吞吐量瓶颈——一台机器的内存和并发处理能力终究有物理上限。集群要解决的是**水平扩展**：把数据拆分到多台机器上。

**朴素方案的碰壁**：直接对节点数取模（`hash(key) % N`）来决定 key 归哪台机器，一旦节点数量变化（扩容/缩容/故障替换），几乎所有 key 的归属都会跟着变，导致大规模数据搬迁。

**方案：引入"槽"这层中间抽象**，类比"先把货物统一编号分格，再把格子分给不同仓库管理"：整个集群固定有 **16384 个槽**，每个 key 通过 `CRC16(key) % 16384` 计算出它属于哪个槽——这个结果只跟 key 本身有关，与集群节点数量无关。节点变化时，只需要调整"槽指派给谁"这一层映射，不需要为每个 key 重新计算归属。

```
key ──CRC16(key) % 16384──► 槽编号（固定不变）
                                  │
槽编号 ──归属关系（可动态调整）──► 具体节点
```

### 集群节点：本质仍是特殊模式下的 Redis 服务器

跟 Sentinel 类似，节点启动加 `cluster-enabled yes` 开关，复用服务器框架，额外维护 `clusterState`、`clusterNode` 等集群专属结构。**但节点发现机制与 Sentinel 不同**：需要手动执行 `CLUSTER MEET <ip> <port>` 主动握手，之后靠 **Gossip 协议**（节点间随机交换"我还知道哪些节点"）持续扩散集群拓扑，最终让每个节点都知道全部节点信息，不需要两两手动握手。

### 槽指派的两份存储：各自角度

- **`clusterNode.slots`**：每个节点自己维护的 16384 位位数组，记录"这些槽是不是归我管"——直接复用第22章讲过的位数组思路，2KB 就能表示完整归属状态。
- **`clusterState.slots`**：大小 16384 的全局索引数组，每个位置存指针指向负责该槽的节点，可 O(1) 查到"槽 X 归谁"。这份全局视图靠 Gossip 消息扩散、每个节点各自维护一份完整拷贝。

**为什么是 16384 个槽（多维度工程折中）**：不用 65536 是因为槽位图在 Gossip 消息里频繁传播，65536 位需要 8KB、16384 位只需要 2KB，节省传播开销；不用更小的数（如1024）是因为节点数多时槽粒度太粗、不利于精细化负载均衡和迁移。16384 是在"消息体积"和"分片粒度"之间的折中，服务于官方推荐的千级节点规模。

### 命令执行：MOVED 重定向，而非转发

节点收到命令后计算 key 所在槽，查 `clusterState.slots` 判断是否归自己：是则正常执行；不是则返回 `MOVED` 错误告知客户端正确地址，**由客户端自己重新连接发送，节点不做转发**——避免额外的跳转开销和代理逻辑复杂度，现代客户端库会缓存槽→节点映射，减少重复重定向。

**多 key 命令必须同槽**：涉及多个 key 的命令要求所有 key 落在同一槽，否则报 `CROSSSLOT` 错误——因为原子性要求所有 key 能在同一节点一次性访问，允许跨节点会引入分布式事务的复杂度或牺牲原子性，Redis 选择在设计层面直接回避。**用 hash tag（`{}`）强制让相关 key 落入同一槽**：如 `user:{1000}:profile` 和 `user:{1000}:orders`，只对花括号内容计算 CRC16。

### 重新分片：外部工具协调的四步迁移

由外部工具（`redis-trib` / `redis-cli --cluster`）协调，不是节点自动触发：

1. 目标节点：`CLUSTER SETSLOT <slot> IMPORTING <源节点ID>`
2. 源节点：`CLUSTER SETSLOT <slot> MIGRATING <目标节点ID>`
3. 工具逐个取出该槽的 key（`CLUSTER GETKEYSINSLOT`），对每个 key 执行 `MIGRATE`（序列化→发送→目标端 `RESTORE`→源端删除），一个 key 一个 key 地搬，不整槽打包迁移
4. 该槽全部 key 迁完后，广播 `CLUSTER SETSLOT <slot> NODE <目标节点ID>`，正式完成指派变更

**为什么按 key 粒度迁移而非整槽一次性搬走**：整槽原子迁移会导致槽在迁移期间完全不可用（可能数秒到更久），生产不可接受；按 key 粒度迁移需要引入 `ASK` 协议应对中间状态，增加了实现复杂度，但换来"迁移期间集群基本保持可用，只有被迁移槽里少数 key 有轻微延迟"的高可用性，是合理的工程取舍。

### ASK 错误：迁移中间状态的临时重定向

迁移进行中，源节点若发现请求的 key 已被迁走，返回 `ASK` 错误告知目标节点地址。客户端需先向目标节点发送 `ASKING`（一次性许可，只对紧跟的下一条命令生效），再重发原始命令——因为目标节点此时仍是 `IMPORTING` 状态，正常情况下会认为槽不归自己而返回 `MOVED`，`ASKING` 临时豁免这一限制。

**`ASK` 与 `MOVED` 的本质区别**：`MOVED` 是永久性的，槽已彻底转移，客户端应更新本地槽→节点缓存；`ASK` 是临时性的，只对这一次访问有效，不代表整个槽迁移完成，客户端不能更新本地缓存。

## 集群中的复制与故障转移：与 Sentinel 同源不同型

底层复制机制仍是第15章那一套（`PSYNC`、offset、backlog）。故障检测和转移**完全去中心化，没有独立的 Sentinel 进程**：

- **故障检测**：每个节点按 `cluster-node-timeout` 周期 `PING` 其他节点，超时未回应标记 **PFAIL**（等价 SDOWN）。PFAIL 信息随日常 Gossip 消息顺带传播（不是主动询问），当半数以上负责槽的主节点都认定某节点 PFAIL，该节点被标记 **FAIL**（等价 ODOWN）并广播全网。
- **故障转移的执行者变了**：不是"哨兵们互相投票"，而是**故障主节点的从节点自己发起竞选，其他健康的主节点投票**。从节点检测到主节点 FAIL 后，等待一段与自身复制偏移量排名挂钩的延迟（offset 越大等待越短，优先让数据最新的从节点率先竞选，减少数据损失）——这跟 Sentinel 选新主库"offset 越大优先级越高"是同一思路，只是这里融入了竞选时机而非事后排序。主节点每 epoch 只投一票，先到先得；从节点拿到超过半数主节点支持后当选，执行 `SLAVEOF NO ONE` 转正，广播接管的槽指派信息。

**消息类型（了解即可）**：`MEET`（握手）、`PING`/`PONG`（心跳+Gossip）、`FAIL`（下线广播）、`PUBLISH`（跨节点转发发布订阅消息，让连在不同节点的客户端也能收到同一频道消息，呼应第18章）。

## 局限性

多 key 操作被限制在同一槽内，业务大量依赖跨 key 原子操作的话，要么被迫用 hash tag 硬绑定（牺牲数据分布自由度），要么不适合上集群。网络分区下依然可能出现短暂脑裂——槽机制只保证正常情况下同一个槽不会被两个节点同时处理，故障转移过程中的窗口期仍有风险，这是 CAP 权衡里绕不开的问题。`cluster-require-full-coverage` 提供了一个直接的 CP/AP 权衡开关：槽不可用时是让整个集群拒绝所有请求（偏 CP），还是只让不可用的那部分槽报错、其他槽正常工作（偏 AP）。

## 易混淆/易错点

- **集群节点之间的发现机制与 Sentinel 不同**：节点需要手动 `CLUSTER MEET` 握手，再靠 Gossip 协议扩散全网拓扑；Sentinel 是通过被监视实例的公告频道被动发现彼此。
- **`clusterNode.slots`（节点自己的位图）和 `clusterState.slots`（全局索引表）是同一份指派关系的两种存储角度**，不要混为一谈：前者回答"这个节点负责哪些槽"，后者回答"这个槽归哪个节点"。
- **MOVED 不是节点帮你转发请求**，而是让客户端自己重新连接目标节点重试，这是出于避免额外跳转开销的性能考量。
- **多 key 命令要求所有 key 同槽，不是"尽量放一起"，而是硬性约束**，跨槽直接报 `CROSSSLOT` 错误；需要绑定同槽用 hash tag。
- **重新分片是外部工具协调触发的，不是集群自动完成的**；迁移按 key 粒度进行，不是整槽一次性搬走。
- **ASK 和 MOVED 不能混为一谈**：MOVED 永久生效、客户端应更新本地缓存；ASK 只对当前这一次访问临时生效，不代表整槽迁移完成，不能更新缓存。
- **集群故障转移的投票主体和 Sentinel 不同**：不是"哨兵之间互相投票"，而是"其他健康主节点给候选从节点投票"，但底层"过半数决定唯一赢家"的数学保证思路是相通的。
- **集群没有独立的哨兵进程**，故障检测（PFAIL/FAIL）和故障转移选举完全由节点自身通过 Gossip 协议去中心化完成。

## 与其他章节的关联

- **第15章「复制」**：集群内主从复制的底层机制完全复用第15章的 `PSYNC`/offset/backlog；故障转移执行的 `SLAVEOF NO ONE` 也是同一套命令。
- **第16章「Sentinel」**：集群的故障检测（PFAIL/FAIL）与 Sentinel 的 SDOWN/ODOWN 是同一类"两级下线判定"思路在去中心化场景下的另一种实现；故障转移选举同样复用"过半数决定唯一赢家"的数学保证，但投票主体从"哨兵互相投票"变成"主节点给候选从节点投票"；从节点按 offset 排名设置竞选等待延迟，呼应 Sentinel 选新主库时"offset 越大优先级越高"的同一设计思路。
- **第18章「发布与订阅」**：集群模式下 `PUBLISH` 消息需要节点间转发扩散，才能让连接在不同节点的客户端收到同一频道的消息，这是发布订阅机制在分片场景下的延伸处理。
- **第22章「二进制位数组」**：`clusterNode.slots` 用 16384 位的位数组记录槽归属，是位数组在集群模块里的直接工程应用。
- **第20章「Lua脚本」/分布式锁正确性（模块五待学）**：集群下多 key 操作必须同槽的限制，直接影响 Redisson 等框架在集群模式下实现分布式锁、批量操作等功能的设计方式，学到模块五分布式锁正确性专题时可以回头关联。
