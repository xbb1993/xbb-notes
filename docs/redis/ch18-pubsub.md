# 第18章 发布与订阅

## 核心概念

**要解决的问题**：前面所有命令都是"一问一答"的一对一交互，但现实中有"一条消息要同时广播给所有关心它的人"这类需求（比如多实例缓存失效通知、跨进程消息分发）。轮询方案延迟高、浪费资源；用 List 结构做队列是点对点的，一条消息被一个消费者取走后其他人就拿不到了——都不满足"一对多广播"这个诉求，需要专门的机制。

### 频道的订阅与退订

服务器维护一个字典 `pubsub_channels`，key 是频道名，value 是"订阅了这个频道的客户端"链表。`SUBSCRIBE news` 就是把当前客户端加进 `pubsub_channels["news"]` 这个链表，`UNSUBSCRIBE` 就是摘掉。是精确匹配，字典查找 O(1)。

### 模式的订阅与退订

另一套独立结构——链表 `pubsub_patterns`，每个节点是一个 `pubsubPattern`（模式字符串 + 客户端）。`PSUBSCRIBE news.*` 就是往这个链表加一个节点。查找匹配是遍历+通配符比对，跟频道订阅的字典查找不是一个量级的效率，两套结构完全独立，不是叠加关系。

### `PUBLISH` 的完整执行逻辑：两条路径都会走

```
PUBLISH news.sports "消息"
   ├─① 查 pubsub_channels["news.sports"] → 有订阅者就发
   └─② 遍历 pubsub_patterns，用通配符规则比对频道名是否匹配某个已订阅模式 → 匹配就发
```

两条路径独立执行，互不排斥。如果一个客户端既精确订阅了 `news.sports` 又模式订阅了 `news.*`，同一条消息会收到两份——这不是重复消费的 bug，是订阅方式重叠导致的正常行为。

### 客户端与订阅信息的双向维护

`redisClient` 结构里也要反过来记录"自己订阅了哪些频道/模式"（呼应第13章预留的坑位）。这是为了客户端断开连接时，服务器能精确知道要去哪些频道/模式链表里把这个客户端摘除干净，否则 `pubsub_channels`/`pubsub_patterns` 里会留下指向已关闭客户端的悬空引用。

### 订阅模式下的命令限制

客户端一旦执行 `SUBSCRIBE`/`PSUBSCRIBE`，这条连接就进入"订阅模式"，此时命令执行预备操作（第14章）只允许它执行 `SUBSCRIBE`/`UNSUBSCRIBE`/`PSUBSCRIBE`/`PUNSUBSCRIBE`/`PING`/`QUIT`，其他命令一律拒绝。正确用法是让这条连接专职接收广播消息，业务操作用另一条独立连接处理——大多数客户端库也是把发布订阅包装成独立连接对象。

### `PUBSUB` 查看命令

`PUBSUB CHANNELS [pattern]`、`PUBSUB NUMSUB [channel...]`、`PUBSUB NUMPAT`，都是对上面两个结构的只读查询，生产上主要用于运维排查，机制上没有新东西。

### 可靠性边界：fire-and-forget，at-most-once

**这是理解这一章最重要的一点**：传统 Redis 发布订阅完全不持久化，`PUBLISH` 那一刻不在线的订阅者，消息永久丢失，服务器不缓存、不重试、没有消费确认。这个设计取舍背后的多维度原因：定位上它的目标是"轻量级实时广播"而不是可靠消息队列；性能上不做持久化和确认往返让 `PUBLISH` 几乎是纯内存操作，延迟极低；实现复杂度上一旦要支持持久化和确认，就要引入消费者组、offset管理这些机制，这正是后来 Redis Streams 要解决的问题（书里没有，模块五候选话题）；工程可靠性上，"消息不能丢"这类需求应该换用专门的消息队列或 Streams，而不是勉强用 pub/sub 凑活。

### 生产实用判断

**适合场景**：多实例缓存失效广播、跨进程/跨网关的消息分发（如 Socket.IO 的 Redis adapter）、对丢消息容忍度高的实时通知。**不适合场景**：需要消息不丢、需要消费确认和重试、需要消费者组语义分摊消费——这些应该用专门 MQ 或 Redis Streams。整体上这是一个"机制简单、生产使用面窄"的轻量工具类功能，不是大多数 Redis 部署的核心用途，理解到"机制原理+可靠性边界+适用场景判断"这个深度即可，不需要在工程细节上继续深挖。

## 易混淆/易错点

- **频道订阅和模式订阅不是互斥关系**：`PUBLISH` 执行时两条路径（字典精确匹配 `pubsub_channels`、链表模式匹配 `pubsub_patterns`）都会走一遍，同时满足两种订阅方式的客户端会收到两份消息，不是"进了这条路径就不会再进另一条"。
- **发布订阅不是消息队列，没有持久化和送达保证**：容易被误当成"轻量版 MQ"，以为断线重连能补收错过的消息。实际是 at-most-once、fire-and-forget，不在线时的消息永久丢失，服务器没有缓存和重试机制。
- **订阅模式下不能在同一连接上混用业务命令**：一旦执行了 `SUBSCRIBE`/`PSUBSCRIBE`，这条连接只能执行订阅相关和 `PING`/`QUIT`，其他命令会被拒绝，业务操作要用另一条连接，不能指望一边订阅一边在同一连接上继续查数据。
- **`pubsub_channels`（字典）和 `pubsub_patterns`（链表）是两套独立结构**，不是一套结构的两种模式，查找效率也不同（O(1) 字典查找 vs 遍历+通配符匹配）。
- **客户端断开时的清理依赖双向记录**：不是只有服务器端的 `pubsub_channels`/`pubsub_patterns` 记着客户端，`redisClient` 也要反过来记自己订阅了什么，两份记录互为清理依据，缺一份就无法在断开时精确清理干净。

## 与其他章节的关联

- **第13章「客户端」**：`redisClient` 结构里预留的发布订阅相关数据结构坑位，在这一章对上号——用来支撑客户端断开时的双向清理；输出缓冲区限制里专门给 `pubsub` 客户端配置的独立档位，这一章补上了具体场景（订阅者消费跟不上发布速度，消息堆积在其输出缓冲区）。
- **第14章「服务器」**：命令执行预备操作里"订阅模式下命令限制"这一项检查，在这一章具体落地——只允许执行订阅相关命令和 `PING`/`QUIT`。
- **第9章「数据库」/第4章「字典」**：`pubsub_channels` 本质也是一个字典结构，跟第4章讲的字典实现是同一套基础设施的复用。
- **模块五「现代补充篇」（待学）**：Redis Streams 是发布订阅"不持久化、无消费确认"这个局限的后续解法，二者的关系值得在学到 Streams 时回头对比。
