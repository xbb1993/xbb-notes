# 第19章 事务

## 核心概念

**要解决的问题**：多条命令要"看起来是一个不可分割的整体"执行（如转账场景 `DECRBY A:balance 30` + `INCRBY B:balance 30`）。如果客户端依次单独发送，服务器虽然单线程执行命令，但不同客户端的命令是交替处理的（第12章I/O多路复用调度），两条命令之间可能被别的客户端插队，读到中间不一致的状态。

### 命令入队与批量执行

`MULTI` 开启事务后，客户端 `flags` 打上 `REDIS_MULTI`（第13章）。之后的命令不立即执行，而是放进这个客户端专属的事务队列（第14章"命令执行预备操作会把普通命令拦下来入队"这个伏笔在这里落地）。`EXEC` 执行时按队列顺序依次真正调用命令实现函数，因为是连续批量执行、中途不会被服务器切去处理别的客户端命令，天然解决了"插队"问题。执行结果打包成一个数组一次性返回。

```
MULTI                          事务队列：
DECRBY A:balance 30    →       [0] DECRBY A:balance 30
INCRBY B:balance 30            [1] INCRBY B:balance 30
EXEC                    →      返回 [70, 80]
```

### 两种"失败"必须严格区分

**入队阶段错误**（命令不存在、参数个数不对）：入队时就被命令表查找/`arity`检查（第14章）发现，客户端打上 `REDIS_DIRTY_EXEC`。`EXEC` 执行时发现此标志，**直接放弃执行整个事务，一条都不跑**，返回 `EXECABORT`。

**运行时错误**（如对字符串键执行 `LPUSH`）：入队时一切正常，不会被标记。`EXEC` 依次真正执行，前面已经成功的命令效果**已经生效、不会撤销**，只有出错的这一条在结果数组对应位置返回错误对象，其余命令继续执行。

**核心易错点**：Redis 事务不是"运行时出错就整体回滚"的关系型数据库式原子性。业务代码必须逐条检查 `EXEC` 返回数组每个位置的结果，不能假设没报 `EXECABORT` 就等于全部成功。

### `WATCH`：事务里的乐观锁

事务队列里的命令在 `EXEC` 前都不返回结果，事务内部无法用某条命令结果决定要不要继续跑另一条——"先读判断再写"（check-then-act）这类逻辑，判断必须在 `MULTI` 之前完成。

`WATCH key` 让服务器盯着这个键：服务器维护 `watched_keys` 字典（键→监视它的客户端列表，结构思路类似第18章的 `pubsub_channels` 但语义不同）。任何写命令（含过期删除、内存淘汰）修改被监视的键时，调用 `touchWatchedKey`，把监视者打上 `REDIS_DIRTY_CAS`（第13章）。`EXEC` 前检查此标志，命中则**直接放弃执行，返回 `nil`**（区别于入队错误的 `EXECABORT`），客户端可选择重新读取判断、重试整个流程。

```
WATCH A:balance
GET A:balance          → 读到100，判断够扣
MULTI
DECRBY A:balance 30
INCRBY B:balance 30
EXEC                    → 若期间A:balance被别人改过，返回nil，未执行
```

**核心易错点**：`WATCH` 不是锁，完全不阻塞其他客户端对这个键的读写，是**事后检查**不是**事前阻塞**——这正是乐观锁和悲观锁的本质区别。

**为什么选乐观锁而不是真正的悲观锁**：性能上悲观锁要维护锁状态、等待队列、超时释放，高并发下锁竞争是瓶颈，乐观锁只是"记一下谁关心、变了就标记"，开销极低；实现复杂度上悲观锁要处理死锁检测这类棘手问题，跟单线程模型不天然契合，乐观锁的"标记+检查"模式反而跟单线程模型无缝衔接；适用场景上乐观锁适合**冲突概率低**的场景，**局限性**：高冲突场景（如秒杀）用 `WATCH`+重试会导致大量客户端反复失败重试，这时更适合用 Lua 脚本（第20章）把"检查+执行"整体打包成原子操作，或者用专门的排队机制。

### Redis 事务的 ACID 边界

- **原子性**：不支持运行时回滚，只保证入队阶段错误会让事务整体不执行。
- **一致性**：事务本身不做任何业务规则校验，是调用方自己的责任。
- **隔离性**：能满足，但原理和数据库不同——不是靠锁或MVCC，而是靠"单线程执行、事务命令连续批量执行、中途不会被其他客户端命令打断"这个更根本的物理前提"免费"获得的。
- **持久性**：完全取决于持久化配置（RDB/AOF），跟事务本身无关，没开持久化的话事务执行完机器崩溃效果照样丢失。

### 边界细节

事务里不能嵌套 `MULTI`（会报错，不当命令入队）；`EXEC`/`DISCARD` 是事务状态仅有的两个出口，客户端中途断开服务器会自动清理未提交的事务队列；`watched_keys` 在事务结束（`EXEC`/`DISCARD`）或客户端断开时也要清理，跟第18章"客户端断开双向清理订阅信息"是同一个道理，避免悬空引用。

### 生产实际使用场景（重点，实用性讨论）

Redis 事务的真正价值不是"通用原子性"，而是两个具体能力：

**批量 ≠ 事务，两者要分清**：纯 Pipeline 只是客户端批量发送命令减少网络往返，**不保证**中途不被其他客户端命令插队；`MULTI`/`EXEC` 比 Pipeline 多的核心价值恰恰是这层**隔离性**——批量执行期间不会被其他客户端命令打断。

**场景一：多个 key 要"看起来同时变化"，不需要失败回滚**——典型例子是限流计数器：

```
MULTI
INCR request_count:user123
EXPIRE request_count:user123 60
EXEC
```

不用事务的话，`INCR` 和 `EXPIRE` 分开发送，中间有个极短窗口期这个 key 已存在但还没设过期时间，若被别的逻辑摸到会读到"应该临时存在却永久不过期"的错误状态，长期运行造成内存泄漏。包进事务消灭了这个窗口期——这里根本用不上"运行时失败回滚"的能力，需要的纯粹是"不被别人看到只做了一半"。类似场景还有：把一个业务对象拆成多个独立key存储时，需要保证读者不会读到"只更新了一部分"的中间态。

**场景二：`WATCH` 配合乐观锁，做低冲突频率的 check-then-act**——如库存扣减、余额判断，在冲突概率不高的前提下足够轻量，不用维护额外的锁服务。

**场景三（了解即可）**：早期用 `WATCH`+`MULTI` 实现简单分布式锁获取逻辑，现在基本被 `SET key value NX EX seconds` 一条原子命令取代。

**真正需要复杂原子逻辑时，生产更常用 Lua 脚本而非事务**：如果场景需要"多步操作+中间条件判断+失败时看起来什么都没发生"，`MULTI`/`EXEC` 做不到（无法在事务内部读取中间结果做分支），Lua 脚本在服务器端一次性原子执行、能在脚本内部拿中间结果做判断，且没有 `WATCH` 高冲突场景下反复重试的问题——复杂原子逻辑用 Lua，`MULTI`/`EXEC` 留给简单的批量隔离场景，是生产上更常见的分工。

**结论**：Redis 事务的定位是"给一组本身不太会失败的写命令提供不被并发插队的隔离保障+省网络往返"，加上"给低冲突场景提供轻量乐观并发检测（`WATCH`）"，从来不是要替代关系型数据库那种运行时出错整体回滚的语义，用之前先想清楚自己要的是"隔离性+批量"还是"真正的原子回滚"。

## 易混淆/易错点

- **Redis 事务不支持运行时错误回滚**：只有入队阶段的错误（命令不存在/参数不对）会让整个事务放弃执行（`EXECABORT`）；运行时错误（如类型不匹配）不影响已经执行成功的命令，事务不会自动撤销之前的改动。业务代码必须逐条检查 `EXEC` 返回结果，不能假设没报错就等于全部成功。
- **`WATCH` 不是锁**：完全不阻塞其他客户端对被监视键的读写，是"事后检查、提交前确认"的乐观锁思路，不是"事前阻塞"的悲观锁思路。
- **`WATCH` 返回 `nil` 和入队错误返回 `EXECABORT` 是两种不同的失败形式**，不要混为一谈——前者是监视的键被改动，后者是事务队列本身有问题。
- **Pipeline 和事务不是一回事**：Pipeline 只解决"减少网络往返"，不保证隔离性；`MULTI`/`EXEC` 额外提供"批量执行期间不被其他客户端命令插队"这层保障，这才是事务独有的价值，不能把两者的作用等同看待。
- **事务内部不能用某条命令的结果去决定另一条命令要不要执行**：判断逻辑必须在 `MULTI` 之前用普通命令完成，事务队列里的命令在 `EXEC` 前都不返回结果。这也是复杂条件逻辑场景更适合用 Lua 脚本而非事务的根本原因。
- **隔离性的实现原理和数据库不同**：不是靠锁或 MVCC，是靠"单线程连续执行、不会有其他命令中途插入"这个物理前提直接获得的，理解这一点才能明白 Redis 事务的隔离性为什么"几乎是免费的"。
- **事务不能嵌套 `MULTI`**，会直接报错，不会被当作一条命令处理。

## 与其他章节的关联

- **第13章「客户端」**：`REDIS_MULTI`、`REDIS_DIRTY_CAS`、`REDIS_DIRTY_EXEC` 这几个当时提到但未展开的 `flags`，在这一章全部被具体用到——事务状态标记、乐观锁冲突标记、入队错误标记。
- **第14章「服务器」**：命令执行预备操作阶段"事务队列拦截"这个当时提前预告但未展开的机制，在这一章完整落地——命令是否入队而非立即执行，判断发生在预备操作阶段，命令实现函数本身对此完全无感知。
- **第18章「发布与订阅」**：`watched_keys` 字典（键→监视客户端）在结构思路上跟 `pubsub_channels`（频道→订阅客户端）类似，都是"键到客户端集合"的映射；客户端断开/事务结束时清理 `watched_keys` 的必要性，跟第18章"客户端断开需双向清理订阅信息"是同一个工程原则的另一次应用。
- **第20章「Lua脚本」（待学）**：Lua 脚本是事务"无法在内部读取中间结果做判断"这个局限的解法，两者的分工边界（事务管简单批量隔离，Lua管复杂条件原子逻辑）值得在学完Lua后专门回顾对比。
