# 第20章 Lua脚本

## 核心概念

**要解决的问题**：呼应第19章——事务只能做"批量隔离执行"，无法在中间读取某条命令的结果做条件判断（比如"库存够就扣减，不够就返回失败"这类 check-then-act 逻辑）。用 `WATCH`+重试能做，但在冲突概率高的场景（如秒杀）会导致大量客户端反复读取、反复提交失败。Lua脚本把"检查+决策+执行"整体作为一段脚本一次性提交给服务器，在服务器本地完成判断和写入，从根本上消除了客户端和服务器之间的时间窗口。

### `EVAL` 的完整执行流程

```lua
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock and stock > 0 then
    redis.call('DECR', KEYS[1])
    return 1
else
    return 0
end
```

`EVAL "<脚本>" numkeys key1 key2 ... arg1 arg2 ...` 执行时：脚本文本被转换/缓存成一个 Lua 函数（缓存进 `lua_scripts` 字典，用SHA1摘要索引）→ `KEYS`/`ARGV` 数组作为参数传入 → 在 Lua 环境里执行这个函数，函数内部每次 `redis.call(...)` 借用第13章讲过的 `lua_client` 伪客户端身份，完整走一遍第14章讲的命令执行四阶段 → 脚本 `return` 的值按转换规则变成 Redis 协议回复。

**脚本执行期间不会被其他客户端命令打断，原因不是特殊加锁机制**：容易误解成 Redis 专门为脚本设计了锁或事务包装。正确理解是纯粹的单线程模型自然结果——一次 `EVAL` 调用本质上就是一条命令，服务器处理命令本来就是一个一个来的，脚本内部不管调用多少次 `redis.call()`，都发生在这"一条命令"被处理的这段时间内，不需要任何额外机制。

### `redis.call()` 与 `redis.pcall()`

`redis.call()` 遇到命令执行错误直接抛出 Lua 错误，**整个脚本立即中断**；`redis.pcall()` 遇到错误返回带 `err` 字段的 table，不中断脚本，可在脚本内自行处理。

**容易被过度神化的点**：以为脚本执行到一半出错，前面已经做的操作会被自动撤销。正确理解：脚本内**已经真正执行**的写操作，效果已经生效、不会自动回滚——跟第19章"事务运行时错误不回滚"是同一类局限，只是触发条件更少见（脚本作者可以用 `pcall` 提前处理可预期的错误分支）。

### 确定性要求

脚本在主/从服务器（或AOF重放）必须产生相同效果，所以不能有真正随机的行为（未处理的随机数、依赖系统时间）。Redis 对 Lua 环境的随机数/时间函数做了处理保证"同一段脚本重复执行结果一致"，但这不能让脚本获得真正有业务意义的随机性——更稳妥的做法是把随机性放在客户端生成好、作为 `ARGV` 参数传进脚本。

### `EVALSHA` 与脚本缓存

服务器维护字典 `lua_scripts`（SHA1摘要→脚本正文），首次 `EVAL` 后脚本被缓存，之后可以用 `EVALSHA <sha1>` 只传摘要执行，省去重复传输脚本文本的开销。找不到摘要返回 `NOSCRIPT`，客户端需要退回用 `EVAL` 重新提交。

**易错点**：以为 `EVALSHA` 是"读本地文件、用哈希当文件名索引"。正确理解：`lua_scripts` 完全是服务器进程**内存态**，跟磁盘/持久化完全无关，服务器重启后一定为空——生产代码的 `EVALSHA`+`NOSCRIPT`降级重试逻辑必须要有，不能假设脚本缓存永远存在。

### 脚本管理命令

`SCRIPT LOAD "<脚本>"`：只编译并缓存脚本、不执行，返回SHA1，生产上常用于应用启动时预热所有脚本，避免高并发下第一次调用集中触发 `NOSCRIPT` 重传。`SCRIPT EXISTS sha1...`：批量检查摘要是否已缓存。`SCRIPT FLUSH`：清空缓存。`SCRIPT KILL`：只能杀掉尚未执行过写命令、运行超时的脚本，一旦已经写过数据就不能被强行杀死（避免半途而废造成不一致）。

### Lua返回值到Redis回复的转换规则

| Lua返回值 | Redis回复 |
|---|---|
| number | 整数回复（**直接截断取整，不是四舍五入**） |
| string | 批量回复 |
| table（数组） | 多条批量回复；数组中间出现nil会截断 |
| true | 整数回复1 |
| false 或 nil | **空批量回复（nil）**，不是字符串"false" |
| 带`ok`字段的table | 状态回复 |
| 带`err`字段的table | 错误回复 |

### 沙箱限制（简述）

Lua 环境去掉了 `os`/`io` 库，脚本不能访问文件系统和系统调用，既防止危险操作也顺带减少不确定性来源；有全局变量保护机制（metatable）防止脚本间互相污染；额外提供 CJSON/Struct/cmsgpack 库处理JSON和二进制编解码。

### 脚本复制：命令复制 vs 脚本效果复制

①**命令复制**：把 `EVAL` 命令本身（脚本文本+参数）复制给从服务器/写入AOF，对方重新完整跑一遍脚本。②**脚本效果复制**：把脚本执行时产生的实际写命令记录下来复制过去，不复制脚本本身。

多维度对比：正确性上①要求脚本必须确定性，②天然绕开这个问题（复制的是已经确定的结果）；传输体积上，写操作少时①更省（只传一次脚本），写操作多时（如批量循环写入）②的传输量会远大于①；实现复杂度上①简单直接转发，②需要动态拦截脚本内每次 `redis.call()` 产生的写命令再打包传输，明显更复杂。本书（Redis 2.9/3.0）主要用①，这是"脚本必须保证确定性"是硬性要求的直接原因；后续版本默认改用②，放宽了这个限制，但脚本本身避免依赖不确定的外部状态仍是更稳妥的工程习惯，不能因新版本"兜底"而放松要求。

### 生产实际用法：分布式锁

```lua
-- 释放锁：比对owner再删除，避免误删别人的锁
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end
```

这是绝大多数生产级分布式锁实现（如 Redisson）底层依赖的手段——`WATCH` 做不到"读取判断+删除"合一，事务做不到内部条件分支，Lua脚本一次性原子解决。

### 深入案例：Redisson分布式锁的自动续期（watchdog）原理

**要解决的矛盾**：锁必须有过期时间兜底（防止持锁客户端崩溃后死锁），但过期时间设多长是两难——设太短，业务没跑完锁就提前释放，破坏互斥语义；设太长，客户端真崩溃时其他人要等很久，可用性受损。

**方案**：把"锁的过期时间"和"业务真正需要的时间"解耦。加锁时给一个较短默认过期时间（如30秒）防死锁；只要客户端还活着，后台线程（watchdog）按固定节奏（默认每10秒，即TTL的1/3）检查"这把锁是否还是自己的"，是则用Lua脚本原子地把TTL刷新回30秒；一旦客户端进程真的崩溃，续期线程自然停止，锁在最后一次续期后的30秒内正常到期释放。

**续期脚本同样要做归属校验**（不是无条件续期）：
```lua
if redis.call('hexists', KEYS[1], ARGV[2]) == 1 then
    return redis.call('pexpire', KEYS[1], ARGV[1])
else
    return 0
end
```
先比对"这个key当前的持有者标识是不是我"，避免A的续期线程误续了已经不属于A的锁（比如A的锁已过期被B抢到，A若不做归属检查就直接续期，会破坏B正常持有的锁）。

只有客户端**没有显式指定过期时间**时，Redisson才会启用watchdog；显式指定了leaseTime，则认为调用方清楚自己要锁多久，不会自动续期，到点正常失效。

**超时自动释放靠的是Redis原生key过期机制**（第9章），Redisson没有另外发明机制，锁本质就是一个带TTL的普通key，Redis服务器按第9章讲的惰性删除+定期删除策略处理它的过期。

**易混淆点**：①以为自动续期让锁变成事实上永不过期——正确理解是TTL机制完全没被绕过，watchdog只是客户端主动周期性"续命"，进程一旦失联（GC长时间停顿、被kill）续期动作中断，锁该过期还是会过期。②以为续期不检查归属——正确理解是续期脚本每次都要先确认持有者标识匹配才会续期。

**局限性**：GC长时间停顿/网络分区场景下，续期线程可能来不及执行，锁在原TTL到期后被释放，另一客户端可能趁机拿到锁，出现两边同时认为自己持锁的情况——这是单实例Redis锁的根本局限，锁的安全性建立在"进程存活假设"上；主从复制的异步性也带来局限：主库刚写入锁key还没同步给从库就宕机，从库晋升为新主库后这把锁并不存在，可能被另一客户端拿到——这是单Redis实例锁方案的已知薄弱环节，也是RedLock方案要解决、但本身有争议的问题（留待模块五"分布式锁正确性"专题深入）。

**串起来看**：Redisson锁 = Redis原生key过期机制（第9章）+ Lua脚本的原子性（本章）+ 客户端侧后台续期线程，三者组合，Redis服务器本身并不知道"分布式锁"这个概念，所有锁语义都是客户端库拼出来的。

## 易混淆/易错点

- **脚本原子性不是靠特殊锁机制**：是单线程执行模型的自然结果，`EVAL` 本质上就是"一条命令"，跟其他命令一样天然不会被打断。
- **脚本内已执行的写操作不会因后续报错自动回滚**：`redis.call()` 抛错会中断脚本，但已经生效的效果不会撤销，这跟事务运行时错误不回滚是同一类局限。
- **Redis对随机数/时间函数的处理只保证"同一脚本重复执行结果一致"**，不代表脚本可以放心写有业务意义的随机逻辑，真正的随机性应该在客户端生成后作为参数传入。
- **`lua_scripts` 缓存是纯内存态，不会持久化**，服务器重启后一定为空，`EVALSHA`+`NOSCRIPT`降级重试逻辑不能省略。
- **Lua的`false`/`nil`返回值会变成Redis的空批量回复（nil），不是字符串"false"**，客户端语言里容易被当成"没有结果"而非"逻辑上的假"，写业务判断时容易踩坑。
- **Lua的number返回值转成整数回复是直接截断，不是四舍五入**。
- **命令复制和脚本效果复制没有绝对优劣，取决于脚本内写操作的规模**：写操作少命令复制更省流量，写操作多（如批量循环写入）效果复制的传输量会远超命令复制。
- **Redisson的watchdog续期不是让锁变成永久不过期**，也不是无条件续期——TTL机制始终有效，续期是客户端主动周期性行为，且续期前必须先校验锁的当前归属。
- **单实例Redis锁（含watchdog）无法保证100%正确性**：GC停顿、网络分区、主从异步复制的窗口期都可能导致锁的互斥语义被破坏，这是根本性的局限而非实现缺陷。

## 与其他章节的关联

- **第13章「客户端」**：`lua_client` 伪客户端（贯穿服务器生命周期的那种）在这一章第一次被具体用到——脚本里每次 `redis.call()` 都是借这个伪客户端的身份走命令执行流程。
- **第14章「服务器」**：脚本内 `redis.call()` 触发的每一次调用，都完整走一遍第14章讲的命令执行四阶段（查找/预备/执行/后续工作），脚本本身对服务器调度而言就是"一条命令"这件事，是理解脚本原子性来源的关键。
- **第9章「数据库」**：Redisson等分布式锁方案的"超时自动释放"，完全依赖第9章讲的key过期删除机制（惰性删除+定期删除），没有另外发明新机制。
- **第10、11章「持久化」**：脚本的"确定性"要求跟持久化/复制场景下"必须产生相同效果"是同一条原则的延伸；`lua_scripts`脚本缓存本身不参与RDB/AOF持久化，是易错点。
- **第19章「事务」**：Lua脚本是事务"无法在内部读取中间结果做判断"这一局限的解法；脚本"已执行写操作不回滚"与事务"运行时错误不回滚"是同一类局限的两次体现；`WATCH`做不到的"读取判断+删除合一"，脚本可以一次性原子完成。
- **模块五「分布式锁正确性」（待学）**：Redisson watchdog机制及其局限（GC停顿、主从异步复制窗口期）已在本章深入讨论，为后续RedLock、多节点锁方案的对比讨论做了铺垫。
- **模块五「生产常用客户端框架」（待学，新增专题）**：Redisson等框架的分布式锁、限流器等能力，底层实现手段正是本章讲的Lua脚本机制。
