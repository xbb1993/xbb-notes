# 第21章 排序（SORT命令）

## 核心概念

**基础用法**：`SORT` 对 `list`/`set`/`zset` 里的元素排序并返回结果（不改变原键，除非用 `STORE`）。默认按数字大小排序，元素不是数字会报错；对字符串排序必须加 `ALPHA` 选项，按字典序比较。

**`SORT` 为什么"贵"**：要排序一个集合，服务器得先把所有元素取出放进一个可排序的数组，再执行排序算法，整体开销是 O(N log N) 起步，这跟集合类型的底层存储特性（第3、7章）直接相关。

### `BY` 选项：排序依据可以不是元素本身

**场景**：商品ID列表 `mylist=[1,2,3]`（list存储），热度分别存在独立key里（`hot_1=50`、`hot_2=90`、`hot_3=10`），想按热度重新排序 `mylist`。

**朴素方案的碰壁**：没有 `BY` 的话，只能客户端把 `mylist` 全部取出，再挨个单独查询每个ID对应的热度key，最后在客户端本地手动排序——排序逻辑被迫搬到客户端，还要多轮网络请求。

**方案**：`SORT mylist BY hot_*`，用元素值替换 `BY` 模式里的 `*`，构造出对应的外部key（`hot_1`/`hot_2`/`hot_3`），取这些key的值作为排序依据。

```
mylist: [1, 2, 3] → BY hot_* → 查 hot_1=50 hot_2=90 hot_3=10 → 按值排序 → 返回原始元素 [3, 1, 2]
```

**核心易错点**：`BY` 只是换了排序依据，**返回的仍然是原始元素（商品ID）**，不是热度值本身，想拿关联数据需要配合 `GET`。

### `GET` 选项：排序完顺便取出关联数据

`SORT mylist BY hot_* GET name_*` 会用排序后的元素值替换 `GET` 模式里的 `*`，取出对应的关联数据返回，类似"`ORDER BY` 热度、`SELECT` 名字"的组合效果。`#` 是特殊写法代表"元素自身"，可以配合其他 `GET` 一起用（如 `GET # GET name_*`）。

**易错点**：多个 `GET` 的返回结果是**平铺的一维数组**（如 `[3,"C商品",1,"A商品",2,"B商品"]`），不是按元素分组的嵌套结构，客户端需要自己按 `GET` 个数切分。

### 哈希版本的 `BY`/`GET`（`->`语法）

如果权重和数据存在哈希字段里而非独立key，用 `BY product_*->hot GET product_*->name` 这种带 `->` 的模式，从哈希的指定字段取值，思路跟独立key版本一致。

### `STORE` 选项

`SORT mylist BY hot_* GET name_* STORE mylist_sorted` 把排序结果保存成新的 `list`。**易混淆点**：如果用了 `GET`，`STORE` 存的是 **`GET` 取出来的结果**，不是原始元素——想存排好序的ID列表，`GET` 要用 `#`。

### 实用技巧：`BY nosort`

`SORT mylist BY nosort GET name_* GET price_*` 让排序**完全跳过**，元素保持原有顺序，纯粹利用 `GET` 做"批量按ID取多个关联字段"——本质是把 `SORT` 当成批量查询工具使用，一条命令代替客户端原本要发的一大堆单独查询。

### 性能真相与生产判断

**核心易错点**：以为 `BY`/`GET` 跟直接排序集合本身（如 `ZRANGE`）性能量级相当。正确理解：`BY`/`GET` 涉及的每个元素都要单独发起一次内部key访问，相当于对N个元素做N次等效 `GET`/`HGET`，是完全不同量级的开销，跟只读一遍集合本身数据不是一回事。

**集群场景的硬限制**：如果外部key分散在 Redis Cluster 不同节点（第17章待学），这类跨key关联操作往往连正确执行都做不到——集群要求一条命令涉及的所有key落在同一哈希槽，`BY`/`GET` 用到的外部key通常不满足这个条件。

**生产实际判断**：现代生产做排行榜类需求几乎都直接用 `ZSET` 把分数和成员存在同一结构里，用 `ZRANGE`/`ZREVRANGE` 直接返回——不需要跨key关联、性能可预测、天然兼容集群。"`list`/`set` 存ID+权重和字段分散在多个key+排序时靠 `BY`/`GET` 关联"这套模式在现代实践里基本被 `ZSET` 取代。`SORT` 真正还有价值的场景是 `BY nosort` 这种批量关联取值技巧，或单机小数据量的一次性数据整理/脚本工具场景。

### 内部实现（了解即可）

服务器用一个数组把待排序元素和各自排序依据放在一起，跑排序算法，排完后如果有 `GET` 再逐个按模式取值拼装最终结果。

## 易混淆/易错点

- **数字/字符串排序要选对模式**：默认 `SORT` 按数字比较，元素是字符串必须加 `ALPHA`，否则直接报错。
- **`BY` 只改变排序依据，不改变返回内容**：返回的仍然是原始集合里的元素，不是 `BY` 查到的权重值本身。
- **多个 `GET` 返回的是平铺一维数组**，不是按元素分组的嵌套数组，需要客户端按 `GET` 个数自行切分。
- **`STORE` 配合 `GET` 时存的是 `GET` 的结果，不是原始元素**：想存排序后的原始元素需要用 `GET #`。
- **`BY`/`GET` 的关联查询不是"免费"的**：每个元素对应一次内部key访问，是 O(N) 次额外访问而非一次集合遍历，大集合下开销显著，不能类比成跟 `ZRANGE` 一个量级。
- **`BY`/`GET` 的跨key关联在 Redis Cluster 下可能根本无法正确执行**，因为涉及的外部key很可能不在同一个哈希槽。
- **`SORT`+`BY`+`GET` 不是现代生产做排行榜的首选方案**，`ZSET` 才是更合适的原生方案；`SORT` 真正的现代价值在 `BY nosort` 批量关联取值这类辅助场景。

## 与其他章节的关联

- **第3章「链表」/第7章「压缩列表」**：`SORT` 需要先把待排序元素整体取出放进可排序数组的开销，跟这两章讲过的 `list` 底层存储结构（链表随机访问慢、压缩列表的访问特性）直接相关，是"`SORT` 为什么贵"的根源。
- **第4章「字典」**：哈希版本的 `BY`/`GET`（`->`语法）底层用到的哈希字段访问，复用的是第4章讲的字典结构。
- **第17章「集群」（待学）**：`BY`/`GET` 关联的外部key很可能不满足"同一命令涉及的key必须在同一哈希槽"这个集群约束，是这类用法在集群部署下受限的直接原因，学到集群章节时可以回头验证这个结论。
- **有序集合（zset，已在第6~8章数据结构模块中接触过其编码基础）**：现代生产用 `ZSET`+`ZRANGE` 替代 `SORT`+`BY`+`GET` 做排行榜类需求，是"选对原生数据结构、而不是拼凑关联操作"这一工程原则的具体案例。
