# 第22章 二进制位数组

## 核心概念

**要解决的问题**：当数据只有二元状态（是/否）、数量又很大时（比如全年签到记录、海量用户的活跃标记），怎么把存储成本压到极致。

**朴素方案的碰壁**：用 `set` 存"已发生的日期/事件"字符串，或用 `hash` 存"日期→0/1"，每个成员/字段都要占独立的存储空间（字符串本身+结构开销），一年365天、几百万用户规模下会是GB级别的开销。

**方案：位数组**——用一个bit表示一个二元状态，365天只需要约46字节（⌈365/8⌉），比前两种方案节省一到两个数量级。

### 位数组不是独立数据结构

**核心概念**：Redis没有为位数组单独设计编码，它就是SDS字符串（第2章），`SETBIT`/`GETBIT` 只是"把字符串字节内容按bit位重新解读"的一组命令，不是新的数据类型。

### 各命令的实现

- **`GETBIT key offset`**：把offset换算成"第几个字节的第几个bit"（`offset/8`定位字节，`offset%8`定位位），直接读取返回0或1。
- **`SETBIT key offset value`**：定位到目标字节和位，如果offset超出当前字符串长度，先扩展字符串空间，中间未被设置过的字节用0填充（复用第2章SDS的空间管理思路），再设置目标位。
- **`BITCOUNT key [start end]`**：统计字符串中被置为1的bit总数，可选按字节范围统计。内部用查表法（类似popcount）批量统计每个字节里1的个数，比逐bit遍历快，属于典型的"用空间换时间"优化（了解即可，不需深挖具体算法）。
- **`BITOP AND/OR/XOR/NOT`**：对多个位数组做按位运算，结果存进目标key。**易错点**：参与运算的字符串长度不一致时，按最长的对齐，短的部分用0补齐，不会报错或截断。

### 生产实用场景

**签到统计**：一年365天对应365个bit，`SETBIT`记录、`BITCOUNT`统计签到总天数，空间效率远超用set/hash存储。

**活跃用户统计**：每天一个位数组，用户ID映射成bit偏移量，当天活跃就置1。`BITOP OR`统计"这几天至少活跃一天的用户"，`BITOP AND`统计"连续几天都活跃的用户"——同等规模下内存和计算开销比用set做交并集小得多。

**布隆过滤器的底层基础**：布隆过滤器（多个哈希函数+一个大位数组）本身不是Redis原生类型，可以用`SETBIT`/`GETBIT`手动搭建简化版，生产更常用RedisBloom模块，但理解位数组有助于理解模块内部原理。

### 易踩的坑：用户ID不能直接当bit偏移量

**常见的错误理解**：直接拿用户ID当`SETBIT`的offset。**正确理解**：如果用户ID很大（如雪花算法ID）或不连续，直接当偏移量会导致位数组被迫扩展到能容纳这个偏移量的长度，哪怕中间大部分位从未被设置，这些空间照样会被分配，完全抵消位数组的空间优势——正确做法是先把用户ID映射成从0开始、连续或接近连续的小整数（维护"ID→序号"映射表），再用这个序号当偏移量。

### 局限性

位数组只能表达"在/不在"二元状态，存不了附加信息（如具体的签到时间点）；一旦业务需要在"是否"之外挂载额外数据，就要换回`hash`等结构。

## 易混淆/易错点

- **位数组不是独立的数据结构/编码**，本质就是SDS字符串，`SETBIT`/`GETBIT`只是换了一种按bit解读字节内容的方式，不要把它当成"第五种基本类型"之外的新类型。
- **`SETBIT`超出当前长度会自动扩展并用0填充中间字节**，不会报错，这是SDS空间管理机制的直接应用。
- **`BITOP`参与运算的字符串长度不一致时按最长对齐、短的补0**，不是报错也不是截断到最短。
- **不能直接拿大数字/不连续的ID当bit偏移量**，会导致位数组变得巨大且稀疏，完全抵消空间优势，必须先映射成连续小整数。
- **位数组只能存二元状态，不能存附加信息**，业务一旦需要更多数据要换用其他结构。

## 与其他章节的关联

- **第2章「简单动态字符串SDS」**：位数组的底层存储就是SDS字符串，`SETBIT`的空间扩展机制复用了SDS的空间管理思路。
- **第6章「整数集合」/第7章「压缩列表」**：朴素方案里用`set`/`hash`存二元状态时涉及的编码和存储开销，是理解"位数组为什么能省这么多空间"的对比基准。
- **第9章「数据库」**：签到统计、活跃用户统计这类场景常配合`EXPIRE`给位数组设置过期时间（如每天/每年一个key），跟第9章的过期机制直接相关。
- **模块五「大key/热key治理」（待学）**：如果ID映射不当导致位数组变得巨大，可能演变成大key问题，学到该专题时可以回头关联这个易错点。
