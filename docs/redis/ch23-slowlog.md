# 第23章 慢查询日志

## 核心概念

**要解决的问题**：生产上想知道"最近有没有命令执行得特别慢、拖慢了主线程"。记录所有命令的执行时间会产生海量无意义数据（绝大多数命令执行只要几微秒）；客户端自己掐表算总耗时又会把网络传输延迟、排队等待时间都混进去，分不清到底慢在哪。

**方案**：只记录执行耗时超过阈值的命令，保存在一个固定长度的链表（`slowlog`）里，超过长度限制删除最旧的记录（FIFO队列）。

### 慢查询记录的组成

每条记录（`slowlogEntry`）包含：唯一递增ID、命令执行时的Unix时间戳、**执行耗时（微秒）**、完整的命令和参数、（较新版本还带）客户端IP:端口和客户端名称（呼应第13章`CLIENT SETNAME`等客户端属性，用来定位是哪个客户端发的慢命令）。

### 两个关键配置

`slowlog-log-slower-than`（阈值，微秒为单位）：`0`表示记录所有命令（相当于全量审计模式），负数表示完全关闭该功能。`slowlog-max-len`：记录条数上限，超过后删除最旧记录。

### 核心易错点：统计的耗时范围

**常见的错误理解**：以为慢查询记录的耗时是客户端感受到的"发请求到收到回复"的完整延迟。**正确理解**：只统计第14章命令执行流程里"③调用命令实现函数"这一步本身的耗时，不包括①②预备操作、不包括这条命令在事件循环里排队等待前面命令执行完的时间（第12、14章讲过的"事件处理不可抢占"），也不包括网络传输时间。

**对生产排障的直接影响**：如果客户端体感延迟很高，但慢查询日志里没有对应记录，不代表这次请求不慢——很可能是命令本身执行很快，但前面排了一大串命令，这条命令在队列里干等了很久才轮到执行，这种"排队慢"不会被慢查询日志捕捉到。排除了慢查询日志不能排除"排队导致的整体慢"，需要结合其他延迟监控指标交叉判断。

### 设计取舍：为什么用FIFO而非"保留历史最慢N条"

**实现复杂度**：FIFO链表插入O(1)，不需要排序；"历史最慢N条"需要类似最小堆的结构，每次插入都要跟堆里最小值比较，复杂度更高。**使用场景**：生产排障关心的是"最近发生了什么"，反映系统当前健康状况，而非几天前的偶发个例。

**局限性**：短时间内慢查询大量涌入时，旧记录会被迅速冲刷掉；`slowlog`本质是内存里容量有限的滚动窗口，不是长期存储方案，需要外部系统定期`SLOWLOG GET`导出或用监控工具抓取才能长期留存和告警。

### 相关命令

`SLOWLOG GET [count]`（获取最近记录，默认10条，`-1`返回全部）、`SLOWLOG LEN`（当前记录条数）、`SLOWLOG RESET`（清空）。

### 生产实用建议

阈值常设在几毫秒到十几毫秒量级（注意单位是微秒，10毫秒要写成`10000`）；配合外部采集做长期留存和告警；排障时牢记核心结论——慢查询日志排除不了"排队导致的整体延迟"，需要配合其他延迟监控指标一起看。

## 易混淆/易错点

- **慢查询记录的耗时不是客户端体感的完整往返延迟**，只统计命令实现函数被真正调用执行的那一段时间，不含预备操作、排队等待、网络传输。
- **没有慢查询记录不代表这次请求不慢**：可能是命令本身执行快但排队等待时间长，这种情况慢查询日志完全捕捉不到。
- **`slowlog-log-slower-than`的0和负数是两种不同语义**：0是记录所有命令（全量审计），负数是完全关闭功能，不要混淆。
- **`slowlog`不是持久化的长期日志**，是内存里容量有限的滚动窗口，长期留存需要外部系统主动采集导出。

## 与其他章节的关联

- **第12章「事件」/第14章「服务器」**：慢查询统计的耗时范围严格对应命令执行流程的"③调用命令实现函数"这一步，理解这个边界依赖对第14章命令执行四阶段和第12章"事件处理不可抢占"规则的掌握。
- **第13章「客户端」**：较新版本慢查询记录里的客户端IP:端口和客户端名称，跟第13章讲过的客户端属性（如`CLIENT SETNAME`）直接对应，是定位"谁发了这条慢命令"的手段。
- **第9~11章「数据库/持久化」**：慢查询日志和这些章节讲过的过期键清理、持久化触发检查一样，都是"周期性/被动触发的运维辅助机制"，但慢查询是命令执行路径上的被动记录，不是`serverCron`主动周期检查的产物，两者触发方式不同，不要混淆。
