# 第24章 监视器

## 核心概念

**要解决的问题**：调试时想实时看清"服务器现在到底在执行什么命令"，需要一种能实时观察命令执行流的手段。

**机制**：客户端执行 `MONITOR` 后，`flags` 被打上 `REDIS_MONITOR` 标志（第13章讲过的字段），并被加入服务器维护的 `monitors` 链表。之后**服务器每次要执行任意客户端发来的命令时**，除了正常执行，还会遍历 `monitors` 链表，把这条命令的执行时间戳、来源客户端的IP:端口、所在数据库号、命令和参数格式化后发给所有监视者。

**核心易错点**：以为 `MONITOR` 只显示"自己这条连接发的命令"。正确理解：`MONITOR` 是**全局广播**，能看到服务器上**所有客户端**正在执行的所有命令，不局限于自己这条连接——这也是它对生产环境风险大的根本原因。

### 与发布订阅、慢查询日志的对比

跟第18章发布订阅相比：两者都是"一对多广播"，但发布订阅需要有人主动 `PUBLISH` 到具体频道才转发；`MONITOR` 不需要任何显式广播动作，服务器在**执行命令**这个动作发生时就顺带广播，监视的是"命令执行事件"本身，不是业务消息。

跟第23章慢查询日志相比：设计目标不同决定了实现方式不同——慢查询日志是**事后、选择性**的，只记录超过阈值的命令，存在内存滚动窗口里可随时回看；`MONITOR` 是**实时、全量**的，不做过滤也不做存储，连接一断开之前看到的内容就没了。前者服务于"事后定位哪些命令慢"，后者服务于"问题发生当下，立刻看清现在发生了什么"。

### 为什么生产环境几乎不能开

**性能影响**：一旦有客户端执行 `MONITOR`，服务器执行的**每一条**命令都要多做一次"遍历monitors链表+序列化+发送"，不是只有被监视对象多付出开销，而是**服务器上所有流量都要为这一个监视连接多做一份广播**，高QPS场景下这笔额外开销会直接影响整体吞吐。

**安全隐患**：`MONITOR` 能看到明文的所有命令和参数，包括 `AUTH` 密码、业务敏感数据，生产环境开启相当于给连接者一份实时全量明文流量。

**结论**：`MONITOR` 只应作为**临时调试工具短暂使用**，用完立刻断开，不能长期挂着；需要持续的命令级可观测性应该用专门的审计/APM工具，而非长期开着一个 `MONITOR` 连接。

## 易混淆/易错点

- **`MONITOR` 是全局广播，不是"自己的调试窗口"**：能看到服务器上所有客户端的所有命令，不局限于自己这条连接。
- **`MONITOR` 的广播触发方式跟发布订阅不同**：不需要显式 `PUBLISH`，是服务器在执行任意命令时顺带广播，监视的是命令执行事件本身。
- **`MONITOR` 和慢查询日志的定位完全不同**：一个是全量实时、不持久化，一个是选择性事后记录、可回看，不要把两者当成同类工具混用。
- **`MONITOR` 的性能代价由全服务器流量承担，不只是被监视的连接本身**：这是生产环境绝对不能长期开启的直接原因，配合明文数据泄露的安全隐患，两条理由都要记住。

## 与其他章节的关联

- **第13章「客户端」**：`MONITOR` 命令依赖的 `REDIS_MONITOR` 标志，是第13.1章提到但当时未展开的 `flags` 字段之一，在这一章落地。
- **第18章「发布与订阅」**：两者都是"一对多广播"机制，但触发方式（显式PUBLISH vs 命令执行时顺带广播）和监视对象（业务消息 vs 命令执行事件）不同，是对比理解两种广播机制的好例子。
- **第23章「慢查询日志」**：同为运维调试工具，但"全量实时不存储"和"选择性事后可回看"是两种完全不同的设计取向，分别服务于"当下排查"和"事后定位"两种不同场景。
