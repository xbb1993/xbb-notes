# 模块五·专题1 内存淘汰策略全貌

## 核心概念

**要解决的问题**：`maxmemory` 达到上限后怎么办。默认策略 `noeviction` 直接拒绝写入（`OOM command not allowed`），只有读命令还能执行——这对"Redis当数据库用（数据不能丢）"的场景是期望行为，但对"Redis当缓存用"的场景体验很差，业务希望内存满了能自动清理旧数据腾地方，而不是罢工。

**两种使用场景决定了这个话题的重要程度完全不同**：Redis 当**数据库**用时，触发淘汰意味着业务数据被静默删除，是要靠容量规划、监控告警去避免的运维事故，淘汰策略的存在感很低；Redis 当**缓存**用时，淘汰不是意外，而是**故意依赖的容量管理核心机制**——故意把 `maxmemory` 设置得比"理论全部数据"小，靠 LRU/LFU 自动把热数据留在内存、冷数据挤出去，这时淘汰策略每天都在稳定运转。即便是精心规划容量的"数据库场景"，大key/热key异常增长、内存碎片、流量突增等因素也可能让淘汰意外触发，理解这套机制、能看懂 `INFO memory` 里的 `evicted_keys` 指标排查"是否在丢数据"，是一项实际的故障排查技能。

### 八种淘汰策略：两个独立维度的组合

- **候选池范围**：`allkeys`（所有key都可能被淘汰）vs `volatile`（只从设置了过期时间的key里挑）
- **挑选算法**：`lru`（最近最少使用）、`lfu`（使用频率最低，4.0+新增）、`random`（随机）、`ttl`（仅volatile系列可选，挑剩余存活时间最短的）

组合出 `allkeys-lru`/`allkeys-lfu`/`allkeys-random`/`volatile-lru`/`volatile-lfu`/`volatile-random`/`volatile-ttl`，加上默认的 `noeviction`，共8种。

### 为什么是近似 LRU，不是精确 LRU（呼应第14章serverCron的伏笔）

精确LRU需要维护一个按访问顺序排列的双向链表，每次访问都要把该key挪到链表头部——代价是额外的链表指针内存开销，以及**每次读操作都要触发链表调整**，这跟"读操作应尽可能轻量、不产生额外写副作用"的设计定位冲突，高并发下会成为性能瓶颈。

Redis 的实际方案：每个对象只记录一个"最后访问时间戳"（第8章 `robj` 结构里的 `lru` 字段），淘汰时**随机采样一小撮候选key**（数量由 `maxmemory-samples` 配置，默认5），比较采样候选者的时间戳，淘汰最久未访问的那个。Redis 3.0+ 引入"淘汰池"优化，让多轮采样结果能够累积比较，逐渐逼近真实LRU效果而非每次独立瞎猜。

**多维度权衡**：空间上不需要额外链表指针；性能上更新时间戳是O(1)且不涉及其他key，读操作几乎零额外开销；代价是牺牲"绝对精确"换来"足够好、性能可控"，`maxmemory-samples` 是可调的精度/性能权衡旋钮。

### LFU：修复LRU的先天盲点

LRU只看"最近是否访问过"，导致一个历史上访问量很大的真热点数据，只要最近一小段时间没被碰，就会被误判成冷数据优先淘汰；反过来一次性访问过的从冷key也会被暂时误判为热。LFU用**访问频率**代替访问时间——计数器对数式增长（避免很快封顶无法区分）并**随时间衰减**（避免曾经热但现在早没人碰的key因历史计数值高而一直占着内存）。适合有明显热点、访问模式稳定的缓存场景。

### volatile-ttl：不看访问情况，直接比过期时间

不依赖访问统计，直接比较剩余存活时间，优先淘汰"反正快要自然过期"的key，思路更直接，但只能在有过期时间的key范围内起作用。

## 易混淆/易错点

- **默认的LRU淘汰不是精确的**：只在随机采样的有限候选范围内比较，不保证全局最优，`maxmemory-samples` 是精度/性能的权衡旋钮，不是"对不对"的问题。
- **`volatile-*` 系列有一个容易被忽略的边界**：如果设置了过期时间的key已经被淘汰光了、内存依然超限，Redis依然会拒绝写入报错，**不会去动没设置过期时间的持久key**——选择 `volatile-*` 时如果业务大部分内存被永久key占用，可能形同虚设。`allkeys-*` 没有这个限制，但代价是业务原本不希望被清理的数据也可能被误伤，选型必须结合"这部分数据能不能丢"判断。
- **淘汰策略选错可能造成真实数据丢失**，这跟"缓存未命中"是完全不同量级的后果，不能简单当成性能优化选项来配置，要先判断数据本身的可丢失性。
- **"Redis当数据库"和"Redis当缓存"两种场景下，淘汰策略的重要程度截然相反**：前者应尽量避免触发（靠容量规划），后者是主动依赖的核心容量管理机制，不能一概而论"生产中用得少"。

## 与其他章节的关联

- **第8章「对象」**：淘汰算法依赖的访问时间戳/频率计数器，就存在 `robj` 结构当时提到但未展开的 `lru` 字段里，这里是该字段的具体用途落地。
- **第14章「服务器」**：近似LRU的随机采样思路呼应了 `serverCron` 讲过的"近似LRU时钟"设计伏笔，都是"用可控的近似换取性能"的同一类工程判断。
- **第9章「数据库」**：`volatile-*` 系列淘汰策略依赖key是否设置了过期时间，这个信息直接来自第9章讲的过期键机制。
- **大key/热key 治理（模块五下一专题）**：内存淘汰是应对整体内存压力的机制，而大key/热key是导致内存压力异常增长的具体成因之一，两者是"整体应对手段"与"具体问题源头"的关系，下一专题会详细展开。
