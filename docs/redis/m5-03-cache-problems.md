# 模块五·专题3 缓存穿透/击穿/雪崩

## 核心概念

### 统一类比：奶茶店的展示柜与后厨

- **缓存** = 展示柜里已经做好、随取随走的现成饮品
- **数据库** = 后厨，现做一杯比较慢
- 正常流程（朴素旁路缓存 Cache-Aside）：查展示柜有没有现成的 → 有就直接拿；没有就等后厨现做，做完顺手补一杯到展示柜方便下一个人

三个问题是这套体系被"击穿"的三种不同方式，**症状相似（数据库被打爆）但根源、触发条件、应对方式完全不同，不能混用同一套方案**：

| | 触发原因 | 波及范围 |
|---|---|---|
| 穿透 | 查询数据库里**根本不存在**的数据 | 单次/持续的无效查询 |
| 击穿 | **存在**的热点数据TTL到期瞬间遭遇高并发 | 单个key的重建请求被并发放大 |
| 雪崩 | 大批key集中过期 / 缓存服务本身不可用 | 大面积甚至全量缓存失守 |

---

### 一、缓存穿透（Cache Penetration）

**本质**：缓存的"命中/未命中"机制，前提是这个 key 曾经被写入过缓存。如果数据库里根本不存在这个数据，它永远没机会进入缓存，每次请求都会原样穿透到数据库。不是缓存"失效"，而是缓存机制从设计上没打算管这种情况——可能被恶意构造大批量不存在的ID用作攻击手段。

**方案一：缓存空值**

- 查数据库返回空，也把"空"结果写入缓存（较短TTL），下次同样请求被缓存层拦住。
- **TTL权衡**：太长——若该数据后续被真实创建，短期内会被"骗"成不存在（假404）；太短——起不到削峰作用。工程上是"止损"而非"根治"。更完整做法：数据创建/写入时**主动删除**对应空值缓存，而不是干等TTL过期（呼应第9章"惰性删除vs主动删除"）。
- **坑**：攻击者用大批不同的不存在ID打，会在缓存里灌入海量垃圾key（缓存膨胀攻击）。淘汰策略（专题1）能兜底内存不至无限膨胀，但不能作为穿透的主防线。

**方案二：布隆过滤器（Bloom Filter）**

机制：位数组 + 多个哈希函数。插入时把 key 通过 k 个哈希函数算出的 k 个位置都置1；查询时检查这 k 个位置是否全部为1，若有一个不是则**绝对不存在**，若全部是则**可能存在**。

**假阳性 / 假阴性**：

- 假阳性（False Positive）：过滤器说"可能存在"，但实际不存在——多余穿透一次数据库，代价可接受（可用缓存空值兜底）
- 假阴性（False Negative）：过滤器说"绝对不存在"，但实际存在——业务直接出错，**布隆过滤器的设计准则是绝不允许假阴性，只允许假阳性**，这是结构本身的数学保证

**为什么必须多次哈希、不能一次哈希独占一个位置**：

- 一次哈希要做到"绝对不冲突"，要么位数组大小要覆盖 key 的全部可能取值范围（对任意字符串/海量ID完全不现实，等于失去省内存的意义），要么需要提前知道全部会插入的key集合构造"完美哈希"（无法应对动态新增数据）
- 位数组大小有限、实际key数量或范围远大于它时，**冲突是鸽笼原理决定的数学必然**（生日悖论同源问题）：例如用普通均匀哈希把800万key映射进1000万位的位图，期望仍有约30%的key会与别的key撞到同一位置，"位图比key多"不等于"不会冲突"
- 多次哈希的作用不是消灭冲突，而是要求**多个独立位置同时命中**才判定"可能存在"，用概率相乘的方式把误判率指数级压低（大致存在 `k ≈ (m/n)×ln2` 的最优哈希次数公式）

**为什么删除只能整体重建**：位数组中的每个bit会被多个key共享（哈希碰撞不可避免）。若直接把某个key对应的几个位清零，可能连带清掉其他仍在使用这些位的key依赖的位，导致那些key被误判"不存在"（产生假阴性，违反核心承诺）。因此标准布隆过滤器**不支持局部删除**，只能拿当前全量有效key重新计算、整体重建。

**关键边界：key域大小决定该不该用布隆过滤器**——如果key本身稠密连续（如自增ID 1~1000万），根本不需要哈希，直接拿ID当位图下标即可（100%精确，即第22章的位数组技术）。布隆过滤器真正解决的是**key稀疏、跳跃、范围巨大到没法直接建索引**的场景（雪花算法ID、UUID、字符串SKU）。

**生产中ID稀疏/跳跃/频繁变动的应对**（新增频繁 vs 删除频繁要分开看：新增是免费的增量操作`BF.ADD`，不需要重建；只有删除/物理失效才是真正的难点）：

1. 标准布隆过滤器 + 定期整体重建：接受一个误差窗口，已删除的key短期内仍可能被判定"可能存在"，配合缓存空值兜底止损，是最主流的方案
2. Cuckoo Filter（布谷鸟过滤器）：用"桶+指纹"代替位数组+多哈希，原生支持精确删除（RedisBloom 提供 `CF.ADD`/`CF.DEL`），假阳性率通常更优，但桶满时插入可能失败
3. 按时间分片：多个"短生命周期"的小布隆过滤器代替一个长期维护的大过滤器，过期分片直接整体丢弃，规避逐key删除问题，适合有时间局部性的数据（订单、日志类）
4. 退化方案：变动模式复杂或穿透压力可控时，干脆不上过滤器，只用"参数合法性校验+缓存空值"兜底——布隆过滤器不是免费的，维护成本要计入决策

**第一道防线（成本最低）**：接口层参数合法性校验，直接拒绝明显不合法的请求参数（如ID为负数/远超当前最大值），不进入缓存/数据库流程。

**两方案多维度对比**：

| 维度 | 缓存空值 | 布隆过滤器 |
|---|---|---|
| 实现复杂度 | 低 | 较高（需额外结构+同步登记） |
| 准确性 | 100%准确，但仅对已查询过的ID生效 | 有假阳性率，首次查询仍可能放行一次 |
| 内存占用 | 可能被攻击造成垃圾key膨胀 | 对海量ID非常省内存 |
| 删除/更新适应性 | 天然支持 | 标准版本不支持，需整体重建 |
| 适用场景 | ID随机、增长频繁、不想维护额外结构 | ID相对可枚举、追求省内存、能接受运维成本 |

生产上两者常常配合而非二选一：布隆过滤器挡住大多数明显不存在的请求，少数假阳性放行、查库为空的，再用缓存空值兜底。

### 二、缓存击穿（Cache Breakdown）

**本质**：这个key在数据库里**真实存在**，只是缓存这份拷贝恰好在某个时刻（TTL到期）失效，赶上了高并发访问——是"时间窗口+并发量"的问题，跟数据存不存在无关。

**与专题2"热key"的区别**：专题2讲的是热key任何时候的高频访问压力（本地多级缓存分散）；击穿聚焦的是**热key的TTL过期瞬间**这个特定窗口期的并发冲击，是正交的问题。

- 错误理解：本地缓存能完全解决击穿。
- 正确理解：若本地缓存TTL跟Redis对齐，所有应用实例的本地缓存会同时失效，问题只是从"用户全部打Redis"变成"应用实例全部打Redis/数据库"，规模缩小但并发瞬间冲击的结构性问题没有根治。

**方案A：互斥锁保护重建**——只允许一个请求去数据库重建缓存，其他请求等待重试或返回降级值。加锁必须用**一条原子命令**（`SET lock value NX EX seconds`），不能分两条命令（`SETNX`+`EXPIRE`）执行，否则进程在两步之间挂掉会导致锁永不过期（呼应第19/20章"多步操作必须原子执行"，完整的分布式锁正确性问题留待模块五后续专题）。

**方案B：逻辑过期**——不用Redis自带TTL，把过期时间作为value的字段存下，缓存本身永不物理过期。读到"已逻辑过期"的数据时，**先直接返回这份旧数据**（不等待），同时异步触发后台任务重建（通常也配一把锁保证只有一个后台任务在重建）。

**A/B本质区别（一致性 vs 可用性的真取舍）**：

| 维度 | 方案A：互斥锁 | 方案B：逻辑过期 |
|---|---|---|
| 数据一致性 | 最终都是新数据 | 主动接受短暂陈旧数据 |
| 用户响应时间 | 部分请求等待/重试，有延迟毛刺 | 所有请求立即返回，无人等待 |
| 实现复杂度 | 较简单 | 需维护过期时间戳字段+异步重建，更复杂 |
| 适用场景 | 必须返回最新数据（余额、库存扣减） | 能接受陈旧数据、响应时间要求极高（详情页、排行榜） |

**打散过期时间**：对单个热key本身无意义，但是雪崩场景A的核心预防手段，这里先埋一个伏笔。

**局限性**：互斥锁依赖"Redis实现的锁可靠"这一假设本身未经审视；逻辑过期只该用在明确的热点key，不是普适方案；两种方案都无法解决"唯一那次查数据库本身很慢"的问题。

### 三、缓存雪崩（Cache Avalanche）

两种独立成因，症状相同（数据库被打爆）但根源、触发条件、应对方式完全不同：

**场景A：大批量key集中过期**——批量导入数据统一设同一固定TTL，到期时几万个不同key同一秒集体失效，比单个key的击穿严重得多（很多不同查询同时涌向数据库，不是同一个查询被重复）。

- 应对：给TTL加随机抖动（`基础TTL + random(0, jitter)`），把集中失效的时间摊薄到一个窗口内，是最简单、成本最低、最常用的预防手段
- 或走主动更新路线：数据变化时后台任务主动写入新值，不依赖被动过期重建

**场景B：缓存服务本身不可用**——进程崩溃、主库故障、网络分区、维护重启，跟TTL设计完全无关，缓存层物理上不存在，所有请求（不管到期没到期）都会直接砸向数据库。

- 应对（直接复用已学的高可用机制）：
  - 第15章复制+第16章Sentinel：故障转移自动化，把"缓存完全不可用"窗口从人工介入的分钟级压缩到自动化的秒级（但故障转移本身有延迟，窗口不为零）
  - 第17章集群：分片存储的附带好处——节点故障只影响它负责的槽范围，不是全量缓存失效，波及面远小于单机主从"一挂全挂"
- **冷启动/重启后空缓存**：本质是场景B的特例（缓存层重新可用但内容为空）。应对：第10章RDB/第11章AOF持久化让重启后快速从磁盘恢复大部分数据；主动预热——上线前提前批量写入预计会被访问的热点数据

**错误理解 vs 正确理解**：随机TTL抖动只解决场景A，对场景B（缓存服务本身故障）完全无效，两条独立故障链路必须分别设计对策。

**连锁传导效应**（雪崩真正可怕之处）：初始触发点很小（一个节点故障或一批key同时过期），但数据库被打爆后查询变慢，应用层请求堆积占满连接池/线程池，最终演变成跟Redis无关的整个后端系统被拖垮。因此需要跟Redis本身关系不大、但生产标配的兜底手段：**限流**（超阈值请求快速失败/排队）、**熔断降级**（对非核心功能降级、保护核心链路）、**多级缓存兜底**（呼应专题2的本地缓存，Redis不可用时降级返回本地旧数据）。

**局限性**：随机抖动范围设太大会牺牲数据刷新及时性；复制/哨兵/集群能缩短缩小故障窗口，但不能保证零故障窗口；限流熔断保护系统整体不被打垮，但意味着部分请求被主动牺牲，是可用性内部的再取舍，不是免费的。

## 易混淆/易错点

- **穿透 ≠ 击穿**：穿透是数据库里也不存在的数据，缓存机制对它天然无效；击穿是数据真实存在，只是恰好在TTL到期瞬间遭遇高并发。两者的应对手段完全不同（穿透靠布隆过滤器/空值缓存拦截无效请求；击穿靠互斥锁/逻辑过期收敛并发重建），不能混用。
- **本地缓存不能替代击穿的专门方案**：如果本地缓存TTL跟Redis对齐，会同时失效，问题只是从"用户打Redis"变成"应用实例打Redis"，规模缩小但没有根治并发瞬间冲击。
- **布隆过滤器允许假阳性、绝不允许假阴性**：这是结构本身的设计准则和数学保证，不是可调参数；一旦出现假阴性（真实存在的数据被误判不存在），说明用法出了问题（比如错误地做了局部删除）。
- **"位图比key数量大"不等于"用普通哈希映射就不会冲突"**：这是生日悖论/装球入桶问题，普通哈希函数的设计目标是均匀分布，不是无冲突，冲突在数学期望上大量存在。
- **一次哈希独占位置只在key域小、可枚举时才成立（应该直接用位图，不需要布隆过滤器）**；key域稀疏巨大（如UUID、雪花算法ID）时才需要布隆过滤器，此时哈希压缩带来的冲突是必须面对的代价。
- **标准布隆过滤器的"变动频繁"要拆开看**：新增key是免费的增量操作，不需要重建；只有删除/物理失效频繁才是真正要解决的难点（对应方案是Cuckoo Filter或按时间分片）。
- **随机TTL抖动只解决雪崩里"大批量key集中过期"这一种成因，对"缓存服务本身不可用"完全无效**，两者需要分别设计对策（前者是数据层面的TTL策略，后者是高可用架构+应用层兜底）。
- **雪崩的破坏力来自连锁传导**：不是Redis失效本身可怕，而是它会像多米诺骨牌一样拖垮数据库、应用服务乃至整个后端系统，所以需要限流/熔断/多级缓存这类跟Redis无关的通用工程手段兜底。

- **第15章「复制」/第16章「Sentinel」**：雪崩场景B（缓存服务不可用）靠故障转移自动化缩短窗口，是这两章高可用机制在缓存稳定性问题上的直接应用。
- **第17章「集群」**：分片存储让节点故障只影响局部槽范围，是雪崩场景B在集群模式下波及面更小的直接原因。
- **第10章「RDB持久化」/第11章「AOF持久化」**：雪崩场景B的特例——冷启动空缓存问题，靠持久化文件快速恢复数据来缓解。

- **模块五后续专题「分布式锁正确性」**：击穿方案A用到的互斥锁，本身的正确性问题（原子性、锁提前过期、释放校验）是该专题要详细展开的内容，本专题只先用、不深挖。
