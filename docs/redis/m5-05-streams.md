# 模块五·专题5 Redis Streams

## 核心概念

**要解决的问题**：第18章讲过发布订阅的两个致命局限——消息不持久化（订阅者断线期间的消息永久丢失）、没有消费确认机制（消息发出去就完事，Redis不知道也不关心订阅者有没有处理成功）。这决定了PUB/SUB只能做"实时广播通知"，做不了"可靠消息队列"。Streams（Redis 5.0引入）就是为了补上这块空白。

**类比**：PUB/SUB像大喇叭广播——喊一嗓子，现场没听到的人永远错过；Stream像一本流水账本——每条消息按顺序记上唯一编号，任何时候都能翻回去查某一页，可以有多个记账员分工处理不同账目（消费者组），每人处理完一条要打勾确认（ACK），没打勾的会被发现要求补处理。

### 从两次朴素尝试的碰壁推演到 Stream

**尝试一：PUB/SUB**——`PUBLISH` 发出的消息，订阅者不在线就永久错过，Redis完全不知道、也不关心有没有被处理。不可用于需要可靠投递的场景。

**尝试二：List 实现队列（LPUSH生产 + BRPOP消费）**——这是Streams出现前的经典土办法，硬伤在于 `BRPOP` 是"取出即删除"，没有"待确认"这个中间状态：消费者取到消息后处理到一半崩溃，这条消息就从list里彻底没了，没人知道它还没处理完，也无法重新派发给别人，消息彻底丢失。

**Stream的设计思路**：把"取出"和"确认完成"拆成两步——消息不会因为被读取就消失，而是保留在日志里；每个消费者读到的消息进入一个"待处理列表"（PEL），只有显式ACK之后才算真正处理完。

```
Stream orders（持久化的、只追加的消息日志）：
┌─────────────┬─────────────┬─────────────┬─────────────┐
│1700000001-0 │1700000002-0 │1700000003-0 │1700000004-0 │  ← 唯一ID：
│order:1001   │order:1002   │order:1003   │order:1004   │    <毫秒时间戳>-<序号>
└─────────────┴─────────────┴─────────────┴─────────────┘
      消息写入后一直保留，不会因为被读过就删除
```

消息ID默认自动生成（`XADD key * field value`），单调递增，同时是"游标"——可以指定"从哪个ID之后开始读"，天然支持历史回溯，这是PUB/SUB完全不具备的能力。

### 消费者组：分摊处理 + 待确认追踪

```
XREADGROUP GROUP workers worker-A ...  →  worker-A 拿到 order:1001
XREADGROUP GROUP workers worker-B ...  →  worker-B 拿到 order:1002
                                            （同一条消息不会同时给A和B，是分摊不是广播）

PEL（Pending Entries List）：
┌──────────────┬──────────┬──────────────┐
│ 消息ID        │ 归属消费者 │ 状态          │
├──────────────┼──────────┼──────────────┤
│1700000001-0  │worker-A  │待确认（已读未ACK）│
└──────────────┴──────────┴──────────────┘

worker-A处理完 → XACK orders workers 1700000001-0 → PEL里这条记录被移除
```

**易错点**：未 ACK 的消息**不会自动重新分发**给别的消费者。它会一直躺在PEL里，需要主动用 `XCLAIM`/`XAUTOCLAIM` 认领，或用 `XPENDING` 巡检发现卡住的消息——这是需要业务自己实现的巡检逻辑（通常是定期脚本检查PEL里停留超过阈值时间的消息，主动认领重试），不是Stream内置的自动能力。

### 多维度对比：Stream 适用边界

| 维度 | PUB/SUB | List(队列) | Stream | 专业消息队列(Kafka等) |
|---|---|---|---|---|
| 持久化 | 无 | 有 | 有 | 有，机制更成熟 |
| 消费确认/防丢失 | 无 | 无（取出即删） | 有（PEL+ACK） | 有 |
| 消费者组/负载均衡 | 无（广播） | 需业务自实现 | 原生支持 | 原生支持，并行度更高 |
| 历史回溯 | 不支持 | 支持但取出即删 | 原生支持（按ID范围查） | 原生支持，策略更灵活 |
| 吞吐量/横向扩展 | 高 | 中等 | 中等 | 专为高吞吐设计 |
| 运维复杂度 | 低（Redis自带） | 低 | 低 | 高（独立中间件运维） |

**关键判断**：Stream 补齐了"持久化+消费者组+确认机制"这几个核心语义，但吞吐量上限、分区并行扩展能力、生态工具链（死信队列、Schema管理、跨语言connector）跟Kafka/RabbitMQ有明显差距。适合"业务已经在用Redis、需要一个轻量级可靠任务队列/事件流，又不想为此单独运维一套Kafka"的场景，不是无条件替代关系；核心交易链路、要求极高吞吐和强顺序保证的场景，专业消息队列依然更稳妥。

## 易混淆/易错点

- **消费者组内未ACK的消息不会自动重试/重新分发**：会一直留在PEL里，必须靠`XCLAIM`/`XAUTOCLAIM`主动认领，或`XPENDING`巡检发现，Stream没有内置的超时自动重新派发机制。
- **Stream ≠ Kafka的Redis平替**：它补齐了持久化+消费组+确认这几个核心语义，但吞吐量、分区扩展性、生态工具链跟专业消息队列有明显差距，不能无条件替代重量级消息中间件的场景。
- **List做队列的根本缺陷不是"没有持久化"，而是"取出即删除、没有待确认状态"**：即便List本身走AOF/RDB持久化，一旦消费者`BRPOP`取到消息，这条消息就从数据结构里消失了，处理失败没有任何挽回余地，这跟持久化与否是两个维度的问题。
- **Stream消息不会自动清理**：不设置`MAXLEN`或不主动`XTRIM`，消息会无限累积占用内存，容易在无意中把一个Stream养成大key。

## 与其他章节的关联

- **第18章「发布与订阅」**：Stream直接针对PUB/SUB"不持久化、无消费确认"这两个局限而设计，是同一问题域（消息通知/异步处理）在可靠性要求更高场景下的解决方案，两者不是替代关系而是适用场景不同（PUB/SUB适合实时广播通知，Stream适合需要可靠投递和处理追踪的任务队列/事件流）。
- **第3章「链表」（List类型）**：List实现队列（LPUSH+BRPOP）是Streams出现之前的朴素方案，其"取出即删除、无待确认状态"的硬伤直接是Stream要解决的问题起点。
- **模块五·专题1「内存淘汰策略」/专题2「大key/热key治理」**：不设置`MAXLEN`的Stream会无限增长，本质上会变成一个持续膨胀的大key，是"忘记配置保留策略"导致大key的一个具体成因；`XRANGE`扫描很大范围的历史消息，代价和"全量遍历命令"是同一类风险，量级失控同样会拖慢单线程事件循环。
- **第23章「慢查询日志」**：大范围的`XRANGE`查询如果耗时过长，会体现在慢查询日志里，是排查Stream相关延迟问题的直接入口。
