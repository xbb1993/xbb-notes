# 模块五·专题7 生产常用客户端框架（Redisson/Jedis/Lettuce）

## 核心概念

前面学的都是Redis服务端原理，本专题换视角：业务代码通过客户端库跟Redis通信，Java生态最常见的Jedis、Lettuce、Redisson经常被混着比较，但它们处在不同层次。

**类比**：Jedis像打电话——每次通话独占一条电话线，说一句等回应才能说下一句；Lettuce像用聊天软件发文字——可以连续发消息不用等回复，系统自动帮你对上是哪条消息的回复，对话框可以多人共用；Redisson像雇了一个秘书——不用自己研究协议细节，直接说"帮我处理这把锁"，秘书在背后拼装Lua脚本和基础命令帮你办成。

### 三者的层次划分：不是同一维度的竞品

**Jedis**：命令方法和Redis命令一一对应，简单直接。但**一个连接同一时刻只能被一个线程用**，不是线程安全的。多线程共享同一Jedis连接会导致协议错乱（命令和响应交织，读到别人的响应）。必须配合连接池（`JedisPool`）使用，每个线程借用、用完归还。连接池配置不当（最大连接数太小）在高并发下会导致"借不到连接"报错，是生产常见事故来源。

**Lettuce**：基于Netty的异步事件驱动模型，**一个连接可以被多个线程并发安全共享**，内部对请求/响应做了正确匹配调度，不需要连接池也能应付很高并发（仍支持连接池用于特定场景）。支持同步/异步/响应式（Reactive）三种调用风格。Spring Boot 2.x之后默认的Redis客户端就是Lettuce。

- 错误理解：Lettuce一个连接能被多线程共享，可以完全不用担心连接数量，一个连接包打天下。
- 正确理解：某些命令天生需要独占连接——阻塞命令`BRPOP`/`BLPOP`会让连接停在那里等新数据，如果和其他命令共用会互相卡住；`MULTI/EXEC`事务执行期间也需要绑定同一个连接才能保证同一事务上下文。这些场景依然需要独立连接，不能无脑认为"一个连接解决所有问题"。

**Redisson**：不是"另一个协议客户端"，而是建立在客户端通信能力之上的**分布式对象/语义封装层**，提供`RLock`（分布式锁）、`RMap`/`RList`（分布式集合）、`RRateLimiter`（限流器）等高层API。第20章讨论过的watchdog自动续期，正是Redisson在`RLock`上做的可靠性封装，背后是拼装Lua脚本+基础命令实现的，不是Redis原生新能力。

### 客户端集群模式下的槽映射缓存（呼应第17章）

第17章讲过集群下节点收到不属于自己的key会返回`MOVED`。如果客户端每次都先猜错、等`MOVED`再重试，等于每个请求多一次网络往返。三个客户端内部都维护一份"槽→节点"映射缓存，初次连接拉取全量映射后按缓存直接路由，绕开大部分重定向。

- 错误理解：客户端第一次拉取到槽映射缓存后，就可以一劳永逸，不用管后续变化。
- 正确理解：集群重新分片或故障转移后槽的归属会变化，客户端缓存会过时，届时会收到`MOVED`错误并据此刷新缓存。**槽映射缓存是"尽力而为的性能优化"，不是"绝对准确的权威数据"**；`MOVED`/`ASK`协议本身就是为兜底"缓存必然滞后"这个现实而设计的，客户端优化只是减少触发这个兜底路径的频率，不能替代它。

### Pipeline：客户端侧的网络效率优化

呼应上一专题的服务端多线程I/O——那是服务端并行处理多连接的I/O，Pipeline是**客户端侧**优化：把多条命令一次性打包发送，不用一条条等响应，减少网络往返次数（RTT）。三个客户端都支持，但使用姿势不同（如Jedis的pipeline需要专门排队+统一flush，和普通命令混用容易出错）。这是"客户端减少往返"和"服务端并行处理连接"对同一"网络交互效率"问题的不同层面应对，不要混为一谈。

### 序列化：容易被忽视但影响很大的选型点

客户端存取的Java对象要转成Redis能存的字节串，序列化方式（JDK原生序列化 vs JSON vs Kryo/Protobuf）直接影响存储体积、(反)序列化性能，也影响跨语言互操作性——多语言服务共享同一Redis时，JDK原生序列化几乎无法被非Java语言读懂，JSON通用性更好。是性能 vs 可读性/调试便利性 vs 跨语言互操作性的多维度权衡，没有放之四海而皆准的答案，且一旦数据已写入生产，换序列化方式要处理存量数据兼容问题。

### 多维度对比

| 维度 | Jedis | Lettuce | Redisson |
|---|---|---|---|
| 定位层次 | 底层命令客户端 | 底层命令客户端 | 高层分布式对象封装 |
| 线程安全 | 否，需连接池 | 是，单连接可多线程复用 | 是（内部基于Netty） |
| 调用风格 | 同步阻塞 | 同步/异步/响应式都支持 | 同步/异步，且封装高层语义 |
| 连接池必要性 | 必需 | 大幅降低（个别场景仍需要） | 内部自行管理 |
| 典型场景 | 简单场景、历史遗留项目 | Spring Boot默认选型、高并发场景 | 需要分布式锁/集合/限流器等高层语义 |

## 易混淆/易错点

- **Jedis必须配合连接池，不能多线程共享单一实例**：这是线程安全模型的根本差异，不是配置问题。
- **Lettuce单连接可复用不代表所有命令都能共用一个连接**：阻塞命令和事务场景依然需要独立连接。
- **Redisson不是又一个协议客户端，而是构建在客户端能力之上的高层封装**：它的"魔法"底层是Lua脚本+基础命令的组合，排查问题时不能当纯黑盒。
- **客户端槽映射缓存是性能优化不是正确性保证**：缓存会因集群重新分片/故障转移而过时，正确性最终依赖`MOVED`/`ASK`协议兜底。
- **Pipeline（客户端减少网络往返）和服务端多线程I/O（并行处理多连接）是同一大类"网络效率"问题的不同层面**，不是同一个机制。

## 与其他章节的关联

- **第20章「Lua脚本」**：Redisson分布式锁的watchdog自动续期本质是客户端后台定时用Lua脚本原子化判断"是不是自己的锁"再延长过期时间，确认了Redisson是"建立在Lua脚本能力之上的封装"这一定位。
- **第17章「集群」**：客户端槽映射缓存是应对`MOVED`/`ASK`重定向机制的客户端侧工程优化，两者是同一问题的两端配合。
- **第13章「客户端」**：之前学的是Redis服务端如何看待和管理一个连接（`redisClient`结构），这里补充的是应用程序如何通过客户端库跟Redis通信，是同一个"连接"概念的两端视角。
- **模块五·专题6「多线程I/O」**：Pipeline和服务端多线程I/O是"网络交互效率"这同一大类问题在客户端和服务端两个层面的不同应对手段。
