# 模块五·专题8 分布式锁正确性（RedLock）

## 核心概念

**类比**：分布式锁像银行金库的钥匙。单实例锁像金库只有一个保管员，钥匙在谁手上谁能进；但如果保管员突然失联（主库宕机），备用保管员（从库）接手时如果钥匙归属信息还没同步过去，可能给新人重新配一把"有效"钥匙，导致两人同时"合法持有"钥匙。

### 单实例锁的基本实现与正确性要求

`SET lock_key <随机值> NX EX 30`——`NX`保证互斥，`EX`防止客户端崩溃后锁永久占用。释放锁必须先校验随机值再删除，且这两步要用Lua脚本原子完成（呼应第19、20章"多步操作必须原子"），否则会误删别人的锁。

### 单实例锁在HA环境下的正确性缺口

```
客户端A在主库拿到锁 → 主库宕机（这条SET命令还没来得及复制给从库，第15章异步复制窗口）
   → Sentinel故障转移，从库升级为新主库，新主库上没有这把锁的记录
   → 客户端B请求加锁，新主库判断"没有这把锁"，直接允许B加锁成功
   → A和B同时认为自己持有同一把锁
```

这是第15章讲的异步复制数据丢失窗口在分布式锁场景下的具体表现——只要锁状态依赖单一主从复制链条，切换窗口期就是绕不开的正确性缺口。

### RedLock：多个独立实例的"过半数确认"

思路：不用一套主从Redis，而是部署多个（通常5个）完全独立、互不复制的实例，加锁时依次请求所有实例，超过半数成功才算全局有效：

```
1. 记录开始时间T1
2. 依次向5个独立实例 SET lock_key <同一随机值> NX PX 有效期（设置合理网络超时）
3. 记录结束时间T2，计算消耗时间
4. 若成功实例数≥3且消耗时间<有效期 → 加锁成功，剩余可用时间=有效期-消耗时间
   否则 → 失败，向所有实例发送释放请求
```

这借用了第16章Sentinel、第17章集群讲过的"过半数"共识思路，但有本质区别：**Sentinel/集群的参与节点之间有明确定义的角色和状态同步协议**；**RedLock的5个实例只是互相独立、没有协议保证一致性的普通Redis进程**，"过半数"只是客户端自己在多处下注、事后统计成功次数。

### Kleppmann的批评：过半数确认解决不了"锁持有者自己失联"的问题

```
客户端A成功拿到RedLock锁 → 发生长时间GC暂停（或网络分区/调度延迟），远超锁的有效期
   → 锁在服务端已自然过期 → 客户端B请求加锁，在过半数实例上成功
   → 客户端A暂停结束，对锁已过期一无所知，继续执行业务逻辑
   → A和B同时操作同一资源
```

**这不是RedLock特有的bug，是所有"基于超时"的锁机制的通病**：锁的正确性依赖"持有者会在过期前执行完毕，或至少能立刻感知锁已失效"这个假设，而GC暂停、网络延迟、调度延迟在分布式系统里无法彻底消除。RedLock的过半数机制只解决"获取锁这个动作是否可靠"，没有触及"持锁期间客户端可能失联"这个更深层问题。

### Fencing Token（栅栏令牌）：更根本的解决思路

每次成功加锁附带一个单调递增的令牌号；下游资源（数据库等）记录"已处理过的最大令牌号"，只接受比这个值更大的请求，拒绝任何携带旧令牌号的操作（即使客户端"自认为"还持有锁）。**关键在于把"防止破坏"这件事从锁本身下放到被保护的资源**——承认锁可能已在客户端认知之外过期，但确保滞后的操作不会造成实际破坏。RedLock本身没有提供这个机制。

### 该怎么选型：多维度论证

- **业务容错能力**：操作幂等、或下游有fencing token式校验能力时，短暂重叠访问不会造成实际损失，单实例锁（甚至Redisson带watchdog的锁）已够用。
- **一致性要求强度**：要求"绝对不能有并发操作者同时碰同一资源"（金融扣款级别），应该用真正的共识系统（Zookeeper/etcd，基于Raft/ZAB，节点间有严格日志复制和状态一致性保证），或在下游加fencing token，而不是依赖任何基于超时的锁。
- **运维和性能代价**：RedLock要求5个完全独立的实例（不能是同一套主从关系），运维复杂度和资源成本显著上升，加锁要等多实例网络往返，性能比单实例慢——这笔代价只降低了"锁获取阶段"单点故障的概率，没解决"持锁期间失联"的根本问题。

### 呼应第20章：watchdog 缓解的是同一类问题，但不是同一个解法

Redisson watchdog（客户端后台持续续期）想让锁"只要客户端还活着就不过期"，缓解的正是"业务执行时间不确定"问题——**但watchdog依赖客户端续期任务正常运行**，客户端本身GC暂停时，续期请求同样发不出去，锁一样会过期。watchdog（治标，降低概率）和fencing token（治本，改变防线位置）是从两个角度应对同一根本问题，可以同时使用而非互斥。

## 易混淆/易错点

- **单实例锁的正确性缺口根源是异步复制窗口，不是Redis本身"不可靠"**：只要锁状态依赖主从复制链条，故障转移窗口期就是绕不开的问题，这是分布式系统的普遍限制。
- **RedLock的"过半数"和Sentinel/集群选举的"过半数"看似同源，实则本质不同**：后者的参与节点间有明确的角色定义和状态同步协议，RedLock的多实例只是互相独立的普通进程，没有协议保证一致性。
- **Kleppmann批评的问题不是RedLock独有的bug，是所有基于超时的锁机制的通病**：RedLock只是没有提供解决它的机制（fencing token），不代表RedLock设计有实现缺陷。
- **watchdog不能替代fencing token**：watchdog本身依赖客户端能正常运行续期任务，客户端失联时watchdog同样失效，两者是缓解概率和兜底防破坏两个不同角度，不是互斥选项。
- **RedLock不是"更高级就一定更好"的选择**：它的工程代价（5个独立实例、更高延迟）只换来"获取锁阶段更可靠"，不解决"持锁期间失联"的根本问题，选型要结合业务容错能力和运维成本判断，不能默认"越复杂越安全"。

## 与其他章节的关联

- **第15章「复制」**：单实例锁在主从故障转移场景下的正确性缺口，直接源于异步复制的数据丢失窗口，是RedLock要解决的问题起点。
- **第16章「Sentinel」/第17章「集群」**：RedLock借用了"过半数确认"的共识思路，但和Sentinel/集群选举的本质区别（参与节点是否有协议保证的角色和状态一致性）是理解RedLock局限的关键。
- **第19章「事务」/第20章「Lua脚本」**：锁的释放（校验+删除）必须用Lua脚本原子完成；Redisson watchdog本身用Lua脚本实现续期判断逻辑，本专题进一步明确了watchdog解决的问题范围和局限。
- **模块五·专题7「生产常用客户端框架」**：`RLock`/`RedissonRedLock`的API认知是本专题讨论正确性争议的直接前置基础。
