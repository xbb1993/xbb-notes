# 模块五·专题9 Redis脚本效果复制（effect replication）

## 核心概念

**要解决的问题**：第15章讲的复制机制，复制的对象是"写命令"，并且隐含一个前提——这些命令都是**确定性**的：同样的命令、同样的参数，在任意一台机器上执行，结果必然完全一致（`SET`/`LPUSH`/`ZADD`都是如此）。但Lua脚本（第20章）不是命令，是一段**程序**，程序里可以包含`math.random()`、`TIME`、依赖内部迭代顺序的遍历等**非确定性**操作。这就产生了一个第15章从未遇到过的新问题：主库把脚本复制给从库后，从库自己重新执行这段脚本，结果还能保证和主库一致吗？

**类比**：总店（主库）研发出一道新菜要同步给分店（从库），有两种做法——发菜谱（命令复制：把"怎么做"发过去，分店自己重新做一遍）或发成品（效果复制：总店做好后把"最终成品"直接送过去，分店不用重新烹饪）。如果菜谱里有一步是"加入当天现摘的柠檬"（对应`math.random()`这类非确定性输入），总店和分店各自摘的柠檬酸度不一样，即便照着同一份菜谱做，两家做出来的菜味道也会不同。

### 朴素方案：直接复制脚本命令，碰壁在哪

Redis最早（2.6引入Lua脚本时）的做法是最直接的想法：主库执行了`EVAL script ...`，就原样把这条命令连同脚本内容一起发给从库，从库收到后自己重新执行一遍。

```
主库执行 EVAL "return redis.call('SET', KEYS[1], math.random())" 1 mykey
   → 主库上 math.random() 生成 0.734...  → mykey = "0.734..."
从库收到同一条EVAL命令，自己重新执行一遍脚本
   → 从库上 math.random() 生成 0.128...  → mykey = "0.128..."

结果：主库和从库上 mykey 的值不一样，主从数据静默分裂
```

常见的非确定性来源不止`math.random()`：脚本里用`TIME`读当前时间、依赖`TTL`剩余时间做判断、调用`SPOP`/`SRANDMEMBER`这类命令本身带随机性、遍历hash/set时依赖底层内部迭代顺序，都会让"同样的代码"在两处产生不同结果。

- 错误理解：只要脚本文本内容完全一样，复制过去在从库上重新执行，结果就该是一样的——"同样的代码跑两遍应该产出同样的结果"。
- 正确理解：**"代码相同"不等于"结果相同"**，这个等价关系只在代码是纯函数式（相同输入必然产生相同输出、不依赖任何外部状态）时才成立。Lua脚本一旦掺入任何非确定性调用，命令复制的正确性假设就从根上被破坏。

### 演进方案一：约束脚本必须"确定性"

Redis最初的应对不是放弃命令复制，而是在协议层面限制脚本写法：规定脚本内部不允许使用会产生随机结果或依赖系统状态的命令，执行时若检测到"写命令出现在随机命令之后"这类可疑模式甚至会报错拦截。

局限很直接：这是一种"靠约束和自觉"的方案——开发者要自己小心翼翼写"确定性脚本"，一旦某种非确定性调用没被规则捕捉到，主从数据就静默分裂，且没有任何报错提示，往往是从库数据对不上之后才被发现，排查成本很高。

### 演进方案二：效果复制（Redis 3.2+，最终方案）

真正的解法是换一个复制的对象：不复制脚本本身，而是复制脚本执行过程中**实际产生的写命令**。脚本在主库上完整执行一遍之后，Redis记录下这次执行到底改动了哪些key、下达了哪些具体写命令，然后把这些**已经产生确定性结果**的具体命令复制给从库，用`MULTI/EXEC`包起来当作一个原子操作单元发送。

```
主库执行 EVAL "...调用math.random()生成随机值并SET..."
   → 脚本在主库上真实执行，产生了确定的效果：SET mykey "0.734..."
   → 复制给从库的不是"EVAL这段脚本"，而是：
        MULTI
        SET mykey "0.734..."
        EXEC
   → 从库直接执行这条已经"算好结果"的SET命令，不重新跑脚本、不重新算随机数

结果：从库上 mykey 的值必然是 "0.734..."，跟主库完全一致
```

举一个更贴近生产的例子：脚本内部用`ZRANGEBYSCORE`查出一批过期member再逐个`ZREM`，效果复制后从库收到的是主库上`ZRANGEBYSCORE`**实际扫描出的那几个具体member**对应的`ZREM`命令，而不是重新执行一遍`ZRANGEBYSCORE`——即便从库上这个查询理论上应该返回相同结果，效果复制的思路也是彻底不给"理论上应该"这种假设留任何空子。

**这跟第19章事务是同一个原子性工具在不同层面的两次应用**：事务用`MULTI/EXEC`包装"一组命令"，保证"要么全部生效要么都不生效"；效果复制用`MULTI/EXEC`包装"脚本执行后产生的具体效果"，保证"从库执行的是主库已经算好的确定结果，而不是重新计算的过程"。

### 多维度对比：命令复制 vs 效果复制

| 维度 | 命令复制（脚本本身） | 效果复制（实际写命令） |
|---|---|---|
| 正确性 | 依赖脚本"确定性"这一强假设，一旦违反会静默产生主从数据分裂 | 从根本上不依赖脚本确定性，主库算好什么从库就应用什么 |
| 复制体积 | 只传输脚本文本+参数，通常很小 | 传输脚本实际产生的全部写命令，脚本内部循环次数多、改动key多时体积可能显著增大 |
| 主库负担 | 只需转发脚本文本 | 需要先完整跟踪本次脚本执行产生的所有写操作再打包转发，有额外记录开销 |
| 从库负担 | 需重新执行整个脚本（包括内部读操作、条件判断等） | 只需执行结果确定的写命令，不需要重新跑脚本逻辑，负担更轻 |
| 语义清晰度 | "复制脚本"跟人类理解的"这段代码做了什么"直觉一致 | 复制的是"效果"，脚本业务逻辑在从库侧不可见，调试时不够直观 |

**关键结论**：效果复制在正确性这个最核心的维度上完胜，代价是复制体积可能变大（脚本内部循环多时产生的写命令会很多）、从库侧看到的是一堆具体命令而不是"脚本做了什么"的业务语义。Redis 3.2之后把效果复制作为默认且唯一行为，`lua-replicate-commands`配置项是这次演进在配置层面留下的历史痕迹。

## 易混淆/易错点

- **"代码相同"不等于"结果相同"**：这个等价关系只在代码是纯函数式（不依赖外部状态、不含随机性）时成立，Lua脚本一旦含有非确定性调用，命令复制的正确性假设就被打破，且这种打破是**静默的**，不会报错提示。
- **效果复制不是"优化传输方式"，是解决正确性问题的必需方案**：不能理解为"为了省流量/省CPU换了个复制格式"，它的存在理由是命令复制在非确定性脚本下会导致主从数据分裂，效果复制是唯一能保证正确性的路径。
- **效果复制会让复制体积变大，不是恒等或更小**：脚本内部循环、批量操作越多，产生的具体写命令越多，不能想当然认为"效果复制传输量应该更小"。
- **判断脚本是否需要担心这个问题的标准是"是否包含非确定性调用"，不是"脚本长短"或"是否复杂"**：一个很短的脚本只要调用了`math.random()`或依赖`TIME`，一样会触发这个问题；一个很长但完全由确定性输入驱动的脚本反而没有风险（只是效果复制机制下依然会走"记录实际写命令"这条路径，只是不会产生分裂问题）。

## 与其他章节的关联

- **第15章「复制」**：命令复制的"复制写命令"整体框架来自第15章，但第15章讨论的命令全部是确定性命令；效果复制是同一个"复制什么内容才能保证主从一致"的问题，在"脚本"这种非确定性载体上的必然演进——本质仍是"复制会产生确定结果的东西"，只是这个"东西"从命令本身变成了命令执行后的具体效果。
- **第19章「事务」**：效果复制用`MULTI/EXEC`包装脚本产生的写命令，直接复用了事务"一组命令原子执行"的机制；两者的共同点是都在用同一个原子性工具解决不同层面的一致性问题（事务保证"客户端视角的一组操作不可分割"，效果复制保证"主从之间传输的是已经算好的确定结果"）。
- **第20章「Lua脚本」**：本专题延续第20章笔记中提前埋下的伏笔——Lua脚本引入"非确定性"这个第15章命令复制框架从未遇到过的新变量，效果复制是Redis应对这个新变量给出的最终方案。
- **模块五·专题8「分布式锁正确性RedLock」**：RedLock释放锁用的Lua脚本（校验随机值后删除）本身是确定性的（纯粹基于传入参数判断，不调用任何随机/时间函数），不会触发效果复制要解决的问题，但理解这个机制有助于判断"自己写的分布式锁释放脚本是否安全"这类工程判断。
